摘要

大型語言模型（LLM）常被要求生成需遵守精確語法規則的結構化輸出，例如程式碼片段或格式化資料。文法約束解碼（grammar-constrained decoding, GCD） 可保證 LLM 輸出符合這類規則——作法是遮蔽（mask）掉那些「可被證明會導致輸出不屬於指定上下文無關文法（context-free grammar, CFG）」的 token。為保證健全性（soundness），GCD 演算法必須計算「給定 LLM 的子詞（subword）分詞器如何與給定 CFG 所用的 token『對齊（align）』」，並據此計算 token 遮罩。要有效率地做到這點很有挑戰性，既有 GCD 演算法在預處理常見文法時需耗費數十分鐘。本文提出一個新的 GCD 演算法與實作，離線預處理較既有方法快 17.71 倍，同時在線上遮罩計算上維持頂尖（state-of-the-art）效率。

1. 引言

約束解碼（constrained decoding）在高度結構化的場景中，以貪婪地強制執行使用者給定的約束來引導 LLM 輸出。GCD 是其中「約束以形式文法給定、LLM 輸出必須符合該文法」的特例：透過套用剖析（parsing）演算法建立一個自動機，該自動機與 LLM 的解碼演算法接口，遮蔽掉所有可被證明會導致「輸出不在文法內」的 token。例如可用 GCD 確保 LLM 只使用特定一組函式名稱。

CFG 的剖析演算法之所以有效率，是把輸入字串分兩階段處理：終端符（terminals）（如變數名或字串字面值）由詞法分析器（lexer） 在預處理階段辨識；而終端符如何排列的語法結構（如迴圈本體應是一串陳述句）則由一個操作於已詞法化終端符之上的自動機來強制執行。實作 GCD 的關鍵挑戰在於：LLM 中子詞分詞器所用的 token，與剖析器所用的終端符並不對齊。

由於這種不對齊，既有 GCD 方法要嘛承受高昂的線上 token 遮罩開銷（每 token >1 秒），要嘛承受高昂的離線預處理成本（>30 分鐘）以預先算出「關聯 LLM token 與終端符」的查表。因此既有 GCD 演算法在「約束文法頻繁改變」的領域中並不實用。這類領域包括程式合成（program synthesis）——每個欲合成的程式都會給定一個文法——以及文法提示（grammar prompting）——文法由 prompt 預測而來、再引導 LLM 走向特定輸出結構。

本文提出一個同時兼具靈活（flexible）與高效（efficient） 的 GCD 新方法：靈活指能處理多樣文法而不付出高得離譜的離線預處理成本；高效指維持頂尖的線上 token 遮罩效率。核心創新是對 LLM token 詞彙表與 CFG 終端符集合的「合併分析（combined analysis）」，有效率地預先算出一個「依詞法器狀態而定（lexer-state-dependent）」、介於「CFG token 序列」與「單一 LLM token」之間的映射。此預計算讓解碼器在解碼時能有效率地辨識合法 LLM token，同時避免對「在給定 LLM 詞彙表下根本無法實現的 token 組合」做無謂處理。

我們把方法實作為工具 GreatGramma：離線預處理較 SynCode 平均快 17.71 倍，同時維持頂尖線上遮罩效率（每 token 5–32ms）。此外，我們的評估揭露既有已發表論文的 GCD 實作含有健全性錯誤（soundness bugs）（例如遮蔽了不該遮的 token、或在預處理簡單文法時不終止），而我們的方法則能導向由簡單模組組成的優雅實作。本文兩項貢獻：(1) 一個靈活（低離線開銷）且高效（低線上遮罩開銷）的 GCD 演算法；(2) 實作該演算法的工具 GreatGramma，離線預處理較其他工具快達 17.71 倍且保有低線上開銷。

2. 方法總覽

2.1 詞法分析與剖析（Lexing and Parsing）

實務剖析工具會先以 lexer 做一趟預處理以提升效率。lexer 由一組定義終端符（識別字、關鍵字、整數字面值等）的正規表示式建構。文中例子定義兩個終端符：B（一個 a 後接一串 b）與 C（一個 a 後接一串 c）。lexer 把輸入字串分詞，使符合終端符正規式的子字串被歸為一組——例如 abaccab 被詞法化為 ab acc ab。此分離讓剖析器可直接定義在終端符之上而非個別字元之上；文法在終端符層級定義。範例文法接受形如 BCBCBC… 的終端符序列。剖析器可定義為自動機；要處理所有 CFG，該自動機須是配有堆疊的下推自動機（pushdown automaton, PDA）。

2.2 以剖析做約束解碼

約束解碼器的一般結構：給定 token 序列 t_{1:k}，在解碼過程中用一個檢查器 C 遮蔽任何「會使前綴 t_{1:k+1} 無任何合法補全能滿足約束」的下一 token t_{k+1}。形式上，給定前綴與詞彙表 V，檢查器算出布林遮罩 C(t_{1:k}; V)=m∈{0,1}^{|V|}：值 1 代表可行 token（存在能滿足約束的句子補全），0 代表無效；此遮罩再套用到 LLM 產生的 logits 上以排除無效 token。剖析器可延伸為「線上」版本——一旦讀入某 token 確定會導致無法剖析就立即拒絕。GCD 的關鍵想法，就是用「剖析器判定某 token 是否被允許」這個原語去建構檢查器 C。

但用剖析器當檢查器有一核心問題：剖析器讀的是語言層級 token（本文為避免混淆稱為終端符），而 LLM 依其子詞詞彙表輸出 token；LLM token 可能橫跨多個終端符、或只是終端符的片段。此問題稱為 token 不對齊（token misalignment），是 GCD 實作複雜度的主要來源。

2.3 本文方法

方法基於一個新的資料結構——token spanner table（token 跨度表）。直觀上，該表儲存「若 lexer 從某個給定狀態讀入一個 LLM token，可能吐出哪些終端符序列」。整個 GCD 方法分兩部分：離線預處理階段建構此表；線上階段用此表在解碼時產生 token 遮罩。

離線部分吃兩個輸入：LLM 詞彙表 V 與終端符定義（正規式）。它先建構代表 lexer 的有限狀態自動機（FSA）——例如狀態 q2 表示「lexer 已讀入子字串 ab、可選擇再讀更多 b 以吐出 B 終端符」。再用此自動機連同 LLM 詞彙表建 token spanner table。表的鍵是配對 (q, v)（q 為 lexer 狀態、v 為 LLM token），該格內容是「lexer 在狀態 q 又餵入一個 token v 後，最終可能產出的終端符序列集合」。例如在狀態 q2 餵入 token aba，可產出 BBB 或 BBC。線上部分則用此表連同剖析器，追蹤 lexer 狀態與剖析器 PDA 狀態，分析剖析器接下來可能消耗哪些終端符序列，再查表決定哪些 LLM token 該遮、該留。
