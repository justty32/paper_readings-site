論文／訪談原始來源

LLM2SMT：用零人類手寫程式碼造出一個 SMT 求解器

引言／動機

「LLM 能否推理、能否寫軟體」被廣泛辯論，但「LLM 能否寫出『本身會推理』的軟體」幾無探討。核心問題：LLM 是否對邏輯原理有足夠理解，能在零人類手寫程式碼下造出可靠的 SMT 求解器。

用 LLM 編碼 agent 的開發流程

全部實作由 Anthropic Claude Code agent（Sonnet 4.6）生成。專案從一句引用 Nieuwenhuis–Oliveras 同餘閉包演算法的最小描述起步。方法論要點：

  • 開發者透過 維護說明 加永久指令（要求求解器跑要設 timeout）。
  • agent 在拿到失敗測例時自主修 bug。
  • LLM 自己生成 fuzzing 與 delta-debugging 工具，比人工除錯省 token。
  • 用 git 歷史追蹤＋回歸測試支援迭代改進。
  • 具體範例最能引導 agent 修正。

初期開發暴露重大缺口：求解器一開始缺布林連接詞處理、且自寫一個 SAT 求解器而非如預期整合 CaDiCaL（透過 IPASIR-UP）。

QF_UF 的 DPLL(T) 架構

求解器採 lazy SMT，遵循 DPLL(T) 框架。理論原子變成布林變數交給標準 SAT。CaDiCaL SAT 求解器透過 IPASIR-UP 介面運作，產候選賦值並由理論專屬檢查驗證。QF_UF（無量詞等式＋未解釋函式）處理 Nelson–Oppen 閉包基礎的等式推理。

同餘閉包實作

Nieuwenhuis–Oliveras 演算法做同餘閉包以偵測不一致的項等式。實作含公式 hash-consing 提效，並處理 SMT2 中布林的雙重性質（既當命題又當項）——這一開始導致假 UNSAT。

Lean 證明輸出

不建低階證明，而依賴 Lean 自動化：grind tactic 驗理論引理、bv_decide 處理命題片段。SMT 型別與常數變成 Lean 公理、理論引理變成獨立定理。證明架構須簡化——初期所有假設都當成單一定理內的 hypothesis，在上千假設的問題上導致 Lean 解析失敗。agent 在證明生成上掙扎最久，尤其搞不清「理論引理 vs 最終證明」的區別；人工提供正確 Lean 證明範例至關重要，作者最終須給出 equational diamond 證明結構的具體指引。

遭遇的關鍵挑戰

  1. Jagged Intelligence：agent 擅長複雜推理卻在瑣事翻車——一開始不把 t=t 化簡為 true。
  2. 布林處理：SMT2 把公式與項混為一談，須明確修正 prompt。
  3. 證明生成：最難的部分；agent 懂證明結構卻難以忠實編碼計算資訊。
  4. 資源管理：無 timeout 的程序會默默累積。

作者指出：「agent 在給定標準工具（fuzzing、delta-debugging）時能有效除錯自己的程式碼。」

SMT-LIB 基準評估

用 QF_UF 非增量基準、180 秒 timeout、並行：

求解器 求解實例數 獲勝數
z3 7,500 7,491
cvc5 7,494 7,308
llm2smt 7,468 6,486
llm2smt-no-prepro 7,355 6,150

有趣的是，關閉理論傳播反而更好（7,478 vs 7,468），顯示傳播在這批基準上帶來開銷卻無補償。

證明認證嘗試：285 認證成功、2,244 因 grind 限制失敗、1,314 timeout、240 超 Lean heartbeat、86 stack overflow。未發現任何錯誤證明。

相關工作

橫跨 SMT 求解器開發（CaDiCaL、z3、cvc5）、形式驗證框架（Lean）、演算法基礎（同餘閉包、DPLL(T)、Nelson–Oppen），並引用 LLM 引導的形式化與證明生成；本工作代表「推理關於推理」能力的新穎探查。

局限與結論

作者以有保留的肯定作結：在適當鷹架下（fuzzing、delta-debugging、明確資源上限、謹慎輸入規格），LLM agent 能產出有競爭力的求解器，在單一理論上逼近成熟求解器。然而完整證明認證仍超出當前能力，雖然 agent 確實理解求解器邏輯與除錯方法論。未來工作：擴展到更多理論、引入 human-in-the-loop 程式碼審查。
