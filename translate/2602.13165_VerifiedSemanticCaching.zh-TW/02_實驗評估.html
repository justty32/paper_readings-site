4. 實驗評估

4.1 資料集與分割

使用 vCache 引入的兩個開放基準：

  • SemCacheLMArena（~60k prompt）：來自 Chatbot Arena 日誌，開放式對話 prompt，詞彙多樣性高
  • SemCacheSearchQueries（~150k prompt）：來自 ORCAS 查詢日誌，短關鍵字搜尋查詢

以 20% 歷史前綴建構靜態層（覆蓋頻率最高且累計達 60% 的 equivalence class，每個 class 取最短 prompt 為 canonical 代表），剩餘 80% 作為線上評估串流。兩策略在相同靜態預載、相同閾值、相同請求順序下比較。

4.2 基線與配置

基線使用 vCache Pareto 分析中的最優靜態閾值配置（錯誤率約 1-2% 的 GPTCache 前沿點）。Krites 使用完全相同的嵌入、標註和閾值，僅啟用灰色地帶的非同步 VerifyAndPromote 迴圈。實驗取 σ_min = 0 以最大化覆蓋。

4.3 結果

資料集 基線（靜態命中率） Krites（靜態來源服務率） 相對提升
SemCacheLMArena 8.2% 19.4% +136.5%
SemCacheSearchQueries 2.2% 8.6% +290.3%

Krites 在對話流量上讓 curated 答案覆蓋率翻倍以上；搜尋查詢的提升更大（近 4 倍）。由於關鍵路徑決策規則不變，基線的延遲與錯誤行為在觸發驗證的請求上完全保留。隨著時間推移，動態層逐漸被 verified pointer 填充，靜態來源服務率持續增長。

5. 討論

成本與 ROI

離線法官的原始請求率約為 λ_J ≈ λ * p_grey（去重/速率限制前）。設 c_J 為每次法官呼叫的平均運算成本，p_app 為核准機率，N 為晉升鍵在被回收前的後續命中次數。則每次法官呼叫預期貢獻的額外靜態來源服務數為 E[p_app * N]——當改述頻繁重現且動態快取保留晉升條目足夠久時，該值最大。

模型選擇方面：使用大模型（如 Claude Opus 4.6）為法官可能在運算上昂貴（因為法官 prompt 包含快取答案），但不影響關鍵路徑延遲。若運算預算緊張，可使用較小法官模型及/或以重現次數為門檻（僅在觀察到重複查詢後才送審），取捨晉升量與驗證器精度/召回率。

與相關工作的關係

Krites 與先前語意快取研究處於互補空間：GPTCache 等系統在單層快取上應用靜態閾值；vCache 證明單一閾值設計的根本限制——相似度分佈高度重疊，最優閾值因嵌入而異。Krites 回答不同的問題：給定營運者已在分層快取前執行調校過的靜態閾值策略，且靜態條目為 curated 且難以更新，如何在不改變服務決策規則及其延遲特徵的前提下，安全地回收更多靜態命中。

同步驗證快取（blocking verified cache）是自然替代方案：將 LLM 法官直接放在服務路徑上。這可增加快取命中，但為許多請求增加額外模型呼叫——增加平均及尾部延遲，侵蝕快取對互動式工作負載的核心效益。Krites 藉由分離服務與驗證避免了此延遲成本。

6. 結論

Krites 示範了一種將非同步 LLM 驗證整合進分層語意快取的實用策略：保留保守的服務路徑閾值，以離線法官安全地將 curated 靜態答案的覆蓋範圍擴展到相似度灰色地帶。在對話與搜尋工作負載上，靜態來源服務率提升 136%–290%，且不增加關鍵路徑延遲。此方法將驗證成本與服務延遲解耦，使營運者可以獨立調整靜態覆蓋率與法官預算，為分層 LLM 服務架構提供了一個新的自由度。
