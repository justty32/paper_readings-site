摘要

大型語言模型（LM）雖然表現驚人，但若未經微調（finetuning）使其嚴格遵循所需輸出格式，在可靠生成複雜輸出結構上仍有困難。文法約束解碼（grammar-constrained decoding, GCD）可用來控制 LM 的生成，保證輸出遵循給定結構。然而多數既有 GCD 方法侷限於特定任務（如剖析或代碼生成）。本文證明：形式文法（formal grammar）能描述遠更廣泛任務的輸出空間，並主張 GCD 可作為結構化 NLP 任務的統一框架。為增加靈活性，我們引入 input-dependent grammar（依輸入而變的文法），讓文法依輸入而定、對不同輸入生成不同的輸出結構。我們在 (1) 資訊抽取、(2) 實體消歧、(3) 成分剖析上實證展示 GCD 增強 LM 的威力與彈性：文法約束的 LM 大幅勝過無約束 LM，甚至打敗任務專用的微調模型。文法約束因此有望讓現成（off-the-shelf）LM 服務於大量結構化 NLP 任務，尤其在訓練資料稀缺或微調昂貴之處。程式碼與資料：github.com/epfl-dlab/GCD。

1 引言

預訓練 LM 在機器翻譯、摘要、對話生成等任務成績斐然；規模化更帶來 in-context learning 能力，LLM 只看少量示範即可免微調適應新任務。然而**封閉資訊抽取（closed information extraction, cIE）、實體消歧（entity disambiguation, ED）、成分剖析（constituency parsing, CP）**等重要任務要求輸出遵循預定格式並限於受限詞彙表（實體、關係、詞義、依存標籤等）。LM 擅長自由文本，卻非為「僅一小撮輸出空間合法」的結構化預測而設計。例如 Josifoski et al. (2023) 證明 few-shot 提示的 GPT-3.5 在 cIE 上表現掙扎——輸出詞彙表包含 270 萬個 Wikidata 實體名與約 1,000 個關係名，靠幾個示範根本無法傳達。

一條路是任務專用微調（把目標輸出線性化成字串、按標準 next-token prediction 訓練，如 GENRE 之於 ED、GenIE 之於 cIE），但每個新任務都需要昂貴的微調管線與專屬訓練資料，缺乏彈性。與之正交的**約束解碼（constrained decoding）**則在推論期對輸出空間施加約束，已用於語意角色標註、成分剖析、代碼生成、實體消歧；但約束多以有限狀態自動機（finite-state automata）或 trie 資料結構表達，實作工程負擔大。

本文證明：對遠更廣泛的 NLP 任務，其輸出空間都可以用形式文法描述，構成結構化 NLP 的統一框架。給定文法，我們用增量剖析器（incremental parser）扮演補全引擎（completion engine）——依當前前綴給出合法後繼 token 集合，與預訓練 LM 整合，迭代生成「依文法合法、依 LM 可信」的序列（圖 1）。實務上研究者只需專注寫文法，忽略約束解碼的實作細節；我們期望 GCD 用起來像正規表達式（regular expression）一樣簡單——使用者宣告式地指定輸出結構，LM 生成即保證合法。引入 input-dependent grammar 後，GCD 的適用範圍進一步擴及 ED、實體連結等「輸出空間非固定、隨輸入而變」的任務。結合強大 LLM 與 GCD，few-shot 即可取得顯著改進，甚至匹敵微調的任務專用模型。

貢獻：(1) 證明許多結構化 NLP 任務的輸出空間可表述為形式語言，任務即轉為 GCD 問題，構成統一框架；(2) 引入 input-dependent grammar，擴大 GCD 可處理的任務集（如 ED 與 CP）；(3) 在 cIE、ED、CP 三任務上實證 GCD 的有效性——cIE 與 ED 不需任何微調即達到有競爭力的結果。

圖 2 要旨：列出 14 個結構化 NLP 任務的形式文法（cIE、ED、CP、語意角色標註、共指消解、詞義消歧、依存剖析、POS 標註、分塊、NER……），全部是 context-free（多數為 regular）文法；其中 13 個需要 input-dependent grammar（以 * 標記）。

2 方法

2.1 NLP 任務作為形式語言

NLP 任務的輸入 x 與輸出 y 通常是 token 序列；輸入任意，但許多任務的輸出須遵循特定結構（如 IE 的輸出須為主詞–關係–受詞三元組）。依 Church–Turing 論題，形式語言足以描述任何可計算的物件集合結構，故適合定義結構化任務的輸出空間。本框架採形式文法定義之，並為可解性（tractability）聚焦於 context-free 文法。

Token 級形式文法：形式文法 G = (V, Σ, P, S)（非終端符集、終端符集、產生規則集、起始符）。使用者先寫字元級文法 G；為約束 LM 的直接輸出（token 序列），以 token 集 Σ_tok 為終端符、把規則中的終端符序列過 tokenizer，得 token 級文法 G_tok，描述與 G 相同的語言；再用增量剖析器判定 token 序列是否屬於 G_tok 生成的語言。局限：BPE 等 tokenization 允許同一字串多種切分（如 "[[[" 有三種切法），目前靠加空格、強制單括號成 token 等非原則性手段避開歧義；原則性的 token 級文法定義留作未來工作。

Grammatical Framework（GF）：token 級文法依賴 tokenizer，同一 G 對應多個 G_tok——類比「同一抽象語法樹（AST）對應多種程式語言」。因此採用 GF（多語文法應用的元語言）同時定義抽象文法（字元級 G）與具體文法（各 tokenizer 專屬的 token 級「語言」）。

Input-dependent grammar（IDG，依輸入而變的文法）：有些任務的文法必須依輸入而定——ED 的輸出須限於該 mention 的候選實體集（通常數十個、語意相關）；CP 的輸出剖析樹之葉節點必須恰為輸入的 token。既有工作皆用單一文法、不看輸入，適合代碼生成或 IE 這類輸出空間與輸入無關的任務；但圖 2 的 14 個任務中 13 個需要 IDG。

2.2 文法約束解碼（GCD）

LM 逐 token 解碼；我們在解碼期介入，把機率分佈剪枝到只剩文法允許的 token 子集。合法子集由增量剖析器回傳——它以部分生成序列與文法為輸入、輸出下一步合法 token 集，角色可抽象為補全引擎（completion engine, Poesia et al. 2022）。本文用 GF 的增量剖析器（Angelov 2009）。此流程相容任何解碼演算法（greedy、beam search、top-k 取樣等）與任何可存取逐步詞彙表分佈的自迴歸 LM；API 型服務（如 OpenAI）不開放該分佈，無法使用 GCD。

2.3 GCD 下的 few-shot 學習

本文將 GCD 與 few-shot learning 結合以免微調地適配新任務：不讓 LLM 生成自由文本，而以 GCD 約束輸出必合文法——同時利用 LLM 的 few-shot 能力與文法注入的任務輸出結構知識。同一任務可用不同文法：如 ED 可用依輸入的 G1（限於輸入專屬候選集）或不依輸入的 G2（任何合法實體名）；G1 削減搜尋空間更多、因此更有效。
