7 結論與 GCD 最佳實踐

本文提出 GCD 以增強 LLM 在困難結構化 NLP 任務上的 few-shot 表現：許多 NLP 任務可表述為形式文法；input-dependent grammar 進一步涵蓋「合法輸出結構受輸入約束」的任務。GCD 是快速、划算的適配策略，讓 LLM 免昂貴繁瑣的微調即生成可靠的結構化輸出；隨 LLM 演進，GCD 的加值可望持續增加。最佳實踐：(1) GCD 對愈大的 LLM 愈有效，儘量用最大可得模型；(2) 文法應盡可能限制性強，考慮用 input-dependent grammar；(3) GCD 非萬靈丹——需要句法理解輸入的任務（如 CP）較不適合；(4) 有任務專屬訓練資料時，微調小模型可能仍更強，只是便利性差（附錄 A）。

局限

與 API 型 LLM 的相容性：GCD 需修改解碼過程；雲端 API（如 OpenAI GPT 系列）不開放解碼控制即無法使用。延遲：約束引入的額外開銷來自「依前綴與文法決定下一步合法 token」的補全步驟，取決於文法複雜度與剖析演算法；文法簡單時開銷可忽略，但文法含數百萬規則（如 cIE）時增量剖析延遲上升（附錄 H：WikiNER 文法 0.05s/步與 LM 相當，REBEL 文法 590 萬實體 0.5s/步顯著較高，可望以更合適的增量剖析器改善）。

附錄擇要

附錄 A（微調 vs GCD）：三個考量因素——訓練資料可得性、微調計算成本、效能增益。約束解碼免訓練資料、只付 LM 推論成本＋剖析器小開銷；資料充足時微調小模型（T5 等）仍是多數結構化任務 SOTA；微調大模型貴但資料效率高，LoRA 等技術已大幅降低成本。作者將 GCD 定位為「免微調而得可靠結構化輸出」的快速廉價適配策略。附錄 B（GF）：抽象語法 vs 具體語法的解耦讓文法「與 tokenizer 無關地」定義一次、自動翻譯至各 token-id 級具體文法（類比高階語言編譯至組語）；GF 增量剖析器支援 PMCFG（介於 mildly 與 fully context-sensitive 之間）。附錄 G：subject-collapsed 線性化更省 token 但效能略低；把全部 888 個關係塞進提示只帶來小幅改善。
