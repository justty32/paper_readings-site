4. 實驗

4.1 設定

  • 資料生成：全程以 CCNet 子集為語言模型資料集 C、以 GPT-J 為模型 M。為降低標註成本，對部分 API 定義啟發式先篩子集（例如只有含至少三個數字的文本才考慮計算器）。權重函數 w̃ₜ = max(0, 1 − 0.2·t) 後歸一化，確保呼叫發生在「API 提供的資訊真正有用」之處附近。表 2 顯示不同過濾門檻 τf 下 C* 各工具的樣本數（如 τf=1.0 時：問答 18,526、維基搜尋 60,974、計算器 994、日曆 20,587、翻譯 1,034）。
  • 微調：batch size 128、學習率 1×10⁻⁵、前 10% 線性 warmup。
  • Baseline：GPT-J（未微調）、GPT-J + CC（在 CCNet 子集 C 上微調、無 API 呼叫）、Toolformer（在 C* 上微調）、Toolformer(disabled)（同 Toolformer 但解碼時停用 API 呼叫）；多數任務另比 OPT(66B) 與 GPT-3(175B，davinci)，分別約大 10 與 25 倍。

下游任務評估一律採 prompted zero-shot（用自然語言指示解題、不給 in-context 範例），比既有工具使用工作更具挑戰性。解碼用貪婪，但對 Toolformer 有一調整：當 <API> 是前 k 個最可能 token 之一時就允許起呼叫（k=1 即一般貪婪，實驗用 k=10 以提高用工具傾向），且每個輸入最多一次 API 呼叫（避免陷入不斷呼叫卻不產出的迴圈）。

4.2 下游任務結果

  • LAMA（SQuAD/Google-RE/T-REx 事實填空）：為避免不公平，禁止 Toolformer 使用維基搜尋。Toolformer 分別比最佳 baseline 高 11.7 / 5.2 / 18.6 分，並勝過 OPT(66B) 與 GPT-3(175B)。它幾乎總是自行選問答工具（98.1%），少數用別的工具（0.7%）或不用工具（1.2%）。
  • 數學（ASDiv/SVAMP/MAWPS）：Toolformer 即使停用 API 也比 baseline 強（推測是微調於大量呼叫範例也提升了自身數學力）；而開啟 API 呼叫使各任務表現翻倍以上，並清楚勝過大得多的 OPT 與 GPT-3。各 benchmark 有 97.9% 的例子自行找計算器。
  • 問答（WebQS/NQ/TriviaQA）：停用問答工具（否則太容易），主要靠維基搜尋（99.3%），勝過同級 GPT-J baseline，但仍不及 GPT-3(175B)。作者歸因於搜尋引擎過於簡單、且 Toolformer 無法與之互動（不能重寫查詢、瀏覽多筆結果）——列為未來方向。
  • 多語問答（MLQA，英文段落 + 六種語言的問題）：使用 API 呼叫在所有語言都提升 Toolformer 表現，顯示它學會用翻譯工具（依語言使用率 63.8%–94.9%，印地語例外僅 7.3%）。但因在 CCNet 上繼續微調對某些語言反而掉分（可能與 GPT-J 原預訓練資料分布偏移有關），Toolformer 未能一致勝過原始 GPT-J。OPT 與 GPT-3 在此表現意外地弱（多因未能依指示以英文作答）。
  • 時序（TEMPLAMA / 自建 DATESET）：Toolformer 兩者皆勝過所有 baseline。但細看：TEMPLAMA 的提升不能歸功日曆（僅 0.2% 用它），多來自維基搜尋與問答（因其命名實體太特定，光知道日期也沒用）；DATESET 的提升則可完全歸功日曆（54.8% 使用）。「先查日曆得日期、再拿去問答」這種最佳策略，既被「每輸入至多一次呼叫」的限制擋住、也因訓練資料裡各呼叫獨立取樣而難以學會。

4.3 語言模型能力

在 WikiText 與一份未用於訓練的 CCNet 子集上測困惑度。最重要的是：在 C*（帶 API 呼叫的資料）上訓練、推論時停用 API 呼叫，其困惑度相較在 C 上訓練並無增加——即加入 API 呼叫不以損失純語言模型能力為代價。

4.4 規模效應

除 GPT-J 外，也把方法套用在 GPT-2 家族四個較小模型（124M/355M/775M/1.6B，僅用問答、計算器、維基搜尋三工具）。結果顯示：善用工具的能力約在 775M 參數才湧現——更小的模型用不用工具表現差不多（維基搜尋是例外，因其較易用）。模型越大自身解題能力越強，但同時也越會善用 API，故即使最大模型，「用工具 vs 不用工具」之間仍有很大落差。

5. 分析

解碼策略。 探討「當 <API> 是前 k 個最可能 token 之一時就允許呼叫」的效果。k 由 1 增至 10，會讓模型對更多例子做呼叫（T-REx 從 40.3% 升到 98.1%、WebQS 從 8.5% 升到 100%）。有趣的是 k=1 時模型有某種校準：它傾向對「不呼叫就會做得特別差」的例子去呼叫（不呼叫子集的表現高於「完全不呼叫」的平均）；但 k 變大後這種校準消失。

資料品質。 對生成的呼叫做定性分析（表 10，按過濾分數 L⁻ᵢ − L⁺ᵢ 排序）：高分通常對應直覺上有用的呼叫，低分對應無用呼叫。也有例外（如某個對「Fast train success」的搜尋不提供相關資訊卻仍降困惑度）；但未被濾掉的少量雜訊其實有益，因為它迫使在 C* 上微調的模型「別總是盲目照單全收每次呼叫的結果」。

6. 相關工作

  • 語言模型預訓練：有多種在預訓練時給 LM 補充文字資訊的做法（元資料、HTML 標籤、維基標記、檢索到的相關文本等）；但這些做法不管有沒有用都一律提供資訊，而 Toolformer 是自己學會明確去索取正確的資訊。
  • 工具使用：既有給 LM 接搜尋引擎、瀏覽器、計算器、翻譯、Python 直譯器的工作，學工具的方式大致兩類——依賴大量人工監督，或以針對特定任務、事先知道該用哪些工具的 few-shot prompt 進行。相較之下 Toolformer 的自監督本質讓它無須任務專屬 prompt 就能學會何時、如何用工具。與本工作最接近的是 TALM，也用類似自監督目標教模型用計算器與搜尋，但只在「為下游任務微調」的設定下探索。
  • Bootstrapping：自訓練/自舉技術已用於詞義消歧、關係抽取、句法剖析、序列生成、few-shot 分類、檢索到推理等；Toolformer 同精神——它是在經過基於困惑度的過濾後、用自己的預測來訓練自己。

7. 局限

  • 無法串接工具：各工具的 API 呼叫獨立生成，微調資料裡沒有「一個工具輸出當另一工具輸入」的鏈式範例。
  • 無法互動式使用工具：尤其搜尋引擎可能回傳上百結果，讓 LM 能瀏覽或重寫查詢對某些應用很關鍵。
  • 對輸入措辭敏感：是否呼叫 API 常受精確用字影響（LM 對 prompt 敏感是已知現象）。
  • 樣本效率低：依工具而定；例如處理超過一百萬份文件才得到區區數千個對計算器有用的呼叫。潛在解法是迭代式套用本方法。
  • 未計入呼叫成本：決定要不要呼叫時，未把該工具的計算開銷納入考量。

8. 結論

我們提出 Toolformer：一個以自監督方式學會透過簡單 API 呼叫使用搜尋引擎、計算器、翻譯系統等不同工具的語言模型。做法是在大量取樣的 API 呼叫上微調，而這些呼叫是依「是否降低後續 token 的困惑度」過濾出來的。Toolformer 顯著提升 6.7B 參數 GPT-J 的 zero-shot 表現，使其在一系列下游任務上甚至勝過大得多的 GPT-3。
