論文／訪談原始來源

編碼代理的 harness 如何自我演化？回顧式調整的實證研究

摘要與第 I～II 節：研究問題

編碼代理的 harness 包含執行軟體、設定與提示文件。代理可將前一任務的經驗保留下來供後續任務使用，但修改被保存，不代表後續代理會讀到、遵循或受益。作者研究 /retro：它要求代理回顧完成的 session，提出需人類批准的 harness 變更。問題是提案與該次經驗有何關係，以及已實作的調整何時改變後續行為。（§I～II）

Claude Code 執行任務、產生回顧並實作獲選提案；研究者選取要實作的提案與後續 issue，並標註結果。這是有人類選擇及評估參與的自我演化研究，不是無人干預的自主迴圈。（§I、§III）

第 III 節：研究設計

作者對 SWE-bench Verified 的 30 個 issue 各開新 Docker session，請 Claude Code 2.1.295／Opus 5.5 修改程式並以既有測試驗證，完成後在同一 session 執行 /retro。前 10 題來自五個 repository，於估計開發時間 15 分鐘至一小時的類別隨機抽樣；後 20 題則刻意選擇已觀察到環境問題、且有同 repository 後續 issue 的專案。結果因此描述此樣本，不代表任意編碼任務的提案分布。（§III）

作者逐條編碼 125 個回顧提案：觸發依據區分 session 中觀察到的事件、未依據該次事件的既有偏好，以及間接關聯；機制區分可執行檢查、導覽指標、指令、資訊取得、工具或設定，以及不改 harness 的建議。兩個獨立 LLM 編碼者使用同一 codebook，但分別看到完整軌跡與軌跡摘錄；兩者的觸發分類和機制分類各有 109／125 條一致，Cohen κ 分別為 0.67、0.84。第一作者解決分歧；這是兩種模型／輸入的標註一致性，不是人類標註者一致率。（§III）

研究者讓代理實作 24 個選定提案，其中 11 個產生可在其他 issue 評估的調整；另加入一個作者自行撰寫、源自既有偏好提案的 pre-commit 對照，共評估 12 個調整。這些調整分別在同 repository 的另一 issue 測試，一個調整用於兩個 issue，共 13 個轉移事件。每事件在原 harness 與調整後 harness 下各跑五個新 session；一個調整後 session 因認證錯誤排除。三個調整另測不相關的同 repository 控制 issue。（§III）

後續 issue 被選來重現調整欲處理的環境問題，並非隨機挑選；因此它測試問題可能出現時的行為，不估計對任意 issue 有幫助的頻率。作者區分：session 是否遇到該類問題、調整是否涵蓋實際遇到的特定例子、代理是否查閱調整，以及是否重複原想避免的動作。至少三個原 harness session 遇到問題的轉移事件才算 informative。（§III）

所謂重複工作是一種事先定義的行為量測，例如再跑未修改程式的測試以確認失敗是否原本存在。它本身不意味該動作不必要；若失敗不在已知失敗清單中，重新比對原始程式可能是合理驗證。（§I、§III）

第 IV 節：回顧提案

作者自報 125 個提案中，101 個依據 session 事件、19 個由既有偏好驅動、5 個關聯較弱。最常見機制是可執行檢查，共 38 條，出現在 30 個 session 中的 29 個；導覽指標 24 條、指令 21 條、資訊取得 20 條、工具或設定 12 條，另 10 條不改 harness。（§IV，表 I）

共有 43 條提案與 lint 相關，其中 18 條雖未依據該次事件仍建議 lint 檢查。38 條可執行檢查中，作者判斷只有九條照原樣可在該任務環境報告失敗；其餘多依賴缺少的工具，或是 session 沒有 commit 因而不觸發的 hook。回顧因此不只是將當次實際問題轉成修改，也會帶入技能本身偏好的做法。（§IV，表 I）

第 IV 節：轉移到後續 issue

13 個轉移事件中有七個 informative；另五個雖在環境中重現目標問題，但原 harness 多數 session 未實際遇到，最後一個是作者撰寫的 pre-commit 對照，五個調整後 session 都未讀該檔或執行 pre-commit。作者將 informative 事件按調整是否涵蓋實際遇到的例子分組。（§IV，表 II）

informative 事件 原 harness 重複動作 調整後重複動作 查閱調整
SymPy：提示 bin/test，涵蓋 5/5 0/5 5/5
Astropy：三項已知失敗，涵蓋 3/5 0/5 5/5
Sphinx：已知失敗＋維護說明，未涵蓋 5/5 5/5 5/5
Sphinx：已知失敗＋維護說明，未涵蓋 5/5 5/5 5/5
SymPy：兩套件清單＋腳本，未涵蓋 4/5 4/4 4/4
pytest：三項已知失敗，未涵蓋 5/5 5/5 5/5
Astropy：快取修復＋腳本，未涵蓋 5/5 2/5 5/5

兩個涵蓋實際例子的調整使目標動作在調整後 session 中消失；五個未涵蓋者中，一個減少、四個不變。未涵蓋的案例遇到清單之外的失敗，比對未修改程式可能仍是合理驗證。查閱檔案也不保證代理按其內容行動。（§IV，表 II）

控制 issue 顯示調整也可能增加工作：一份 Sphinx 清單要求將未列失敗視為自身修改所致；不相關 issue 上，原 harness 0/5 次做基線比對，調整後為 4/5。各事件的任務成功數在兩種 harness 間最多差一個 session，沒有一致的成功率提升證據。（§IV）

避免重複動作也不一定縮短時間。SymPy 的測試指令提示消除了先嘗試不存在的 pytest，但同時增加執行 CI lint 的指令；五個調整後 session 都執行 lint，中位時間由 88 秒升至 156 秒。另一 Sphinx 控制 issue 中位時間由 82 秒升至 245 秒。（§IV）

第 V～VI 節：限制與結論

作者指出，挑選能重現目標問題的 issue 可能高估調整在未篩選任務上有用的頻率；代理在產生提案的原 session 和容器實作變更，因此成品可能含提案文字以外的資訊。軌跡可揭露是否讀了移轉檔案，第一作者標註並非完全盲測。每個 harness 五個 session、七個 informative 事件，且事後依涵蓋情況分組；調整本身同時有多個差異，不能據此證明涵蓋程度造成了觀察差異。（§V）

作者建議持續評估保存的變更：確認目標問題有無出現、代理是否查閱、行為是否改變，以及舊指令是否增加工作。研究只涵蓋一種代理、一個 /retro 版本與環境問題；其他代理、程式導覽或編碼慣例，以及未依目標問題挑選的後續任務，仍待研究。（§VI）
