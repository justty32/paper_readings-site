摘要

大型語言模型（LLM）愈來愈多用於需要多次生成呼叫、進階提示技術、控制流與結構化輸入輸出的複雜任務，但目前缺乏高效地「編寫並執行」這類應用的系統。我們提出 SGLang，一套高效執行複雜語言模型程式的系統，由前端語言與 runtime 兩部分組成。前端以「生成」與「並行控制」原語簡化編寫；runtime 以 RadixAttention（KV 快取重用） 與 壓縮有限狀態機（更快的結構化輸出解碼） 等新優化加速執行。實驗顯示在 agent 控制、邏輯推理、few-shot 學習基準、JSON 解碼、檢索增強生成（RAG）管線、多輪對話等任務上，SGLang 相對 SOTA 推論系統取得最高 6.4 倍吞吐。程式碼開源於 github.com/sgl-project/sglang。

1. 引言

LLM 能力提升使其能作為自主 agent，進行多輪規劃、推理與環境互動，透過工具使用、多模態輸入、以及 few-shot、self-consistency、skeleton-of-thought、tree-of-thought 等提示技術完成任務。這些用例都需要多次、常互相依賴的 LLM 生成呼叫，標誌著我們與 LLM 互動方式的轉變：從單純聊天，走向「用程式排程與控制 LLM 生成過程」的程式化使用。我們把這類程式稱為「語言模型程式（LM Programs）」，其兩個共通性質：(1) 多次 LLM 呼叫交錯控制流（為完成複雜任務、提升品質）；(2) 收結構化輸入、產結構化輸出（為使 LM program 可組合、可嵌入既有軟體系統）。

儘管 LM program 廣泛使用，現有系統仍低效。作者指出兩大挑戰：

  • 編寫繁瑣：因 LLM 非確定性，開發常需大量字串處理、prompt 試調、脆弱的輸出解析、多模態處理與手工並行，嚴重降低可讀性（§2）。
  • 執行低效（更關鍵）：因冗餘計算與記憶體使用。SOTA 引擎（vLLM、TGI、TensorRT-LLM）不了解具體 workload，通用穩健但對任一 workload 都有顯著低效。例一：KV 快取重用——KV 快取是生成推論必需的可重用中間張量，批次執行 LM program 時大量呼叫共享前綴、本可重用，但現有系統缺機制而重算浪費記憶體。例二：結構化輸出的受約束解碼（如 JSON mode，輸出須遵守正則定義的文法）——多個 token 常可一次解完，但現有系統一次只解一個。

SGLang（Structured Generation Language） 的核心想法是系統性地利用 LM program 的多呼叫結構以高效執行。如圖 1，它含前端語言與後端 runtime 兩部分，可協同運作也可獨立運作。SGLang 是嵌入 Python 的 DSL，提供生成原語（extend、gen、select）與並行控制原語（fork、join），相容 Python 語法與函式庫。提供直譯器與編譯器：直譯器把 prompt 狀態當 stream，非同步提交原語、確保正確同步與程式內並行；程式亦可被 trace、編譯以做更多優化。

runtime 三項新優化：

  • RadixAttention：跨多次生成呼叫自動重用 KV 快取。不像既有引擎完成後即丟棄，本系統把所有請求的 KV 快取以 LRU 快取存進基數樹（radix tree），用樹做高效匹配、插入、逐出，並以 cache-aware 排程處理各種重用模式。
  • 壓縮有限狀態機：既有系統只對「下一個 token」遮蔽非法機率、故一次一 token；本系統分析約束、建壓縮 FSM，把多 token 路徑盡量壓成單步，一次解多個 token。
  • API 推測執行：對僅能呼叫黑箱 API 的模型（如 GPT-4）優化多呼叫程式。

作者用 SGLang 實作了 agent 控制、邏輯推理、few-shot 基準、JSON 解碼、RAG、多輪對話、多模態等應用，在 Llama-7B/70B、Mixtral-8x7B、LLaVA（圖／影片）上、A10G 與 A100 GPU，較 Guidance、vLLM、LMQL 取得最高 6.4 倍吞吐。

2. 程式設計模型

SGLang 是嵌入 Python 的 DSL，透過靈活可組合的原語簡化多呼叫工作流中繁瑣的字串處理、API 呼叫、約束指定與並行。

執行範例（圖 2）：一個用 branch-solve-merge 提示法評分「關於某圖片的短文」的程式 multi_dimensional_judge(s, path, essay)——s 管理 prompt 狀態、path 是圖片路徑、essay 是文本。用 += 把新字串與原語接到 s。先加圖片與短文；用 select 判斷短文是否與圖片相關（存 s["related"]）；若相關，fork 出三份副本從不同維度並行評分（gen 存進 f["judgment"]）；再合併判斷、生摘要、給字母等級；最後依 regex 定義的 schema 以 JSON 回傳。等價的 OpenAI-like 介面程式需2.1 倍行數。

語言原語：gen（呼叫模型生成、存進具名變數，支援 regex 約束輸出遵循文法如 JSON schema）；select（從清單選最高機率選項）；+=／extend（接字串）；[變數名]（取生成結果）；fork（建 prompt 狀態的並行副本）；join（重新合併）；image／video（多模態輸入）。

執行模式：最簡是直譯器——prompt 當非同步 stream，extend/gen/select 非阻塞提交（類似非同步啟動 CUDA kernel），各 prompt 由背景執行緒的 stream executor 管理、達成程式內並行；取結果時阻塞以確保同步。另可編譯成計算圖由 graph executor 執行以做更多優化（本文預設直譯器模式，編譯器模式見附錄 D）。支援開源權重（自帶 SGLang Runtime, SRT）與 OpenAI/Anthropic 等 API 模型。

比較：LLM 程式系統可分高階（LangChain、DSPy，提供預定義或自動生成的 prompt，如 DSPy 的 prompt optimizer）與低階（LMQL、Guidance、SGLang，不改 prompt、允許直接操作 prompt 與原語）。SGLang 屬低階，類似 LMQL / Guidance，但更著重 runtime 效率並自帶協同設計的 runtime。高階語言（如 DSPy）可編譯到低階（如 SGLang）；§6 展示把 SGLang 當 DSPy 後端以提升效率。
