4. 方法論：STATIC

4.1 問題形式化

設 V 為語意 token 詞彙量、L 為 SID 固定長度、C ⊂ V^L 為受約束子集。定義約束函數 F_t(y_{<t}, y_t) = I(∃c∈C s.t. (y_{<t}, y_t) ⊑ c)，若附加 y_t 到前綴 y_{<t} 產生 C 中的合法前綴則回傳 1。目標是在僅推論期強制 P(y_t|y_{<t}) = 0 當 F_t = 0，且以最低延遲開銷達成。

4.2 基於稀疏過渡矩陣（STM）的 Trie 轉換

核心構想：將前綴樹展平為 CSR 稀疏過渡矩陣。令前綴節點總數為 S，將每個唯一節點對應至狀態整數 s ∈ [S]。定義稀疏矩陣 T ∈ Z^{S × |V|}：T_{s,v} = s_next（若從 s 經 token v 存在過渡到 s_next），否則為 0（0 表示終端"sink"狀態）。

矩陣建構（離線）：三陣列 CSR 表示如下：

  • Row Pointers (P)：儲存每狀態 s 的合法過渡索引範圍
  • Column Indices (C)：儲存觸發過渡的合法 token ID v
  • Values Array (V)：儲存目標狀態節點 ID s_next

以圖 1 為例：從 Node 4 提取過渡時，row_start = P[4] = 5，row_end = P[5] = 7，切片得 C[5:7] = [2,3]（合法 token 2 與 3），V[5:7] = [6,7]（分別導向 Node 6 與 Node 7）。

4.3 加速器原生解碼演算法

為在硬體加速器上達成高吞吐量，將有效性檢查重構為向量化查詢。關鍵機制：

  • 過渡狀態向量 n_t：追蹤每條 beam 在 trie 中的當前節點索引。
  • 混合稠密／稀疏查詢：前 d 層使用預計算稠密遮罩張量 D ∈ R^{|V|^d}（標記哪些長度-d 前綴存在於 C），做極快的 O(1) 查詢；但 D 的儲存成本在 d ≥ 3 時爆炸（|V|^d 指數增長），因此 d ≤ 2，後續層依賴 CSR 稀疏矩陣。

每步解碼流程（Algorithm 1）：

  • Phase 1（Log-Space Projection）：LogSoftmax(L_t) → log-probabilities。
  • Phase 2（Constraint Masking）：若 t-1 < d，呼叫 DenseLookup 做稠密查詢；否則呼叫 VNTK（Algorithm 2）做稀疏矩陣查詢，將無效 token 設為 -∞。
  • Phase 3（Beam Search）：結合遮罩後機率與累積分數，選取 top-M 序列。
  • Phase 4（State Update）：以 Gather 提取對應的 tokens、分數與約束狀態 n_t，用於下一輪。

4.4 實作與硬體最佳化

核心工程挑戰：處理前綴樹的動態特性（節點的子女數量不一）於靜態執行模型中。指標追逐無效率：TPU 上動態分支觸發代價高昂的圖重編譯或強制序列 while 迴圈（阻止硬體管線化）；GPU 上不匹配的子女數導致 warp divergence。

分支無關過渡內核（VNTK, Algorithm 2）：定義 B_ℓ = max_{n∈N_ℓ} b_n^ℓ 為層級 ℓ 的最大分支因數（一次性計算）。關鍵操作：

  • Boundary Lookup：idx_start = P[n_curr]，N_child = P[n_curr+1] - idx_start
  • Speculative Slicing：以 DynamicSlice 固定切片 B_ℓ 個元素（不問實際子女數），讀取 d_col（候選 token ID）與 d_val（目標節點 ID）
  • Sanitization：以 Range(B_ℓ) 生成索引向量，建立 m_valid = (J < N_child) 遮罩，用 Where 對超額欄位清零
  • Projection：以 Scatter 將稀疏有效性列表投射為稠密布林遮罩 m，直接套用至 log-probability

此設計確保 TPU 算術單元完全飽和，整步解碼為單一靜態計算圖。額外優化包括：

  • 堆疊 CSR 佈局：將 Column Indices 與 Values 堆疊為 (N_edges, 2) 張量，單次記憶體交易同時獲取候選 token ID 與目標節點 ID，減半隨機記憶體存取。
  • 稠密遮罩優化：前 d 步以少量靜態記憶體換取最計算密集層的顯著吞吐量增益。
  • 跨平台可移植：JAX/XLA 上的 jnp.take (Gather) 可直譯為 PyTorch/Inductor 上的 torch.gather。

5. YouTube 大規模部署

5.1 實驗設置

YouTube 影片推薦語料庫：SID 長度 L = 8，token 詞彙 |V| = 2048，可推薦語料庫規模約 1-10 億項目。d = 2（前 2 層用稠密遮罩 D ∈ R^{2048×2048}），後續層用 CSR。模型為 Gemini-based 生成式檢索模型（類似 PLUM），3B 稠密參數（非 MoE），batch size = 2（每晶片），beam size M = 70。所有實驗於 Google TPU v6e 進行。

5.2 系統效率分析

約束集：「7 天內上傳」的新鮮影片子集，約 2000 萬高品質項目。比較基線（表 1）：

方法 延遲開銷 (ms) 佔推論比例
Unconstrained +0.0 -
PPV Exact +34.1 260%
CPU Trie +31.3 239%
Hash Bitmap +12.3 94%
PPV Approximate +1.56 11.9%
STATIC (Ours) +0.033 0.25%

STATIC 比 CPU Trie 快 948 倍，比 PPV Exact 快 1033 倍，比 PPV Approximate 快 47 倍。關鍵洞察：PPV 雖為「片上」且向量化，但二分搜尋的 O(log|C|) I/O 複雜度（疊加對 logits 數量的線性縮放）是瓶頸；STATIC 以單次 VNTK 內核將 I/O 複雜度降至 O(1)。

5.3 可擴展性

記憶體用量（見附錄 B）：每 100 萬約束項約需 90 MB HBM（上限）。20M 項目上限約 1.5 GB（實務上 ≤ 75%）。主因：儲存成本由約束集的 trie 節點數主導，早期層的稠密遮罩貢獻恆定（17.3 MB）。

延遲縮放 （圖 2-3）：

  • 對 |C|（10^5 → 10^8）：STATIC 延遲亞線性，幾乎常數。PPV Exact/CPU Trie 大幅縮放（最高 38.7 ms / OOM）。
  • 對 |V|（256 → 32k）：STATIC 延遲近乎常數——前 d=2 層的 O(1) 稠密查詢吸納了大量分支，後續層的最大分支因數理論上線性縮放但實務上保持小常數。目前所有生產系統 |V| ≤ 8192 [8, 37]，STATIC 在此範圍內始終保持極低延遲。

5.4 線上 A/B 測試

在 YouTube 短影片產品「Home Feed」部署 STATIC 強化的 PLUM 模型，以「7 天新鮮度」為約束。結果（表 2）：

  • 7 天新鮮影片觀看 +5.1% [95% CI: 5.0%, 5.2%]
  • 3 天新鮮影片觀看 +2.9% [2.8%, 3.0%]
  • 點擊率 (CTR) +0.15% [0.01%, 0.29%]
  • 策略用戶滿意度 +0.15% [0.03%, 0.27%]

STATIC 達成 100% 約束合規——無約束模型常生成舊影片 SID，STATIC 嚴格僅生成 7 天內的新鮮影片。

6. 冷啟動檢索（Amazon Reviews 資料集）

6.1 設置

為每個 Amazon Reviews 子資料集獨立訓練 RQ-VAE（L = 4，|V| = 256，每子集 10–20k 項目）。基於 Gemma 1B 稠密架構，batch size = 16，beam size M = 20，TPU v6e。

6.2 冷啟動結果

實驗方法：以「最舊評論的年齡」定義項目年齡，分離最新 2%（及 5%）項目為冷啟動集合，過濾掉不含冷啟動項目的訓練序列。比較方法：(1) Unconstrained beam search；(2) Constrained Random Guessing；(3) Dense Retrieval（雙塔模型）；(4) STATIC。

結果（表 3，Recall@1 %）：

子資料集 方法 2% 冷啟動 5% 冷啟動
Beauty Unconstrained / Const. Random / Dense / STATIC 0.00 / 0.42 / 0.88 / 4.29 0.00 / 0.17 / 0.63 / 1.60
Sports & Outdoors 同上 0.00 / 0.27 / 0.85 / 1.24 0.00 / 0.11 / 0.36 / 1.17
Toys & Games 同上 0.00 / 0.42 / 0.49 / 4.39 0.00 / 0.17 / 0.44 / 2.25

STATIC 在所有設置中大幅優於無約束（皆 0%）、隨機猜測與稠密檢索——證明僅靠受約束填碼即可實現非平凡的生成式檢索冷啟動效能。

7. 結論

生成式檢索承諾將 LLM 應用於下一代推薦系統，但其工業採用一直受限於輸出空間控制能力的缺失。本文在前綴樹約束與向量化硬體之間架起了橋梁。STATIC 框架將指標追逐的 trie 查詢轉化為向量化稀疏矩陣運算，實現比替代方案快 47–1033 倍的加速，並在服務數十億用戶的生產環境中展示了嚴格約束可以規模化強制執行而不損害服務延遲，同時證明僅靠受約束填碼即可改善冷啟動效能。

未來工作：目前 CSR 過渡矩陣建構為離線過程，開發動態稀疏更新以支援即時庫存變更（無需完全重編譯模型）是重要延伸方向。
