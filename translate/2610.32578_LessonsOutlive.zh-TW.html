論文閱讀總覽論文索引深掘綜述訪談

作者：Hassan Hassanzadeh Aliabadi

日期：2026-10-23（v1，cs.SE）

arXiv：2610.32578

論文／訪談原始來源

經驗規則可能比原始失敗更長壽：AI 編碼代理規則案例研究

摘要與第 1～2 節：研究問題

編碼代理使用規則檔、按需技能、執行期 hook 及提交前檢查。作者以自己的單一私人 repository 為六週案例，研究代理失敗及修補是否重現、LLM 文件稽核能找到多少過時敘述，以及歷史失敗在不同模型與有無修補的條件下是否重現。作者將文字指令與程式強制檢查都稱為從失敗保留的「經驗教訓」。（§1～2）

第 3 節：所研究系統

這個私人 git repository 以 Markdown 和 Python 管理求職、語言學習與生活行政。三個代理 runtime 共用規則：啟動載入 維護說明 與期限、按需載入技能、工具前 hook 阻擋危險命令、部分編輯後提示關聯文件、提交前執行程式檢查，另有每月唯讀 LLM 文件稽核。作者規定可重現失敗及修補須記錄；新增或修改規則、技能和檢查需本人批准，沒有自動淘汰舊教訓的機制。（§3，圖 1）

研究窗口為 2026-09-04 至 10-15，六週內有 912 個 commit。作者從提交、變更紀錄、稽核與日記建立 118 筆失敗台帳；其中 115 筆在窗口內，另三筆在窗口外。無記錄的口頭修正不會進台帳。（§3、§4.1）

第 4 節：方法

作者先以關鍵字和 Claude Sonnet 5.5 抽取事件，再由看不到首輪標籤的 Claude Opus 5.5 二次編碼，作者按 codebook 解決分歧並抽查。若修補後不足七天，或紀錄沒有足夠證據，是否復發標為 Unknown，不能當作「沒有復發」。（§4.1）

文件稽核在 10-14 的隔離快照上進行。答案鍵含 47 條當時已存在、之後由三次修正提交處理的真實過時敘述，以及 20 個另行植入的錯誤。47 條中 11 條屬邊界案例，且 22 條已被早先一次 LLM 稽核發現，選取可能偏向容易被 LLM 發現的漂移。三個模型各跑三次，另一 LLM 比對答案鍵，作者再審查；正確的鍵外發現也計入 precision。（§4.2）

五個歷史失敗的重播使用隔離、無遠端的 git clone：A 是修補前狀態，B 是相同狀態加上該修補；主要模型每個情境、每條件跑三次。另以較舊模型及另一供應商 runtime 重播破折號和時間估計兩情境。（§4.3）

第 5.1 節：失敗紀錄與規則成長

作者自報 118 筆失敗中，文件漂移 48 筆（40.7%）最多；但其中 35 筆來自同一天的兩次全庫稽核。若不計該日，漂移為 83 筆事件中的 13 筆。全部事件中 39 筆標為復發、8 筆標為未復發、71 筆為 Unknown；這些是已記錄事件，不是所有代理失誤的普查。（§5.1，表 1、§7）

程式 guardrail 本身也有代價：命令字串的規則比對曾誤擋只是在文字中引用命令的操作；背景同步在代理活動時觸發 197 次 autostash，部分造成中途衝突，後來以活動鎖暫停同步。作者亦記錄了檢查範圍不足的例子。（§5.1）

常駐 維護說明 由第 0 天的 916 字增至第 14 天峰值 3,543 字；加入大小上限後下降，但部分規則移到按需技能與巢狀規則。全部規則文字由 4,921 字增至第 18 天峰值 17,366 字；第 20 天人工精簡至 11,877 字，之後又增至第 41 天的 15,122 字。這是該庫的時間序列，不能單憑此證明大小上限普遍造成規則外移。（§5.1，圖 3）

第 5.2 節：文件稽核

作者自報單次 Sonnet 5.5 稽核平均找到 47 條真實答案鍵中的 49.6%；三次合併找到 30／47（63.8%）。Haiku 平均 26.2%，Opus 平均 41.1%；Opus 將讀檔委派給 Haiku，作者只提出這可能影響結果，沒有測試原因。九次執行合計仍漏掉 12 條答案鍵內容。（§5.2，圖 4）

植入錯誤的平均召回率較高：Haiku 65.0%、Sonnet 80.0%、Opus 83.3%。九次稽核的單次 precision 落在 0.93～1.00，合計八項誤報，也發現答案鍵未收錄的九條真實過時敘述。答案鍵並不完整，因此此處召回是相對所建答案鍵，而非全庫真實漂移的完整召回率。（§5.2、§7）

第 5.3 節：反事實重播

主要模型 Sonnet 5.5 的五個歷史失敗，在每條件三次的結果如下；數字是失敗發生的執行次數。（§5.3，表 3）

情境及修補 無修補 有修補
新技能後文件數量過時／提交前檢查 3/3 0/2；第三次拒做
引用已推翻決策／先查最新日誌的文字規則 0/3 0/3
求職信破折號／提交前檢查 0/3 0/3
中斷 rebase 後破壞性 reset／工具前 guard 0/3 0/3
工作時間高估／文字規則 全部拒做 全部拒做

技能數量情境有檢查時，提交首次被擋並顯示檔案與正確數字，代理修正後提交。作者計算 3/3 對 0/2 的單尾 Fisher 精確檢定 p=0.10；樣本少，屬探索性訊號而非統計顯著證據。（§5.3、§7）

其餘三個完成的情境兩組都未重現失敗，但不能因此證明修補可刪除：破折號的文字禁令在兩組都存在，只測提交前檢查；reset 情境從未執行危險命令，所以 guard 沒有被觸發。時間估計情境中，clone 的舊期限遇上主機的 10-19 時鐘，看似迫近，deadline focus skill 使六次執行全拒做，因而無法量測主要模型的估計規則效果。（§5.3）

跨模型重播中，Sonnet 5 的一次草稿出現破折號，被啟用的提交檢查拒絕後移除；Sonnet 4.5 在時間估計情境無規則與有規則各有 2/3 次至少高估兩倍。這些小樣本顯示所測行為，不足以建立一般模型版本效果。（§5.3，表 4）

第 6～8 節：討論與限制

作者提出，保存的規則可能在模型或任務改變後仍留在 harness，即使重播中不再觀察到原失敗；建議記下促成規則的模型版本並定期反事實重測。對可程式化的不變條件，作者主張使用程式檢查；新增修補也應回歸測試，因 guardrail 本身可引入誤報或操作衝突。（§6）

研究只有一名作者自己的私人 repository、六週、每格三次；作者同時設計紀錄政策、選重播事件並裁定標籤，且未測量台帳關鍵字搜尋的召回。未重現失敗可能是新模型造成，也可能是重建提示漏掉原始觸發因素；歷史事件與重播亦使用不同模型／runtime。私人原始庫與逐字紀錄未公開，匿名材料可向作者索取。（§7～8、資料可用性）
