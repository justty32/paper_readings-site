論文／訪談原始來源

經驗證的工具呼叫改善非原子失敗下的 LLM Agent 可靠性

摘要

LLM agent 依賴外部工具完成多步任務。既有框架多假設工具呼叫是原子的，只回成功或失敗；真實系統卻會在 dispatch 後 timeout、延遲顯示更新或只完成部分狀態。本文加入輕量 wrapper，結合 postcondition verification、verify-before-retry 與 idempotency key。在注入非原子故障的模擬環境中，方法大幅減少重複動作，並維持相近或較高的任務成功率，不必修改底層語言模型。

1. 引言

ReAct 與 MCP 改善模型如何選工具與填參數，卻較少處理工具執行後的分散式系統現實。agent 看到的 response channel 與伺服器實際改變世界的 effect channel 並不相同。請求可能已成功，回應仍可能遺失；若 agent 將 timeout 解讀為未執行，再送一次支付、訊息或資料寫入，就會造成重複副作用。

本文的貢獻是定義四種非原子故障，提出先驗證再重試的 wrapper，並在不改模型的條件下測試它。

2. 背景與問題形式化

2.1 工具呼叫模型

工具呼叫表示為動作、回應、執行前真實狀態與執行後真實狀態。原子工具的回應忠實表示完整狀態轉移；非原子工具則可能讓回應與真實效果分離。這與資料庫交易全成或全敗的 atomicity 不同，許多分散式 API 為了 availability 使用較弱一致性。

2.2 真實工具為何非原子

網路 timeout 可能發生在伺服器已執行後。Eventually consistent store 可能在寫入後暫時讀到舊值。複合操作也可能只有部分子動作成功。這些情況都會讓 agent belief 與 ground-truth state 分岔，即使 agent 和工具各自沒有推理或程式錯誤。

2.3 四種故障

Timeout-after-dispatch 表示效果可能已發生但確認遺失；delayed visibility 表示寫入成功、驗證讀取過時；partial success 表示只有部分效果生效；stale conflict 表示其他 agent 或行程先修改狀態，使本來合法的動作失效。

3. 相關工作

ReAct、Toolformer、ToolBench、AgentBench 多假設工具乾淨且回應可信。Reflexion 與 tree search 可修正推理或規劃錯誤，但無法解決「動作已成功、agent 不知道」；此時 retry 不是修正，而是重複。

分散式系統早已區分 at-least-once 與 exactly-once，常以 idempotency key 讓重送不重複生效。本文把這些 execution semantics 引入 agent 工具層，位置在模型與工具之間。

4. Verified Tool Wrapper

4.1 原則

第一，將效果與回應分離，成功與否應以外部狀態驗證。第二，任何模糊失敗都先驗證，再決定 retry。第三，需要 retry 時沿用 idempotency key，讓伺服器去重。

4.2 任務與成功定義

activate_customer 要建立客戶、設為 ACTIVE 並只送一則 welcome message；record_invoice 要更新 invoice row、建立紀錄並設為 RECORDED。前者主要暴露重複副作用，後者暴露部分寫入。

每個動作的成功由 postcondition predicate C(S') 判定。存在某筆 row 不夠；ID、amount 與其他預期欄位都要正確。Postcondition 含領域知識，不能只從 API 名稱自動推出，因此既是方法的可靠性來源，也是每個任務要額外工程的限制。原文此處把客戶狀態寫成 "activate"，與任務的 ACTIVE 不一致。

4.3 Verifier

每個動作有對應 verifier，輸出 True、False 或 Unknown。第三值用來避免 eventual consistency 下把暫時看不到誤當失敗。verifier 可用直接讀取、API polling，或在非結構資料上使用 LLM 判讀；但必須唯讀，重複執行才不會增加副作用。

4.4 Idempotency key

key 由 agent ID、動作類型、payload 與時間 bucket 的 hash 決定。同一邏輯操作所有嘗試使用相同 key。底層支援去重時可近似 exactly-once；不支援時只能依 verifier 降低重複，並行 retry 的 race 仍存在。

4.5 Agent 與演算法

所有方法使用 Gemini Flash-Lite、temperature 0、最多 1024 tokens；LangGraph 中由 LLM node 與 tool node 形成 ReAct loop。Baseline prompt 要求錯誤後直接 retry 且不帶 key；每個邏輯操作最多 retry 一次。模糊狀態由 wrapper 內部消化，不回傳給模型。

流程是先執行；明確成功就返回成功，明確失敗就停止。模糊時 backoff 後驗證：True 停止，False 以相同 key 重試，Unknown 等待後進下一輪。由於實驗 N=1，Unknown 究竟能重查幾次在偽碼中交代不足。

5. 實驗設定

實驗使用可控制真實狀態的合成工具環境。故障率分低、中、高三級；timeout 分別 5%、20%、35%，delayed visibility 為 5%、15%、25%，partial success 為 3%、10%、15%，conflict 為 2%、5%、10%。

主實驗每個 task、fault level、method 跑 25 episodes，共 2×3×2×25=300 runs。seed 從 42 逐 episode 增加，兩方法使用同一串 seed。另有只測 activate_customer 中故障的獨立 ablation，其絕對數字不能和主實驗比較。

6. 結果

6.1 任務成功

activate_customer 的 wrapper 在低、中、高故障皆 100%；baseline 低故障 92%，高故障降到 64%，高故障差 36 個百分點。record_invoice 的 baseline 為 100%、96%、96%，wrapper 為 100%、96%、100%。後者成功率已有天花板，wrapper 的價值主要是避免不安全路徑。

6.2 重複副作用

activate_customer baseline 的 duplicate rate 為 20%、44%、72%，wrapper 為 0%、16%、20%。record_invoice baseline 為 32%、52%、76%，wrapper 同樣為 0%、16%、20%。這顯示只看終局成功會漏掉大量重複寫入。

6.3 消融

獨立 run 中，baseline 約 58% success／42% duplicate；verify-only 約 80%／20%；full 約 72%／28%。驗證是主要效果，retry 未必增加成功，因為它會再次碰到工具故障，也可能造成新副作用。

7. 討論與未來工作

錯誤回應不代表操作失敗。Agent framework 應要求工具暴露 idempotency key、operation identifier、status endpoint 與可驗證 postcondition。未來可將三值 verifier 擴成信心分數，綜合回應、狀態、key 與執行歷史，決定立即 retry、等待、人工介入或安全終止；也需要自動建構更完整的語意 verifier。

8. 結論與限制

Verify-before-retry 把恢復策略從「相信模糊回應」改成「查看真實狀態」，在小型模擬中顯著降低重複副作用。它不證明已能處理 production：任務只有兩種、verifier 手工撰寫、每格僅 25 次，baseline 也刻意不使用去重。真實系統還有 stale verifier、rate limit、認證、跨服務補償與長時間未知狀態。方法應視為正確的 execution-layer 原則，而非已完成的通用可靠性方案。
