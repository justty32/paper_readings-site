6. 分析

主要實驗建立了 SKILLGUARD 的錯誤輪廓：高精確率、有用但不完整的召回、以及來自定位的修復增益。我們現在問系統的哪些部分產生這些行為，以及目前合約觀點的邊界在哪。

6.1 什麼解釋精確率-召回輪廓？

SKILLGUARD 精確率穩定但召回不完整，因為精確率與召回由不同階段控制。精確率主要是角色門的結果：只有當變更值為技能的 OPERATIONAL 義務時才被監控。召回則受相關義務是否被提取及是否有驗證器能檢查它限制。

獨立的角色標籤審計支持此分解。兩位標註者對 200 個環境提及獨立標註，分歧於評估前仲裁。以 OPERATIONAL 為正類，SKILLGUARD 達 89.5% 精確率、83.4% 召回、86.3% F1。分割級模式與端到端行為匹配：在語義 hard negatives 上角色精確率達 100.0%（保守於值變更但合約保留的案例），同分割角色召回 72.7%（指出被錯過的作業假設來源）。

提取敏感性指向取捨的另一面。將確定性提取器從 7 擴至 15 類正則家族，受控分割純 regex 召回從 13% 升至 33%，真實世界從 45% 升至 78%，FPR 保持 0%。新增模式涵蓋 Docker 映像、GitHub Actions 版本、環境變數、雲端區域、分支名稱、CLI 旗標及配置檔名。因此目前召回差距非精確率需要棄權的證據：覆蓋率可在不削弱角色承載合約過濾器下提升。

6.2 修復證據實際顯示什麼？

修復實驗應解讀為定位結果，而非 SKILLGUARD 支配所有修復方法的主張。失敗合約識別哪個作業假設被失效、在技能何處、什麼證據觸發了違反。這將偵測轉換為受限的編輯請求而非開放式重寫。

此定位訊號遠強於模糊過時技能提示（從 10% 升至 78% 單輪）。然而更強基線仍具競爭力：純漂移文字 60%，三輪 Self-refine 80%。SKILLGUARD 與純漂移文字或 Self-refine 的差異在目前樣本中不顯著。支援的結論因此更窄且更有用：違反合約是可操作的修復證據，縮小模糊修復與更強多輪替代方案之間的大部分差距，同時使用較少互動。

6.3 目前合約觀點在何處破裂？

兩個邊界保留。

測量邊界。 嚴格的字面驗證器僅在所需新值出現且過時值消失時接受值替換修復。這避免許多虛假修復成功，但非語義技能正確性證明。類型感知驗證器接受 168/174 案例，對比字面驗證器的 165/174，留下約 2% 保守拒絕差距。此差距主要出現在依賴更新——語義上有效的編輯可能滿足新依賴約束而不保留精確字面形式。

機制邊界。 SKILLGUARD 最強時為漂移使可定位環境假設失效（URL、版本、API 路徑、配置值）。當修復需要改變互動機制時較弱。Qwen3.6-Plus 逐類型分解中，URL 變更與版號躍升達 100% 偵測；配置、廢棄與 schema 變更落至 60-67%。認證漂移是此切片中最難案例：偵測 67%，但三個範例的修復全失敗（0%）。這些失敗不與合約框架矛盾；它們標誌表面合約應以 schema 感知驗證器、執行支撐檢查或更豐富修復計畫補足之處。

失敗模式：認證漂移常需替換互動機制而非值；schema 變更常嵌在散文或範例輸出中使提取困難；行為耦合出現於多個相依欄位須一起變更時。這些失敗反映提取與修復定位的限制，非角色承載驗證本身導致誤報的證據。

7. 結論

長期存在的 agent 技能不會只因環境變更而失敗；它們在那些變更使技能在作業上依賴的假設失效時失敗。本文將技能漂移框架化為合約違反，並引入 SKILLGUARD：提取環境合約、僅驗證角色承載假設、並用失敗合約定位修復。此粒度改變了監控錯誤輪廓：無合約 CI 探針產生 40% FPR，而 SKILLGUARD 在 599 個無漂移與 hard-negative 案例中零誤報；在開放世界發現中，以 86% 保守精確率浮現即時漂移。相同違反使修復局部化，將單輪修復從無定位的 10% 提升至 78%。與 DRIFTBENCH 一起，這些結果使技能劣化可作為維護問題被量測，同時將窮盡語義驗證留給互補的執行式方法。

附錄要點

附錄 B：記號與範圍。 r_i 角色變數是核心區分——OPERATIONAL 提及作為合約監控，INCIDENTAL 提及在驗證前被抑制。範圍：SKILLGUARD 是環境合約違反的精確優先監控器，非技能正確性的完整語義驗證器。

附錄 C：限制。 保證僅在提取覆蓋與可用驗證器內適用。隱含、行為性、或僅透過執行才可觀察的假設可能被錯過。即時驗證基於套件註冊表與 URL 回應，提供有用的發現訊號但不取代執行式 canary。

附錄 D：演算法。 關鍵排序為角色過濾先於驗證（Algorithm 1）。無合約探針驗證每個提取的 URL/版本/路徑而對附帶提及過度警報；SKILLGUARD 先決定提及是否為作業義務，才進行驗證。

附錄 E：匹配正規化規則。 匹配器刻意保守：使用精確匹配→雙 token 重疊→類型相容單 token 退路。更積極的語義正規化可恢復 schema 重命名或 API 行為變更，但可能在附帶範例中產生近碰撞。

附錄 F：DRIFTBENCH 建構細節。 受控漂移以 Qwen3.6-Plus 生成、DeepSeek-R1 跨家族驗證、作者仲裁（有效性 99.6%）。真實世界分割從 PyPI、npm、GitHub Actions、Docker Hub 收集，無 LLM 參與生成。

附錄 G：人類審計結果。 176/880 對審計（20%），14 對需修正：值正規化 5、證據跨度 4、hard-negative 措辭 3、來源元資料 2。無一審計漂移標籤翻轉，驗證 DRIFTBENCH 作為技能劣化（非裸文字變更）基準。

附錄 H：角色標籤獨立審計。 200 個提及的雙人標註：總體 OPERATIONAL 判定達 89.5% 精確率、83.4% 召回、86.3% F1。語義 hard negatives 上精確率 100%、召回 72.7%——支持精確優先機制，同時標誌召回邊界。

附錄 J-K：負控制統計與基線。 合計 599 負控制（49 + 300 + 250），零誤報 Wilson 95% CI [0%, 0.6%]。無合約 CI 探針 40% FPR；NL2Contract 式 0% FPR 但召回僅 45%；S KILL G UARD 達 76% 召回、0% FPR。

附錄 L-N：即時發現與修復補充。 標記的 14 個技能清單包含 analyze-ci、distributed-tracing、gitops-workflow、rag-implementation 等。修復消融嚴格驗證合約的定位價值；字面 vs 類型感知驗證器差距約 2%（主要在依賴更新）。
