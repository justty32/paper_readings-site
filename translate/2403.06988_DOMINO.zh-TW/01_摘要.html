摘要

為確保大型語言模型（LLM）產生的文本符合預期格式，約束解碼（constrained decoding）提出在生成過程中強制施加嚴格的形式語言（formal language）約束。然而本文指出：這類方法不只在生成時帶來效能開銷，其中許多方法若未能正確地把底層 LLM 的子詞詞彙表（sub-word vocabulary）與外部約束對齊，還會顯著損害任務準確率。為此，我們提出一個新的解碼演算法 DOMINO，能以完全子詞對齊的方式施加約束，同時透過**預先計算（pre-computation）與推測解碼（speculative decoding）**達到近乎零開銷、某些情形下甚至比無約束解碼還快近 2×，大幅勝過既有方法。

1. 引言

LLM 的成功催生了各種約束生成方法，讓使用者把 LLM 輸出裁切成特定任務或格式。

約束解碼：為確保輸出符合語法約束，這些方法在解碼時限制每一步只允許「語法上合法」的 token，藉此保證輸出必定符合如高階模板（template）、正規表達式（regular expression）或上下文無關文法（context-free grammar, CFG）等約束。好處是輸出必然合法、減少事後解析、重試與提示的需求，讓 LLM 更容易嵌入更大的管線，無需微調或後處理。

關鍵挑戰：Token 不對齊（Token Misalignment）。由於 LLM 的子詞 token 與多數語法約束並不直接對齊，約束解碼的核心難題就是把「LLM 詞彙表」與「像是『輸出必須是合法 JSON』的語法約束」接起來。以圖 1 為例：無約束時 LLM 會選 ·"（帶前導空白的引號）作為第四個 token；但若天真地只限制它使用即時合法的 JSON 文法終端符（如單獨的 " 或空白），就會逼它選出較差的 \t。這類次佳 token 一旦引入，被錯誤約束的 LLM 其機率分布很容易偏離無約束情形，導致推理表現與下游準確率明顯下滑（圖中被逼出的 token 具高困惑度 perplexity，代表模型本來不會選它們）。根本原因是天真約束沒有考慮橋接 token（bridge tokens）——那些跨越多個文法終端符的 token（此例中即空白＋雙引號）。既有的程式碼生成研究曾觀察到此現象（Poesia 等人 2022），但要「高效」解決仍具挑戰，因為在每個解碼步驟線上計算所有橋接 token，在高吞吐環境下代價過高。

本文工作：高效、最小侵入式的約束。我們研究上述 token 不對齊問題並實證其後果，提出最小侵入式約束解碼（minimally invasive constrained decoding）的概念：一種既強制文法、又在生成過程中盡可能少介入、避免 token 不對齊、追求忠實低困惑度輸出的約束方式。基於此我們提出 DOMINO——能以最小侵入方式強制 CFG，且開銷極低，多數情形甚至比無約束生成更快（藉由預先計算與一種新的約束式推測解碼）。

主要貢獻：(1) 指出約束解碼的挑戰，尤其是子詞 token 與文法終端符的正確且高效對齊（§2）；(2) 提出 DOMINO，解決 token 不對齊並利用預計算與推測解碼達成極低開銷（§3）；(3) 大量評估顯示 DOMINO 為最小侵入、低開銷，顯著勝過其他方法，且多數情形超越無約束生成的吞吐量（§4）。

2. 約束解碼的挑戰

方法總覽（表 1）：作者以四個維度比較既有方法——是否支援 Regex、是否支援 CFG、是否可預先計算（Pre-Computed）、是否最小侵入（Minimally Invasive）。lmql、guidance、Outlines、Picard、Synchromesh、llama.cpp、gcd 各有缺項；唯有 DOMINO 四項全部滿足（Regex ✓、CFG ✓、Pre-Computed ✓、Minimally Invasive ✓）。

約束解碼一般流程（演算法 1）：一個檢查器 C（parser 或 regex checker）確保輸出 o 符合約束。每產生一個新 token，先用已生成序列更新 C，再產生遮罩 m 強制下一 token 必須為合法延續；用 m 遮蔽 logits 後才解碼。每當遮罩否決一個「本來會被選中」的 token，即稱該演算法介入（intervene）了一次；介入愈少即愈最小侵入。

定義 2.1（最小侵入）：若對任意提示，凡是無約束模型能生成的合法輸出，受約束模型在相同提示下也都能生成，則稱該約束方法為最小侵入。把圖 1 的天真約束換成最小侵入方法，輸出會與無約束生成一致，直到 JSON 物件的最後一個 }；此後無約束模型會續寫非 JSON 文本，而最小侵入解碼器則透過強制 EOS token 在此停止，確保輸出仍為合法 JSON。

作者以 GSM8K 的 JSON 編碼版說明差異：天真約束把準確率從無約束的 41.5% 降到 30.8%，而最小侵入約束反而微升至 41.8%（五-shot，Mistral 7B）。

既有方法分三類：

Regex-Based（正規表達式類）：許多框架支援（lmql、Outlines、guidance、llama.cpp），通常不受 token 不對齊之苦，因為判斷某 token 是否為合法延續較簡單。Willard & Louf（2023）並提出可離線預計算針對模型詞彙表的 regex 檢查器以加速推理。

Online Parser-Guided（線上解析器導引類）：讓 parser 與 scanner 與 LLM 同步逐步運行，線上計算每步哪些 token 為合法延續（Picard、gcd、llama.cpp）。可支援完整 CFG，且如 Synchromesh（Poesia 等人 2022）所示能支援橋接 token 而做到最小侵入。但這些方法推理開銷相對高，因為最壞情況下每一步都得檢查整個模型詞彙表。

Template-Based（模板類）：guidance 與 lmql 提出模板法，固定部分結構、只對輸出的一部分在 regex 約束下取樣（例如 schema 驅動的 JSON，欄位固定）。因為模板 token 可在生成時確定性地直接加入、不需呼叫 LLM，故較有效率（減少前向傳遞次數）。

模板誘發的不對齊（Template-Induced Misalignment）：要不呼叫模型就插入模板 token，必須用外部 tokenizer 把模板文本轉成 token。圖 2 以 guidance + Mistral-7B 生成 JSON 為例：(1a)(1b) 顯示模板的具體措辭（空白、格式）不同，輸出會大幅變化；模板輸出困惑度高達 24.50–26.75，遠高於無約束生成的 4.17。把整段模板輸出改用「模型偏好的 tokenization」自然化後 (2)，困惑度甚至爆炸到 49.39，代表若非侵入式約束，模型極不可能自然產生這種輸出。§4.1 進一步證實這種侵入式模板生成會顯著拉低任務準確率。

Token Healing（token 修復）：guidance 以 token healing 減緩模板誘發的不對齊——它把提示截斷回倒數第二個 token 邊界，並把其餘部分當作生成的前綴強制施加，藉此在模板與非模板 token 的交界處改善 tokenization、整合部分橋接 token。但多數模板 token 仍固定不變（圖 2 已啟用 token healing 卻仍有顯著差異）。

關鍵挑戰（表 1 總結）：約束解碼的核心是要找到一種方法同時做到——(i) 對 regex、CFG、模板解碼皆具表達力；(ii) 在所有情境下皆最小侵入；(iii) 推理開銷低。DOMINO 正是為滿足這三點而設計。
