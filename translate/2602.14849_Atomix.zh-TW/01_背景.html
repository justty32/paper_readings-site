摘要

LLM agent 透過工具執行會改動外部狀態的多步工作流。常見編排器把工具回傳視為 settlement 觸發點，因此故障、推測執行與併發 agent 可能留下部分效果、落選分支殘留、陳舊寫入或不可逆傳送。正確 settlement 必須知道哪些效果應共同落地，以及較早的衝突工作何時已全部結束。

Atomix 以 progress-aware transaction 明確拆開這兩件事。runtime 在執行時記錄讀取與效果，footprint 完整後 seal，並只在每資源 frontier 證明不會再有較早衝突工作時 commit。commit 釋放可緩衝效果、確認已外部化的可逆效果，並讓不可逆效果離開 gate；abort 抑制未釋放效果，且在可能時補償已外部化效果。代表性 workload 顯示此組合改善注入故障下的 clean recovery、隔離併發與推測工作，並阻止分類正確的不可逆操作外洩。

1. 導論

agent 會編輯程式、更新資料庫、填表、寄信與呼叫第三方 API，也愈來愈常讓多 agent 共享資源、平行探索方案或提前執行下游工作。核心問題是：工具效果何時可以成為永久狀態？

retry、checkpoint 與 Saga 都是在效果可能已外部化後恢復；snapshot rollback 不能收回郵件，Saga 也只能處理有正確補償的可逆效果。per-call lock 跨不過 read-plan-write 間隙，workflow lock 又會序列化不相關工作。OCC 還需要封閉的 footprint 與不可逆效果何時可離開 gate 的規則。Atomix 因此結合 transaction grouping、seal、per-resource progress 與 effect-class settlement。

主要主張為：在 τ-bench 的重故障注入下，Atomix clean task success 為 57%，除 Checkpoint-Replay 外的比較機制為 0–7%；強制 multi-agent overlap 下沒有 conflict-cycle witness；不可逆傳送測試有 0/500 invalid sends，且 500/500 valid sends 均釋放。作者把它定位為 execution-layer runtime，不取代資訊流控制、規劃語義驗證或 kernel confinement，也不主張 distributed deployment 或完整 crash-safe exactly-once。
