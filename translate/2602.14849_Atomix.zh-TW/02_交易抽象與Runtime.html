2. 交易抽象與 Runtime 語義

2.1 核心物件

Atomix 使用五種 runtime 物件：epoch 是全序單調邏輯時間；scope 為資源命名，分 read 與 effect scope；effect 包含資源、idempotency key、類別及可選 handler；frontier 是每資源的單調 epoch cursor；transaction 則把必須一起 settle 的讀取與效果組合起來。交易粒度由 integration layer 決定，通常應是最小的 agent intent 單元，例如一次 read-plan-write phase，而不是單一 call 或整個長工作流。

對「K 個方案選一個」的推測執行，每個方案是獨立交易；controller commit 勝者、abort 其餘分支。

2.2 生命週期與責任

交易狀態為 open → sealed → waiting_on_progress → committed/aborted。open 時 adapter 可登記 scope 與 effect；所有 in-flight call 已回傳、記錄或取消後由 orchestrator seal。seal 是 footprint 不再增長的契約，任何 late append 都會被拒絕並 abort。

agent 選工具，但不被信任來做 concurrency control。orchestrator 選交易粒度、追蹤 pending calls、seal、選 speculative winner、abort loser、推進 frontier；adapter 提供 scope、效果類別、idempotency key 與 handler；transaction manager 執行 state machine；progress tracker 判斷能否 settle。需要語義驗證時，交由 pre-commit hook。

2.3 效果分類與 Adapter

  • Reversible：例如檔案或 DB 寫入，可 eager execution，abort 時依反向相依順序補償；可另標記 reversible-with-cost。
  • Bufferable：例如能由 runtime 暫存的本地狀態，先回 staged acknowledgment，commit 套用，abort 丟棄。
  • Irreversible-gated：例如郵件、轉帳或物理操作，在 adapter gate 暫留，先回 queued acknowledgment，commit 才呼叫。
  • Idempotent-known-outcome：有 provider-side idempotency key 的選用類別，共用 reversible 路徑而不需自訂補償。

adapter 宣告 scope extractor、effect builder、key、類別及可選 release/compensation handler。若執行前不知道精確資源，可先登記保守 may-touch scope，結果回來後再細化。scope 過粗只會降低併發，過窄或漏登記則會讓衝突逃逸。

2.4 Commit、Abort 與可見性

設交易 T 的 sealed footprint 資源集合為 R(T)，其讀取與效果最大 epoch 為 e(T)。只有每個 r ∈ R(T) 都滿足 frontier(r) ≥ e(T) 才可 commit；而 frontier 只能在所有 commit_epoch < e 且觸及該資源的交易已 finalise 後推至 e。strict-less-than 避免交易等待自己。

abort 的原因包括工具失敗、補償失敗、pre-commit veto、落選分支、seal 後 late effect，或等待期間讀取被較早交易更新而 stale。結果按效果標記：補償成功為 clean；不可逆效果在 abort 決定前已釋放為 leaked；補償失敗、有成本殘留或缺 handler 為 unresolved；多個 gated irreversible calls 中前者成功、後者重試耗盡則為 partial-commit。

Atomix 區分 provider visibility 與 Atomix-mediated visibility。reversible-eager 操作一呼叫就可能被 provider 與外部觀察者看見；abort 只能補償。frontier 加 abort-on-stale 能保護後續經 Atomix 讀取的交易，但不能消除外部的中途觀察。bufferable 與 irreversible-gated 才在 commit 擁有單一可見事件。

2.5 安全假設

安全性依賴三點：所有 effect-bearing calls 經 adapter；metadata 正確；frontier 按協定推進。在此前提下，bufferable 效果 all-or-nothing，可逆效果在 abort 補償，不可逆效果留在 gate。idempotency key 與 durable dedup 只提供單一 orchestrator process 內的 retry 去重；不主張分散式 crash-safe exactly-once。prototype 約為 2,000 行 Python、單程序。
