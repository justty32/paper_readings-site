論文／訪談原始來源

HELIX: Model–Harness Co-evolution for Recursive Self-Improvement

摘要與第 1 節：問題

擴大 agent 能力多半只從「把模型做強」下手，但互動式 agent 是模型透過 runtime harness（系統指令、context 建構、session 狀態、tool schema、權限檢查、provider 適配、turn loop、重試／壓縮策略、停止規則、verifier）執行的。harness 不是中性外殼：它同時決定模型今天能做到什麼，也決定模型明天要從哪些軌跡學習。模型與 harness 在兩個時間尺度互動：任務內是快迴圈，跨輪次是慢迴圈（已驗證軌跡形塑下一個模型，改變後的模型又決定下一輪該重建怎樣的 harness）。作者因此主張把「模型－harness 配對」而非模型單獨視為遞迴自我改進的狀態，組織成 build（為固定模型建構並評測可溯源的 harness 候選）、update（把驗證過的 sibling 軌跡轉成學習紀錄更新模型）、rebuild（為更新後的模型重新演化 harness）三段。

HELIX 是支撐這個交接的系統性基底：把 OpenCode、Pi Mono、Nanobot、Hermes Agent 四套開源 harness 拆解成型別化的 port、atom、recipe、product shell、runtime policy，執行前做一致性檢查，並用 evidence plane 保留 trace、測試結果、policy 決策與 provenance。每個 product contract 暴露 96 個 port，可枚舉 1,024 種耦合 recipe。

第 2 節：模型—harness 共演化的形式化

設第 t 輪系統狀態 Z_t=(M_θt, Φ_t)，Φ_t 是為當前模型建的 harness portfolio。任務內快迴圈：harness 構造觀察／行動介面 → 模型回應 → harness 執行並回饋，得到軌跡；verifier 依任務、軌跡、workspace diff、測試與 policy 證據輸出標籤，不必是二元，可以是 resolved／target-miss／regression／no-action／policy-violation／patch-noise／evaluator-gap 等多類。

一輪演化有兩個輸出：固定 harness 的部署效用（reward 減去 runtime cost 與 policy risk 加權懲罰），以及候選集合暴露的 sibling 資料集合。作者刻意不把兩者壓成單一調過的純量，而是分開量測代理指標。

驗證後的證據映成訓練紀錄用以更新模型（SFT、偏好最佳化、critic 訓練、RL 或 router 學習皆可），同一批證據也回饋下一輪 harness 建構。harness 效用條件於模型，新模型的最佳 harness 未必等於舊模型的，把舊 harness 永久固定給新模型或只用單一 harness 軌跡訓練都會留下改進空間，因此每次模型更新後都要重建。固定 harness 表現與 portfolio 的 oracle union 覆蓋率要分開報：後者只有存在能提前選對候選的 router 時才可部署，否則只代表資料上限。

第 3–4 節：HELIX 系統與設計效益

Harness 表示為八元組（shell、session/hooks、config、prompt、tools、turn loop、acceptance、policy）。Port 是穩定能力槽，atom 分 product-neutral 的 common atom 與保留特定來源語意的 personality atom，recipe 綁定 atom／策略／policy／shell 成宣告式候選，product shell 把候選暴露成 SDK/CLI/TUI/web 介面。編譯器展開組合、解析依賴、產生確定性 lockfile；conformance／boundary／source-purity 檢查在評測前擋掉無效或語意含糊的組合。Runtime 是七步迴圈：建立/恢復 session、構建 context、串流 provider 收集 tool call、preflight 與權限檢查後執行工具、評估 acceptance、視情況 continuation 或停止、持久化 transcript 供評測層讀取 workspace diff。

設計效益三點：(1) bounded modification——以 recipe 為演化單位複用編譯器與執行/證據路徑，讓 build/rebuild 是可重複的元件級操作而非重寫整個 runtime；(2) persistent identity——recipe 與 lockfile 全程跟隨 model–task–attempt 身分與執行證據，避免隱性差異汙染比較；(3) evidence-linked siblings——sibling group 由建構本身產生，直接支援 clean SFT、critic、filter、preference 四類學習訊號，且整組留在同一 train/dev split 避免跨界洩漏。

第 5–6 節：實驗與結果

主評測用 100 題 LiveCodeBench 衍生修復任務（26 easy／24 medium／50 hard），trace-strict 判定要求觀察到實際執行測試且通過。65-candidate 矩陣＝Pi＋64 個以 Pi 為中心的 source-pure recipe，每候選對每題跑一次。另選定 Pi 與兩個 OpenCode 家族成員做 10 次重複跑，並在 SWE-bench Verified 55 例上做官方評測跟進。模型統一為 MiniMax-M2.7-highspeed（deterministic=false）。

RQ1：完整矩陣中 Pi 解 50/100，最佳候選 52/100（+4.0%），64 個非 baseline 候選僅 2 個勝過 Pi。重複跑中選定 OpenCode 成員覆蓋 75/100（Pi 72/100）。SWE-bench 官方評測下 LCB 矩陣最強兩候選各解 44/55（與 Pi 打平），選定 OpenCode 成員解 46/55——最佳固定候選因評測協定而異，無單一跨環境贏家。

RQ2：完整 65-candidate portfolio 覆蓋 79/100（比 Pi 多 29 題、+58.0%），23 個候選掛零，說明任意組合不可靠，需 typed gate 與 adaptive selection 才能兌現互補性。SWE 選定成員 union 覆蓋 49/55（最佳固定成員 46/55、Pi 44/55）。

RQ3：SWE 550 個評測 slot 中 543 個有非空 patch，官方判 411 resolved／132 gap／7 空 patch；411 個 resolved 中僅 205 個同時 production-only 且 path-clean——resolved 是乾淨正例的必要非充分條件。作者舉例：pytest-5787 案例中 Pi 的 patch 通過目標測試卻破壞既有測試被判 gap，sibling 全過才判 resolved；sphinx-10673（Pi 0/2 miss，sibling 7/8 resolved，更短 patch 反而更接近正確語意）與 xarray-6461（兩份都乾淨但 fallback 語意不同，一 resolved 一 gap）；LCB 案例一例支持「重試後修復」機制，另一例兩重組都退化，排除「harness 越活躍越好」的敘事。200-slot 精篩切片產出 438 筆紀錄：clean SFT 63、需清理 SFT 56、critic negative 52、filter sample 113、preference pair 154。

第 7 節：討論

build–update–rebuild 的遞迴不是模型呼叫內的遞迴，而是「更新後的模型—harness 狀態回到同一個改進流程」。作者強調「固定 harness 執行表現」與「portfolio 資料產出」是兩個不必一致的前沿：最佳部署 harness 不必是最佳探索策略，失敗候選仍可能提供高品質負例。23 個掛零候選不該一律丟棄也不該不篩選就當負例——無效/不相容者該用更強 gate 剔除，合法但表現差者可作訓練負例，但需保留 harness 身分與失敗類別以便正確路由或排除。

第 9–10 節：限制與結論

限制：評測範圍僅 100 題 AtCoder 衍生任務（非隨機抽樣的前 100 題）與 55 題 SWE-bench Verified，結論未必適用非程式碼 agent；每候選同時改動多個元件，無法歸因單一 atom；矩陣單次嘗試，選定成員驗證用 10 或 2 次，排名不可直接比較，深評選材有選擇效應；自動化測試無法涵蓋所有需求；本文只 materialize 訓練資料，未真的訓練更新模型驗證迴圈是否閉合；跨 harness 組合可能產生不安全權限，需隔離工作區與限權。

結論重申：遞迴自我改進要改進的是「模型—harness 這一整個被執行的系統」，狀態 Z_t=(M_t, Φ_t)，從 Z_t 到 Z_t+1 的回歸才是共演化的定義性結構；HELIX 讓此三方影響變得可用且可稽核，但完整多輪閉環實驗仍是未來工作。
