4. 效率

受約束解碼的樸素實作會為標準 LM 推論增加開銷：每步的遮罩計算，以及可選的一次性文法編譯。但多種最佳化可大幅降低開銷：遮罩計算可與 LM 前向傳播平行、文法編譯可與 prefill 計算並行；文法快取、基於約束的推測解碼（speculative decoding）也能進一步降低開銷。

指標拆為三項：

  • GCT（Grammar Compilation Time，文法編譯時間）：花在文法編譯上的時間（若適用）。
  • TTFT（Time to First Token，首 token 時間）：從開始生成到產出第一個 token 的時間。
  • TPOT（Time per Output Token，每輸出 token 時間）：第一個 token 之後平均每 token 的生成時間。

4.1 設定

效率取決於模型大小與 tokenizer 詞彙量。以 Llama-3.1-8B-Instruct 搭 Llamacpp 推論引擎作為 Outlines、Guidance、Llamacpp 的後端；因 XGrammar 不支援 Llamacpp 後端，另補一組以 Hugging Face Transformers 為推論引擎的 XGrammar（與 Guidance）實驗。硬體為單張 NVIDIA A100-80GB + AMD EPYC 7543（12 核），batch size = 1。

消除覆蓋率偏差（關鍵）：效率指標只對「引擎能處理的實例」有意義。不同引擎覆蓋率不同，低覆蓋率引擎往往只處理較簡單、較短的 schema，這些自然編譯與生成得更快。若在各自能覆蓋的實例上平均，會偏袒低覆蓋率引擎。為求公平，只在所有引擎都覆蓋的實例交集上計算效率指標。

結果（Table 2、Table 3，取樣中位數）

以 LlamaCpp 為推論引擎（Table 2，摘 GlaiveAI 一列）：LM only 的 TTFT 0.10 s、TPOT 15.40 ms；Guidance GCT 0.00、TTFT 0.24、TPOT 6.37 ms（最快）；Llamacpp GCT 0.05、TPOT 29.98；Outlines GCT 3.48 s、TTFT 3.65、TPOT 30.33（明顯偏慢）。

  • 文法編譯時間：Guidance 與 Llamacpp 在生成過程中動態計算約束，編譯時間極小；XGrammar 有非平凡的編譯步驟，但靠與 prompt prefill 並行大幅緩解其影響；Outlines 把 JSON schema 轉成正則約束，編譯時間顯著偏高（Table 2 中 GCT 隨難度升到 3–8 秒）。
  • 每 token 時間：Outlines 與 Llamacpp 的吞吐明顯低於 LM-only，而 Guidance 反而比 LM-only 還高效（靠 guidance acceleration 跳過某些生成步）。以 HF Transformers 後端比較（Table 3），Guidance 的 TPOT（約 36–44 ms）顯著優於 XGrammar（約 65–67 ms）。
