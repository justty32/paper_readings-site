論文／訪談原始來源

Verify Smarter, Evolve Further: Efficient Harness Evolution through Behavior-Aware Verification

摘要與問題

Agent harness 決定模型如何接收指令、使用工具、保存記憶與執行任務。既有自我改進法多採「提出修改、再驗證」的套路，卻常讓每個候選修改跑同一批固定或隨機任務。若某項修改只影響特定行為，大量無關任務不但浪費 rollout，也會用彙總分數沖淡真正的改善或退步。

HarnessLens 把驗證問題改寫成行為歸因問題：候選修改想改變什麼行為，就挑能顯示該行為、相關任務型態、受影響元件與回歸風險的任務驗證。軌跡不只負責打分，也成為下一輪診斷與選題的證據。

問題形式化與方法

論文固定基礎模型與 harness framework，只允許修改使用者可設定的元件，例如指令、技能、prompt template、工具、角色與 runtime extension。目標是在有限互動預算下，從訓練任務的軌跡找出較好的元件設定，再以完全隔離的測試集衡量泛化。

流程分成三段。Context Exploration 先看任務描述、環境規則與工具介面，按主要目標整理任務群；同時盤點每個可編輯元件的作用範圍、更新方式與可能影響的行為。這一步不執行任務，也看不到測試集。

Trajectory Diagnosis 從成功與失敗軌跡提取可重用經驗與反覆缺陷，保留其證據來源，再把行為問題連到可修改元件。缺乏足夠支持軌跡的提案會被淘汰，避免只憑單一分數猜原因。

Harness Evolution 每輪從已確認的 harness 複製出候選，做輕量 runtime 檢查後，為這項修改建立行為相關的驗證批次。現行版本規定每批至少含五個不同任務（作者自報），並在現行與候選 harness 間採匹配條件執行。若軌跡顯示目標行為改善且沒有回歸，候選還要接受另一批新任務確認；只有行為證據與主要指標共同支持，才會取代現行版本。若沒有足夠提案或預算不足，演化即停止。

實驗與主要結果

作者在 OpenCode、Codex CLI、Pi Coding Agent 三種 harness，以及 Retail、Banking、Terminal-Bench 2.0、BIRD Mini-Dev Challenging 四項 benchmark 上評估（作者自報）。每個 benchmark 隨機抽三十個訓練任務；測試資料在演化期間完全不可見（作者自報）。HarnessLens 的總預算上限為二百個單位，且同時計入 task rollout 與 LLM session；三個比較法的上限分別是四千八百、六百六十與三百個訓練 rollout（作者自報）。

在十二組 harness 與 benchmark 配對中，HarnessLens 有八組取得最佳或並列最佳結果，且從未低於初始 harness（作者自報）。三種 harness 的平均 held-out 改善介於百分之七點六至十三點六（作者自報）。作者把穩定性歸因於兩個互補機制：行為導向選題減少無關變異，可歸因證據 gate 則拒絕只有總分上升、卻看不出是哪個行為真正改善的修改。

消融也支持這項解釋。固定批次、隨機批次與 RHO 選題常找不到能通過驗證的候選；只看指標的 gate 較容易接受修改，卻未在部分 held-out 任務留下清楚改善。任務結構同樣關鍵：BIRD 裡相近的極值查詢能反覆支持同一項 SQL 修正，而 Terminal-Bench 的目標與執行路徑較分散，較難形成可泛化的共同證據。

結論與局限

HarnessLens 的核心不是提出更多修改，而是讓每次驗證對準修改聲稱影響的行為，並要求軌跡能把成效歸因於該修改。在有限互動預算下，這種設計能保留既有能力，同時把 rollout 轉成後續演化可重用的證據。

作者明列兩項限制：實驗只涵蓋一個模型家族、三種 harness 與四個公開 benchmark，其效果尚未在更多模型、架構與開放部署環境中驗證（作者自報）；預算雖計入 LLM session 與 task trial，卻沒有跨角色與 benchmark 正規化 token、延遲或金錢成本。
