2. OPTO：以 Trace Oracle 進行優化

預備：計算圖 g 是一個 DAG，節點代表物件（張量、字串等），邊表示輸入—輸出關係。無父節點者為根（輸入）、無子節點者為葉（輸出）；部分輸入被標記為可訓練參數。工作流的執行軌跡＝從輸入計算輸出時被呼叫的操作序列及其執行結果，可表為上述計算圖。

2.1 OPTO 問題定義

一個 OPTO 問題實例由三元組 (Θ, ω, T) 定義：Θ 是參數空間，ω 是問題的脈絡（context），T 是 Trace Oracle。每輪迭代中，優化器選定參數 θ ∈ Θ（可為異質），Trace Oracle 回傳 trace feedback τ = (f, g)：g 是以 DAG 表示的執行軌跡（參數在 g 的根節點中），f 是對 g 的某一個輸出節點給的回饋。優化器依脈絡 ω 用 τ 更新參數，進入下一輪。

輸出回饋 f 是泛用的：分數、梯度、自然語言的提示/解釋、console 訊息皆可。脈絡 ω 提供解讀 f 的不變資訊與已知的附帶資訊（如參數應滿足的性質），對一個 OPTO 實例固定不變（類似指令或問題定義）；f 則隨 θ 與計算 g 而變。例如 ω 可以是「最小化損失函數」而 f 是損失值；ω 也可開放式如「遵循回饋」而 f 描述輸出該如何改。本文聚焦 f 與 ω 可精簡文字化的 OPTO 問題。OPTO 與黑箱設定的差異在於執行軌跡 g 展示了通往輸出的計算路徑，提供從 f 與 ω 建構參數更新方向的資訊：只有 f 的點值評估時不清楚參數如何改進；有 g 記錄產生輸出的函數時就能推導更新方向（如梯度）。注意 g 的結構在每輪迭代可以不同（工作流會隨輸入與參數改變）。

OPTO 涵蓋的既有問題示例：(1) 神經網路＋反向傳播——參數＝權重、g＝神經計算圖、f＝損失、ω＝「最小化損失」，反向傳播＋梯度下降可嵌入為一個 OPTO 優化器；(2) RL——參數＝policy、g＝軌跡（狀態/動作/獎勵的圖模型）、f＝成功旗標、ω＝「最大化回報」；(3) LLM 代理的 prompt 優化——參數＝prompt、g＝代理的計算圖、f＝對行為的回饋（分數或自然語言）。附錄 C 另有程式碼除錯（g＝stack trace、f＝編譯器錯誤訊息、ω＝「不出錯」）、ML pipeline 超參數調校、多代理協作等例。

3. Trace：下一個 AutoDiff

Trace 把 OPTO 從抽象概念變為現實，是實作 Trace Oracle 的輕量 Python 工具。透過 OPTO 框架，Trace 把優化器設計與領域特定組件分離，使通用優化器得以跨多樣領域工作。

3.1 Trace 的設計

兩個原語（primitives）：

  • node：Python 物件的包裝器。被包裝的物件註冊為計算圖中的唯一節點；node 可設為 trainable（成為 OPTO 參數），宣告參數時還可用自然語言描述參數應遵守的約束。
  • bundle：把 Python 方法轉為操作子（operator）的裝飾器。被裝飾函數的 docstring 與原始碼被記錄為操作子的定義，用以推斷輸出回饋應如何改變參數。bundle 裝飾的函數也可設 trainable——此時該方法的程式碼本身成為參數。

使用流程：使用者以 node/bundle 宣告參數、定義工作流的概念區塊；建立 OPTO 優化器（可選提供 ω，OptoPrime 預設為「遵循回饋」）；定義對計算結果提供回饋的機制（類比於神經網路訓練中定義損失函數）。之後重複：(1) 執行被裝飾的工作流，後端建 DAG；(2) 呼叫 backward 啟動輸出回饋向參數的傳播（執行錯誤也被當作回饋），Trace 抽取連接參數與輸出的最小子圖 g，把 τ=(f,g) 交給優化器；(3) 呼叫優化器 step 更新參數。

3.2 用 Trace 原語做有效的執行追蹤

把工作流表示為計算圖有多種抽象層級——從整個過程抽象為單一大操作子，到列出所有底層步驟。在 Trace 中抽象層級由 bundle 的施加方式決定（bundle 之下的所有步驟被抽象為一個操作子）。不同選擇是圖複雜度與操作子描述負擔的取捨：全部抽成一個操作子則圖平凡但需大量描述；暴露所有底層操作子則圖過度雜亂。我們認為此問題類似神經網路架構設計，建議定義操作子時模仿工作流的白板系統圖（whiteboard system diagram）層級。另一設計問題是資訊該放脈絡 ω 還是操作子描述：建議在 bundle 定義時提供操作子描述，讓 Trace 自動產生工作流特定資訊，而同一個 ω 可跨許多工作流共用。

3.3 反向回饋傳播：實現 OPTO 的 Trace Oracle

Trace 用遞迴圖遍歷演算法（演算法 1）以反拓撲序傳播回饋；搭配不同的 propagator 可實作各種前向—反向方案，包括反向傳播本身（訊息＝梯度、propagate 回傳 Jacobian 轉置乘梯度和）。我們提出通用的 Minimal Subgraph Propagator（MSP，演算法 2）：傳播 trace feedback τ=(f,g)，g 以優先佇列實作。兩演算法合併即實現 OPTO 的 Trace Oracle——抽取參數節點與輸出之間的最小子圖。

定理 1：對 N 節點、最大度 W 的圖，演算法時間複雜度 O(WN²logN)、空間複雜度 O(WN)（反向傳播為 O(WNd²) 與 O(d)，d 為張量最大維度）。差異源於：在最一般的計算圖與回饋設定下，被傳播的回饋沒有常數大小、需要完整子圖。定理 2：對一般 N 節點計算圖，最壞情況下被傳播的回饋需 Ω(N) 描述長度才能建構改進方向。實務上 MSP 只涉及合併引用的優先佇列，多數計算發生在前向傳播與優化器 step，差異可忽略（除非最小子圖達百萬節點）。

4. 第一個 OPTO 優化器的設計：OptoPrime

子圖表示：核心挑戰是如何向 LLM 表示執行軌跡子圖 g（含各種圖結構與異質資料）使其能推理參數更新的下游效應。我們利用 LLM 卓越的程式撰寫與除錯能力，把 trace feedback (f,g) 呈現為擬演算法問題：子圖 g 表示為一份程式碼執行報告，含 #Code（圖結構偽程式碼）、#Definitions/#Documentation（操作子描述）、#Variables（可改參數）、#Constraints、#Inputs、#Others（中間值）、#Outputs、#Feedback 等欄位，然後 prompt LLM 依據對輸出的回饋 f 更新 g 中的參數。注意這些程式行不是真實程式，而是 bundle 定義的計算圖。

參數更新：以 ReAct-CoT 風格 prompt 單次查詢 LLM，要求基於圖生成推理（reasoning）與參數修改建議（suggestion，JSON 格式）；若能從回應抽取建議即更新參數。

優化記憶：僅靠當輪的圖與回饋在某些場合資訊不足（如回饋是獎勵但無獎勵生成方式的描述）。為穩健性，OptoPrime 內建基本記憶模組，追蹤過往的參數—回饋對作為 in-context 範例。
