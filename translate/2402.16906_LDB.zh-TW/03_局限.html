局限

LDB 承襲人類除錯法的固有限制：正確測資是必要條件（LDB 需執行程式並把執行流對照任務描述）。「LLM 是否能只看中間執行、卻不知結果對錯就自我修正（即 test-case-free debugging）」仍是未解的開放問題。

附錄（擇要）

  • A 更好的推理器：除錯 backbone 越強，LDB 越好——以 Reflexion 為 seed、GPT-4o（2024-05-13）為 backbone，HumanEval 達 98.2%（GPT-3.5→95.1、GPT-4→96.9、GPT-4o→98.2）。
  • B 程式語言概念：定義 basic block（單一入口單一出口、進入首指令後後續指令必依序各執行一次）、CFG、執行軌跡（整支程式的控制流軌跡，即 CFG 上從入口到出口的路徑）。
  • C/D 實作與開銷：T=0 貪婪解碼、最多 10 輪。LDB 總時間 17.23s，與 Self-Debug（17.08s）相當；額外的 Profiling 步驟純由程式分析完成、HumanEval 平均僅 0.09 秒，可忽略，全流程無人力。
  • F 批次除錯複雜度：無批次時除錯 B 個區塊約需 O(B²·N) token，批次除錯每輪只送一則訊息、為 O(B·N)。
  • H 錯誤分析：用 GPT-4 自動核驗 LDB 是否正確定位出錯 block——定位準確率各資料集 >85%（HumanEval 93.7%、MBPP 95.3%、TransCoder 86.7%，後者因 C++ 隱含意圖較難）。所修 bug 約 80% 為語意錯誤、其餘為語法錯誤（語法錯較少見，因現有 LLM 生成能力已不錯；LDB 靠詳細 runtime 資訊更擅長修語意錯）。
  • I 可延伸性：本文用 Python（因其流行、亦與 Self-Debug/Reflexion/Gorilla 一致）。LDB 不依賴 Python 專屬特性，只需替換程式執行器與分析工具即可移植到其他語言（runtime 資訊在各語言皆可用現成程式分析工具取得）；多語系（如 HumanEval-X）留待未來。
  • J Prompt 範例：列出 chat 模式（圖 8，即 is_sorted 案例，要求 LLM 對每個 BLOCK 輸出含 block/correct/explanation 的 JSON）與 completion 模式（圖 9，以 [debug]…[/debug] 標記逐塊回饋、[python]…[/python] 給修好的碼）的完整 prompt。
