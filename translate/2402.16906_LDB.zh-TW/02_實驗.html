3. 實驗

在三個基準評測：HumanEval、TransCoder、MBPP。HumanEval 與 MBPP 為文字轉程式碼（任務描述是概述功能的短文）；TransCoder 為程式碼翻譯（要求把 C++ 翻成 Python，任務描述即待翻譯的 C++ 程式）。以隱藏測資的 Pass@1 準確率評估。Backbone 用專有模型 GPT-3.5（turbo-0613）與開源模型 CodeLlama（34B-Instruct）、StarCoder（~15B）。

3.1 實驗設定

seed 程式沿用對照方法（Chen et al. 2023c）的相同 prompt 與生成參數；最大除錯迭代數設為 10。可見測資取得：HumanEval 從任務描述抽出既有可見測資；MBPP 取每題第一筆測資為可見、其餘為隱藏；TransCoder 把資料集所有測資都當可見（可由執行原始 C++ 程式產生，對 LLM 可見）。除錯階段用貪婪解碼、溫度 T=0 以利重現（附錄 C）；抽樣區塊數與輸入 token 門檻分別設 10 與 3,097。

3.2 對照方法

以 seed 程式表現作為 Baseline（無除錯器）。對照兩種來自 Chen et al.（2023c）的「橡皮鴨除錯（rubber duck debugging）」法：Self-Debug (+Expl.)（讓 LLM 逐行解釋程式當回饋）與 Self-Debug (+Trace)（讓 LLM 乾跑 dry run 程式當回饋）。因原始碼未開源，依其說明重現。提及「Self-Debug」時預設取兩者中較高準確率者。所有除錯法皆用相同 LLM 設定、可見測資、seed 程式與 prompt 格式以求公平。

3.3 主要結果

表 1（擇要）——三基準、三 backbone 下 LDB vs Self-Debug（SD），Pass@1 準確率與相對基線增益 Δ：

Backbone 方法 HumanEval TransCoder MBPP
GPT-3.5 Baseline 73.8 82.3 67.6
GPT-3.5 SD (+Expl.) 81.1 (+7.3) 85.9 (+3.6) 74.4 (+6.8)
GPT-3.5 LDB 82.9 (+9.1) 87.7 (+5.4) 76.0 (+8.4)
CodeLlama-34B Baseline 49.4 69.8 51.2
CodeLlama-34B LDB 55.5 (+6.1) 79.6 (+9.8) 57.4 (+6.2)
StarCoder-15B Baseline 39.0 61.8 51.6
StarCoder-15B SD (+Expl.) 38.4 (−0.6) 68.9 (+7.1) 54.4 (+2.8)
StarCoder-15B LDB 39.6 (+0.6) 69.8 (+8.0) 55.4 (+3.8)

LDB 在所有資料集、所有 backbone 上一致提升最高 9.8%，且較「讓 LLM 乾跑/解釋」的 Self-Debug 更高更穩。作者歸因於細粒度的除錯回饋與作為外部補充的 runtime 資訊：block 級回應讓 LLM 聚焦出錯區、更好對齊任務描述。更關鍵地，如 Huang et al.（2023c）指出，LLM 自我修正推理能力有限——尤其在程式碼上易錯，因為它無法準確計算具體變數值、無法正確預測分支/迴圈的執行流；LLM 給出的不準回饋會誤導修復（這解釋了 Self-Debug 在 StarCoder + HumanEval 上為何失效）。LDB 則基於準確的中間值與執行流產生判決，把程式導向正解。此外，可見測資雖也在 seed 生成時提供給 LLM，但其效用有限（見 Baseline 的次佳表現）——印證「真實 runtime 執行資訊能顯著幫 LLM 錨定推理」。

3.4 對進階生成器的結果

把 LDB 與 Self-Debug 套用到更強生成器 GPT-4（1106-preview）與 Reflexion 產生的 seed 程式（以 HumanEval 為例）。除錯 backbone 皆用較弱的 GPT-3.5。

表 2（擇要）——以 GPT-3.5 為除錯 backbone：

除錯器 \ 生成器 GPT-3.5 GPT-4 Reflexion
無除錯器 73.8 87.2 91.5
SD (GPT-3.5) 81.1 (+7.3) 88.4 (+1.2) 92.1 (+0.6)
LDB (GPT-3.5) 82.9 (+9.1) 89.6 (+2.4) 95.1 (+3.6)

即使除錯 backbone 弱於生成器，LDB 仍能精修程式、揪出強生成器忽略的細微 bug，把 Reflexion 推到 95.1% 的新 SOTA。這顯示 LDB 能檢視 runtime 執行、修正被先進生成器漏掉的錯誤，是現有生成技術的正交補充（orthogonal supplement）。

3.5 表現 vs 除錯迭代數

圖 3（要旨）：在 HumanEval + GPT-3.5 上，比較 LDB、Repeated Sampling（反覆取樣直到通過可見測資）、Self-Debug(+Expl.)、Self-Debug(+Trace) 每輪表現（跑到 10 輪）。

  • LDB 的持續除錯潛力：隨迭代增加，LDB 持續改善並在 10 輪後達最佳（雖上升速度略慢）；而 Self-Debug 約 2 輪後幾乎停止改善（與 Chen et al. 2023c 觀察一致）。附錄 G 顯示 LDB 跑到 20 輪仍成長、達 84.1%。
  • runtime 資訊的必要性：Self-Debug 在 3 輪後趨勢與 Repeated Sampling 相似，兩者都在早期（約 2~3 輪）停止有效改善。這揭示 LDB 與 Self-Debug 的根本差異：Self-Debug 的自解釋/自乾跑回饋只增進對任務的初步理解、卻無法把任務對齊到具體程式碼，故很快收斂。LDB 則靠來自 runtime 執行的新資訊持續把模型推向正解，貼近人類除錯過程。

3.6 LDB 的不同分解粒度

在 Profiling 中，LDB 依 CFG 把軌跡切成 basic block（單一入口單一出口，是 runtime 分析的理想基本單元）。為探討分解粒度的效果，另做 LDB (line-level) 與 LDB (function-level)（分別以行、函式為單元），與原始 LDB (block-level) 對照，三者架構相同、皆在各單元結束處收集中間狀態，並用 Selective Debugging 適配 token 上限。

圖 4／表 5、6（要旨）：block-level 以最少 token 成本達最高準確率。line-level 雖更細，但每行語意不完整，LLM 難以完整理解程式單元、定位 bug 較差；function-level 最粗、大致保留完整程式，但缺乏細部 runtime 資訊，需約 8.1 輪才修好一支程式（遠多於其他粒度），token 成本反而最高。HumanEval + GPT-3.5 下三者準確率：line 80.5、block 82.9、function 79.9。故 LDB 選 block-level。

3.7 不同難度的表現

深入 LDB 在 TransCoder 成功修好的題目，用 GPT-4（1106-preview）依標準解自動標成 Easy/Medium/Hard 三難度（避免主觀）。圖 5（要旨）：GPT-3.5 生成表現隨難度上升而下降，但除錯器的增益隨難度上升而增大——LDB 在 Hard 題增益最大（+9.1%），顯示它能偵測非平凡的 bug、理解複雜執行流。

3.8 案例研究

圖 6（要旨）：HumanEval + GPT-3.5 的例子（is_sorted 函式）。題目要求檢查兩條件：(1) 數字升冪排序；(2) 同一數字重複不超過 1 個。seed 程式正確檢查條件 (1)，卻把條件 (2) 誤寫成「不能有任何重複」（lst.count(x) > 1）。LDB 對 BLOCK-0 到 BLOCK-4 判定正確檢查了條件 (1)；在 BLOCK-5 找出條件寫錯、精準定位 bug，提議改為 lst.count(x) > 2（保留數字本身那次出現）以對齊任務描述，修復後通過可見與隱藏測資。

4. 相關工作

  • Augmented Code Language Models：既有工作以多候選、更好的測資、自我一致性增強初次生成，或訓練驗證器預測解的品質。LDB 則不靠擴大取樣數來增強生成、與這些方法互補（它們可提供更好的 seed 給 LDB）。
  • Feedback-based Code Refinement：人類回饋有效但費工；語言模型的程式精修法利用直譯器輸出、自生解釋、他人提交等；有些額外訓練 bug 修復模型，LDB 則直接利用原 LLM 的除錯能力。LDB 屬迭代精修範式（Self-Refine 等），並受執行導向程式合成啟發利用執行結果。用 RL 的 agent 框架擅長搜尋生成空間，LDB 則專注於精修、在各種初始程式上一致改善。
  • Decomposition in Reasoning：分解問題有助 LLM 推理（CoT、least-to-most、let's verify step by step 等）。Zhang et al.（2022a）提出 program trunking 提升修復率；受此啟發，LDB 把程式切塊查詢判決與解釋，並引入 batch debugging 提升效率。

5. 結論

提出 LDB——用 runtime 執行資訊幫 LLM 精修生成程式的除錯框架。透過把程式切成 basic block、追蹤中間值，實證顯示它顯著提升生成準確率、達程式除錯的 SOTA，並揭示一種「以 runtime 資訊除錯」的獨特範式。
