§6 討論

§6.1 為何有效？

機制在闡明後很直接：自由文本 LLM-judgment 基線在過濾、先驗抑制與答案生成糾纏於一步中時，不可靠地應用顯式新鮮度規則。當 prompt 寫入「事實以序號索引；較新序號覆蓋較舊」並展示反事實（較高序號）與真實事實（較低序號），LLM 傾向以先驗覆蓋規則——此失敗隨候選池增大而加劇（262K 暴跌至 61%）。

Python max() 無此病理：精確、快速、上下文無關。LLM 角色窄化為候選提取，其擅長。提取刻意嚴格：匹配主語與謂語逐字、包含所有匹配項。無匹配→"no answer"（約 2% 題目；SubEM 下計為錯，生產設定為校準棄權）。

非嚴格支配，而是精確率-召回率權衡。確定性管線以少量召回（~10% 題目被嚴格提取過度拒絕）換取較大精確率增益（無 prior-override、無序號漂移）。淨效果 +10.8pp，但兩管線部分互補（21% Python-only、10.5% LLM-only）。混合管線（空候選時 fallback LLM-judgment）可望關閉殘餘 10.5% 差距。

§6.2 對記憶框架設計的含義

Agent 記憶子領域在精緻儲存架構上投入大量工程。在此基準上，架構精緻化本身未能解決衝突解決：

  • 知識圖譜（GraphRAG/Cognee/Graphiti）：需 LLM 驅動的實體/關係提取（引入雜訊與額外 LLM 判斷步驟），FC-SH 7–28%
  • 海馬迴檢索（HippoRAG-v2）：最強已發表 RAG 54%。架構複雜性（多階段檢索、迭代精煉）未解決查詢時 LLM 判斷瓶頸
  • Agentic 迴圈（MemGPT/MIRIX/Self-RAG）：迭代幫助檢索覆蓋但增加更多 LLM 步驟而未使其新鮮度感知，14–28%
  • 時間知識圖譜（Zep/Graphiti）：明確設計處理取代，卻 FC-SH 僅 7%。可能解釋：Zep 在攝入時使用 LLM 判斷新事實是否與既有矛盾（resolve_edge prompt），繼承相同的 LLM 判斷問題

衝突解決的正確原語是對 LLM 識別為語意相關的候選進行確定性聚合。此觀點與 Memanto 的「簡單勝複雜」論點一致。

§6.3 CAR為何在 FC-MH 有效？

多跳衝突解決結合兩挑戰：分解問題為原子 hop＋每 hop 解決衝突。CAR 分別處理。既有系統要麼跳過分解（BM25、嵌入 RAG、所有記憶框架）、要麼跳過逐跳衝突解決（Self-Ask/IRCoT/MultiHop-RAG）。CAR 兩者兼具。30.2% avg vs 7% 最佳已發表證明多跳衝突解決在兩元件皆處理時變得可行。多數 CAR 失敗在 hop-1：LLM 偶爾提取錯誤候選（真實與反事實同時在檢索中），錯誤級聯至後續 hops。

§6.4 限制

  • 主要一個基準：MAB FactConsolidation（MQUAKE 衍生反事實），加上 LongMemEval 跨基準檢查（n=45，CIs 寬）
  • 版本標記假設：確定性 max(serial) 要求全序；無法處理偏序或因果依賴
  • 非嚴格支配：10.5% LLM-only 正確（嚴格提取過度拒絕）
  • 匹配比較變動超過 resolver 本身：+10.8pp 是管線級效果
  • 失敗模式分析為定性：抽查約 30 題而非系統性 100 題標註
  • 三骨幹探索：結果可能在其他模型家族不同
  • 多跳仍難：30.2% 雖為 4–5× 改善，遠未解決

§6.5 給記憶框架設計者的建議

  1. 索引時保留事實級 metadata：確保版本標記（時間戳/序號/版本字串）在衝突可能發生的粒度可用
  2. 將新鮮度/新近度比較移出 LLM prompt、移入確定性程式碼：顯式 metadata 存在時，確定性聚合精確、便宜、可審計、易測試
  3. 勿假設圖或知識圖譜基礎設施單獨解決衝突解決：Zep/Graphiti FC-SH 7% 為實證證據
  4. 早期在 FactConsolidation 測試：乾淨的衝突解決壓力測試，生產系統應通過
  5. 誠實說明系統處理哪些子任務：FC-SH 18% 的記憶框架不應宣稱處理「演變知識」

§6.6 開放問題與未來工作

已完成（此版本）：

  1. chunk-4096+LLM-judgment 匹配（確定性 80.8% vs LLM 61.0%，+19.8pp）
  2. 骨幹 sweep（gpt-4o+CAR 51.5%、o4-mini+CAR 43.2%）
  3. 跨基準泛化+時間戳（LongMemEval）

待完成： 4. 乾淨隔離 resolver（共享候選提取，相同候選列表餵 Python-max 與 LLM-picker） 5. 可組合的題型感知管線（Yes/No 包裝、k-th-newest 選擇器、聚合處理器） 6. 真實世界衝突模式（使用者偏好更新、政策取代、協作知識庫更正）

§7 結論

我們提出一個記憶衝突解決的確定性配方，在 MemoryAgentBench FactConsolidation 上達成新 SOTA：單跳 78–94.8%（vs HippoRAG-v2 54% 與 GPT-4o long-context 60%@262K）、多跳 30.2%（vs 已發表最佳 7%）。匹配設定比較（相同骨幹/檢索/切片/TOP_K/n=100）顯示，將 LLM-judgment 答案管線替換為候選提取 + Python max(serial) 管線獲得 +10.8pp，262K 差距擴大至 +21pp。確定性 max() 是更簡單、精確、可審計的 resolver。

含義對記憶框架子領域具修正性：衝突解決的瓶頸在組裝（檢索後如何提取與聚合候選），不在儲存（graph/hippocampal/agentic/typed）。精緻的記憶架構在此任務上無幫助；一個簡短的 Python 函數在 LLM 提取的候選上匹配或超越它們。LongMemEval 跨基準檢查界定主張：新鮮度機制移植到真實時間戳但整體平手；確定性聚合是當前值衝突解決的正確原語，須與題型感知處理組合以涵蓋更廣泛的記憶 QA。

這指向下一代記憶系統的更廣泛設計模式：將 LLM 的工作窄化為其可靠擅長的任務（語意識別、候選提取），將對結構化 metadata（序號、時間戳、版本標記）的比較委派給確定性程式碼。所有程式碼、prompts 與 Langfuse 追蹤公開釋出以確保可重現性；headline 實驗 15 分鐘內以約 $3 API 花費完成。
