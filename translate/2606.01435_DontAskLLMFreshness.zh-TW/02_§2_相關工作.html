§2 相關工作

§2.1 MemoryAgentBench 上的記憶框架

MemoryAgentBench（Hu, Wang, & McAuley, 2026）是迄今最全面的 LLM 記憶系統評測，涵蓋四能力（準確檢索、測試時學習、長程理解、選擇性遺忘）橫跨 22 系統×5 骨幹。FactConsolidation 是選擇性遺忘下的衝突解決任務：引入 MQUAKE（Zhong et al., 2023）反事實編輯，測試 agent 能否正確優先處理後來新增的資訊。基準暴露驚人弱點：最強已發表 RAG（HippoRAG-v2, Gutiérrez et al., 2025）僅 54.0% 單跳。產業標準記憶框架低於確定性新鮮度基線 50–87pp：Mem0 18.0%、Graphiti/Zep 7.0%、MemGPT/Letta 28.0%。階層 RAG（RAPTOR、GraphRAG、MemoRAG）集群於 14–21%。多跳 FC-MH 全數 0–7%。

§2.2 透過分解的多跳 QA

CAR 管線建立在問題分解的成熟脈絡上：Self-Ask（Press et al., 2022）、Decomposed Prompting（Khot et al., 2022）、IRCoT（Trivedi et al., 2023）、Iter-RetGen（Shao et al., 2023）、MultiHop-RAG（Tang & Yang, 2024）。Madhwal et al. (2026) "Decomposed Prompting Does Not Fix Knowledge Gaps" 方法論相鄰：研究多跳 QA 分解並提出跨域不一致棄權。我們貢獻非分解本身，而是應用於鏈中每一步的逐跳確定性新鮮度解決。

§2.3 檢索中的時間/新鮮度處理

  • temporal-rag（Emmimal, 2025）：檢索後時間層（有效性過濾、指數衰減、取代鏈）。README：「解決兩個當前文件間的分歧是 LLM 的問題，不是檢索器的」——正是我們挑戰的設計選擇
  • Grofsky (2025)「Solving Freshness in RAG」：簡單新近度先驗在網路安全單跳新鮮度任務達 1.00 準確率。我們差異：(i) 標準基準跨系統證據、(ii) 結構化候選提取配方、(iii) 多跳逐跳解決、(iv) 跨基準範圍界定
  • Memanto（Abtahi et al., 2026）：typed 語意記憶＋資訊論檢索，論證「知識圖譜複雜性對高傳真 agent 記憶非必要」
  • DYNAMICQA+MULAN、MAGIC：確認 LLM 難以應用顯式上下文內新鮮度規則

§2.4 知識編輯與 LLM 先驗

「Uncovering Overfitting in LLM Editing」（Zhang et al., 2024）、「Unveiling Divergent Inductive Biases」（Kishore & He, 2024）、「Adaptive Token Biaser」（Bi et al., 2024）均證明知識編輯傳播超出預期範圍，LLM 時間先驗難以僅靠 prompting 覆蓋。

§2.5 本研究定位

貢獻位於多跳 QA 分解 × 時間衝突解決 × MAB 評測的交集。新增：(1) 匹配設定管線比較量化組裝瓶頸、(2) 特定實證結果擊敗所有已發表系統、(3) 立場陳述：瓶頸在組裝非儲存。

§3 方法

兩條管線：SH-conflict（單跳衝突解決）與 CAR（Chain-Aware Resolution，多跳）。共享三原語：事實級（或 chunk 級）檢索、LLM 候選提取、確定性新鮮度揀選。

§3.1 SH-conflict 管線

給定編號事實語料庫 C = {(s_i, t_i)}（s_i 版本序號，t_i 事實文本）與查詢 q：

  1. 檢索：R = BM25(C, q, k=10)，回傳 BM25 排序的 top-k 事實
  2. 候選提取：prompt LLM 以 q 與檢索的 R 產生 C = {(s_j, t_j, e_j)}，e_j 為從語意匹配事實提取的答案實體。LLM 被明確指示包含所有匹配項（不比較序號、不挑最佳）、逐字提取
  3. 新鮮度揀選：c* = argmax_{c in C} c.s，回傳 c*.e。若 C=∅，回傳 "no answer"

完整管線約 50 行 Python：

def sh_conflict(question, corpus, bm25, llm):
    retrieved = bm25.retrieve(question, top_k=10)
    candidates = llm_extract(question, retrieved)
    if not candidates: return "no answer"
    return max(candidates, key=lambda c: c.serial).entity

與先前方法的兩個對比：

  • vs chunk 級檢索（MAB BM25 基線、Mem0、Cognee、HippoRAG）：我們獨立索引每條事實，保留序號為索引鍵。多數既有系統以 chunk-512 或 4096 切片，將多序號擠入同一 chunk，迫使 LLM 做 chunk 內新鮮度推理
  • vs LLM 判斷新鮮度：我們將新鮮度比較移出 LLM、移入確定性 Python。LLM 僅提取候選，不揀選贏家

候選提取 prompt 刻意嚴格：LLM 必須逐字匹配主語與謂語，包含所有匹配項。這推動保守行為：無匹配時回傳 "no answer" 而非幻覺（約 2% FC-SH 題目；SubEM 下計為錯誤，生產設定中為校準棄權）。

§3.2 CAR 管線：多跳的 Chain-Aware Resolution

對「X of Y of Z」形式的多跳問題，以 Self-Ask 風格分解步驟擴展單跳管線：

  1. 分解：prompt LLM 以 q 產生原子 hop 鏈 h_1,...,h_n，使用 {hop_k_answer} 佔位符串接
  2. 逐跳執行：每 h_i，代入鏈中佔位符值後執行 SH-conflict
  3. 最終答案：最後一跳答案。中間任一跳回傳 "no answer" 則跳過後續 depend hop，回傳最後有效答案或 "no answer"

工作實例：「"American Pastoral" 作者的配偶的國籍」分解為：h1 作者→h2 配偶→h3 國籍。分解 prompt 使用 Graphiti 風格格式，通用佔位符範例避免領域洩漏。HARD_CONSTRAINT 禁止每 hop 超過一個關係詞（防止 gpt-4o-mini 將 4-hop 鏈壓縮為 2-hop）。

§3.3 為何確定性新鮮度有效

候選提取產生小候選集（通常 1–3，至多 TOP_K=10）。新鮮度比較是單一 Python max() over integers——精確、快速、無 LLM 風格失敗。兩個被消除的失敗模式：

  1. Prior-override：確定性原語在比較期間從未看到實體文本，僅見整數序號
  2. Serial-comparison drift：max() 精確，無關池大小

LLM 擅長語意候選提取；不擅長的是在一步中聯合過濾、解決新鮮度、抵抗先驗、並在雜訊上下文上自由文本回答。結構化提取將這些分離。
