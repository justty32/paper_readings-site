摘要

語言模型（language model, LM）在程式碼生成上表現卓越，但確保型別正確性（type correctness）仍是挑戰。傳統方法如受約束解碼（constrained decoding）藉由「從外部拒絕不可型別化（untypable）的程式碼」來緩解，但模型本身並未真正在內部學會型別推理，最終限制了整體表現。本文提出 TyFlow——一套把型別推理內化（internalize）進程式碼生成、以引導模型學會型別系統的新系統。其核心是一套新穎的型別導引程式合成系統，維持型別推導樹（type derivation tree）與合成推導樹（synthesis derivation tree）之間的同構（isomorphism），從而支援一種基於合成決策序列（synthesis decision sequence）、而非傳統文字 token 序列的新程式碼表示。藉由把「學習型別系統」的複雜度卸載到表示本身，模型得以把算力重新導向更高階的程式語意。評估顯示 TyFlow 不僅消除型別錯誤，更顯著提升功能正確性，凸顯「在內部把 LM 與型別系統對齊」的重要性。

關鍵詞：型別正確性、程式合成、程式碼生成、LLM

1. 引言

LM 通常把程式當作純文字，編碼為 token 序列，透過「給定當前部分程式、迭代預測下一個 token」來生成程式碼。然而 LM 常在型別系統上出錯，產出違反基本型別約束的程式碼。實證研究指出，型別錯誤單獨就佔了 LM 生成失敗程式的 33.6%；即便是最先進 LM 驅動的工具也會生出無法編譯的程式碼——例如 GitHub Copilot 在 LeetCode 上有 24% 的建議導致編譯錯誤，且主要源於型別錯誤。在資源稀缺或型別系統複雜的語言上，此問題尤為突出。

確保型別正確性的意義超出「減少型別錯誤」本身：其一，型別系統本質是一套靜態分析系統，理論上可把任何可判定約束併入型別系統，故豐富型別系統即可強制任何可判定的安全性質；其二，近期研究顯示，即使 LM 有足夠資料能學會像語法正確性這類簡單約束，若在訓練與推理時藉外部設施協助滿足約束，模型整體表現仍會進一步提升——可能是因為模型算力得以省下來處理更高階任務（演算法設計、程式與自然語言描述之間的語意對齊）。

挑戰的根源：純文字 token 序列表示與型別檢查的實際結構化過程之間存在巨大鴻溝。論文以 CodeT5 生成的一個病態範例說明（圖 1）：期望函數需回傳 list 中第一個奇數，正解 return l.get(i); 的型別化其實依賴 get 方法簽名與 Java 的 auto-unboxing 規則（允許 Integer 當作 int 回傳），但這些規則都被埋沒在文字 token 序列中。具體有兩重困難：

  • 訓練時：LM 只看到語法 token 序列，難以從中還原並學會整套型別系統。
  • 生成時：型別檢查需複雜分析以蒐集上下文（如檢查變數是否在 scope 內須辨識所有先前定義並判斷是否仍有效），這種非平凡的全域推理隨程式碼庫增大而愈發困難。

既有做法的不足：主流做法是拒絕不合法生成（一系列受約束解碼方法），靠外部型別檢查器剔除不可型別化程式。但這種外部補丁原則上補不了鴻溝：它只能排除病態程式，缺乏對型別系統的充分學習，還會擾動 well-typed 程式間的分布。範例中 CodeT5 對正解給了低機率（可能因它不懂 auto-unboxing、誤判其為病態），受約束解碼幫不上忙——它只是換成另一個「仍然錯誤但 well-typed、避開了 auto-unboxing」的程式（圖 1c）。另一種思路是把程式加上型別正確性證明（先生成程式、再生成其型別推導樹），但訓練時程式與證明分離、需額外對齊，生成時上下文推理難題依舊，評估顯示此法表現不佳。

本文方法：作者提出一套在內部把型別系統與 LM 調和的新合成系統。關鍵洞見是——LM 不必侷限於生成純文字程式；它可被納入任何「以決策序列建構程式」的搜尋式系統，每個決策在特定上下文中做出。於是問題化約為設計一個合成系統 𝒮，使其與 LM 有效協作並保證型別正確。𝒮 須滿足四項性質（也精煉了前述挑戰）：

  • 型別顯性（Type Explicitness）：𝒮 應在整個決策過程中追蹤型別推導。
  • 上下文局部性（Context Locality）：每一步應在一個小的上下文視窗內呈現必要型別資訊，免去 LM 從冗長上下文推斷。
  • 推導鄰近性（Derivation Vicinality）：決策的表示應使程式片段與其型別推導相鄰，便於訓練時對齊。
  • 資料可用性（Data Usability）：𝒮 的決策序列與原始碼可自動且雙向轉換，便於從既有程式抽取決策序列、也能從決策序列重建程式。

三項貢獻：（1）一套受型別導引程式合成啟發的新合成系統——把型別系統形式化為合成程序，逐步將「在型別約束下合成程式」的初始目標細化為子程式的子目標；型別規則與合成規則間存在雙射，任何程式的型別推導樹都有一棵結構相同的合成推導樹（圖 2，同構）。所有型別規則以約束 Horn 子句（CHC）表述，不僅涵蓋既有的語法正確性工作，更能容納更廣的圖靈可計算規格。（2）一種基於合成決策序列的新程式表示，取代把程式當純文字的傳統 tokenization——每個決策對應「選一條合成規則」或「使用某變數」，可系統化 tokenize 並餵給 LM，同時顯式編碼型別推導與程式結構（滿足推導鄰近性）。（3）TyFlow，一套自動化系統：輸入為（1）語言定義（語法、型別規則、含型別檢查器的工具鏈）與（2）一組訓練任務（prompt＋目標程式），自動建構同構的合成系統，含把程式轉為決策序列供訓練的元件、與從 NL prompt 生成 well-typed 程式的元件（滿足資料可用性）。
