摘要

樹型遺傳編程（TGP）是符號迴歸、分類、機器人控制等任務廣用的演化演算法。因 TGP 算力需求大，GPU 加速對可擴展性至關重要。然而 TGP 的高效 GPU 執行仍困難，主要卡三點：(1) 程式個體結構異質；(2) 整合多層並行的複雜性；(3) 高效能 CUDA 執行與彈性 Python 環境不相容。本文提出 EvoGP，一個以群級（population-level）並行加速 TGP 的高效框架。其一，引入張量化表示，把變長樹編碼成定形、對齊記憶體的陣列，讓不同個體間能統一記憶體存取與並行計算。其二，採自適應並行策略，依資料量動態結合「個體內」與「個體間」並行，確保各類任務皆高 GPU 利用率。其三，把自製 CUDA kernel 嵌入 PyTorch runtime，無縫接 Gym、MuJoCo、Brax、Genesis 等 Python 環境。

實驗顯示 EvoGP 峰值吞吐 超過 10¹¹ GPops/s，相當於比現有 GPU 版 TGP 快達 304×、比 SOTA CPU 庫快 18×；且精度相當、在大族群下擴展性更佳。開源於 https://github.com/EMI-Group/evogp 。

關鍵詞：遺傳編程、並行演算法、GPU、CUDA。

I. 引言

GP 自主演化電腦程式，產人類可解釋解、結構可動態演化（非預先固定），同時搜尋結構與參數空間，降低人工設計與模型偏差。依結構表示分為 Linear GP、Cartesian GP、基因表達式編程、文法演化等，其中 TGP 因在搜尋效率與可解釋性間取得良好平衡而最被廣泛採用。TGP 把程式編碼成樹（內部節點＝運算子，葉節點＝變數／常數），用交叉、變異等遺傳算子做演化搜尋；成功應用於符號迴歸、分類、複雜系統設計、機器人控制。

多數既有實作仍限於 CPU 執行；資料量與任務複雜度一升、效能急降。評估每個個體常要處理大資料集或模擬複雜環境互動，且每代每個個體都要重跑，龐大開銷阻礙演算法調參，更嚴重限制 meta-優化（自動調參、自適應算子選擇）——這些都需跑大量配置，高成本下不可行。

為此，越來越多工作用 GPU 的大規模並行與高吞吐。TGP 的 GPU 並行有兩種直覺策略：個體內並行（intra-individual）——單一個體在所有資料點上並行求值，貼合 SIMD，多數既有 GPU 版 TGP 採此；個體間並行（inter-individual）——同時評估多個候選解，即群級並行，是現代高效能演化計算的核心（JAX 系 EvoJAX/evosax、PyTorch 系 EvoTorch，及 EvoX 等）。但群級並行在 TGP 中相對少被探索。對 TGP，個體間並行能讓 fitness 評估與遺傳操作（交叉／變異／選擇）並行執行、大幅降開銷，更為擴展到更大族群奠基。

三大技術障礙：(1) 結構異質——TGP 個體大小／拓撲／求值邏輯差異大，與張量框架不合，連 CUDA 也須先把變長結構編成規則化、對齊記憶體格式（尚未解決）；(2) 多並行整合——資料級並行貼合 SIMD 已被善用，但與群級並行結合須協調記憶體佈局、kernel 融合、排程以免資源競爭；(3) Python 互通——須在 Gym/MuJoCo/Brax/Genesis 等生態無犧牲效能地接軌。

四項貢獻：① 提出張量化表示做群級 GPU 並行，把結構各異的樹轉成定形對齊陣列、統一記憶體存取——EvoGP 是首個在全部演化階段（初始化／評估／遺傳操作）皆 GPU 加速的框架；② 自適應並行策略，依資料量動態結合個體內／間執行；③ 把自製 CUDA 算子嵌 PyTorch，無縫部署 Gym/MuJoCo/Brax/Genesis 並提供豐富可客製介面；④ 大量實驗驗證——峰值 >10¹¹ GPops/s、對 GPU 版加速達 304×、對最快 CPU 庫 18×、大族群擴展性更佳。

II. 背景

II-A 樹型遺傳編程（TGP）

TGP 把候選解表示為樹，明確定義輸入到輸出的計算流。一棵樹是 （節點集， 邊集， 根節點），每節點恰一父。樹代表函數 Func，自底向上計算：每節點算其結果，根節點結果即最終輸出。每節點是 （類型， 值） 元組，分三類：常數節點（數值常數）、變數節點（值＝輸入向量索引）、函數節點（值＝函數類型，對子節點結果作用）。TGP 透過選擇、交叉、變異反覆精煉族群（Algorithm 1）：選擇＝依表現挑個體（好的較易傳代）、交叉＝父樹交換資訊增多樣性、變異＝隨機改節點／分支防早熟。

II-B GPU 架構與 CUDA

現代 GPU 由數千核心組成 SM（流多處理器）達大規模並行；記憶體階層含高延遲全域記憶體、L1/L2 快取、唯讀最佳化的常數記憶體。但 GPU 上動態記憶體管理因執行緒競爭／同步開銷／碎片化而遠慢於 CPU，故處理變長結構（如樹）特別棘手。CUDA 採 SIMT 執行模型，並行組織成三層 grid／block／thread。

II-C 既有 TGP 實作

  • CPU 版：DEAP（重擴展性、多種演化算法、multiprocessing）、gplearn（專注 SR/分類、joblib 跨核並行）、Operon（現代 C++，靠 Taskflow 群級並行 + SIMD 向量化資料級並行，較舊庫明顯加速）。
  • GPU 版：KarooGP、TensorGP 建於 TensorFlow——KarooGP 為每個體建靜態計算圖、重複編譯開銷大；TensorGP 改 eager 執行避編譯，但缺對 GPU 資源細控、加上 Python/TF 抽象成本，效能仍次優。SRGPU 直接用 CUDA 實作核心操作、單一個體的所有資料點並行（資料級並行好），但評估／選擇／交叉／變異在群級仍序列執行，多數 GPU 並行未用、擴展性受限；且無 Python 綁定，難接主流 ML／機器人管線。
  • 多數庫用指標式／鏈式樹表示，序列執行內部夠用，但記憶體不規則、非連續，阻礙 memory coalescing 與共享記憶體，群級並行時全域記憶體存取低效、吞吐下降。
