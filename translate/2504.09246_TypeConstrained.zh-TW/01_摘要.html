摘要

大型語言模型（LLM）在程式碼生成上已有顯著成就，但仍常產出無法編譯的輸出，因為其 next-token 推理程序並不建模程式的形式面向。Constrained decoding（約束解碼）是緩解此問題的有力途徑，但過往只被用於處理 DSL（領域特定語言） 或通用語言的語法特徵。然而 LLM 常生成帶型別錯誤（typing errors） 的程式，這超出語法範疇、一般也難以妥善約束。為此，我們提出一種利用型別系統引導程式碼生成的型別約束解碼方法：開發新式 prefix automata（前綴自動機） 與「可棲居型別（inhabitable types） 的搜尋」，構成一套在 LLM 生成碼上強制 well-typedness（型別正確性） 的 sound（可靠）方法。我們先在一個基礎的簡單型別語言上形式化，再擴充到 TypeScript 展示實用性。在 HumanEval 與 MBPP 上的評測顯示：本法在合成、翻譯、修復三類任務上，於各種尺寸與家族（含 >30B 參數的 SOTA 開源模型）的 LLM 上把編譯錯誤減少一半以上，並顯著提升功能正確性。

1. 引言

LLM 已能從自然語言合成程式碼、在語言間翻譯、修復錯誤程式，但生成碼常含編譯錯誤、邏輯瑕疵或安全漏洞——根源在於「逐 token 機率取樣」不提供任何形式保證。Constrained decoding 是有力對策：在生成過程中強制程式語言的形式規則，拒絕無效 token、只讓有效 token 成為候選；既有研究已證明它能提升對語法的遵循。

關鍵挑戰：生成 well-typed 的程式碼。 但語法只占整體正確性的一小部分——作者實測 SOTA 開源 LLM 生成的 TypeScript，語法錯誤平均僅占編譯錯誤的 6%，而 94% 的編譯錯誤來自型別檢查失敗。這指出明確方向：把型別系統的形式規則納入 LLM 生成。但難點有二：(i) 型別系統一般無法用 context-free grammar 表達，故過往為語法設計的前綴演算法無法直接套用；(ii) 除了像傳統型別系統那樣為「完整運算式」維護型別環境，還須準確處理部分運算式——對每個當前生成的部分運算式，判定它「能否被補全成符合某要求型別」。後者觸及難解的 type inhabitation（型別可棲居性） 問題。

本作：型別約束解碼。 作者設計一套 sound 演算法，判定「某部分程式能否補全成 well-typed 程式」。核心是一種新式非確定性自動機，它增量式地建構部分程式描述的抽象語法樹（AST），並以型別相關脈絡（已宣告識別子、運算式型別）標註之，藉此維持一個 prefix property（前綴性質）：解析某程式前綴只在「它能補全成 well-typed 程式」時才得到非空狀態集。為保證此性質，設計一套 sound 的型別搜尋演算法，判定部分運算式能否棲居某給定型別。先在一個泛用、簡單型別、Turing-complete 的演算 L_B 上建構自動機，再實例化到 TypeScript 的一個非平凡子集。選 TypeScript 因為：(i) 它是 GitHub 上最活躍語言之一；(ii) SOTA LLM 無法可靠生成 well-typed 的 TypeScript；(iii) 其核心型別系統夠簡單，適合開發首個原型。

實驗結果：型別約束對 2B–34B 的各式 LLM 都顯著改善程式碼生成。合成與翻譯：編譯錯誤減半以上、功能正確性相對提升 3.5%–5.5%；修復不可編譯碼的功能正確率平均相對提升 37%。本法普遍適用於任何可從核心演算導出的語言、這些語言上的任何生成任務、以及任何用 next-token 生成的 LLM。

主要貢獻：(1) 一套 prefix automaton＋型別搜尋演算法，在泛用簡單型別核心演算上實現型別約束（§3）；(2) 對 TypeScript 的實例化與擴充（§4）；(3) 跨多種 LLM 與任務的廣泛評測（§5）。

2. 背景與總覽

LLM 程式碼生成（§2.1）：LLM 逐 token 增量生成（Algorithm 1，不含藍色高亮）——每輪把 prompt x 與當前部分程式 s 串接餵入，輸出詞表上的機率分佈 v，取樣一個 token 附加到 s，直到遇到 EOS。這些分佈隱含地編碼語言規則，但 LLM 可能推不出複雜規則、對罕見語言規則不完整、且因機率本質不總是遵守形式規則。

Constrained decoding（約束解碼）：藉一個語言專屬的 completion engine CE_L，CE_L(s) 回傳「部分程式 s 能否補全成 L 中的良構程式」，等價於判定 s 是否屬於 L 的前綴語言 L_p。

  • 定義 1：語言 L 的前綴語言 L_p := {s | ∃s′: s◦s′ ∈ L}。
  • 如 Algorithm 1 藍色高亮：在取樣外加一層 sample-and-check 迴圈——取樣的 token t 只在「s◦t 能補全成良構程式」或「t=EOS 且 s 已良構」時才被採納，否則把 t 機率歸零重取。因詞表含所有常見字元，恆存在合格 token，迴圈次數受詞表大小上界，且不需額外 LLM 推論。token 級保證歸納地延伸為最終程式對 L 的有效性。
  • 關鍵：一般的語法/型別檢查器不能直接當 completion engine——它們判定「s∈L（完整程式是否良構）」，而當 s 只是有效前綴時給出的答案與 CE_L(s) 不同。

本法總覽（§2.2）：以 Figure 1 為例（MBPP #113 的部分 TypeScript 程式，五個補全候選）：純語法約束能擋掉含非法字元者（1），但擋不掉語法合法卻型別錯誤者——(2) 存取未宣告識別子、(3) 對 number 做函式呼叫、(4) 傳錯型別給 parseInt（此例 (4) 由 CodeLlama 34B 生成，語法約束會誤放行導致不可編譯）。只有型別系統能正確只接受良構的 (5)。

做法：先建構帶 prefix property 的非確定性自動機（每個可達狀態都能通往接受狀態），用它當 completion engine。以 Figure 2 的具體例子說明「prefix automaton」：每個狀態代表當前已解析的語法成分並額外追蹤周邊型別資訊。例如解析 parseInt 的首參時，已知 num 是 number 型別、要求型別是 string；自動機要判定「對 number 的 num 施加哪些運算能得到 string」——這靠 type reachability search 找出 num.toString() 與 num.isFinite().toString()，於是放行 .toString、.isFinite 兩個成員存取轉移（CodeLlama 34B 依訓練分佈選了較可能的 .toString()）。實際自動機的轉移是字元層級的，Figure 2 為呈現而濃縮成字串層級。

type reachability（Figure 3）：概念上在一張「型別為節點、well-typed 運算為邊」的抽象型別圖上搜尋——從 num 的 number 出發，經 member access 邊到 () => string，再經 function call 邊到目標 string，得知 .toString() 是良構補全。每解析一個部分運算式就呼叫一次此搜尋以決定前綴自動機的有效轉移。
