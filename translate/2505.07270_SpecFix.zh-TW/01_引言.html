1. 引言

自然語言（NL）因大型語言模型（LLM）的強大能力而在軟體開發中扮演重要角色。然而，NL 固有的歧義性與被誤解的可能性會損害生成程式碼的品質。Vijayvargiya 等人觀察到歧義問題描述使模型效能下降 20%。

既有工作（ClarifyGPT）分析 LLM 取樣程式的語意差異以量化描述歧義，再促使 LLM 向使用者提澄清問題。然而實驗顯示，LLM 產生的澄清問題往往與其自身對問題的詮釋無關，導致冗長且無效的描述，增加使用者認知負擔。

鑑於上述限制，本文引入自動修復歧義 NL 問題描述的問題，定義為系統性地修改描述以確保符合預設品質標準的任務。核心洞察：許多歧義可以完全自動解決——(1) 可透過增加 LLM 產出最可能詮釋的機率來降低程式碼生成不確定性；(2) 雖然 SOTA LLM 在歧義語言下難以正確解讀輸入輸出範例，但可透過將 NL 對齊到釐清範例來消除歧義。

SOTA LLM 難以直接修補歧義描述，常產生不相關或不一致的變動。我們假設這是因為 LLM 難以反思「自然語言文字的變化如何影響基於修改後文字所生成的程式」。為克服此問題，我們提出 SpecFix，將任務拆解為較簡單的子任務：(1) 先分析並修復該描述所誘導的程式分佈，(2) 再透過**對比規格推斷（contrastive specification inference）**將分佈變化映射回描述文字。

本文貢獻：

  • 首個針對 LLM 程式碼生成的自動 NL 問題描述修復方法。
  • 新的問題描述品質標準：範例一致性（example consistency），源於 LLM 無法從釐清用的 I/O 範例中抽取潛在意圖。
  • 透過程式分佈反思的修復機制——對比規格推斷。
  • 廣泛評估展示描述修復的有效性及其跨模型泛化能力。

2. 動機範例

2.1 NL 歧義降低 LLM 效能（圖 1）

考慮一個要求「移除圖中節點間重複連線」的規格。歧義在於：(1) 刪除所有出現超過一次的連線，還是 (2) 從第二次出現起刪除。雖然嵌入的 I/O 範例明確支持第一種解讀，但 DeepSeek-V3 取樣 20 個程式全部落入第二種（錯誤）語意簇，範例一致性 EC=0。SpecFix 透過添加「only keep connections that appear exactly once」成功消除歧義，使 DeepSeek-V3 以 P=1 產出正確實作。

觀察 1：細微的 NL 歧義可能使 LLM 即使在有釐清用 I/O 範例的情況下仍產生錯誤程式碼。將 NL 對齊到範例可實現自動精確消歧。

2.2 既有 LLM 方法的限制（圖 2）

ClarifyGPT-auto（以使用者模擬 prompt 回答澄清問題並附加到原始描述）被測試時，對一個因缺少「and」等連接詞導致的歧義（swap cases／replace vowels 的先後順序），問了五個問題——四個多餘，唯一相關的問題答案模糊，導致修補後 pass rate 降為 0。SpecFix 改為先分析語意簇的機率（P）與範例一致性（EC），選取 EC=1 的最大簇 vs 拒絕簇，以對比推斷產生最小修訂（加上「Additionally」表明順序性），修補後 Pass@1 達到 1.0。

觀察 2：LLM 難以進行歧義修復，常產生多餘或誤導的澄清。透過拆解任務，SpecFix 達成小而意圖對齊的修補。

2.3 問題描述修復 vs. 推理（圖 3）

µFix（SOTA 推理式程式碼生成方法）在面對「金字塔的 height 到底是垂直高還是斜高」的歧義時，雖正確辨識表面積公式，但計算結果與範例不符時，錯誤歸因於「四捨五入誤差」而非質疑其對 height 參數的理解。結果 Pass@1=0。SpecFix 改為先對 EC=0 的簇中程式進行程式修補（以 I/O 範例為正確性標準），再以對比推斷將描述改為「slant height（斜高）」，Pass@1 達 1.0。

觀察 3：SOTA 推理方法在歧義存在時難以正確「逆向工程」釐清範例。SpecFix 改為修補程式分佈使其對齊範例。

3. 背景與記號

  • 問題描述 D：本工作聚焦功能性規格（可觀察的程式行為），即 LLM 程式碼生成 prompt。
  • LLM 可形式化為條件機率分佈 m(·|D)，實際以取樣 N 個程式近似。
  • 語意簇：取樣程式依輸入輸出行為分群（等價類）。同一個簇內的程式在所有測試輸入上產出一致輸出。
  • 語意熵（SE）：語意簇分佈的熵。SE>0 表示多種不同詮釋。ClarifyGPT 以此定義歧義。
  • 範例一致性（EC）：給定描述中嵌入的 I/O 範例 {(x_i, y_i)}，對一個語意簇 [P]，EC 為該簇中程式通過這些範例的比例。對整個分佈，EC 為加權平均。

問題描述修復的正式定義：尋找 D' 使得 SE(m_≡(·|D')) < SE(m_≡(·|D)) 且 EC(m_≡(·|D'), EX) > EC(m_≡(·|D), EX)，且 diff(D, D') < τ（τ 為預設閾值）。終極目標是 SE=0（單一語意簇）且 EC=1（所有生成程式通過嵌入範例）。

4. SpecFix 方法

4.1 分佈修復（Algorithm 1）

輸入：問題描述 D、LLM m、迭代上限 K、取樣大小 N。

  1. Extract_Examples(D)：從描述中提取嵌入的 I/O 範例。
  2. Interpret(m, D, N)：取樣 N 個程式，生成測試輸入以覆蓋功能，依輸出分群為語意簇，得近似分佈 m̂_≡(·|D)。
  3. 計算 SE 與 EC。

兩種修復策略：

機率引導修復（存在 EC=1 的簇時）：選取 EC=1 中機率最大者為 P_select，其餘為 P_reject。優先在範例一致的詮釋中挑選最可能者。

程式修復式描述修復（無任何簇 EC=1 時）：對最大簇（代表 LLM 的主要詮釋）中的程式以 self-refine 方法修復——給定錯誤程式與執行回饋（測試失敗、預期 vs 實際輸出），自動產生修正版。修復後的程式為 P_select，原程式為 P_reject。

迭代最多 K 輪，每輪接受條件為 ec' > ec 且 se' < se。

4.2 對比規格推斷

SpecFix 的核心創新：將 P_select（支持證據）與 P_reject（反對證據）同時餵給 LLM，要求 (i) 診斷歧義來源，(ii) 重寫規格使只有預期行為可接受。原理：解釋在對比「為何是 A 而非 B」時最具資訊量，而非孤立描述 A。
