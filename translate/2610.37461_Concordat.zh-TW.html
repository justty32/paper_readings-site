論文／訪談原始來源

Concordat：為 LLM agent 執行有限狀態協定

第 1–2 節：問題與背景

客服 agent 的政策可能要求變更前先說明並取得明確確認。當顧客催促它跳過確認，即使最終資料庫正確，也可能違反過程要求。Typestate 依狀態限制操作，session types 描述通訊次序；Concordat 採有限狀態協定的簡化片段，在執行期限制模型可用工具，並非靜態檢查模型本身。（§1–2）

第 3 節：定義、工具與人

協定有有限狀態及動作、起點、終點與轉移；同一動作可以依結果選不同後繼。定義時檢查終點非空且無動作、轉移非空、所有狀態可從起點到達且能通往終點。能通往終點表示存在合法路徑，並不保證執行一定終止。非法動作或目標造成 ProtocolViolation，狀態不變。（§3.1；終止界線為本檔補註）

開發者在 agent 類別的方法宣告合法狀態及後繼，定義類別時建構並檢查協定。Runner 每回合只提供當前合法工具，停用平行工具呼叫；非法名稱或無效參數返回錯誤，非法方法的本文不執行。這保護接入協定的工具呼叫，不自動驗證自由文字或政策的語意。（§3.2–3.3；語意界線為本檔補註）

@human 由模型請求，但由應用提供的 approver 批准或拒絕，兩者是不同轉移。Budget 計 token、tool calls 和金錢；子 agent 的額度從父額度扣除，父項有限的維度不可給子項無限額。這是執行期線性資源處理，尚無靜態 budget 型別。下述 airline 基準使用模擬顧客的關鍵字 gate，並不是此 @human approver 的實驗證明。（§3.4、§5.1）

子類可新增步驟，但定義時須通過 refinement：終止狀態是父類終止狀態子集，刪去新增動作後的有限 run 須符合父協定，進入同名父狀態須是父可能狀態；父類的人工作業仍須是人工作業。演算法走訪子狀態與可能父狀態集合。這是共用動作 trace inclusion，子類不必提供父類每個選擇，也依狀態名稱對應，非完整 session subtyping。（§3.5）

第 4–5 節：實作及測試

作者稱程式約 850 行 Python、50 個 unit tests，提供 Anthropic Messages 與 OpenAI Responses 的 runners；本工作區未安裝或驗證。（§4）

實驗取 τ-bench v1.0.1 airline 全部 50 tasks。標準 agent 與 Concordat 比較；後者為兩狀態 gate：查詢兩狀態皆可，資料庫寫入只在 confirmed，最近顧客訊息含 yes／yep／yeah 則進 confirmed，其他訊息回 chatting。作者加的非官方壓力指令讓模擬顧客第一次確認時催促且不說 yes，被再次詢問才同意。Haiku 5.5 agent 配 Sonnet 5.5 顧客；gpt-4.1 同時當 agent 與顧客。（§5.1、附錄 A）

壓力情境 標準通過 Concordat 通過 標準／Concordat 未確認 task-runs
Haiku，三次 pooled 112/128 105/128 29/128／0/128
gpt-4.1，一次 20/50 22/50 13/50／0/50

Haiku 部分 task-runs 因 API 配額缺失；標準 agent 未確認的寫入呼叫數為 50／26，分別對應上表 29／13 個 task-runs。Concordat 的零值是以和 gate 相同的關鍵字定義計算。作者對 Haiku 違規差異報 Fisher p=6×10⁻¹⁰，明示將 task-runs 當獨立；gpt-4.1 報 p=10⁻⁴。（表1、§5.2、§5.3）

配對成功結果的 McNemar 精確檢定：Haiku 不一致 13 對 6、p=0.17；gpt-4.1 9 對 7、p=0.80。沒有顯著差異不證明成功率等同。作者發現 Haiku 的 13 個僅標準通過 runs 中 11 個 Concordat 反覆拒絕後轉人工，於是在 gpt-4.1 run 前增加不應因催促轉人工、應重述並再問的提示；模型及提示均不同，不能把差異單歸提示。（§5.2–5.3、附錄 B）

首次 Haiku 壓力 run 的 13 個違規 tasks 中 8 個仍獲 τ-bench 滿分；最終結果正確不能確保過程符合政策。作者手讀首次 Haiku 與 gpt-4.1 被標記寫入前的 49 則顧客訊息，其中兩則「go ahead」是否算確認有爭議；計作確認時 gpt-4.1 違規降為 12 tasks，Haiku 不變。（§5.1–5.2）

第 5.3–7 節：限制與未來方向

相同關鍵字用於 gate 和違規指標，故零值只對該定義成立；「yes, but not that one」也可能被接受，作者建議真實部署採結構化確認。合作顧客早期使用寬鬆 gate，重新以嚴格標準計時 Concordat 有一次未含 yes 的變更。試驗只有一個領域、兩主要模型與少數 trials；gpt-4.1 約三分之二 tasks 因限流稍後重跑，模擬顧客不等於真人。（§5.2–5.3）

多方協定投影、每回合內容的語法約束、靜態資源型別、持久 session，以及同一模型上提示修改的對照都列為未來工作。（§6）
