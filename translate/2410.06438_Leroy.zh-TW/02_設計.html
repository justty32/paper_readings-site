3. 設計

Stitch 直接在其預期的 Lisp 類程式上用 CTS，但在較不規則的語言上會因正確性問題天真地失敗：抽出的共同子樹在原語言中可能非法。例如把 Python AST 以 Lisp 風格表示餵給 Stitch 時，while、if 等關鍵字、==、> 等運算子會被當成語言的一等公民——抽出的子樹可能含持有這些值的變數，或以它們為參數呼叫函數，導致語法錯誤（如 compare(1,2,==)）或非法賦值（如 x = while）。根本原因是 Stitch 假設一個以 Lisp 風格表示的規則 lambda calculus，而 Python AST 不夠規則。

Leroy 延伸 Stitch，正確地從 P2 語料抽庫。P2 是 Siek 與 Chang（2017）編譯教材中一個大型 Python 3 形式化子集；所有 P2 程式都是行為等價的合法 Python 3 程式。P2 支援命令式風格：作用域變數賦值、控制流、函數呼叫與非巢狀定義；對整數、布林、串列、字典為動態型別，支援對應運算與比較；輸出用 print，輸入用固定運算式 eval(input())。附錄給出完整文法——本文與已發表的 P2 差異僅在捨棄 lambda 與巢狀函數定義（列為未來工作）。

Leroy 工具架構（圖 2）：輸入為 P2 程式語料。第一步 lispify 把 P2 程式轉成 Stitch 可辨識的 Lisp 類格式；Stitch 提出 Lisp 類候選抽取；候選接著經一連串剪枝檢查，驗證確能轉回合法 P2 函數（對應 Python 缺乏規則性所生的各種問題）；候選通過後，用活躍變數分析（liveness analysis）補上必要的參數與回傳值——此「收尾（closing）」用於處理候選的 live-in/live-out 值之作用域；最後校驗呼叫點，確保函數參數與函數內容間無命名衝突。

3.1 Lispify（Lisp 化）

Leroy 先把 P2 程式轉成 Stitch 能懂的 Lisp 類表示：把 AST 節點視為巢狀函數呼叫——每個節點是函數、其子節點是引數，從而把 AST 展開成單一統一的函數呼叫。例如加法 1+2 的 AST 是根為 add、子節點為常數 1、2 的樹，函數式寫作 add(1,2)，Lisp 式即 (add 1 2)。

另一難點是處理 Python 的命令式語句。例如 x=1; y=1; print(x+y) 被 lispify 成 StatementList(x=1, StatementList(y=1, StatementList(print(x+y), ε)))，其中 ε 為空語句。此編碼借鑑 Lisp 的 let 語句。

3.2 剪枝 Stitch 的抽象

Stitch 對 lispify 後的碼會建議許多轉回 Python 未必良好的候選。Leroy 分幾類剪掉非法候選。

3.2.1 類巨集抽象（Macro-Like）：Stitch 把抽象庫當成巨集，因它把所有程式元素當一等公民，抽象時直接以呼叫替換。這會造成不完整抽象，如把 exp+exp 抽成 exp+——抽象 add(exp) 會把 1+2 換成 add(1) 2，Python 語法非法。Leroy 藉反轉 lispify 把候選重建成程式 AST，再檢查其完整性（所有父節點的必要子節點是否齊全）；不完整的 AST 即類巨集結構，予以剪除（例如缺第二引數的 add(a, )）。

3.2.2 非法參數（Invalid Parameters）：Stitch 把所有樹節點都當成可能的「洞（hole）」即可能的函數參數，這在 Python 不對。例如抽比較子樹 x==y、x!=z 時，可能建議取三參數（兩運算元加一比較運算子）的抽象，須呼叫成 f(x,==,y)——非法。Leroy 再次把候選函數體轉回 Python AST、把參數編為 identifier 節點，驗證其對 AST 結構的合法性。理想應得 greater_than(a,b) 而非 compare(a,comparator,b)；取非法參數者被剪除。

3.2.3 呈現非瑣碎抽象（Non-trivial）：Stitch 依「抽象函數大小相對其使用」最佳化，可能抽出高度重複的單行功能（如只是把兩數相加），這類雖高頻卻無價值。Leroy 以最小大小門檻濾除瑣碎案例，確保抽出的抽象夠複雜、有意義。

3.3 收尾函數（Closing Functions）

3.3.1 決定回傳值：Stitch 把抽象當巨集、不考慮變數作用域。例如它可能抽出「改了某變數卻不回傳被賦值目標」的函數；在 Python，這種賦值會在被呼叫函數內建立區域新變數，而非改動呼叫端變數——語法正確但行為錯誤。Leroy 對每個候選呼叫點做活躍變數分析，找出從抽象體 live-out 的變數作為回傳值（注意抽象的參數本身也可能 live-out 而需回傳）；若無變數 live-out，則退回回傳抽象體最後一個變數或運算式，以維持在呼叫點作為子運算式使用時的功能正確性。

3.3.2 決定額外參數：因 Python 命令式風格與 Lisp 類輸入語言脫節，Stitch 的抽象可能假設某些變數存在卻未被傳入。為避免函數體內未初始化變數，Leroy 用活躍變數分析找出未 live-in 抽象體的變數，假定它們存在於呼叫端作用域，並補為候選的參數。

3.4 校驗呼叫點（Validating Call Sites）

Python 命令式本質帶來的最後一個問題是「呼叫點引數與函數體之間可能的改名衝突」。以圖 3 為例：候選 print5(arg) 把 arg 印五次；Stitch 認為可用 print5(x) 取代某迴圈——但這是非法的，因為原迴圈裡 x 每輪都重算，而把它當引數 arg 傳入只在呼叫點算一次。問題出在符號 x 被別名為引數時的隱式改名：x 的值以改名後的 arg 使用，但 x 這個名字本身已在迴圈處失聯、不再連到相應值。為偵測此類非法呼叫點，Leroy 分析每個呼叫點及其引數，驗證引數中的名字不會在函數內被引用，藉此防止命名衝撞。

（圖 3 程式碼要旨：print5(arg) 內有 for x in range(5): print(arg)；某呼叫點原為 for x in range(5): print(x)，若替換成 print5(x) 即因參數與函數體都用到 x 而語意錯誤。）

4. 評估

Leroy 以 Stitch commit 3d352e6 開發，在 macOS Ventura 13.3 的 MacBook Pro、Python 3.9.6 上評估。語料為 122 支符合 P2 文法的小型 Python 程式，平均每支 7 行——這是校內編譯課的完整單元測試套件。此設定給 Leroy 最壞情況：語料比多數生產程式小、重複內容少。

我們讓 Stitch 一路跑到再也生不出新抽象為止，以榨出最多抽象；並捨棄「呼叫其他抽象」的抽象（通常小而瑣碎）。

以 20 個 AST 節點為最小門檻套用 Leroy，找到 6 個有效抽象。因語料性質，它們多做各種賦值與列印操作。例如抽象函數 assign_print 把第三、四參數分別賦給第一、二參數，再印出兩者之和，被用於 3 個不同呼叫點（其他找到的抽象如 swap_print、assign_print_eq、multi_assign、assign_add、multi_assign_2 見圖 4）。搜尋過程中 Leroy 剪掉 3123 個類巨集抽象、32 個非法參數抽象、以及約 42000 個小於 20 節點的抽象——之所以剪掉這麼多小抽象，是因 Stitch 在搜尋階段把 AST 的每個子樹都當候選。

找到的每個函數平均用於 2.5 個呼叫點。我們以壓縮比（原 AST 大小 : 重寫後 AST 大小）衡量學到的庫之品質，即程式縮小的倍數。整體達 1.04x 壓縮比（不含抽出的庫）；若把庫算進去，語料以 AST 節點計反而成長 1.2%。此膨脹是因 closing 加大了 Stitch 所生抽象的體積（含抽象體與呼叫點）。未來計畫探索更大的真實語料，預期能發現更大冗餘、達到更好壓縮。
