5. 結論

本文聚焦「讓 LLM 為特定任務準確找出正確 API」這一重要但常被忽視的面向。API 是讓異質系統有效溝通的通用語言，用對 API 能放大 LLM 與外部世界互動的能力。我們提出 Gorilla——微調 LLM 撰寫 API 呼叫的新管線，其表現在三個大型資料集上超越以 prompt 驅動的 SOTA（GPT-4）；Gorilla 生成可靠、無幻覺的 ML API 呼叫，能適應測試期 API 用法變更，並能在約束下選 API。

6. 局限與社會影響

為求資料集有挑戰性，選擇了功能高度相似的 ML API。ML 領域 API 的潛在缺點是：若以偏斜資料訓練，可能產生有偏預測、不利特定子群體。為回應此疑慮並促進對這些 API 的理解，作者釋出逾 11,000 筆指令-API 對的資料集，供社群研究與評測既有 API。

附錄擇要

  • 資料集：TorchHub 6 個領域、TensorHub 57 個、HuggingFace 37 個；每筆含 API 呼叫任務、提供者、解釋（含約束）、範例程式碼（未經執行驗證，留待未來工作）。
  • 訓練超參數：LLaMA-7B 微調 5 epochs、學習率 2e-5（cosine 衰減）、batch size 64、warmup ratio 0.03、最長序列 2048，8×A100（40GB）。
  • 評測細節：TorchHub 檢查 torch.hub.load 的 repo_or_dir 與 model；TensorHub 檢查 hub.KerasLayer 與 hub.load 的 handle；HuggingFace 除 pipeline 外均要求 pretrained_model_name_or_path（pipeline 指定 task 後可自動選模型故豁免）。
  • 表現全貌：零樣本下 Gorilla 大幅領先；GPT-4/GPT-3.5 在結構化的 TorchHub 與 TensorHub 僅約 40%；HuggingFace 更彈性多樣，各模型在其上競爭力最弱、GPT-4 幻覺問題也最嚴重。
