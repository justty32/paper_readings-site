3. 方法

（圖 3 要旨：上半為訓練流程——三大模型庫的 API 文件經 self-instruct 生成訓練資料再微調；下半為推理——支援「帶檢索」與「零樣本」兩種模式，能為使用者的自然語言需求給出正確 API 呼叫。）

3.1 資料集蒐集

記錄 HuggingFace「The Model Hub」、PyTorch Hub、TensorFlow Hub 的線上 model cards。HuggingFace 平台託管約 203,681 個模型，但許多文件貧乏、缺依賴或 model card 空白，故每領域取前 20 名，涵蓋多模態 7 域、CV 8 域、NLP 12 域、音訊 5 域、表格 2 域、強化學習 2 域，過濾後得 925 個；TensorFlow Hub v2 共 801 個模型，過濾後留 626 個；Torch Hub 得 94 個。將這 1,645 個 API 呼叫的 model card 轉為 JSON 物件，欄位為 {domain, framework, functionality, api_name, api_call, api_arguments, environment_requirements, example_code, performance, description}——此欄位設計刻意可推廣至 ML 領域之外（含 RESTful API）。

指令生成：以 self-instruct 範式用 GPT-4 生成合成指令資料——給三個 in-context 範例與一份參考 API 文件，要求生成呼叫該 API 的真實使用情境，並明確禁止在指令中出現任何 API 名稱或暗示。每個模型庫僅手工建構 6 個「指令-API」範例，全篇僅這 18 筆為人工資料。對 1,645 個 API 各取 6 例中之 3 例為 context，生成 10 對指令-API。作者強調：生成指令的 GPT-4 可換成 LLaMA、Alpaca 等開源替代。

3.2 Gorilla

Gorilla 是retriever-aware 微調的 LLaMA-7B，專為 API 呼叫而生。將 {指令， API} 對轉成使用者-代理各一輪的對話格式，做標準指令微調（instruction finetuning）。實驗中分別訓練帶檢索與不帶檢索兩種版本。

帶約束的 API 呼叫：API 呼叫常帶固有約束，LLM 不僅要理解功能、還要按約束參數分類。例如「呼叫一個參數少於 10M、但 ImageNet 準確率至少 70% 的影像分類模型」——模型須同時理解功能描述並推理內嵌的多重約束。這正是需要為 API 微調 LLM 的原因之一。

Retriever-aware 訓練：帶檢索訓練時，指令資料在 user prompt 後附加「Use this API documentation for reference: <retrieved_API_doc_JSON>」，目的是教 LLM 解析問題的後半段（文件）來回答前半段（需求）。這 (a) 使模型適應測試期 API 文件變更、(b) 提升 in-context learning 表現、(c) 降低幻覺錯誤。但作者也意外發現：給 LLM 加檢索不一定變好，有時反而傷害表現（詳見第 4 節）。

推理：使用者以自然語言給 prompt——可以是具體任務（「我想辨識影像中的物體」）或模糊目標（「我要去動物園，想追蹤動物」）。零樣本模式直接把 prompt 餵給 Gorilla；檢索模式先用 BM25 或 GPT-Index 從 API 資料庫取最新文件、串接到 prompt 後再餵入。除此之外不做任何額外 prompt 調整。輸出即是要呼叫的 API；執行系統存在但非本文重點。

3.3 驗證 API（AST 子樹匹配）

以測試案例驗證的歸納式程式合成（inductive program synthesis）不適用於 API 呼叫——語意正確性難驗證：例如影像分類有 40 多個可用模型，光 Densenet 一族就有四種配置，存在多個正確答案，單元測試無法判斷功能等價。因此改以 AST 子樹匹配對照資料集判定功能等價：由於本文只考慮單一 API 呼叫，檢查候選呼叫的 AST 是否為資料庫中某參考 API 的子樹即可得知呼叫的是哪個 API。

幻覺的定義：呼叫的 API 不是資料庫中任何 API 的子樹——即憑空捏造的工具——為幻覺（hallucination）；呼叫真實 API 但用法錯誤則為錯誤（error），兩者區分開來。

匹配細節：每個 API 引數眾多且 Python 允許預設引數，故為每個 API 預先定義需匹配的引數（如 torch.hub.load 檢查 repo_or_dir 與 model）。圖 4 例：Gorilla 回傳的 torch 呼叫沿 torch.hub.load、pytorch/vision、densenet121 節點與資料庫子樹匹配成功，而 pretrained=True 屬可選引數不檢查。

4. 評估

基線：GPT-4（gpt-4-0314）、GPT-3.5-turbo（0301）、Claude（claude-v1）、LLaMA-7B，皆為零樣本。檢索器設定：0-shot（無檢索）；BM25 與 GPT-Index（OpenAI text-davinci-003）皆以每個 API 為一份文件、取 top-1 串接到 prompt；另設 oracle 檢索器（100% 給對文件）作為上界。評測用 holdout 測試集（self-instruct 資料按指令-API 對切分；HuggingFace 90/10、TorchHub 與 TensorHub 80/20）。

不帶檢索微調：輕度微調的 Gorilla 零樣本即達 SOTA——整體勝 GPT-4 20.43%、勝 ChatGPT 10.75%、勝 LLaMA 達 83%，量化顯示在此範疇內微調優於檢索。且「微調時不帶檢索、測試時硬塞檢索」幾乎無益（TensorHub -0.88%、HuggingFace +0.97%），塞 BM25 或 GPT-Index 反而大跌（TorchHub -21.50%、HuggingFace -47.57%）——測試期加入次佳檢索器會誤導模型、產生更多錯誤。

帶檢索微調（表 2 擇要）：微調時納入 ground-truth（oracle）文件，比不帶檢索訓練好 12.37%（TorchHub）與 23.46%（HuggingFace）；oracle 檢索下 Gorilla 達 TorchHub 67.20、HuggingFace 91.26、TensorHub 94.16，幻覺低至 0／7.08／1.89。但現實檢索器與 oracle 落差巨大：評估時用 GPT-Index 掉 29.20%、BM25 掉 52.27%。結論：有好檢索器時 retriever-aware 微調較佳；沒有時零樣本微調可能是首選。

LLM 的幻覺：零樣本 prompt GPT-4/GPT-3.5 呼叫 API 時幻覺嚴重，常見如以任意 GitHub repo 名呼叫 AutoModel.from_pretrained(dir_name)、或假設使用者本地有 your_model_name 這種路徑。意外的是三個庫上 GPT-3.5 幻覺都比 GPT-4 少，且各檢索設定下一致——暗示 RLHF 可能在模型誠實性（truthful）上扮演核心角色。

4.2 測試期文件變更

API 文件更新頻率常超過 LLM 重訓／微調週期，使模型對其處理的資訊格外脆弱、效用隨時間衰退。Gorilla 的 retriever-aware 訓練使其可即時適應文件變更（圖 6 要旨）：如 FCN 的 backbone 從 ResNet-50 升級到 ResNet-101、model registry 從 pytorch/vision 換成 NVIDIA/DeepLearningExamples:torchhub，Gorilla 均能跟著文件給出更新後的正確呼叫——面對底層模型升級與 API 來源遷移仍維持準確。

4.3 帶約束的 API 呼叫

選哪個 API 通常是多因素權衡：RESTful API 有單次成本（$）、回應延遲（ms）；ML API 則有準確率、可學習參數量、磁碟大小、峰值記憶體、FLOPS 等。例：使用者要求「ImageNet top-1 至少 80% 的影像分類模型」時，正確答案是 top-1 84.2% 的 ResNeXt-101 32x16d 而非 71.88% 的 MobileNetV2。實驗取 TorchHub 中 model card 至少含一組準確率數據的子集（占 65.26%）。結果（表 3 擇要）：加上約束後所有模型準確率均降；Gorilla 在零樣本下約束準確率最高（47.88，vs GPT-3.5 與 GPT-4 各 43.66），帶 BM25/GPT-Index 檢索時與最佳的 GPT-3.5 相當——顯示 Gorilla 能在權衡多重約束下導航 API。
