摘要

大型語言模型（LLM）日益用於程式碼生成，引發其可能被濫用產生惡意程式碼的擔憂。與此同時，語法約束解碼（Grammar-Constrained Decoding, GCD）已被廣泛採用，透過強制語法合法性來提升 LLM 生成程式碼的可靠性。本文揭示一個違反直覺的風險：這個面向可靠性的技術本身可以成為攻擊面。我們發現一個名為 CodeSpear 的新型越獄攻擊，利用 GCD 誘導 LLM 生成惡意程式碼。實驗表明僅套用一個良性的程式碼語法約束即可有效越獄 LLM。

為應對此漏洞，我們提出 CodeShield，一個在攻擊者控制語法約束下仍能穩健保留安全行為的安全對齊方法。CodeShield 在 code modality 中對齊模型，教其在 GCD 下生成蜜罐程式碼（honeypot code）。此類程式碼語意無害（不實現惡意請求）且結構多樣（難以透過收緊語法來壓制）。在 10 個熱門 LLM 與 4 個基準上的實驗表明，CodeSpear 平均提升攻擊成功率逾 30 個百分點；CodeShield 亦在 CodeSpear 攻擊下恢復安全性，同時保留良性效用。

1. 引言

LLM 日益部署於真實應用，但同時可被越獄繞過安全對齊產生有害內容。此風險在程式碼生成領域尤為令人擔憂——有害輸出不是文字指令，而是可直接武器化的可執行程式。

本文揭示 CodeSpear，利用廣泛使用的 GCD 以極低成本誘導 LLM 生成惡意程式碼。GCD 原設計為約束 LLM 產出語法合法程式碼以提升可靠性，現已被 vLLM、SGLang 等主流框架支援。但我們發現：當要求 LLM 生成惡意碼時，僅套用標準 code grammar 即可阻止模型表達拒絕行為，迫使其產生惡意碼——即使語法本身完全良性。

我們將此歸因於既有安全對齊幾乎完全立足於自然語言模態：教模型說「I cannot assist with that」，隱含假設推論時自然語言永遠可用。GCD 打破此假設——自然語言拒絕落在合法輸出空間外，模型無法表達所學拒絕，被迫在未受安全對齊的 code modality 中繼續生成。

為此提出 CodeShield，在 code modality 中訓練模型生成蜜罐程式碼：語意無害（不實現惡意請求）且結構多樣（難以透過收緊語法移除）。教模型總是生成 pass 看似安全，但綁定於固定語法模式，攻擊者禁止 pass 即可重開攻擊。蜜罐碼賦予模型多種無害方式，使安全行為難以被壓制。

貢獻：(1) CodeSpear——利用 GCD 的越獄攻擊；(2) CodeShield——code-modality 安全對齊；(3) 10 LLM × 4 benchmark 全面實驗驗證。

2. 背景與相關工作

2.1 語法約束解碼（GCD）

主流 LLM 逐 token 從詞彙表選擇下一個 token，可自由產生 V* 中任何序列。這在程式碼生成中成為不可靠性來源——即使領先 LLM 也可能產出語法無效的 token。GCD 緩解此問題：將生成限制在語法定義的語言 L(G) 中。每步計算使當前前綴可延伸至合法程式的 token 集合 V_G(y<t)，將其他 token 機率設為零，從重整化分佈取樣。效果是保持 prompt 與參數不變，但將輸出空間支撐集從 V* 改為 L(G)。

GCD 現被 vLLM、SGLang 原生支援，也被 OpenAI 與 Fireworks AI 暴露。既有研究主要從防禦角度使用約束解碼強制安全規則；少數攻擊性使用需精心設計對抗性語法，限制可實用性。我們揭示更根本的風險：良性現成語法即可武器化。

2.2 LLM 的越獄與安全對齊

越獄攻擊分三類：輸入端（精心 prompt 繞過安全）、模型端（微調弱化對齊）、輸出端（操縱解碼誘導不安全輸出）。CodeSpear 屬第三類，但僅需標準 GCD 介面與普通語法，無需對抗性組件。

現代 LLM 部署前經安全對齊（SFT/偏好優化/RL），目標是對惡意 prompt 將機率質量放在 R_refuse。此表述隱含將安全立足於 NL 模態，code modality 安全未被充分探索。DPO 是最廣泛使用的對齊方法之一：直接在成對回應偏好上優化。我們的 CodeShield 保留相同 DPO 目標，但改變偏好對建構方式使模型在 code modality 中學習安全行為。

3. 威脅模型

3.1 攻擊者設定

  • 場景：攻擊者可透過支援 GCD 的推理介面查詢目標 LLM。(1) 本地部署——攻擊者可用 vLLM/SGLang 伺服模型，GCD 為內建功能；(2) API 部署——OpenAI（含 GPT-5）與 Fireworks AI（含 MiniMax-M2.7）皆暴露 GCD 介面。
  • 目標：繞過安全對齊，使 LLM 針對 DoS 攻擊、惡意軟體、憑證竊取等請求產出惡意程式碼。攻擊成功判定為模型產出部分或完全實現惡意需求的程式碼（而非拒絕或無害內容）。
  • 能力：(1) 提交任意 prompt；(2) 提供 grammar 約束解碼。兩者皆在標準 GCD 介面中輕易可得。

3.2 防禦者設定

  • 場景：防禦者為模型開發者，負責部署前安全對齊。模型可能在無約束解碼或 GCD 下被使用。
  • 目標：確保 LLM 在自然語言可用時拒絕惡意請求，在 GCD 限制輸出為程式碼時避免生成惡意碼。
  • 能力：完整存取模型參數，可應用任何安全對齊技術。但假設無法依賴推論期防禦（輸入過濾等），因本地部署中下游用戶控制推理配置、API 部署中推論期防禦引入額外延遲。聚焦提升模型內在安全。

4. 方法論

4.1 CodeSpear

動機：CodeSpear 利用既有安全對齊與 GCD 之間的不匹配。對惡意 prompt p，經對齊的模型在無約束解碼下以自然語言拒絕。但當 code grammar G 強制執行，合法輸出空間從 V* 限制為 L(G)，自然語言拒絕無效：R_refuse ∩ L(G) = ∅。GCD 移除所學拒絕，迫使模型在未受安全對齊的 code modality 中繼續生成。

攻擊流程：給定惡意 prompt p 與普通 code grammar G（如 Python 標準語法），以標準 GCD 介面取樣：y ~ P_M^G(· | p)。輸出必然滿足 y ∈ L(G)，導向可能實現惡意需求的語法合法程式碼。算法極簡：初始化前綴 → 每步計算合法 token 集合 → 從重整化分佈取樣 → 附加至前綴 → 遇 EOS 停止。

與先前越獄相比，CodeSpear 有兩個重要特性：(1) 不需對抗性 grammar——G 可以是標準 Python/C++/Java 語法；(2) 不需梯度優化、模型微調或 prompt 工程——僅呼叫既有 GCD 介面，攻擊成本近乎零。

4.2 CodeShield

動機：CodeSpear 的成功表明安全對齊一旦自然語言拒絕不可用就變得脆弱。為在 GCD 下恢復安全，模型必須在 code modality 中學習安全行為。此行為需滿足兩條件：(1) 語意無害——不實現惡意需求；(2) 結構多樣——無法透過修改語法輕易移除。

CodeShield 訓練模型生成蜜罐程式碼：語意無害且橫跨多樣語法結構的程式碼回應。蜜罐碼賦予模型在 code modality 內保持安全的多種方式。

偏好階層：以 DPO 實作，目標是使安全行為條件化於輸出空間。對每個惡意 prompt p，建構三種回應類型的偏好：

y_refuse ≻ y_honeypot（無約束解碼：自然語言拒絕最優先） y_honeypot ≻ y_harmful（GCD 限制：蜜罐碼優於惡意碼）

第一個偏好保持自然語言拒絕在可用時為最優先；第二個偏好確保 GCD 限制輸出為程式碼時模型仍偏好蜜罐碼。

偏好對建構：(1) y_refuse 取自既有安全對齊資料；(2) y_harmful 以 GCD 查詢目標模型 M 收集（y_harmful ~ P_M^G(· | p)）；(3) y_honeypot 從 OpenCodeInstruct 抽取 K 個片段，語意與惡意請求無關且結構多樣。最終偏好資料集：

D_pref = ∪_{p∈P_mal} ∪_{k=1}^K { (p, y_refuse, y_honeypot^{(k)}), (p, y_honeypot^{(k)}, y_harmful) }

訓練：在 D_pref 上以標準 DPO 目標優化 M_θ。模型學會：自然語言可用時偏好拒絕；GCD 限制時偏好蜜罐碼而非惡意碼。關閉 CodeSpear 暴露的攻擊面。
