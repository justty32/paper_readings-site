論文／訪談原始來源

工具增強 LLM agent 中政策合規的求解器輔助驗證

引言

工具增強 LLM（TaLLM）讓 LLM 能呼叫外部工具、與真實環境互動，但要部署到客服、業務流程自動化等敏感域，缺乏對領域特定操作政策（工具使用與 agent 行為）的可靠遵循。現行政策執行靠「把政策塞進 prompt」或啟發式 guardrail——皆無形式保證。本文把工具使用政策建模為約束滿足問題，讓 SMT 求解器在執行前驗證每個計畫中的工具呼叫。

政策→SMT 翻譯方法

把自然語言政策轉成形式邏輯極具挑戰。作者測了四條漸進路線：

  1. Proof-of-Thought 生成：直接 LLM→SMT-LIB，持續語法錯誤、結構不完整。
  2. 迭代修復迴圈：產出語法正確（50–60 行）但約束不足的政策。
  3. AWS Bedrock 自動推理：產更完整編碼（~600 行、~95% 覆蓋），但仍欠約束。
  4. Bedrock＋客製 prompt＋人工微調：最終採用，結合自動生成與專家審閱、精修。

三大核心挑戰：語法正確、語意完整、約束緊度。作者最終把政策編碼當成「顯式、可審查的工件」，承認完全自動化仍是 open problem。

執行期攔截與執行架構

框架以「工具規劃迴圈中的外部閘門」運作：

  • SMT-LIB 約束建構：agent 提議工具呼叫時，相容性檢查器取出該工具的驗證 schema、用 LLM 從對話歷史抽出所需政策變數、把值轉成邏輯斷言、附到靜態政策編碼上。
  • 求解器檢查：Z3 判可滿足性（SAT＝放行；UNSAT＝擋下）。被擋時 agent 收到**最小不可滿足核（unsat core）**當解釋，最多 3 次重規劃後交還使用者。

τ²-bench 評估與量化結果

評估用 τ²-bench 的航空域：「50 任務、13 工具、1242 字政策文件」。兩模型：GPT-4.1 做 agent 規劃、GPT-4o 做工具呼叫驗證。指標用 pass∧k（k=4，所有 k 次 i.i.d. 試驗皆成功的機率）。

  • RQ2（政策違規）：基線產出有效/無效寫入工具呼叫約各半；加上政策檢查器後，無效寫入呼叫降到全部寫入呼叫的 29%，但正確寫入呼叫也略降（精度/召回取捨）。
  • RQ3（任務正確率）：兩系統整體成功率相近，檢查器略升。關鍵在一致性：隨 k 增大成功率僅下降 26%（基線 40%），顯示跨多次執行更可靠。

相關工作

定位於三條研究線：

  • 工具增強 LLM：回顧 Chameleon、Gorilla、ToolkenGPT 的工具供給法。
  • agent 政策執行：現有工作靠系統 prompt 或後處理，缺確定性保證。
  • 形式驗證：指出缺口——先前工作（Proof of Thought）未把形式驗證直接整合進工具使用規劃迴圈。

局限與結論

作者坦承「手動或半結構化的政策編碼仍屬必要」以驗證正確性與緊度。形式方法對 TaLLM 政策執行可行，但政策翻譯的完全自動化尚未實現。本工作顯示求解器輔助檢查能減少違政策的工具呼叫、同時維持任務成功——對安全關鍵性質而言，形式保證有其價值。未來方向：進一步自動化、改良政策檢查機制。
