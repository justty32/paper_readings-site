1. 引言

程式碼生成是根據程式設計規格自動產生原始碼的任務，近年來因大型語言模型（LLM）的進步受到廣泛關注。然而，由於真實世界問題的複雜性，LLM 生成的程式碼常常無法完全對齊原始規格。現有技術（prompt-based 與 agent-based）主要聚焦於規劃、實作、修復三個階段，卻忽略了第一階段——感知（perception）——的根本問題：LLM 對輸入規格的感知偏誤（specification misalignment），即 LLM 可能隱式忽略或誤解規格中的關鍵成分，導致生成的程式碼偏離預期需求。

準確的規格感知是 LLM 程式碼生成範式的基礎，因此確保規格對齊至關重要。Specine 借鑒軟體需求工程，提出了一種新穎的規格對齊技術，其核心思想是：識別偏誤的輸入規格，提取（lift）LLM 實際感知到的規格，並將其對齊以提升程式碼生成效能。

三個關鍵挑戰：(1) 如何識別偏誤規格——對所有案例執行對齊會引入不必要的開銷甚至破壞原本正確的案例；(2) 如何獲取 LLM 實際感知到的規格——需要在識別出偏誤後顯式提取；(3) 如何對齊感知規格以生成正確程式碼——需要全面且有效的對齊規則。

為應對這些挑戰，Specine 設計了三個主要組件：雙代理偏誤識別（coder + tester agent 聯合判斷）、規格提取（基於需求工程 DSL 從程式碼 lift 出結構化規格）、規格對齊（十條預定義對齊規則 + aligner agent 逐步貪婪搜尋）。

實驗在 4 個先進 LLM（DeepSeek-Coder-1.5、Qwen2.5-Coder、GPT-4o-mini、Gemini-1.5-Flash）與 5 個競賽級基準（APPS、APPS-Eval、CodeContests-Raw、CodeContests、xCodeEval）上，對比 10 個流行或 state-of-the-art baseline，在所有 20 個 subjects 上全面勝出。例如平均 Pass@1 勝過所有 baseline 29.60%∼93.55%。

2. 動機範例

以 Codeforces 上的一個真實問題為例：題目要求處理兩種 query——型別 1 將元素 x 加入陣列尾端，型別 2 將陣列中所有 x 替換為 y。GPT-4o-mini 以 Zero-shot 生成的初始程式碼錯誤地處理了替換邏輯（未即時替換已有陣列）。PairCoder 以多方案探索與執行回饋修復後仍存在邏輯錯誤。相比之下，Specine 透過對齊「兩種 query 型別」的目的（說明型別 2 的替換必須立即生效於已有元素，而非僅記錄映射），使 LLM 成功生成正確程式碼。

這說明兩個要點：(1) 直接讓 LLM 自行對齊規格不成功——必須顯式提取 LLM 感知到的規格（lifted specification），再系統性比對與原始規格的差異；(2) 讓 LLM 自由生成十個候選對齊規格仍無法修正偏誤——需要設計有效的結構化對齊規則。

3. 方法

Specine 由三個主要組件構成。

3.1 偏誤規格識別（Misaligned Specification Identification）

設計雙代理框架：coder agent 根據輸入規格生成初始程式碼，tester agent 獨立生成測試案例（不依賴初始程式碼以確保客觀性）。合併公開測試案例與 LLM 生成的測試案例後執行，若程式碼無法全部通過則認定規格存在偏誤，啟動後續對齊。若通過則直接輸出最終程式碼。

此步驟的設計理由：若無此鑑別，Specine 將對所有規格執行對齊——對已正確感知的規格強制對齊可能因 LLM 幻覺反而引入錯誤，且增加不必要的時間與 token 消耗。

Tester Agent Prompt 設計：指引生成三類測試案例——基礎測試（正常條件）、邊界測試（極端/異常條件）、大規模測試（可擴展性）。

3.2 規格提取（Specification Lifting）

在識別偏誤規格後，需要分析偏誤的具體細節。但直接比對程式碼（低層次程式語言）與輸入規格（高層次需求描述）存在顯著的抽象層次鴻溝。因此設計規格提取組件，從 LLM 生成的程式碼中顯式提取 LLM 實際感知到的規格。

定義一個專為需求規格設計的 DSL（Domain-Specific Language），包含七個關鍵屬性：

  • Problem Background：程式碼的背景與上下文
  • Functional Requirements：核心功能摘要
  • Input Requirements：輸入型別、格式與約束
  • Output Requirements：輸出型別、格式與約束
  • Test Case Examples：程式碼內含的測試案例
  • External APIs：使用的外部 API/函式庫及其用途
  • Additional Explanation：補充資訊（設計意圖、限制等）

此 DSL 與 IEEE 規格標準一致，確保提取的 lifted specification 全面且有效地呈現 LLM 感知到的規格。Lifter agent 根據初始程式碼、DSL 定義與任務指令生成結構化提取結果。

3.3 規格對齊（Specification Alignment）

核心思路：分析 lifted specification 與輸入規格之間的偏誤成分，然後用預定義的對齊規則修正這些偏誤。

基於軟體需求工程文獻定義 十條對齊規則，對應規格中的不同成分：

  1. Specification Background：補充背景、動機或領域特定知識
  2. Specification Purpose：強調規格的詳細目標或核心任務，防止生成的程式碼偏離所需功能
  3. Key Concepts：識別並解釋規格中的關鍵術語，最小化因概念誤解導致的程式碼錯誤
  4. Input Requirements：強調輸入需求（資料型別、格式、約束）
  5. Output Requirements：強調輸出需求（精度、分隔符、排序規則等）
  6. Examples with Explanations：逐步分析測試案例，說明從輸入到輸出的邏輯
  7. Edge/Corner Cases：LLM 生成三個額外邊界案例
  8. APIs：指定相關的外部 API 或函式庫及其功能
  9. Error Handling Requirements：定義無效輸入時的預期行為（預設值、例外、特殊機制）
  10. Hints or Tips：建議的演算法或資料結構，作為前九條未覆蓋的補充

Aligner Agent：根據輸入規格、lifted specification、十條對齊規則與任務指令，自動分析偏誤或遺漏，選擇一或多條規則生成 aligned ingredients，構成 aligned specification。

逐步貪婪搜尋：每輪迭代生成 aligned specification 並產生新程式碼，以階層式通過率評判——(1) 主通過率：公開測試案例的通過比例（優先，因正確性保證）；(2) 次通過率：LLM 生成測試案例的通過比例。若新程式碼的階層通過率較前一輪提高，則保留本輪對齊成分並繼續迭代；否則捨棄。達到預定義迭代數 N（預設 10）後輸出最高階層通過率的程式碼。

4. 實驗設計

研究問題

  • RQ1：Specine 的有效性與效率 vs state-of-the-art 技術
  • RQ2：超參數（迭代數）對效能的影響
  • RQ3：各主要組件的貢獻（消融實驗）

基準資料集

APPS、APPS-Eval（每題 100+ 額外測試案例）、CodeContests-Raw、CodeContests（~190 額外測試案例）、xCodeEval。不包含 HumanEval/MBPP 等基本資料集，因 LLM 已達 >95% Pass@1。

指標

Pass@1（首次生成即通過所有私有測試案例的比例）、AvgPassRatio（所有問題的私有測試案例平均通過比例）、時間開銷、token 開銷。

對比技術

六個 agent-based（Self-collaboration、MetaGPT、AgentCoder、TGen、FlowGen、PairCoder）與四個 prompt-based（Zero-shot、SCoT、Self-repair、μFiX）。
