4. 語法正確的生成（形式化）

4.1 語法解碼問題：給定文法 G、部分輸出 C_k ∈ L_p(G) 與有限詞彙 V，求 V_k ⊆ V 使得任意 t ∈ V_k 都有 C_k.t ∈ L_p(G)。

4.2 剖析部分輸出：pparse 函數把 C_k 分割為已剖析的終端序列 Λ□ 與 remainder r（定義 5）。accept sequence（定義 7）：終端符序列 Λ1，使 Λ□.Λ1 仍是合法部分句子。accept sequence 越長精度越高但計算越貴；實作用 LR(1) 剖析器高效取得 1、2 長度的序列。

4.3 文法遮罩：定義 pmatch(w, ρ)（字串 w 與正則 ρ 部分匹配：w 的前綴屬 L(ρ)，或 w 可延伸至屬 L(ρ)）——容許「前綴匹配即接受」使 SynCode 對任何長度的 accept sequence 都保守健全（過近似）。dmatch（定義 10）是 pmatch 在 DFA 上的等價概念，可藉由走過一串終端符的 DFA（允許從一個 DFA 的接受狀態跳到下一個 DFA 的起始狀態）遞迴計算。DFA mask store M_α（定義 12）：M_α : Q_Ω × Γ^α → {0,1}^|V|，把「DFA 狀態 × α 個後續終端符」映射到詞彙遮罩，t ∈ set(m) 若 dmatch(t, q, Λ) 成立。離線枚舉所有 DFA 狀態、終端符組合與 token 建表；每個「文法 × tokenizer」組合建一次、快取重用。推論時演算法 2：對每個 Λ ∈ A，以 r 從 Λ 首終端符的 DFA 起始狀態走到 q_r，若 q_r 為活狀態則把 M(q_r, Λ[1:]) 併入遮罩。

4.4 健全性與完備性：定理 1（健全）——對任意長度 d ≥ 1 的 accept sequences，若 C_k.t ∈ L_p(G) 則 t ∈ set(m)：合法 token 絕不會被誤殺。定理 2（完備）——當 accept sequence 長度 d > len(t)（大於詞彙表中 token 的長度；LLM token 通常很短）時，t ∈ set(m) 保證 C_k.t ∈ L_p(G)。注意完備性定理只保證部分輸出合法延伸，不保證生成終止於完整合法輸出（終止性超出定理範圍）。

4.5 實作：採 LR(1) 剖析器——其「立即錯誤偵測」性質使剖析表中對應 shift/reduce 的項目直接給出可接受終端符，計算複雜度 O(|Γ|)；LALR(1) 雖省記憶體但需逐終端符試 reduce，複雜度 O(T_P·|Γ|)；LR(κ)（κ>1）記憶體代價過高。實作聚焦 1、2 長度的 accept sequences（犧牲部分精度、保持健全），預先算好 M_0 與 M_1。

4.6 時間複雜度：每步為 O(T_A + T_P + |Γ|·len(r) + T_∪·|Γ|)；增量 LR(1) 剖析加上 remainder 恆小的假設，可簡化為 O(T_∪·|Γ|)。離線建表成本 O(|Q_Ω|·|V|·|Γ|^α)，實務上每個「文法 × LLM」組合 10 分鐘內完成，屬一次性成本。

4.7 SynCode 框架：Python 實作，內建 JSON、Python、Go 等文法；使用者以 EBNF 提供無歧義 LALR(1)/LR(1) 文法即可支援任意新語言。支援 ignore terminals（註解、空白）；在 Lark 之上自行實作 LR(1) 剖析器生成器與增量剖析（快取剖析器狀態）。非 CFG 片段：以額外機制處理 Python/YAML 的縮排（追蹤下一 token 可接受的縮排並遮罩違規者）與 Go 的自動分號插入；使用者可覆寫特定函數加入自訂規則。目前不支援語意約束（如變數先定義後使用）。

5. 實驗方法

模型：閉源模型（GPT-4 等）不開放 logits，故聚焦開源模型——JSON 用 Llama-2-7B-chat 與 Gemma2-2B-it；SQL 加測 Llama-3.2-1B/3B；程式碼補全用 LLaMA-7B、WizardCoder-1B、CodeGen-350M。資料集：JSON-Mode-Eval（100 題零樣本，附 JSON schema）、Spider text-2-SQL（1034 題分四級難度）、多語言 HumanEval（164 題）與 MBXP（974 題）的 Python/Go 版。文法：Python 文法取自 Lark（520 條產生式、94 個終端符）、Go 由 ANTLR 的 LL(*) 文法轉為 LR(1)（349 條、87 個）、JSON（19 條、12 個）；涵蓋語言的大部分常用特性（Python lambda 等除外——補齊只需工程功夫，不改變技術本身）。基線：Outlines v0.1.1、guidance v0.1.16、llama.cpp v0.3.1、GCD；為公平比較，SynCode 亦採 opportunistic masking 優化（先讓模型出 token、僅在該 token 非法時才算遮罩）。語法錯誤以各語言標準編譯器判定。

6. 實驗結果

6.1 JSON 生成（表 1）

在 JSON-Mode-Eval 100 題上（n_max = 400），SynCode 引導下兩個模型的語法錯誤皆為 0；標準生成則分別有 98%（Llama-2-7B-chat）與 59%（Gemma2-2B-it）的補全語法非法（多為 JSON 前後夾雜自然語言）；明確要求「只輸出 JSON」的提示仍留下 41% 與 59% 的錯誤（未閉合括號、未終結字串等），llama.cpp、Outlines、guidance、GCD 也有同類問題。Schema 驗證準確率：Gemma2-2B-it 由標準生成的 41% 升至 99%（原始提示）／100%（明確提示）；Llama-2-7B-chat 上 SynCode 比 llama.cpp／Outlines／guidance／GCD 分別高 3%／4%／9%／4%（原始提示）與 16%／28%／19%／20%（明確提示）。殘餘 schema 錯誤屬語意層（型別不符、缺欄位、多欄位）。速度：SynCode（3.07 秒/題）快過所有文法導引基線（llama.cpp 21.91、guidance 5.14、Outlines 38.07 秒），甚至快過標準生成——因為約束避免了無關自然語言的多餘 token。（Outlines 在 Gemma2 上較快是因大量輸出空 JSON。）

6.2 SQL 生成（表 2）

Spider 上，SynCode 全面改善執行成功率與執行準確率：Llama-3.2-3B 執行成功率 67.4% → 81.4%、準確率 28.6% → 34.9%；Llama-2-7B-chat 準確率 20.4% → 24.6%。Gemma2-2B-it 即使與「用 regex 從 markdown 標記中抽出 SQL」的加強基線（Standard+）相比，準確率仍略勝（25.4% → 26.3%），且生成 token 數由 221 降到 135、提速 1.7 倍——顯示對「只要查詢、不要解釋」的應用，SynCode 同時改善效率與準確率。

6.3 通用程式語言（GPL）生成（表 3、4）

Python 與 Go 上與標準生成相比（其他基線皆不支援 GPL 文法）：每語言共生成 4154 個樣本，標準生成中 Python 6%、Go 25% 有語法錯誤；SynCode 在多數設定削減逾 90%（平均 96.07%），把語法錯誤壓到總樣本的 1% 以下。Go 錯誤遠多於 Python（訓練資料較少），故 SynCode 對低資源語言尤其有效。殘餘錯誤全部源於 LLM 在 token 上限內未完成程式——SynCode 保證部分程式合法，但不保證收斂到完整程式。功能正確性（pass@1/pass@10）：SynCode 較標準生成有小幅提升（如 LLaMA-7B Go pass@10 8.8% → 8.8%、Python 17.1% → 18.9%）——語法修正對邏輯正確性有輕微助益。

6.4 Mask store 開銷（表 5）

Llama-2-7B-chat × JSON 的 mask store 建表 113.72 秒、佔 181 MB；Python/Go 文法 × 各模型建表約 380–600 秒、記憶體低於 2 GB。屬一次性成本，之後載入重用即可。
