7. 相關工作

改善形式語言生成的另兩條路——微調/提示工程（無形式保證）與修改架構/tokenization（表現尚不及主流 LLM）——皆與本文的約束解碼互補。表 6 從 Regex/CFG 支援、是否預計算、是否支援 GPL、最大文法規模、輸入格式比較各方法：lmql、guidance、Outlines、PICARD、Synchromesh、llama.cpp、GCD、Domino 最大都只支援 50–100 條規則的文法且皆不支援 GPL；SynCode 支援 500+ 條且唯一支援 GPL。重點對比：

  • guidance／lmql：模板式受控生成；guidance 用 Earley 剖析做 CFG 約束，但每步檢查整個詞彙表、開銷高，且按機率序迭代詞彙表的作法無法與任意解碼策略組合。
  • Outlines：原為正則導引，後擴至文法導引；推論時用增量 LALR 剖析器取可接受終端符、把各終端符正則取聯集再即時轉 DFA、再迭代全詞彙表找合法 token——SynCode 在 JSON 上勝過它，且它不支援大型 GPL 文法。
  • llama.cpp：以 N 個堆疊模擬非確定性下推自動機；C++ 實作省了些剖析開銷但演算法上低效（推論時仍需遍歷整個詞彙表並更新堆疊），非標準文法語法限制其只能用於 JSON 等簡單文法。
  • Synchromesh：微軟閉源工具，同樣在生成期間做正則聯集、且用非增量剖析器；額外含語意約束（Constrained Semantic Decoding）與範例選擇，只針對 DSL。
  • PICARD：綁定 beam search 的特定解碼策略（維持候選 beam、剔除違法者），增量 monadic 剖析器專為 SQL 打造；引入新文法需大量工程（無文法定義語言）。
  • Domino：最接近的並行工作——也預計算（NFA 狀態 × 前綴樹）結構。關鍵差異：Domino 採欠近似（只允許與剖析器前瞻對齊的 token），需無限前瞻才健全；SynCode 採保守過近似（前綴匹配即允許），任何前瞻長度都健全。Domino 目前最大支援 70 條規則的簡化 C 文法（約 25% 開銷），程式碼未公開無法實測比較。
  • 固定 schema 生成：固定 schema 下許多步驟只有單一或少數合法選擇，可跳過生成或用投機解碼加速；SynCode 專注於 schema 不固定的 CFG 導引生成，此時投機等技巧無用武之地。

8. 結論

既有語法導引方法慢且受限。SynCode 在解碼期間增量剖析部分輸出、計算 remainder 與 accept sequences，再結合預計算的 DFA mask store 產生遮罩，把 LLM 詞彙表約束到語法合法的 token。在 JSON、SQL、Python、Go 上的評估顯示：JSON 語法錯誤歸零且 schema 驗證勝過基線；Python/Go 語法錯誤平均削減 96.07%。此方法為真實應用中更高效、更高品質的結構化 LLM 生成鋪路。
