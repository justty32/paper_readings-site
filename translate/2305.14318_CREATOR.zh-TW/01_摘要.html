摘要

LLM 在使用工具（tool utilization）上已有長足進展，但其能力受限於 API 可得性與隱式推理（implicit reasoning）的不穩定——尤其當規劃與執行同時牽涉時。為克服這些限制，我們提出 CREATOR：一個讓 LLM 以文件（documentation）與程式碼實作（code realization）創造自己的工具的新框架。CREATOR 把抽象的工具創造與具體的決策執行解耦（disentangle），從而提升表現。在 MATH（高難度數學競賽題）與 TabMWP（多樣表格內容）上，CREATOR 超越既有 chain-of-thought（CoT）、program-of-thought（PoT）與 tool-using 基線。我們並推出 Creation Challenge 資料集（2K 道多樣問題），凸顯 LLM 工具創造能力的必要性與益處。進一步研究顯示：讓 LLM 當工具創造者可促進知識遷移（knowledge transfer），且 LLM 展現不同層級的工具創造能力。程式碼與資料已開源（github.com/qiancheng0/CREATOR）。

1. 引言

GPT-3、Codex、PaLM、LLaMA、ChatGPT、GPT-4 等 LLM 在 in-context learning、程式碼生成等方面能力驚人，但仍有侷限：無法處理最新資訊、無法給出精確數學結果、長鏈邏輯推理不穩。研究者遂為 LLM 配備外部工具（QA 系統、搜尋引擎、GitHub 資源、HuggingFace 模型、程式碼直譯器等）以減輕記憶負擔、增強專業能力。

然而工具增強的 LLM 仍面臨三項挑戰：

  1. 範圍受限（limitation in scope）：現有方法聚焦於少量工具，面對新問題型態難以找到合適的現成工具。
  2. 推理脆弱（fragility in reasoning）：任務常很複雜，逐例臨場推理（reasoning on the fly case-by-case）易受隨機錯誤影響；人類則能從多個相似問題中找出穩健的共通性獲益。
  3. 錯誤處理不足（insufficiency in error-handling）：現有工具使用管線缺乏自動且針對性的錯誤處理，準確性與穩健性有待改進。

本文不把 LLM 當工具的使用者，而是賦能其成為工具的創造者。CREATOR 框架含四階段：

  • Creation（創造）：基於問題，透過抽象推理創造出普遍適用的工具（含文件與實作）。
  • Decision（決策）：面對可用工具，決定何時、如何用它們解題。
  • Execution（執行）：執行程式，套用所選工具解題。
  • Rectification（矯正）：依執行結果修改工具與決策。

此設計分別回應三挑戰：(1) 讓 LLM 創造通用性、可復用性、多樣性更高的工具，而非仰賴少量給定 API；(2) 卸載 LLM 認知負擔，把抽象推理（創造可泛化工具）與具體推理（帶細節的決策）解耦；(3) 以程式碼為工具創造的媒介——程式碼對錯誤更敏感，可依錯誤回溯（error tracebacks）自動矯正工具與決策。

實驗上，基於 ChatGPT 的 CREATOR 在 MATH 與 TabMWP 分別達 59.7% 與 94.7% 平均準確率，大幅超越 CoT、PoT 與 tool-using 基線。由於既有基準並非為評估工具創造而設計，我們另建 Creation Challenge——由現有工具或程式套件不足以解決的新穎難題組成。我們並以實驗證明工具創造促進「共享核心知識但情境各異」的相似查詢之間的知識遷移，且以案例研究呈現 LLM 不同層級的工具創造能力。

2. 相關工作

  • 大型語言模型：CoT、instruction-following 等提示方法引導 LLM 解題並對齊人類期望；本文把它們納入框架並作為基線。
  • 語言模型的工具使用（tool using）：既有研究以 scratch pad、搜尋引擎、QA 系統、計算器等增強 LLM，近期更把工具使用整合成「任務規劃—工具呼叫—結果合成」的管線。本文更進一步：讓 LLM 創造工具而非只依賴既有工具。
  • 以程式推理與執行：PoT（Chen et al., 2022）、PAL（Gao et al., 2022）等展示程式碼生成能提升數學/符號/演算法基準表現，但這些做法是線性邏輯的 code-based CoT，不產出可復用、可測試的強化工具。CREATOR 中程式碼是工具創造的媒介而非外部工具；相較 PoT，我們增設工具創造階段、程式碼矯正階段，並解耦複雜推理中的邏輯。

表 1（方法對照，擇要）：CoT 無創造/無工具/無程式碼/線性推理；PoT 用程式碼但線性、不可復用；Tool Use 用工具與程式碼但線性；CREATOR：創造工具＋使用工具＋程式碼＋強調可復用性＋非線性推理。

3. CREATOR 的設計

先前 CoT/PoT 主要以線性推理解題，解題過程缺乏可復用性；CREATOR 創造的工具可遷移到其他查詢，矯正階段更使推理過程非線性。

3.1 創造階段（Creation Stage）

實作：以帶示範例的指令明確要求 LLM 針對問題創造工具與文件。提示格式為「###Instruction [INSTRUCTION]\n [EXAMPLE 1]\n [EXAMPLE 2]…」，每個示範例遵循「### Question [QST]\n ### Tool [TOOL]」，[TOOL] 內含以程式碼註解呈現的文件。示範例事先固定：從訓練集隨機抽取子集、讓 LLM 生成工具後人工修正錯誤、移除冗贅說明後定案。示範例不需與測試查詢語意相似——其目的只是激發 LLM 創造力並規範輸出格式。

抽象推理能力：工具創造階段的核心，是觸發 LLM 用抽象思考減輕後續階段的推理負擔。創造工具時，LLM 實質上是在對問題類型做抽象——聚焦問題的內在特徵而非具體數值細節。例如面對三元方程組問題，LLM 只需辨識問題本質並創造「解三元方程組」的工具，完全不管數值細節與被查詢的特定表達式。

3.2 決策階段（Decision Stage）

實作：同樣以示範例指導 LLM 決定如何使用工具，示範例格式為「### Question [QST]\n ### Tool [TOOL]\n ### Solution [SOL]」，[SOL] 是 LLM 以程式碼形式呼叫工具的決策，並被要求以 print(...) 印出最終答案與重要資訊，確保後續階段能輕易擷取答案。

具體推理能力：決策階段要求 LLM 對解題的規則與細節投以縝密注意——即具體推理。例如工具回傳的解還需加總才是最終答案：LLM 必須理解工具輸出、將之連結到特定查詢，才能做出明智決策。把創造與決策分開，CREATOR 解耦了 LLM 兩個階段的能力，讓不同面向的知識更順暢地被引出，提升任務表現。

3.3 執行階段（Execution Stage）

以前兩階段的資訊，借程式碼直譯器執行工具。此階段不使用 LLM：把創造的工具（封裝為函數）與 LLM 的決策（呼叫該函數）串接成一個完整程式碼區塊執行。執行期間截獲印出的輸出、或（在子行程中攔截的）錯誤訊息，作為後續階段判斷「已得答案」或「需要矯正」的輸入。

3.4 矯正階段（Rectification Stage）

實作：依傳入資訊二擇一。若發生錯誤，以示範例提示 LLM 矯正——示範例格式為「### Question [QST]\n ### Original [ORI]\n ### Error [ERR]\n ### Rectification [REC]」：[ORI] 為原工具實作與呼叫決策，[ERR] 為錯誤回溯，[REC] 為對錯誤的自然語言推理串接矯正後的程式碼。若執行成功，則從截獲的輸出擷取答案、與標準答案比對計分。

意義：錯誤回溯提供 LLM 定位錯因的關鍵資訊，使其能從先前錯誤中恢復、調整推理、再次嘗試。後續實驗顯示納入矯正顯著提升表現，也展現 LLM 辨識誤解並自我修正的能力。
