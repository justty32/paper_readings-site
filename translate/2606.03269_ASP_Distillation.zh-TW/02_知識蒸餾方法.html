3 知識蒸餾方法

我們的 VQA 方法從針對特定資料集建構的初始 ASP 理論開始。給定影像與問題的正確表示，理論始終能計算正確答案。若資料集以某種方式擴展使理論不再能正確回答，就需要修改或添加規則來處理新範例。為此，我們提出一個基於 LLM 的系統來提供自動化支援。

目標：一個推理模組管理理論並能識別自己能處理哪些範例；若某範例無法解決，則更新理論。我們的方法稱為「宣告式知識蒸餾」——從 LLM 蒸餾知識，並以 ASP 規則表示。方法涉及不同提示策略來獲取規則，並使用 ASP 求解器回饋來修正 LLM 的錯誤答案。

3.1 規則蒸餾演算法（Alg. 1）

假設我們想擴展初始 ASP 理論 T，並有一個蒸餾套件（distillation suite）包含新的 VQA 範例。每個範例為三元組 (s, q, a)：場景描述 s（ASP 事實）、問題描述 q（ASP 事實）、預期答案 a（ASP 事實）。

演算法流程：

  1. 對蒸餾套件中的每個範例逐一迭代。
  2. 呼叫 ASP 求解器檢查預期答案是否能從 T + s + q 推導──若能則跳過。
  3. 否則，呼叫 LLM 產生候選規則（候選池 = multi-prompting + CoT_simple + CoT_complex 三路結果合併）。
  4. 對每個候選規則逐一檢查：
    • (i) 語法檢查：若求解器回報語法錯誤，將錯誤訊息傳給 LLM 要求修正（syntactic mending）。
    • (ii) 語意檢查：若求解器輸出不等於預期答案，將正確與錯誤答案傳給 LLM 要求更新（semantic mending）。
    • (iii) 迴歸測試：將新規則加入 T 後，測試所有過往已處理範例是否仍正確。
  5. 僅在全部通過後才接受該規則延伸、將當前範例加入迴歸清單，並跳到下一個範例。

三類錯誤：

  • (i) 語法錯誤：模型產生無效的 ASP 語法，常為幻覺數學符號（如 ∀、∈），求解器不支援。
  • (ii) 語意錯誤：規則語法正確但未能對當前範例產生正確答案。
  • (iii) 迴歸錯誤：規則對當前範例有效但與先前蒸餾的規則產生語義衝突。

3.2 提示設計

所有提示共用一個 preprompt，再根據目的（產生新規則或修補）添加特定指令。提示設計力求清晰可讀而非效能最佳化。

3.2.1 Preprompt（預提示）

包含六個部分：

  1. 語境化：描述 VQA 設定，說明場景與問題已解析為 ASP 事實。
  2. 邏輯表示：描述 ASP 語法（規則、頭部/體部、變數、否定等）。
  3. 場景與問題表示（資料集客製）：解釋場景與問題的 ASP 事實格式並舉例。
  4. 答案表示（資料集客製）：說明答案格式（ans(X)）。
  5. 邏輯理論（資料集客製）：展示初始理論 T。
  6. 任務說明：解釋 LLM 將接收的輸入與預期回應。

轉移到新資料集時，僅需手動調整場景表示、問題表示與答案表示三個部分，其餘結構靜態不變。

3.2.2 多重提示（Multi-prompting）

要求 LLM 一次產生 N 個（預設 5 個）不同解決方案，以 ### 分隔。優點是一次 LLM 呼叫獲得多個候選，增加找到正確解的機率而不增加呼叫次數。

3.2.3 思維鏈（Chain-of-Thought）

兩種版本：(i) 簡單版——逐步使用理論中的謂詞展示如何到達正確解，每行一個謂詞；(ii) 複雜版——更詳細的結構化四步驟：理解問題→分解領域知識→制定 if-then 語句→構造邏輯規則。

3.2.4 規則修補提示（Mending Prompts）

語法修補：將求解器錯誤訊息傳給 LLM，要求修正語法。語意修補：說明規則產生錯誤答案、給出正確答案與求解器實際輸出，要求更新規則。
