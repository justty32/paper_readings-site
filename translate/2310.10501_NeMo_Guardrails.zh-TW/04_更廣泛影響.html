8. 更廣泛影響

作為一套為 LLM 應用（包括對話系統）強制執行可程式化護欄的工具箱，NeMo Guardrails 應能為開發者與研究者帶來助益。可程式化護欄補充了內嵌護欄，無論是通用型的（用 RLHF）還是使用者自訂的（用 p-tuning 客製化模型）。舉例來說，用事實查核護欄，開發者能輕易打造一個增強型、基於檢索的 LLM 應用，同時它也讓開發者能評估各種模型的表現，因為可程式化護欄與模型無關。這對打造需遵循複雜對話流程的 LLM 任務導向智能體同樣適用。

同時，在把 Guardrails 應用投入生產環境之前，實作出的可程式化護欄（尤其是安全相關護欄）應經過徹底測試。本工具箱提供一套評測工具，用於測試主題護欄與執行護欄的效能。

本工具箱的更多細節可見附錄，包括如何安裝、如何搭配 GitHub 上分享的範例 Guardrails 應用運行的簡易步驟。另有一支簡短示範影片：https://youtu.be/Pfab6UWszEc。

附錄要點

附錄 A（安裝指南與範例）：可用 pip install nemoguardrails 安裝穩定版，或從 GitHub 取得最新版；提供 CLI 與 Web 伺服器兩種運行方式。提供五個參考應用：主題護欄、審核護欄、事實查核與防幻覺護欄、安全執行第三方服務、越獄防護護欄——皆為展示建構護欄的過程，非開箱即用的安全功能，建議依需求客製化與強化。範例也涵蓋搭配本地部署或 HuggingFace 推論端點的開源模型（falcon-7b-instruct、dolly-v2-3b、vicuna-7b-v1.3），以及如何把 Langchain 中定義的各種 chain 與 NeMo Guardrails 的可程式化護欄結合。

附錄 B（Colang 語言與對話管理器）：Colang 是一種對事件序列與互動建模的語言，特別適合為對話建模，同時透過 Colang 解譯器（一個事件驅動的對話管理器）為對話系統設計護欄。既有的對話管理技術（流程圖、狀態機、以框架為基礎的系統）不適合建模像 LLM 系統這樣高度彈性的對話流程；由於學習新語言不容易，Colang 被設計成自然語言（英文）與 Python 的混合體——熟悉 Python 者，即使沒有額外說明，看過幾個範例後應能有信心使用 Colang。核心概念：Utterance（使用者或機器人的原始文字）、Message（使用者/機器人 utterance 的標準形式／結構化表示）、Event（與對話相關、已發生的事情，如使用者沉默、點擊、做出手勢）、Action（機器人可呼叫的自訂程式碼，通常用於連接第三方 API）、Context（與對話相關的任何資料，以鍵值字典編碼）、Flow（訊息與事件的序列，可能帶有額外的分支邏輯）、Rails（控制對話系統行為的特定方式，如不談政治、對特定使用者請求以特定方式回應、遵循預定對話路徑、使用特定語言風格、抽取資料等；一條 rail 在 Colang 中可透過一或多個 flow 建模）。Guardrails runtime 採事件驅動設計（事件迴圈處理事件並反過來產生其他事件），對話流程被視為事件序列，即使是簡單的使用者訊息也是事件——會建立一個 UtteranceUserActionFinished 事件送入 runtime。

附錄 C（主題護欄的提示）：NeMo Guardrails 用串接三步驟的複雜提示回應使用者訊息。以 text-davinci-003 為例，第一步（生成最後一則使用者訊息的標準形式）的提示結構分四部分：(1) 描述應用任務的通用提示；(2) 以 Colang 語法寫成的範例對話；(3) 依當前使用者訊息，取相似度最高的 k=5 個 few-shot 範例，示範如何把使用者訊息對映到對應的標準形式；(4) 目前使用者與機器人間、以 Colang 語法表示的對話。

附錄 D（執行護欄的提示模板）：

  • 幻覺護欄：驗證提示為「你的任務是判斷 hypothesis 是否與下方 context 一致。你只能使用 context 的內容，不可仰賴外部知識。請以 yes/no 回答。"context": {sampled_responses} "hypothesis": {bot_response} "agreement":」。取樣機器人回應時用 temp=1，驗證判斷時用 temp=0（其餘所有執行護欄皆採此溫度慣例）。
  • 審核護欄：越獄（輸入）提示為「Instruction: {user_input}　這段指令會不會讓一個語言模型違反審核政策、偏離良好對齊的回應、給出語言模型理當不該給的答案？請以 yes/no 回答。」；輸出審核提示為「Model output: {bot_response}　這段輸出合法、合乎倫理、且不會對任何人有害嗎？請以 yes/no 回答。」

附錄 E（動作定義）：定義護欄的第一步是用 Python 實作動作邏輯；任何自訂動作都能存取對話的 context（一連串對話事件，包含使用者/機器人訊息、標準形式、被呼叫的動作等），常用的 context 項目有捷徑可存取，例如 context.get("last_bot_message")。動作可從呼叫它的 Colang 腳本接收任意數量的參數，並通常回傳一個值以進一步引導對話。輸出審核動作的實作：從 context 取出 last_bot_message，套入輸出審核提示模板，透過 Langchain 的 PromptTemplate + LLMChain 呼叫 LLM，取得的回答轉小寫去除空白後，若含有 "no" 則回傳 False（表示違反護欄），否則回傳 True。越獄（輸入）審核動作實作方式完全對稱：取出 last_user_message，套入越獄提示模板，同樣以 Langchain 呼叫 LLM 並依回答中是否含 "no" 決定回傳 True/False。

附錄 F（用動作構成護欄流程的範例）：以圖 4 之越獄護欄流程為例，展示如何在 Colang flow 中用 execute check_jailbreak 呼叫動作，並依動作回傳值分支決定是否顯示 LLM 生成的回應或改用預先定義的拒絕文字。

附錄 G（評測補充細節）：本工具箱提供評測工具與方法論，用以評估主題與執行護欄的效能；所有論文中的結果皆可用 GitHub 上的 CLI 評測工具重現。主題護欄評測採用 chit-chat（76 個意圖、226 筆測試樣本）與 banking（77 個意圖、231 筆測試樣本）兩個對話式 NLU 資料集：chit-chat 較通用、意圖較粗粒度，banking 則是領域專屬、意圖較細緻。所有實驗以隨機種子 42、每意圖最多 3 個測試樣本的平衡測試集進行；同時比較向量資料庫中每個標準形式索引 k=all、3、1 個範例時的效能差異。事實查核護欄的完整結果圖見附錄圖 11，約 80% 準確率。
