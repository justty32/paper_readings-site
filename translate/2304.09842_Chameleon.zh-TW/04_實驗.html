5. 實驗

在 ScienceQA 與 TabMWP 上評估 Chameleon 的效果與適應性，實驗細節見附錄 A.2。

5.1 實驗結果

ScienceQA（Table 3）：以 ChatGPT 為底層 LLM，Chameleon 達 79.93% 準確率，較 CoT 提示的 ChatGPT 提升 1.62%；Chameleon 可視為 CoT 的一般化形式（CoT 對應計畫恰為「Solution Generator, Answer Generator」），並受益於 Knowledge Retrieval、Bing Search、Image Captioner、Text Detector 等額外工具。以 GPT-4 為底層，Chameleon 達 86.54% 準確率，較 GPT-4 CoT 提升 2.55%、較 GPT-3 CoT 提升 11.37%，在少樣本設定下創新 SOTA。

TabMWP（Table 4）：與微調模型及少樣本模型相比均見顯著提升。CoT 與 Program-of-Thought（PoT）皆可視為 Chameleon 的特例：CoT 除 Solution/Answer Generator 外不使用任何工具，PoT 僅依賴 Program Generator/Executor 等符號程式工具。Chameleon(ChatGPT) 較 ChatGPT CoT 與 ChatGPT PoT 分別提升 11.25% 與 3.79%，凸顯豐富工具集的優勢。搭配 GPT-4，Chameleon 再增益 5.50%，達 98.78% 準確率——超越已發表最佳模型 Codex PoT-SC 17.0%，超越人類表現 8.56%。

5.2 質性分析

工具使用規劃：ChatGPT 與 GPT-4 展現不同的規劃行為。ChatGPT 對特定工具有強烈偏好，深受 in-context 範例影響——例如在 ScienceQA 上 72% 查詢呼叫 Knowledge Retrieval，卻僅 3% 呼叫 Bing Search；在 TabMWP 上高度依賴 Row Lookup（47%），較少呼叫 Column Lookup（4%）。GPT-4 的工具選擇則更客觀理性：在 ScienceQA 上更常呼叫 Knowledge Retrieval（81% vs 72%）、也更常呼叫 Bing Search（11% vs 3%）；GPT-4 能依工具使用描述，穩定地同時呼叫 Query Generator 與 Bing Search，ChatGPT 則不具備此推理能力。

關鍵模組消融（Table 5）：以 ChatGPT 為底層、500 筆測試樣本，逐一停用生成程式中的關鍵模組並觀察準確率下降。Knowledge Retrieval 在兩任務中皆是關鍵（ScienceQA −7.8%、TabMWP −2.2%）；ScienceQA 的領域專屬工具（搜尋引擎、視覺模型）與 TabMWP 的程式工具同樣重要（Text Detector −8.4%、Bing Search −7.4%、Image Captioner −6.0%；Program Generator −7.4%）。

模組轉移：Figure 7、8 視覺化 Chameleon(GPT-4) 在兩任務上生成程式的模組轉移圖（依測試集上觀察到的工具轉移機率計算），顯示 GPT-4 規劃器能在少樣本下對工具排序做出合理決策——例如 ScienceQA 上常見「僅用 Knowledge Retrieval」或「僅用 Bing Search」而非兩者並用；TabMWP 上主要有兩種模式：走 Solution Generator，或走 Program Generator→Verifier→Executor。

5.3 案例研究

ScienceQA 視覺化範例：如 Figure 1 所示，Chameleon(GPT-4) 能依不同輸入查詢生成組合不同工具的程式並依序執行以得到準確回應——例如問「這個推力的方向為何？」時呼叫圖像字幕模型擷取圖像語意、再用知識檢索模型收集多模態推理所需的背景知識；問廣告訴求時規劃器推斷需要文字偵測工具理解廣告脈絡；問動物皮膚適應力的科學術語問題時，規劃器選擇呼叫 Bing 搜尋引擎存取領域知識。

TabMWP 視覺化範例：如 Figure 2，稅務表格問題中 Chameleon 先呼叫知識檢索模型回憶稅務基礎知識，再把表格轉為更易讀的自然語言描述，最後靠程式輔助工具做精確運算；另一例中系統生成的 Python 程式碼與知識檢索模型提供的背景知識高度吻合；第三例需在大型表格脈絡中定位儲存格，Chameleon 呼叫 Row Lookup 模型精準定位相關列，再以 LLM 生成語言解答，而非依賴程式工具。

失敗案例與限制：附錄 Table 5–24 列出 Chameleon(GPT-4) 的失敗範例。錯誤回應可能源自現有模組本身的限制，或規劃器生成的次優程式；模組庫也可能缺乏處理特定能力所需的工具。未來方向包括升級模組與規劃器、或擴充模組庫以支援更廣泛能力。

5.4 錯誤分析

為檢視底層 LLM 的錯誤來源、理解 Chameleon 如何從不同面向減少錯誤，從 ChatGPT 在 ScienceQA 上的錯誤中選取 50 例作評估集，分類統計 ChatGPT、Chameleon(ChatGPT)、Chameleon(GPT-4) 各類錯誤數量（Figure 6：圖像理解／知識理解／解答生成三類）。結果顯示 Chameleon 大幅減少錯誤數：藉圖像字幕與知識檢索工具，圖像理解類錯誤由 ChatGPT 的 32 例分別降至 Chameleon(ChatGPT) 的 10 例與 Chameleon(GPT-4) 的 19 例；知識理解類錯誤由 37 例分別降至 6 例與 3 例。受益於工具的循序執行，解答生成類錯誤也顯著減少；此外 GPT-4 的任務規劃能力大幅優於 ChatGPT。

6. 結論

本文提出即插即用組合式推理框架 Chameleon，藉以即插即用方式擴增外部工具來彌補現有 LLM 的固有限制。該方法運用多樣工具集，在 ScienceQA 與 TabMWP 兩項高難度基準上展現優異的適應性與有效性；相較現有 SOTA 模型取得顯著準確率提升，展示了 Chameleon 應對跨領域真實查詢的潛力。

附錄要點

  • 附錄 A.1（既有工具增強 LLM 綜述）：概述以外部工具／資源、即插即用模組化方法強化 LLM 的研究方向，含 WebGPT（網頁搜尋/知識）、Codex 系工作（程式化數學推理）、ViperGPT／Visual ChatGPT／VisProg／HuggingGPT（整合視覺基礎模型做視覺推理）。
  • 附錄 A.2（實驗細節）：規劃器統一用 gpt-3.5-turbo（ChatGPT）與 gpt-4 引擎，程式最大長度 128、溫度 0（最確定性生成）；各 LLM 型模組預設 4 則 in-context 示範、溫度 0、最多 512 token；Image Captioner 用 nlpconnect/vit-gpt2-image-captioning、Text Detector 用 EasyOCR、Bing Search 呼叫 Bing Search API 回傳前三筆結果。Row/Column Lookup 分別在表格列數/欄數與儲存格數超過門檻時才啟用（以加速推論）。
  • 附錄 A.3（生成程式統計，Table 7）：GPT-4 生成的獨特程式種類遠少於 ChatGPT（ScienceQA 11 vs 14、TabMWP 19 vs 28），顯示 GPT-4 規劃更一致；此現象與 GPT-4 在長脈絡理解、指令對齊、高階推理上的既有優勢一致。
  • 附錄 B（限制）：尚未在 ScienceQA/TabMWP 之外驗證更廣泛任務與領域的適應性；規劃器品質可能左右整體效能，且系統設計上計畫一次性生成、模組執行過程中無 re-planning 機制；假設模組列表與描述能放進 LLM 脈絡窗，隨任務複雜度與模組庫擴大，可能面臨脈絡長度限制或運算需求上升。
  • 附錄 C（廣泛影響）：正面影響包括為教育、金融、決策支援等領域提供更準確的複雜多模態任務回應，且免訓練的程式合成方式有望讓非專業使用者也能運用 AI；潛在負面影響包括資料來源/外部工具未經妥善篩選時的錯誤資訊與隱私疑慮，以及過度依賴系統自主性可能削弱使用者的批判思考或取代部分工作職能，作者主張以資料/工具的嚴謹篩選、使用者資料保護、以及把系統自主性定位為「輔助而非取代人類」來緩解上述風險。
