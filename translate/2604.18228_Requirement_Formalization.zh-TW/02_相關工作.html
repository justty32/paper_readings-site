2. 相關工作

從非形式規格進行需求形式化：既有綜述整理了從自然語言（NL）需求生成形式規格的（半）自動化方法，涵蓋 NL、本體論式領域建模與 LLM，並討論文獻中已辨識的關鍵挑戰，包括語意模糊、缺乏 ground-truth 資料集、工具互通性有限、跨產物的可追溯性，以及可解釋性與使用者信任等疑慮。近期工作愈來愈多利用 LLM 直接翻譯成時序邏輯：例如有工作以端到端與兩步驟管線從軟體文件生成時序邏輯（TL）規格，但回報了規格過度簡化與捏造的問題；亦有開源框架 nl2spec 經 LLM 把非結構化 NL 需求翻成 TL 陳述句，或專注於自動轉成計算樹邏輯（CTL）。

另有幾項工作引入中介表示法以結構化翻譯過程：例如以 LLM 把非形式需求映射成類 JSON 語言 OnionL，再以規則式技術翻成線性時序邏輯（LTL）；或把 NL 需求轉成屬性規格模式（PSP），這種中介形式論可支援翻譯到多種目標邏輯。除時序邏輯生成外，亦有工作以 LLM 為基礎的技術，在多種程式語言中合成前置/後置條件註解；相關研究也探討形式定理陳述與證明的生成，值得注意的是自動形式化（autoformalization）這條工作。然而，這些方法雖處理生成形式產物的正確性或合理性，卻未明確評估其與原始非形式規格之間的一致性。

相較於規則式需求萃取或設計來導出可驗證屬性的自然語言處理（NLP）管線，以 LLM 為基礎的方法提供更高的彈性與可攜性：傳統方法往往需針對每個領域、建模語言或驗證框架大幅客製化，而本文提出的方法論只需調整提示指令與提供給 LLM 的文字範例，無需重新設計萃取規則或重新訓練專用模型，即可以極低成本調適，使此管線成為彌合非形式系統描述與形式、具語意意義的驗證屬性之間鴻溝的實用且可擴充方案。

LLM 輔助需求工程：以 LLM 輔助軟體工程是學界與業界皆重視的主題。一致性檢查長久以來是需求工程的核心議題，而 LLM 近期擴展了此方法論版圖：有綜述指出「多數研究聚焦於用 LLM 做需求萃取與驗證（validation），而非缺陷偵測與分類」，其中 validation 指評估「需求是否準確反映利害關係人意圖」，但此意義下的 validation 通常不含檢驗萃取需求是否與給定文字系統規格保持一致；被歸類為「缺陷偵測與分類」的工作同樣忽略此面向，這些研究主要聚焦於需求之間的不一致、單一需求內的邏輯瑕疵，或違反撰寫最佳實務等問題。

例如有工作處理⑴依安全性、效能、可攜性等類別分類，⑵偵測模糊或不符需求撰寫準則等缺陷，以及⑶辨識需求間衝突；另有工作檢視大型工業需求集中的模糊性、需求間不一致與不完整性，或以 LLM 作為外部知識來源偵測 NL 需求中的不完整性；亦有工作專注於模式分類與翻成受更嚴格文法約束的結構化英語。最後，也有工作探討需求之間的矛盾偵測，前者結合形式推理的決策樹框架與 LLM，後者則生成基於 SMT 的命令式程式碼檢查器。

雖然既有方法著重語法正確性、形式良構性，或成功翻譯成驗證產物，但對於評估生成的形式屬性是否忠實捕捉原始非形式規格的意圖，支援有限。明確評估此種語意一致性，正是本文工作的核心目標。

3. 預備知識

LLM 與少樣本學習：LLM 是基於大量資料訓練的自迴歸機率式文字生成模型，建立在以 self-attention 機制處理文字 token 序列的 Transformer 架構上。作為自迴歸模型，LLM 依當前脈絡與先前已生成的 token，逐一預測下個最可能的 token；被提示（prompt）後即生成完成內容（即回應）。為明確引導此生成過程，常使用系統提示（system prompt）定義整體人設、指定操作邊界，並規範 LLM 在互動過程中須遵循的一般規則。此外，已發展出多種結構化提示的方法（提示策略），其中最常用的是少樣本學習（few-shot learning，又稱 in-context learning）：把輸入-輸出範例（即「shots」）連同任務指示一併納入提示，有助 LLM 辨識文字模式，並釐清期望的輸入/輸出格式。

UPPAAL SMC：具隨機特性的形式模型適合做統計模型檢驗（SMC），可透過 UPPAAL 工具進行。SMC 對具隨機特性的形式模型 M 執行一組「跑（run）」，套用統計技術以估計所欲屬性成立的機率。UPPAAL 具體計算表達式 ℙ_M(ψ) 之值，以估計屬性 ψ 在模型 M 上成立的機率。屬性 ψ 以**度量區間時序邏輯（Metric Interval Temporal Logic, MITL）**表達，這是一種線性時序邏輯，可在具時序的狀態序列上解釋，能捕捉即時性約束。特別是，MITL 包含運算子 ◆[a,b]（a<b），公式 ◆[a,b]φ 表示屬性 φ 在未來某個不早於 a、不晚於 b 個時間單位的時刻成立（即「最終 eventually」）。具體而言，ℙ_M(ψ) 中的 ψ 形如 ◆≤τ ap（◆≤τ 是 ◆[0,τ] 的縮寫），其中 ap∈AP 是一個原子命題；公式 ◆≤τ ap 若在模型 M 某一跑的第一時刻成立，代表 ap 在時刻 0 起算的 τ 個時間單位內成立。在 UPPAAL SMC 查詢語言中，ℙ_M(◆≤τ ap) 表示為 P[<=τ](<> ap)，其中 ap 是一個原子命題或其合取/析取式。

4. 方法論

本節詳述所提出的代理式管線，用以彌合非形式 NL 規格與語意對齊的形式屬性之間的鴻溝。方法分成三個獨立階段，以確保可追溯性、緩解整體複雜度並提升 LLM 的表現。

管線如下（本文以綠色標示所探討之部分：非形式 NL 規格 → Stage 1 需求萃取 → Stage 2 可驗證性分類 → Stage 3 形式翻譯 → 驗證就緒屬性 → 〔連同形式模型〕→ 模型檢驗），其中 Stage 1、Stage 2、Stage 3 各對應一個單一代理 LLM 步驟。

Stage 1：需求萃取。第一階段把非結構化非形式規格轉成一組結構化的**原子（atomic）**自然語言需求，每條配一識別碼，孤立出系統描述中蘊含的功能與安全約束，並使用標準需求句式（如「The system must…」「The human agent has to…」「The robot shall…」）。以 LLM 辨識規格中描述的相關實體、系統動態與操作約束；萃取出的需求被正規化並結構化為機器可讀的表示形式（即 JSON 格式），使其能在管線後續階段被系統化處理。

Stage 2：可驗證性分類。第二階段過濾掉那些無法在目標形式模型語意邊界內表達的需求。並非所有萃取出的需求都能在所考慮模型的限制下被形式驗證。為執行此分類，我們使用 LLM——因其在不同領域間的可調適性有利於重用，且以其本質，能執行基於語意評估的分類任務。得益於這第二道分類階段，第一階段的 LLM 得以只專注於生成一份完整的需求集合，而不因直接考量指定形式模型的限制而產生偏誤。在此階段，每條需求會針對系統的建模假設與可觀測變數進行分析；指涉不可觀測屬性、定性設計意圖，或模型外部現象的需求會被剔除，剩下的需求構成可被形式分析的子集。

Stage 3：形式翻譯。最終階段把經過濾的需求翻譯成與目標形式模型相容的形式驗證查詢。此階段的目標是彌合天生模糊的自然語言規格與形式驗證產物之間的鴻溝。得益於 LLM 依精確文法（以系統提示中的 BNF 格式提供）生成文字的能力，每條需求被翻譯成可在系統模型上求值的對應時序屬性；生成的查詢代表可直接透過模型檢驗分析的形式化約束，為自然語言需求中原本模糊的語意提供形式化。
