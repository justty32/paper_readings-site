論文／訪談原始來源

Evo-Harness: Context-to-Harness Skill Compilation for Self-Evolving Agents

摘要與第 1 節：問題

從經驗學習是打造能自我改進的 LLM agent 的關鍵，既有方法多半用 reflection、memory、rule 或 skill 從累積的軌跡離線挖知識。但現實環境中 agent 持續遇到新任務，每次執行往往只有一次改進機會；真實執行產生的 context 豐富卻雜訊很高，把有用教訓和任務特定細節、部分失敗、偶發工具痕跡糾纏在一起。既有方法很少在複雜真實任務上嚴格驗證效果，也很少系統性拆解「改進到底是什麼驅動的」。

作者因此提出 online harness learning：凍結的 agent（solver）不改參數，只靠持續更新一個外部結構化 harness 跨任務序列改進。Evo-Harness 用 skill 實例化這個 harness，因為 skill 能把失敗、回饋、限制、操作程序整合成會形塑未來規劃與復原的結構化知識。核心是 context-to-harness skill compilation：solver 反思 context 提出候選 skill，evolver 更新既有 harness；一般技能捕捉可跨任務遷移的模式，主題技能捕捉局部操作知識，雙層設計保留關鍵學習訊號同時過濾軌跡層級雜訊。

第 3 節：Online Harness Learning 形式化

設任務批次流 {B₁,…,B_K}，批次 B_i 前 agent 持有 harness ℋ_i（外部於凍結 solver 的可重用指引集合，不同於原始軌跡儲存）。對每個任務先用 Select 挑出最多 b 條 harness 條目、Inject 進任務，再由凍結 solver 執行得到 (τ, y, f)（軌跡、結果、回饋，回饋可以是 verifier 結果、單元測試輸出、工具診斷或裁判回饋）。Execution context c=(x, τ, y, f)。Online harness learning 就是用這些 context 把 ℋ_i 更新成 ℋ_i+1，同時保持 solver 參數不變。

Execution reflection：只在執行失敗或收到負回饋時才產生候選記憶 r=(lesson, trigger, evidence, scope_hint)，reflection 使用完整 task-side context（指令、軌跡、觀察、工具輸出、結果、回饋）。只針對失敗做 reflection 是因為失敗才暴露 solver 目前的能力邊界（錯誤假設、缺失限制、無效工具使用、脆弱驗證、失敗復原），成功案例可能夾帶不必要的任務特定細節。此階段不比對現有 harness，輸出只是候選訊號而非最終更新。

Harness evolution：批次結束後候選記憶集合 ℛ_i，evolver 讀入 ℋ_i 與 ℛ_i 輸出一組編輯 𝒪_i，每條候選記憶依 π_evolve 判給 Add／Merge／Revise／Skip 四種算子之一——過濾雜訊或冗餘記憶、合併相容訊號、修訂既有指引、把可重用教訓升級。更新後 ℋ_i+1=ApplyEdits(ℋ_i, 𝒪_i)：候選記憶不是直接附加，而是編譯進會影響未來行為的指引。

第 3.3–3.4 節：Harness 分層與演算法

演化出的 harness 含兩層：跨任務通用模式（比對多任務找出共享操作結構）與任務型局部程序（保留重複任務格式/介面/領域的局部指引），兩層不是預先貼的標籤，而是 evolver 篩選、比對、整合候選記憶後自然浮現的結果。演算法用批次層級更新：每批任務跑完後同時執行 CompileTaskType（局部程序）與 CompileCrossTask（跨任務模式），聯集成 𝒪_i 套用到 harness；批次大小為 1 時退化成逐任務型更新。模組化設計（solver、evolver、回饋來源、初始 harness 狀態互相解耦）刻意用來支援系統性研究「什麼驅動線上 harness 改進」。

第 4 節：實驗

五個 benchmark：WebArena-Infinity（網頁導覽）、TerminalBench2（命令列）、SWE-bench Lite（軟體工程）、CL-Bench（適應性推理）、τ-bench（工具使用）；預設 solver/evolver 為 Claude Opus 4.6，另用 Opus 4.7／4.5、Kimi-K2.5、GPT-OSS 做模型消融。baseline 含 AWM、Dynamic Cheatsheet（DC-Cu/DC-RS）、Evo-Memory、ACE、XSkill。

RQ1：Evo-Harness 在全部五個 benchmark 都勝過 No-Evolve 與最強 baseline XSkill，TerminalBench-2 增益最大（62.92%→73.03%）。幾個 baseline 在部分 benchmark 甚至輸給 No-Evolve，說明外部經驗重用不必然有益。CL-Bench 上 Opus 4.7/4.6/4.5 增益 +3.7/+4.5/+3.8，Kimi-K2.5 與 GPT-OSS 只有 +1.1/+0.8——較強模型更能解讀並套用 harness 指引。類別層級上 Procedural Task Execution 增益最一致（Opus 4.6/4.5 各 +9.8），Empirical Discovery & Simulation 增益不穩定甚至對部分模型下降。

RQ2 harness 內容與元件消融：不同 benchmark 演化出的 harness 內容分布不同（WebArena 偏工作流程／程序、TerminalBench-2 偏驗證與復原），顯示 compilation 會依環境操作結構調整。消融（No Propose 移除 solver 側候選提案、General Only 只留跨任務指引、Topic Only 只留局部指引）顯示哪種指引更重要取決於任務：CL-Bench 上 Topic Only（33.70）接近完整方法（34.02）而 General Only 掉到 30.28，SWE-bench Lite 上則反過來 General Only（66.67）接近完整方法（67.00）而 Topic Only 只有 64.33。No Propose 優於 No Evolve 但仍不及完整方法，提案與 harness 層編譯互補。

RQ3 遷移與適應性：SWE-bench Lite 上比較 No-Evolve（68.8）、Train-Split Transfer（Sonnet 4.5 在訓練切分演化技能，Opus 4.7 solver 在測試切分套用，73.4）、Online-Updated（同模型在測試任務流中直接更新，75.0）——技能可跨任務與跨模型遷移，但線上更新仍最好。Solver-evolver 配對實驗更耐人尋味：Opus solver 下 Cross（Sonnet 演化）76.0 略高於 Same（Opus 演化）75.3，皆遠高於 No-Evolve 70.7；但 Sonnet solver 下 Same（55.3）與 Cross（Opus 演化，55.7）都低於 No-Evolve 的 58.0。Sonnet 演化出的技能能幫助 Opus，卻不必然幫助 Sonnet 自己——遷移效果同時取決於 solver 本身能否理解並套用該指引。

RQ4 回饋接地：比較 Self-Generated（LLM 自判成敗與該學什麼）、Minimal（只給環境成敗訊號）、Standard（含失敗訊息、error trace、verifier 輸出等完整診斷）三種回饋來源。Self-Generated 在兩個 benchmark 都輸給 No-Evolve（CL-Bench 29.54→27.96、SWE-bench Lite 63.67→61.67），顯示未接地於外部執行證據的 LLM 自我判斷會引入誤導性更新。Minimal 與 Standard 都用環境訊號，整體更可靠，但何者更好依 benchmark 而異：CL-Bench 上 Standard（34.02）明顯優於 Minimal（29.86）；SWE-bench Lite 上 Minimal（67.33）反而略高於 Standard（67.00），作者推測詳細錯誤訊息有時讓 harness 過度綁定任務特定失敗，稀疏的通過/失敗訊號反而鼓勵更可泛化的指引。

第 5 節：結論與限制

作者將 online harness learning 定位為研究「凍結 LLM agent 如何從序列化、單次執行中改進」的框架，Evo-Harness 的目標不只是提出管線，更是把 harness 當作理解線上自我改進的分析透鏡，推進自我演化 agent 研究從單純比較成功率到系統性理解 agent 如何產生、組織、遷移、套用可重用經驗。作者自陳限制：僅涵蓋文字型、工具使用、網頁、命令列、軟體工程環境下的單一 agent 系統，未評估具身或多 agent 系統；harness 僅以自然語言指引實例化，未涵蓋可執行程式碼技能等其他形式。
