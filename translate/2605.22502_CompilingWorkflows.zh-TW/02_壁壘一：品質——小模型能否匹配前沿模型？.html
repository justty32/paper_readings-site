4. 壁壘一：品質——小模型能否匹配前沿模型？

4.1 實驗一：旅行訂票（3B）

四個條件（n=200 each）：(1) 3B 地下代理（Qwen 2.5 3B Instruct，微調）、(2) 3B 表面編排器（同一基礎模型，顯式流程圖狀態追蹤）、(3) LangGraph 編排器、(4) in-context 基準。條件 1 vs 2 隔離編譯本身的效應（同模型、同程序、不同架構）；1 vs 3 測試編譯 3B 能否與前沿編排器競爭。

訓練：2,125 段合成對話（1,912 訓練、213 驗證保留），Qwen 2.5 3B Instruct bf16，單 RTX 5090 全參數微調。AdamW 8-bit，lr=2×10⁻⁵（餘弦衰減），有效 batch size 16（梯度累積），20 epochs（∼3.5 小時），依保留驗證 loss 選最佳 checkpoint（epoch ∼4 收斂後持平）。

結果（表 1）：3B 地下代理在全部五項標準領先同模型編排器。編譯有效：任務成功 +0.18（p<0.001）、一致性 +0.22（p<0.001）、優雅處理 +0.20（p<0.001）、自然度 +0.17（p<0.001）；資訊準確性 +0.05 趨勢正向但未顯著（p=.29）。vs LangGraph 編排器：資訊準確性領先（4.75 vs 4.21, p<0.001），但優雅處理與自然度落後。vs in-context：資訊準確性強（102%），但優雅處理與自然度∼82%——3B 學到了程序但缺乏邊界案例自然處理的容量，驅動擴大到更大模型。

4.2 實驗二：Zoom 技術支援（8B）

三條件（n=200 each）：8B 地下代理、LangGraph 編排器、in-context 基準。訓練：基礎管線每次產出 870 段對話；用八個不同種子（42–49）重複執行，合併訓練分割（8×783=6,264 段）。Qwen3-8B bf16，全微調，DeepSpeed ZeRO-3 在 8×A100，lr=2×10⁻⁵，有效 batch size 32，10 epochs，最佳 checkpoint 在 epoch 2。

結果（表 2）：優雅處理與自然度差距已封閉。8B 達到 in-context 的 92%（優雅處理）與 97%（自然度）——vs 3B 的 82%。剩餘差距集中在資訊準確性（87%），瓶頸是廣域世界知識（非程序遵循）。vs LangGraph：自然度顯著領先（4.87 vs 4.64, p<0.001）；編排器在資訊準確性領先（4.75 vs 4.26, p<0.001）；任務成功、一致性、優雅處理相當。

4.3 實驗三：保險理賠（8B）

三條件（n=200 each）：8B 地下代理、LangGraph 編排器、in-context 基準。訓練：3,000 段合成對話（2,700 訓練、300 驗證），Qwen3-8B bf16，全微調，DeepSpeed ZeRO-3 8×A100，lr=2×10⁻⁵，有效 batch size 32，20 epochs，最佳 checkpoint 在 epoch 3。

結果（表 3）：8B 編譯模型在保險理賠達到 in-context 品質的 92–98%（4.40–4.92 vs 4.78–5.00）——證明編譯可規模化到大幅更大的程序（55 節點 vs 14）。vs LangGraph：優雅處理（4.81 vs 4.38, p<0.001）、自然度（4.92 vs 4.58, p<0.001）、一致性（4.51 vs 4.39）皆顯著領先；任務成功與資訊準確性相當。

4.4 效率與失敗模式

（表 4–5）旅行訂票：3B 地下代理對話回合較多（22.6 vs ∼16），反映從訓練資料學來的「一問一答」風格。但端到端延遲仍與 LangGraph 相當（自託管免 API 延遲）。Zoom 與保險：編譯模型更快（Zoom 29.5s vs 52.1s；保險 43.2s vs 120.8s）。保險差距最大——LangGraph 在 6 個決策樞紐各有額外 API 呼叫，且 55 節點程序膨脹每回合 prompt。

失敗率（表 5）：編譯模型失敗率遠低於 LangGraph——旅行 5.5% vs 24.0%，保險 9.0% vs 17.0%；Zoom 相當（11.0% vs 9.0%）。編排器在旅行的 24% 失敗率反映了決策樞紐的路由錯誤——這是編譯模型在建構上就消除的失敗模式。

地下代理從訓練資料學到「訪談風格」：每次 agent 回合一問（64% 回合僅含一個問題），產生更清晰的審計軌跡，可能降低使用者認知負荷。LangGraph 編排器受限於當前節點模板，有時一回合塞進多個問題。每段對話總字數跨條件相當（∼1,200–1,400 字）——相同資訊交換，只是切成不同大小的回合。

編譯的結構性優勢（解釋為何 3–8B 模型能與 ∼70 倍大的 Claude Sonnet 4.5 競爭）。Dennis et al.（2026a）指出編排的三個結構成本：(1) 僅從局部節點上下文生成，碎片化推理；(2) 引入路由失敗模式；(3) 模板注入限制自然對話風格。地下代理三者全避：經內化權重對整份程序全局推理、建構上零路由失敗、產出不受限的自然回應。這些結構性優勢補償了巨大的容量差距。

5. 壁壘二：成本——自託管後真的比較便宜嗎？

成本削減有兩個獨立成分（表 6）。

Per-token 成本

編譯的地下代理部署在自託管商品 GPU 硬體上，而非透過前沿 API。8B 模型部署在保留雲端 A100 80GB（$2.50/hr），使用 vLLM 批量推理。公開基準顯示 8B 模型在 A100 batch size 64 達 4–5K total tokens/s（∼15K tokens/s prefill，∼3K tokens/s autoregressive decode）。

將小時 GPU 成本除以這些吞吐量：∼$0.05/M input tokens、∼$0.23/M output tokens。vs Claude Sonnet 4.5 發佈費率（$3/M input、$15/M output）——per-token 約便宜 65 倍。

Token 用量

In-context 基準必須每回合在 system prompt 中嵌入序列化程序——一個隨程序複雜度增長的開銷：travel ∼2×（14 節點）到 insurance ∼7×（55 節點）。編譯模型的 prompt 是常數大小，無論程序複雜度。這個開銷完全消失。

複合優勢

兩因素疊加：travel 便宜 128×，insurance 便宜 462×——最大優勢落在最複雜的程序上。編譯模型也比 LangGraph 編排器便宜 77–249×（編排器雖用較少 token，但仍每回合支付 Claude API 費率）。

一次性編譯成本

編譯產生一次性設置成本（與運行成本分離）：資料生成約 $40 + 微調計算約 $10–40（合計 $50–80）。分攤到每次對話取決於部署的 agent 終生對話量：在所有領域，500 次對話內即可回本（vs in-context 基準）；10,000+ 次對話時，編譯的每對話攤提成本低於 $0.01。

6. 壁壘三：靈活性——程序變更時能適應嗎？

編譯模型在程序變更時必須從頭重新訓練，但重新編譯管線在所有三個階段都可平行化，在生產級 GPU 集群上不到一小時完成。

資料生成

Claude Sonnet 4.5 遍歷新流程圖產出約 1,600 段合成對話。對話彼此獨立，API 調用可簡單平行化；合理並行度下這步需 15–30 分鐘（瓶頸是 per-account API rate limit，非本地計算）。順序執行約需 60 分鐘。

微調

8B 模型可舒適放進單張 H200 進行全精度 AdamW（參數 + 梯度 + 優化器狀態合計 ∼96 GB），無需分片——8×H200 僅做資料並行，H200 的 ∼3× BF16 吞吐量壓縮 12 epochs 到 10–15 分鐘。單張 A100 80GB（與推理相同硬體），優化器需用 8-bit AdamW 才放得下，訓練約 3 小時。

評估

50 情境的 vLLM 批量抽查約需 5 分鐘（推理伺服器已預熱），或 10–15 分鐘（含伺服器啟動）。

總計

完全優化週期（8×H200 + 平行化 API 請求）：30–50 分鐘——與大型應用的 CI/CD 建置週期相當。無法存取 8 GPU 集群的實務者可單張 A100 80GB 約 3–4 小時完成（瓶頸是訓練，非資料生成）。
