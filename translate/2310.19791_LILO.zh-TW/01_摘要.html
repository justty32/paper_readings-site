摘要

LLM 已擅長程式碼生成，但軟體開發的關鍵是重構（refactoring）的藝術：把程式碼整併成可重用、可讀的函式庫。本文提出 LILO——一個神經符號（neurosymbolic）框架，迭代地合成、壓縮、文件化程式碼，為特定問題領域打造函式庫。LILO 結合 LLM 引導的程式合成與 Stitch（一個能在大型程式語料中高效找出最優 λ 抽象的符號壓縮系統）的自動重構演算法。為讓抽象可解讀，本文提出自動文件化（auto-documentation, AutoDoc）程序：依上下文使用範例推斷自然語言名稱與 docstring。AutoDoc 除了改善人類可讀性，還藉由幫助 LILO 的合成器理解與部署學到的抽象而提升效能。在字串編輯、場景推理、圖形合成三個歸納式程式合成基準上，LILO 比既有方法（含 SOTA 函式庫學習演算法 DreamCoder）解出更複雜的任務，並學到紮根於語言知識的更豐富函式庫。

1. 引言

LLM 在補全、對話式編程乃至競賽級題目上表現出色，但軟體工程師關心的不只解決眼前任務，而是建立能覆蓋整個問題領域的函式庫。重構的目標是找出讓程式碼庫更簡潔（整併共享結構）、可重用（泛化到新任務）、可讀（他人易懂）的抽象——一個多目標最佳化問題。

LILO（Library Induction from Language Observations）由三個相互銜接的模組組成（圖 1）：

  • 雙系統合成模組（dual-system synthesis）：LLM 引導搜尋提供強領域通用先驗＋枚舉搜尋（enumerative search）發現領域特定表達式；
  • 壓縮模組（compression）：用 Stitch（Bowers et al., 2023）這個高效能符號壓縮系統，從既有解集中識別有用抽象；
  • 自動文件化模組（AutoDoc）：生成人類可讀的函式名稱與 docstring，提升可解讀性並改善下游 LLM 引導搜尋。

架構靈感來自 DreamCoder（Ellis et al., 2021）的 Wake-Sleep 迭代演算法：在「搜尋任務解（Wake）」與「把共享抽象重構進函式庫（Sleep）」間交替。DreamCoder 能從少量例子做強泛化、概念知識以符號形式存於函式庫，但其搜尋極耗算力（學一個領域要超過 2 CPU-月），且大量時間花在「起飛」——發現人類程式設計師早已知道的基本抽象；其函式庫也不易解讀（需領域知識＋lambda 演算素養）。LILO 以 LLM 從兩方面切入：(1) 加速搜尋期的解發現；(2) 用文件化提升函式庫可解讀性。例如 LILO 學會「母音（vowel）」概念——它是字串編輯領域的關鍵墊腳石，若靠枚舉需在 26^5 個字元基元析取式中搜尋。與 LLM-only 基線不同，LILO 把這種知識壓縮成符號抽象，同時可供傳統搜尋與 LLM 引導合成使用；其中 AutoDoc 是神經符號整合的關鍵。

2. 預備知識：程式搜尋與函式庫學習

程式合成：給定基元函式庫 L（構成 DSL）與以輸入輸出對指定的任務 t，找出正確映射的程式 π。因解不唯一，以描述複雜度（description length）為先驗，將問題表述為機率推論（式 1）：argmax_π [log p(t|π) + log p(π|L)]，先驗由機率式上下文無關文法（PCFG）定義——越長的程式機率越低。歷來的枚舉搜尋即使加上類型導引、神經網路導引等技巧，仍高度依賴 DSL 設計：漏掉關鍵基元使難題無解、多餘基元使搜尋不可行，DSL 工程因此極耗專家心力。

函式庫學習（library learning）：把 L 本身納入最佳化——從任務集 T 與基礎函式庫 L0 出發，聯合推斷「擴充函式庫 L = L0 ∪ {f*}」與「以 L 撰寫的程式集 Π」（式 2），新增的抽象要可重用（同時簡化多個任務的解）且簡潔（層級式互相堆疊）。DreamCoder 以座標上升近似：交替「固定函式庫、搜尋解」與「從解集抽出共同結構、更新函式庫」，其可行性關鍵在高效重構。

利用語言引導：描述長度這類通用先驗常不足以解式 1，故有研究把自然語言任務描述 d_t 當作額外學習訊號。函式庫學習場景中 L 是新造的，如何用語言不明朗：LAPS（Wong et al., 2021）靠擬合「程式→語言」反向翻譯模型（IBM Model 4），受限於嚴格的 token 對 token 對齊假設。LILO 反其道而行：從已具語言×程式碼聯合分佈強先驗的大模型出發，藉由累積上下文範例與文件，讓函式庫去貼近這個分佈——不是改用常見語言（如 Python），而是在線學出一個既為領域最佳化、又紮根自然語言的新 L。

3. LILO：由語言觀察歸納函式庫

LILO（演算法 1）沿用「搜尋↔重構」座標上升結構，但因用 LLM 搜尋而必須多一步 AutoDoc，使學到的抽象對合成器可讀。迴圈為：對每個任務跑 LLM Solver → 跑枚舉搜尋 → Stitch 壓縮出 k 個新抽象 → 以 L0 ∪ {f*} 重建函式庫並改寫解集 → 對每個新抽象跑 AutoDoc 補上名稱與 docstring。

雙系統程式搜尋（圖 1A）：受認知雙歷程理論（dual process theories）啟發——LLM 作為字串空間的「快」近似搜尋模型，利用預訓練的強歸納偏置；之後在程式空間做「慢」枚舉搜尋，由「辨識網路（recognition network）」推斷的任務條件 PCFG 引導。LLM 提示由三部分程序化構成（式 3）：(1) 函式庫描述（枚舉可用基元與已學抽象）、(2) 從已解任務取樣的「描述–解」配對範例、(3) 目標任務描述。每個補全都經解析、類型推斷、執行檢查驗證是否為有效解。

經由 Stitch 壓縮重構（圖 1B）：解集成長後充滿重複片段，重構將之整併為可重用抽象。對枚舉式系統，重構省去為每個新任務重新發現積木的成本；對 LILO，重構讓生成更容易——配備抽象庫的 LLM 只用少數 token 即可部署整塊程式碼，還藉縮短 few-shot 範例的描述長度緩解上下文視窗限制。LILO 把重構表述為語料壓縮問題（式 4）：找出「自身描述長度最小、且能高效改寫 Π」的抽象 f*。Stitch 以 branch-and-bound 搜尋在 λ 演算程式資料集中找可重用抽象，比 DreamCoder 的壓縮演算法快 1000–10000 倍、省 100 倍記憶體；LILO 首次把它放進合成迴圈，通常單 CPU 數秒內跑完。這種效率讓 LILO 每輪都從 L0 重新推導整個函式庫（「深度重構」），得以丟棄學習早期發現的次優抽象。

函式庫自動文件化（圖 1C）：LLM（如同人類程式設計師）在乎函數叫什麼名字——它從詞彙內容推斷程式語義。但 PL 工具輸出的是匿名 λ 抽象（Stitch 以編號表示，如 fn_42）。早期實驗發現：把 Stitch 匿名抽象直接餵給 LLM 反而顯著降低解題能力——壓縮時以匿名 λ 改寫程式範例形同程式碼混淆（code obfuscation）。AutoDoc 利用「LLM 天然適合去混淆（deobfuscation）」的特性，循序提示指令微調 LLM 為每個抽象產生可讀名稱與 docstring。圖 2 示例（REGEX 領域）：Stitch 抽出常見表達式 (or 'a' (or 'e' (or 'i' (or 'o' 'u')))) 為匿名零元函數，AutoDoc 命名為 vowel_regex；後續 consonant 表為 (not vowel_regex)，再支撐「子音替換」抽象——命名選擇透過對話式結構循序級聯，形成一致且可解讀的引用鏈。
