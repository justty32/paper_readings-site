附錄擇要

  • A.1 LLM Solver 提示結構：每個提示＝簡短領域描述＋自動生成的「DSL 基元與類型簽名」清單＋隨機取樣的「任務描述–解」配對＋目標任務描述；每提示取 N=4 個補全，過濾無效程式後檢查是否解題。
  • A.2 AutoDoc 提示：以 ChatGPT 對話序列進行——先給含「已文件化函式庫＋一個匿名 fn」的標頭，再附最多 10 個使用範例，要求以 JSON 格式回覆 readable_name 與 description。Codex 做不好此任務；指令微調的 gpt-3.5-turbo / gpt-4 100% 遵守 JSON schema，兩者下游合成效能相當，但 gpt-4 每輪超過 2 分鐘、gpt-3.5-turbo 僅 10–20 秒，故選後者。全程零樣本（zero-shot）、無 few-shot 示範，使 AutoDoc 成為極易跨場景實作的領域通用技術。
  • A.4/A.5 實作與超參數：枚舉搜尋跑在 96-CPU 機器（batch_size=96，每任務一 CPU），搜尋時限沿用 LAPS（REGEX 1000s / CLEVR 600s / LOGO 1800s）；LLM Solver 用 code-davinci-002、溫度 0.9；Stitch 只在「抽象具壓縮性」（出現在多個程式且改寫後總描述長度下降）時才產出——自動避免引入無用抽象。
  • A.3 範例挑選：比較隨機取樣與依任務描述 embedding 餘弦相似度挑範例，未見顯著差異（壓縮已讓每個提示塞得下約 20–40 個範例，降低了精挑的必要）；相似度法易被表面詞彙重疊誤導。主實驗用隨機取樣。
  • B.3 與 LAPS 的基準比較：REGEX 上 LILO 顯著超越 LAPS 全部條件（best 93.20 vs 57.00），且不需顯式的語言/程式對齊翻譯模型；CLEVR 相當（99.03 vs 96.5）；LOGO 上略遜於 LAPS 最佳離群跑（best 73.87 vs 92.79，平均 48.95 vs 52.93）——LOGO 特別適合 IBM 翻譯模型的 token 對 token 假設，且純 LLM 搜尋條件無法像 CNN 辨識模型那樣看到圖像。
  • B.4 人類語言標註：人類描述詞彙句法變異大（同一雪花任務從詳細描述到只寫「boomerang」），整體效能以合成語言為上界。LLM Solver 在人類語言下嚴重退化（LOGO 從 32.13 → 8.11）；加搜尋可緩解；完整 LILO 最穩健（LOGO 30.03），且整體仍優於 DreamCoder。
  • C.1 成本分析：每輪訓練用 0.8M–1.2M GPT tokens；以 gpt-3.5-turbo 計價，LLM 搜尋每輪約 $1.6–2.2，與 96-CPU 枚舉搜尋（$0.7–2.1）同一數量級；LLM 推論成本可望持續下降。
  • C.2 LLM 能做壓縮嗎？：用 GPT-4 替代 Stitch 做壓縮的受控實驗失敗——Stitch 壓縮率 1.5–3.5 倍且隨學習提升，GPT-4 徘徊在 1.0 倍基線；生成的抽象僅 19.01%（998/5250）語法有效（LOGO 只有 4.93%），且偏短、瑣碎。生成有效抽象需對「抽象與整個語料的互動」做形式推理，遠難於合成程式——印證 LILO 的神經符號分工：LLM 管合成，重構交給為此工程化的符號模組。
