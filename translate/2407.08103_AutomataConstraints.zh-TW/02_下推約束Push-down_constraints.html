3. 下推約束（Push-down constraints）

3.1 下推自動機（PDA）

PDA 可視為「配備一個堆疊（stack）」的 FSA：邊除輸入外還記錄要彈出（pop）與壓入（push）的堆疊符號。以圖 6 的 aⁿbⁿ 文法為例，堆疊符號採 Earley 式的帶點規則（dotted rules）表示「返回位址」。關鍵差異：非確定性與確定性 PDA 不等價——前者接受上下文無關語言（＝上下文無關文法定義者），後者只接受其嚴格子集「確定性上下文無關語言」。但此子集已涵蓋所有正則語言以及 LL(k)、LR(k) 語言，足以覆蓋多數程式語言的語法。由於不等價，並無「確定化任意 PDA」的通用演算法；故本系統如 LL(k)/LR(k) 解析器一般，偵測到非確定性文法即報錯，交由文法作者改寫成確定性形式。

3.2 把文法適配到 token

雖然 PDA 比 FSA 更具表達力，但兩者行為相似，且FST 與 PDA 亦可組合（Allauzen & Riley）。因此與 T_V 組合即可把字元 PDA 適配成接受 token 的 PDA。演算法 3（約束 LM 到文法 G）幾乎重用演算法 2，只多維護一個堆疊：合法 token 集合的條件多一項「堆疊須以該邊的待彈符號結尾」，走邊時同步彈出／壓入堆疊符號。值得再次強調：正因把整個任務用自動機表述，方法才能從 regex 輕鬆推廣到文法並保留諸多良好特性——正如 FST-FSA 組合讓 token 可跨越 regex 子表達式邊界，FST-PDA 組合讓 token 可跨越文法的（非）終端邊界（見圖 7）。

4. 相關工作

4.1 序列模型的自動機：Sproat & Jaitly、Zhang 等在 TTS 文本正規化用 FST 引導深度模型；Deutsch 等用 FSA/PDA 約束序列模型輸出——但這些工作早於通用 LM 興起，未處理 LM tokenization 與形式語言的錯位問題。

4.2 通用 LM 的自動機：最相關的是 Outlines（Willard & Louf 2023），其核心是客製的「indexing」運算，在 FSA/PDA 上疊一層 token overlay。缺點：(a) 套到 PDA 時對 tokenization 過度約束（over-constrained，見附錄 A.1）——不允許 token 跨越文法終端邊界；本文則自然推廣到 PDA 並保留 tokenization 自由。(b) 難以推廣到不同 tokenization 方案，本文則容易。(c) 編譯速度慢約 7,000 倍，只有能預編譯時才實用。本文核心創新是把整個流程改用自動機語彙重述，因而可擴充（分解為 FST 與 FSA/PDA 模組）、正確（靠 FST 基本性質）、快速（用高度優化的演算法）。SynCode（Ugare 等 2024）也用 FSA 但以 LALR(1)/LR(1) 解析器處理文法，靠「推測性展開未來 lexer token」讓 LM token 跨越多個 lexer token——相較本文純自動機路線引入可觀複雜度，且展開幾個 lexer token 是計算成本與完整性的取捨。其他方法如 Synchromesh（每步遍歷整個詞彙表，不實際）、Guidance（快取 trie 改良）、grammar-constrained decoding（Geng 等，表達力超越上下文無關但較低效）、以及事後拒絕採樣式的 PICARD、Lew 等的序列蒙地卡羅（與預測式遮罩正交，可與本文合併）。

4.3 LM tokenization 的自動機：與審稿同期，Berglund 等（2024）提出只接受「正確 BPE tokenization」的有限狀態機——與本文 2.3 的簡單 detokenizing FST（有歧義）不同，他們的是無歧義的。其建構可直接推廣為 FST，進而與本文任何 regex FSA 或文法 PDA 組合，得到「只接受正確 BPE 且合乎約束」的自動機。換言之，任何能以有限狀態形式表達的 tokenization 策略都能插進本文方法，展現其模組化與通用性。

5. 應用

5.1 JSON 表達式：研究「生成符合 schema 的 JSON」。雖然所有 JSON 是上下文無關語言，但符合特定 schema 的 JSON 卻是正則語言（schema 限制了遞迴），令人略感意外。手寫對應 regex 很難，故實作了「把 schema 自動翻譯成 regex」的工具。也探索了 schema-free JSON（上下文無關）：對物件與陣列的巢狀深度施加常數上限即可由上下文無關降為正則；或直接把 JSON 文法轉成 PDA 約束。

5.2 Python dataclass：對 dataclass 做反射（reflection）自動建出匹配其建構子呼叫的 regex，形成便利 API——用型別 T 建約束，再把受約束的 LM 回應解析回 T 的實例。

5.3 推測解碼（Speculative decoding）：推測解碼用較快的近似模型採樣短串 token，再由較準的目標模型驗證。近似模型通常較小、更難遵循形式語法，故自然的應用是約束近似模型以提高其在形式語言輸出上的接受率。需處理幾個複雜點：約束須「可回捲（rewindable）」（目標模型可能拒絕部分推測 token），作法是追蹤完整狀態歷史而非單一狀態；目標模型的 logits 也須被懲罰，否則兩模型的分歧會降低接受率、甚至讓目標模型重採到非法 token——作者設計了與目標模型共享懲罰的方法以免重複評估約束。

6. 實驗

6.1 速度：用 Gemma、在同一工作站上比較本系統與 Outlines，取 10 次平均，報告相對於 Outlines 的加速倍率（表 2）：多選、ISO 日期時間、IP 位址、引號字串、JSON 物件五種約束的編譯加速分別約 7,970×／7,110×／6,850×／13,400×／7,240×；每步開銷加速約 29.5×／24.3×／26.1×／6.5×／33.6×。粗略延遲：編譯上 Outlines 在 JSON 上要數十秒、其他數秒，本系統 JSON 僅數毫秒、其他數百微秒；每步開銷 Outlines 數十微秒、本系統數微秒。每步開銷兩者其實都可忽略，影響不大；但編譯的巨大加速是質變——降低使用約束的門檻、開啟新使用模式（不再需要預編譯）。加速主因是採用 OpenFST 高度優化的 FST 運算實作，而這只因把整個問題改用自動機重述才可能（類比：手寫科學計算程式 vs 化約為線性代數並用 NumPy）。

6.2 正確性：在 GPQA 上用 Gemma 測輸出格式合規率（表 3）。無約束時 Gemma-2B 僅 0.09、Gemma-7B 0.65 符合所需 schema；加約束後兩者皆達 1.0（完美合規）。

7. 結論與未來工作

核心貢獻是「把 detokenization 重述為 FST」，將整個受約束解碼任務帶進自動機領域，從而為歧義又錯位的 tokenization 導出簡單、優雅、高效能的解法。未來想更深入探索 PDA（迄今多聚焦更穩健可擴充的 FSA）：如何撰寫文法以避免非確定性 PDA（有深厚的確定性文法文獻可借鏡）；PDA 的使用情境與表示效率——注意解碼有最大 token 預算，會縮小上下文無關與正則的差距（如限制 100 字元則 aⁿbⁿ 因 n≤50 不再是上下文無關），值得研究長時、可能多階段的約束情境；即使短輸出下 FSA 已具競爭力，PDA 仍可能因通常比等價 FSA 更精簡而有價值。

附錄 A：Tokenization 錯位問題（要旨）

以「可呼叫 foo(123) 或 bar(456)」為例，每種呼叫有兩種 tokenization，LM 給分如下：fo o(1 2 3)＝0.4、bar ( 456 )＝0.3、foo ( 123 )＝0.2、ba r(4 5 6)＝0.1。允許所有 tokenization 時，foo(123) 明顯是最佳輸出。但像 r(4 這種跨越不同語法單元邊界的 token 很難支援（Gemma 詞彙表真的含 .")、==""){ 這類跨多個語法單元的 token）。若粗暴地強迫 tokenization 貼合形式語法（排除第一、四列），剩下的最佳輸出反而變成 bar(456)——排名被倒置，即強迫對齊會有害地扭曲評分。A.1：Outlines 的文法約束目前不允許 LM token 跨越文法終端邊界，故會禁掉 r(4 這類 token，導致上述排名倒置——這正是「過度約束」的具體體現。
