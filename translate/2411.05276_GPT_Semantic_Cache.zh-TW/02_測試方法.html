3 測試方法

為評估 GPT Semantic Cache 系統的成效，作者設計一系列實驗以模擬使用者與 AI 服務互動的真實情境，目標是評估系統處理重複或語意相似查詢的能力、驗證快取回應的準確度，並量化回應時間與營運成本的改善程度。

3.1 資料集準備與快取填充

作者建構了一個涵蓋四個類別、共 8,000 筆問答對的資料集：Python 基礎程式、客服詢問、技術支援問題、一般知識，選定這些類別以反映真實應用中常見的查詢多樣性。每則問題用 all-MiniLM-L6-v2（Reimers & Gurevych, 2020，384 維句子嵌入模型）轉為語意嵌入，嵌入與對應回應皆存入 Redis，並更新 ANN 索引以納入這些嵌入供高效相似度搜尋。

3.2 測試查詢生成與執行

為評估系統表現，作者另外生成 2,000 筆測試查詢（每類別 500 筆）。每則查詢送入系統後轉為嵌入，並與 ANN 索引中的快取嵌入比對；若找到相似嵌入（相似度 ≥ 0.8），回傳對應快取回應（快取命中）；否則查詢轉送至 LLM 生成新回應（快取未命中），該回應隨後被快取。

3.3 快取命中的驗證

為驗證快取回應的適當性，作者採用 GPT-4o mini 評估被檢索的快取回應對測試查詢是否有效：對每筆快取命中，將測試查詢與原始快取問題一併提供給該模型，模型回傳二元判定，指出兩查詢是否語意相似、快取回應是否準確。此驗證步驟用以量化快取機制的準確度。此外，作者也測量並平均了快取系統與傳統方法（不使用快取）的查詢回應時間，藉以判定回應時間上的效能改善程度。

4 結果

GPT Semantic Cache 的評估結果顯示其在減少 API 呼叫與改善回應時間上有顯著影響，本節詳細分析系統效能，並與傳統方法比較。

4.1 API 呼叫的減少

GPT Semantic Cache 藉由對語意相似查詢從快取提供回應，減少了 API 呼叫數。如 Figure 1 所示，傳統方法在各類別皆為 100% API 呼叫，而 GPT Semantic Cache 顯著降低 API 依賴度。各類別的減少幅度如下：Python 程式基礎——67% 快取命中率，API 呼叫降至 33%；網路技術支援——67% 快取命中率，API 呼叫降至 33%；訂單與物流相關問題——68.8% 快取命中率，API 呼叫降至 31.2%；客服購物問答——61.6% 快取命中率，API 呼叫降至 38.4%。（Figure 2：傳統查詢處理 vs 語意快取系統的 API 呼叫頻率比較。）

4.2 回應時間分析

為評估效能改善，作者測量並比較了快取系統與傳統方法的平均查詢回應時間。Figure 3 呈現 GPT Semantic Cache 帶來的回應時間顯著縮短，惟正文並未附上具體秒數/毫秒數值，僅以圖表呈現趨勢。

4.3 快取命中與準確度分析

快取命中率顯示系統辨識語意相似查詢的效率，正確命中率則凸顯從快取檢索之回應的準確度。如 Figure 2 所示，系統在各類別皆達到高正確命中率，介於 92.5% 至 97.3%。（Figure 4：各查詢類別的快取命中率與正確匹配準確度。）

表 1（各類別每 500 筆查詢的快取命中數與正確命中數）：Python 程式基礎——快取命中 335、正確命中 310（92.5%）；網路技術支援——快取命中 335、正確命中 326（97.3%）；訂單與物流相關問題——快取命中 344、正確命中 331（96.2%）；客服購物問答——快取命中 308、正確命中 298（96.8%）。

5 討論

GPT Semantic Cache 的結果顯示，在所有受評估的查詢類別中，API 呼叫顯著減少、回應時間明顯改善。最高達 68.8% 的快取命中率、以及超過 97% 的正確命中率，凸顯系統在辨識並運用語意相似度處理查詢上的成效。然而，仍須將這些結果置於其優勢與潛在限制的脈絡下理解。

5.1 優勢與貢獻

高快取命中率與正確命中率證實了「語意嵌入方法＋記憶體內快取系統」組合的穩健性。系統在「訂單與物流查詢」等類別中效率格外顯著，因使用者問題往往遵循可預期的模式，帶來較高的語意重疊，驗證了此設計對客服聊天機器人這類常見此模式的應用高度適用。此外，減少 LLM API 呼叫帶來的營運成本節省相當可觀；TTL 機制確保快取資料維持相關性，回應了「回應準確度隨時間下降」的常見疑慮；系統同時支援雲端（OpenAI API）與本地 ONNX 模型做嵌入生成，展現對多元部署情境的彈性與適應力。

5.2 挑戰與限制

雖然系統在結構化或重複性查詢類別中表現良好，但在較多樣的查詢類型（如「客服購物問答」）中觀察到一些限制。此類別的快取命中率略低（61.6%），可能是因為客服詢問種類更廣、用語的語意變異度更大。在這類情況下，固定的相似度門檻（0.8）可能排除部分有效匹配；針對特定類別或使用情境的自適應門檻機制，可望緩解此問題並進一步提升命中率。

對大規模資料集維護 ANN 索引存在運算開銷，尤其當嵌入數量成長至數百萬筆時；儘管目前以 HNSW 實作已具效率，但面對頻繁更新或動態嵌入（如即時使用者輸入流）的情境，可能引發延遲或一致性挑戰。結合語意快取與啟發式查詢分組的混合式快取方法，或可強化系統在此類環境下的表現。

5.3 門檻選取（0.8 為最佳值）

餘弦相似度的門檻值 0.8 是透過在驗證資料集上大量實驗、以經驗方式決定的。實驗將門檻自 0.6 至 0.9、以 0.05 為間距變動，並測量對快取命中率與回應準確度的影響。結果顯示：門檻低於 0.8 會提高快取命中率，但也引入不相關匹配，降低正確命中率，進而拉低整體回應準確度；門檻高於 0.8 則顯著降低快取命中率，因較少查詢被判定為語意相似，導致更多 LLM API 呼叫與更高成本。在 0.8 時，系統達到最佳平衡，維持高快取命中率（最高達 68.8%）而不犧牲回應準確度（正確命中率超過 97%）。因此，此門檻被選為效率與準確度間的最佳取捨，與系統目標一致。

5.4 可擴展性與未來強化

此架構在目前形態下展現出強健的可擴展性，Redis 提供快速記憶體內儲存、HNSW 確保高效相似度搜尋。然而，若部署至具多節點的分散式環境，可能需要額外最佳化以管理資料一致性並減少同步延遲。整合進階嵌入模型，尤其是領域專用模型，可望進一步提升專門應用中的語意理解與準確度；依查詢模式、使用者回饋或系統效能指標動態調整相似度門檻，也可能隨時間精煉快取命中率；納入偵測與處理邊緣情況（如高度含糊的查詢，或需要超越語意相似度之脈絡的查詢）的機制，將進一步強化系統可靠性。
