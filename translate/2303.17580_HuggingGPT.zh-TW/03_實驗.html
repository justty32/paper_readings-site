4. 實驗

4.1 設定

實驗使用 OpenAI API 公開提供的 gpt-3.5-turbo、text-davinci-003 與 gpt-4 作為主要 LLM。為使輸出更穩定，解碼溫度設為 0；為讓 LLM 輸出滿足預期格式（如 JSON），對格式相關 token（如 {、}）設定 logit_bias 為 0.2。

4.2 定性結果

以兩個案例展示 HuggingGPT：其一，用戶請求含「描述圖片」與「數物件」兩個子任務，HuggingGPT 規劃出圖片分類、圖片描述、物件偵測三項任務，分別啟動 google/vit、nlpconnect/vit-gpt2-image-captioning、facebook/detr-resnet-101 模型，並整合結果回應用戶。其二，更複雜的案例中，用戶請求含三項任務（偵測人物姿勢、依姿勢與指定文字生成新圖、為圖片生成描述語音），HuggingGPT 將其解析為六項任務（姿勢偵測、依姿勢生圖、物件偵測、圖片分類、圖片描述、文字轉語音），並正確編排任務間的執行順序與資源依賴（如「依姿勢生圖」須接在「姿勢偵測」之後並使用其輸出作為輸入）。

4.3 定量評估

任務規劃是 HuggingGPT 整個流程的關鍵環節，決定後續 pipeline 要執行哪些任務，因此其品質可用來衡量 LLM 作為控制器的能力。評估時只考慮任務類型、不考慮其引數，把任務分為三類並設計不同指標：

  • 單一任務（Single Task）：只涉及一項任務的請求，任務名稱與預測標籤完全一致才算正確，用 F1 與 Accuracy 評估。
  • 序列任務（Sequential Task）：可拆解成一連串多個子任務的請求，用 F1 與正規化編輯距離（normalized Edit Distance）評估。
  • 圖任務（Graph Task）：可拆解成有向無環圖的請求，因規劃拓撲可能有多種，僅用 F1 不足以反映能力，故仿照 Vicuna 的做法，讓 GPT-4 當評審給出判斷（"GPT-4 Score"）。

資料集：邀請標註者提交請求，用 GPT-4 生成任務規劃作為偽標籤（涵蓋 single/sequential/graph 三類），總計 3,497 則請求（single 1,450、sequential 1,917、graph 130）；並另邀專家標註者為 46 則複雜請求人工標註（24 則 sequential、22 則 graph）高品質資料集。

主要結果：在三類 GPT-4 標註資料集上，GPT-3.5 全面優於開源 LLM Alpaca-7b 與 Vicuna-7b，尤其在較複雜的 sequential 與 graph 任務上優勢明顯。這說明任務規劃評估能反映 LLM 作為控制器的能力，也印證了持續提升 LLM 任務規劃能力的重要性。在高品質人工標註資料集上（表 6），結論一致：GPT-4 sequential task Accuracy 41.36%（vs. GPT-3.5 18.18%、Vicuna-7b 7.45%、Alpaca-7b 0%），graph task Accuracy 58.33%（vs. GPT-3.5 20.83%）。同時，即便 GPT-4 優於其他 LLM，與人工標註相比仍有明顯落差，凸顯強化 LLM 規劃能力的必要性。

4.4 消融研究

考察 few-shot demonstration 的數量與多樣性（涉及的任務類型數）對規劃效果的影響：增加示範多樣性能適度提升 LLM 規劃表現；示範數量增加也能略微提升表現，但超過 4 則後改善幅度趨於有限。

4.5 人類評估

除客觀評估外，另邀請人類專家做主觀評估：收集 130 則多樣化請求，評估 HuggingGPT 在任務規劃、模型選擇、最終回應生成各階段的表現，設計三項指標——Passing Rate（規劃出的任務圖或所選模型能否成功執行）、Rationality（生成的任務序列或所選工具是否合理對應用戶請求）、Success Rate（最終結果是否滿足用戶請求）。結果（表 8）：GPT-3.5 大幅領先 Alpaca-13b 與 Vicuna-13b——任務規劃 Passing Rate 91.22%（Rationality 78.47%）、模型選擇 Passing Rate 93.89%（Rationality 84.29%）、最終 Success Rate 63.08%（vs. Alpaca-13b 6.92%、Vicuna-13b 15.64%）。這與前述客觀評估結論一致，進一步證明自主智能體框架中強大 LLM 控制器的必要性。

5. 局限

1）HuggingGPT 的規劃高度依賴 LLM 的能力，因此無法保證生成的計畫永遠可行或最優，探索如何優化 LLM 以提升規劃能力至關重要；2）效率是本框架的通病——要建構這種具任務自動化能力的協作系統，高度仰賴強大的控制器（如 ChatGPT），但整個流程需與 LLM 多次互動，帶來不小的回應時間成本；3）Token 長度是使用 LLM 的常見問題，最大 token 長度總是有限，即便已有工作把長度擴展到 32K，若要連結大量模型仍嫌不足，因此如何簡潔有效地總結模型描述值得探索；4）不穩定性主要源於 LLM 本質上難以完全受控——儘管 LLM 擅長生成，仍可能不遵守指令格式或在預測中給出錯誤答案，導致程式流程出現例外，如何在推論時降低這些不確定性應在系統設計中被納入考量。

6. 結論

本文提出 HuggingGPT 系統，用語言作為介面連結 LLM 與 AI 模型解決 AI 任務。其原則是：LLM 可被視為管理 AI 模型的控制器，能利用 Hugging Face 等機器學習社群中的模型自動解決各種用戶請求。借助 LLM 的理解與推理能力，HuggingGPT 能剖析用戶意圖並拆解成多個子任務，再依專家模型描述為每項任務指派最合適的模型、整合不同模型的結果生成最終回應。透過運用機器學習社群中大量 AI 模型的能力，HuggingGPT 展現了解決具挑戰性 AI 任務的巨大潛力，為實現通用人工智慧鋪出新路徑。
