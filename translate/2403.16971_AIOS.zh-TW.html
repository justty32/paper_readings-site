論文／訪談原始來源

AIOS：LLM Agent 作業系統

摘要與 1. 引言

既有 agent 直接使用 LLM 與工具，缺乏集中排程、資源隔離與存取控制；並行時常把 prompt 載入 GPU，直到 OOM 才釋放重試。AIOS 將這些服務移入 kernel，agent 透過 SDK 發出 syscalls。Kernel 提供 LLM scheduling、context、memory、storage、tool 與 access management。實驗最高達 2.1× 執行效率。

2. AIOS 架構

Application layer 放 agent framework 與應用邏輯。Kernel layer 同時包含傳統 OS kernel 與 AIOS kernel：前者管 CPU、GPU、磁碟，後者提供 LLM-specific abstractions。Hardware layer 仍由傳統 OS 間接存取，因此 AIOS 是 serving middleware／agent kernel，而非取代 Linux 的完整作業系統。

Agent query 被拆成較小的 syscall units。Scheduler 把它們送到 LLM Core、memory、storage 或 tool manager；SDK 隱藏 kernel 細節。

3. AIOS Kernel

LLM Core 用 adapter 統一 hosted API 與 local models。Scheduler 支援 FCFS、round-robin 與 time limit，使多 agent 請求公平輪替。Context Manager 在 generation 中斷時保存上下文，之後恢復；這是模型請求層 preemption，不是完整 agent process checkpoint。

Memory Manager 處理執行期暫存，Storage Manager 保存持久資料。Tool Manager 負責註冊、載入、argument format check 與共享資源衝突。Access Manager 根據 agent 權限決定允許、拒絕或請使用者確認。SDK 再把這些功能映射到現有 agent framework。

4. 評估

Quality 使用 GPT-4o-mini、temperature 1.0。HumanEval／MINT／GAIA／SWE-bench-Lite 上，AIOS 大致保持原 performance；ReAct GAIA 從 5.5% 到 7.3%，AutoGen 從 7.3% 到 9.7%。這些增益包含 structured prompt、regex validation 與 conflict hashmap，不能視為 scheduler 的單獨效果。

Efficiency 使用 Llama-3.1-8B、Mistral-7B、單張 RTX A5000。Syscall throughput 最高提升 2.1×，等待時間下降。250 到 2,000 active agents 的複製 HumanEval workload 中，時間近似線性增加，AIOS 相對 baseline 的優勢隨負載擴大。

5–6. 相關工作、結論與限制

AIOS 把傳統 OS 的 scheduling、memory、filesystem、access control 類比到 agent serving，提供跨框架共用 kernel。它證明資源集中管理可改善單機吞吐，但未評估故障恢復、持久事件、不可逆工具作用、分散式排程或大規模 dormant agents；access control 也只有機制描述，沒有安全實驗。
