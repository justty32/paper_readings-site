論文／訪談原始來源

Ontology-Grounded Project Memory for Coding Agents

摘要與第 1 節：問題

Coding agent 已成為許多軟體專案產生新程式碼的主要方式，變更速度之快讓「為什麼這樣改」的原因難以追蹤——這被稱為「理解負債（comprehension debt）」：程式碼是決策的產物，但推理、理論、原因卻活在別處（Naur, 1985）。Notes 檔、Markdown 規格、RAG 式記憶都有幫助，但問題是：agent 需要知道一則筆記代表哪種知識（決策、限制、理由、教訓、反模式）、是否仍有效、記錄之間如何關聯（這個決策推翻了那個）——這些是本體論（ontological）問題。向量搜尋能找到語意相近的字詞，但不知道一筆記錄是什麼、扮演什麼生命週期角色。既有對程式碼本身建知識圖的工作（如抽取類別與使用關係、API 演進圖）模的是程式碼，MOOSEDev 模的是關於程式碼的知識——這是既有工作的留白。

第 2 節：系統設計

MOOSEDev 把架構決策（Nygard, 2011）、教訓、限制、理由、反模式存進專案知識圖，根基於兩個小型本體：軟體工程本體（程式碼結構詞彙）與軟體架構本體（關於結構的知識），都是帶 SHACL shape 的 OWL 本體，在作者的本體工程工作台（Trivyn）中互動生成、人工精修，並在執行期由 MOOSE 引擎推理；兩者刻意保持精簡（分別 9 類與 11 類，合計 51 個屬性）。關係是關鍵：一筆記錄可以攜帶理由、推翻另一筆記錄、影響某元件，並帶生命週期狀態、作者、時間戳——這些邊構成可遍歷網路。

結構為 agent 提供型別化擷取、對 SHACL shape 的驗證、可查詢性（如「已核准但沒有記錄理由的決策」）、生命週期與來源追蹤、以及對齊新概念的能力。底層 neurosymbolic 引擎把 LLM 當成不可靠但有用的感測器：關鍵字與結構比對、本體遍歷、確定性證據融合、驗證、執行痕跡全是符號層的事，模型只在窄且宣告過的節點被諮詢，因此可以用小模型（8–32B）。當 agent 詢問當前指引時，引擎遍歷圖找相關記錄、沿型別化關係走訪、過濾被取代的記錄、確定性地把剩餘證據排序進上下文；LLM 只負責解讀問題與整合答案，每一步都寫入執行痕跡。MOOSEDev 透過 MCP 暴露四類工具：型別化擷取、讀取（上下文檢索、自然語言查詢、SPARQL）、生命週期、完整性。

第 3 節：評測——結構化 vs 向量記憶

測試設定：基準比較五種記憶／檢索條件：B0 無記憶（下限）、B1-notes（真實文件攤平成純文字）、B1-mem0（生產級向量記憶工具 mem0，用自己的原生擷取方法吃入同批文件）、B1-rag（對圖內容本身攤平文字做 BM25 檢索，測試「內容本身、不靠結構」有沒有用）、B2（本文的結構化圖）。測試語料是第三方開源工具 CodeGraph 的文件，存成 835 筆型別化記錄與 553 筆 mem0 記憶。單一 CLI agent 配置與模型（GPT-5.x 家族）跑完所有實驗；裁決預先註冊，真值來自原始來源或 SPARQL 衍生集合，用嚴格 LLM 判官（GPT-5.4-mini）評分（容許改寫但拒絕主題對、事實錯的答案），並用重現圖條件的嚴格比對分數驗證判官本身。

能力差異：在需要結構性推理的任務類上呈現質性差異——B0 在這些任務類得零分故省略，B1-rag 另用 F1 呈現。集合完整性 B2 達 1.00、B1-mem0 僅 0.18、B1-notes 0.08；否定（不存在）問題 B2 達 0.98、mem0 0.06、notes 0.00;supersession 追溯 B2 達 0.98、mem0 0.27、notes 0.12。差距不是因為擷取不完整——B1-mem0 確實含相關事實，但其 top-k 檢索只能返回有限排序切片，無法列舉完整集合、確立不存在、或追溯關係。結構優勢隨所需答案的規模與複雜度增加而增加（兩項目的集合下兩系統相當）。對 B1-rag，集合重疊 F1 在私有語料是 0.94 對 0.25、中立公開語料是 0.90 對 0.34。這種能力是有 token 代價的：122 項完整性集合經 SPARQL 需 78k–167k token，對比目標式檢索約 35k；但基線系統無論花多少 token 都答不出完整答案。

相關性與時效性：簡單相關性任務上兩系統打平——圖在約 35k agent token 下達 coverage 0.82,mem0 約 40k token 下 0.67–0.90。50 到 634 筆記錄的規模研究顯示圖在每個規模都領先（最大規模 hit@5 0.84 對 0.60）但差距大致固定，斜率信賴區間跨零。時效性則不同：四組真實反轉案例、四模型、兩種投遞方式共 40 次試驗，圖因為被取代記錄依構造被排除於當前指引檢索之外，全數 40 次給出當前答案；在同一項反轉測試上，B1-mem0 也打平圖達 100%（冷 agent 得 0%），但自由文字 B1-rag 條件在被取代記錄排名高於當前記錄、且該內容被推入提示的那組情況下，13 次試驗只有 1 次（8%）給出當前答案。

第 4 節：部署、回填與教訓

回填既有 repo：只根據當前狀態建圖會扁平化、丟失歷史關係，故回填流程逐 commit 走訪歷史、抽取帶歷史時間戳的型別化記錄；在作者自家 repo 上還原出七條真實 supersession 鏈。本體是領域層級（如軟體架構概念）而非專案特定，新專案不需要自訂 schema，只需在回填時建實例圖。

預註冊正式試用：「結構化記憶能否在數月真實工作中降低理解負債」無法靠一次性 benchmark 驗證，作者在兩個生產 codebase 上做日常使用測試，設十六個固定的上下文回復參考點（每個對應一個較早做法已從當前樹刪除的反轉案例，答案無法只靠程式碼重建）；黃金答案來自原始來源（從不取自圖本身），盲評判官每月對照月零基準線評分，並設預定失敗條件（每專案每月少於四次記錄引用協助即觸發系統退役）。試用前 21 天，圖提供 71 次未經提示、引用記錄的協助，同時記錄 38 次遺漏（其中 35 次集中在由較薄 commit 歷史回填的那個專案）。

給實踐者的教訓：評測 LLM 記憶系統容易以可預期的方式誤導。作者的評測差點出爐三個錯誤結論：一個 20 分的自家系統勝出其實是評分假象；一個看似的相關性下滑其實是配置錯誤——記憶伺服器掛掉、agent 靜默改用原始儲存直接 grep；一則誤導性 commit 訊息同時污染了一個黃金答案與一則回填的理由。抓住這些問題的規則可推廣到 benchmark 之外：可重判的不可變逐字稿、對照已知分數驗證過的判官、確認記憶工具確實被觸發的執行檢查、只從原始來源取黃金答案。

採用障礙：能力優勢仰賴正確擷取——攤平式擷取會讓圖退化到與純文字相當，這種紀律要求帶來向量儲存沒有的摩擦。設計也依賴主動工具呼叫：MCP 是被動的，agent 自己決定何時呼叫，這偏好層級較高的模型；作者只評測了一個 agent 家族（GPT-5.x）。

第 5 節：結論

對比常見向量記憶工具，本體接地記憶（在有效擷取的前提下）在檢索強項上打平，在完整性、否定、supersession 上明顯更優。小型本地模型與有限上下文視窗應最受益，自然的下一步是把它推進迴圈內部：在程式碼被觸碰時主動推送實體精確的記錄，並依已記錄的限制門控編輯。
