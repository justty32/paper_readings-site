1. 引言

程式碼生成基準長期仰賴單元測試作為正確性的代理指標。HumanEval、MBPP 與 APPS 等基準以「通過測試案例的數量」衡量模型能力，但單元測試本質上不完整——它們只能驗證特定輸入，無法保證所有邊界案例的行為正確。這在安全關鍵系統中尤為危險：通過 10 個測試案例的程式碼仍可能在第 11 個輸入崩潰。

FVAPPS（Formally Verified Automated Programming Progress Standards）提出了一條不同的路徑：將 APPS 基準從 Python 單元測試升級為 Lean 4 形式規格與數學證明。在 FVAPPS 中，模型不僅要實作所要求的函數，還必須完成形式正確性定理的證明——證明空缺以 Lean 的 sorry 佔位，正確提交需同時包含實作程式碼與使所有定理編譯通過的證明策略。

核心洞見：信任從「黑箱 LLM 輸出通過幾個測試案例」轉移到「確定性 Lean 4 核心型別檢查器」。這不是漸進式改進，而是正確性判準的典範轉移——從取樣式實證到窮盡式機械驗證。

2. 背景：APPS 基準與形式驗證

APPS（Automated Programming Progress Standards）是一個包含競賽程式設計與程式面試題目的基準，涵蓋從「入門」到「競賽」難度的 10,000 個 Python 問題。每個問題以英文敘述、輸入輸出範例與單元測試構成。APPS 的局限：測試案例由問題作者提供，覆蓋率不均，且對邊界行為無保證。

Lean 4 是一個依賴型別的函數式程式語言與定理證明器。其核心型別檢查器是信任根基——一個相對小型（約 2,000 行程式碼）的確定性程式，驗證每個定義與定理的型別正確性。sorry 是 Lean 中表示「此處待證明」的佔位符，一個含 sorry 的檔案可以編譯通過但被標記為不完整；完全不含 sorry 的證明被視為完全驗證。

形式驗證的獨特優勢：證明一次，永遠信任。單元測試只對已執行的輸入提供保證；形式證明對所有可能輸入提供保證。這對安全關鍵系統（自動駕駛、醫療裝置、加密協定）不可或缺。

3. FVAPPS 基準建構

3.1 五階段管線

FVAPPS 的建構經過五個階段，從原始 APPS Python 問題逐步升級為 Lean 4 形式規格：

Stage 1（預處理與聚合）：從 APPS 提取問題敘述、函數簽名與輸入輸出範例，聚合為結構化任務描述。

Stage 2（屬性式測試生成）：以 Claude 3.5 Sonnet 驅動的 scaffold loop，使用 Pytest 與 Hypothesis 框架從問題敘述自動生成屬性式測試。這些測試比單元測試更強——它們以隨機生成輸入驗證不變量，提供比少數固定案例更全面的覆蓋。

Stage 3（翻譯為 Lean 4）：將 Python 函數簽名翻譯為 Lean 4 函數定義，並從屬性式測試推導形式規格定理。每個定理以 sorry 佔位證明。此階段產出 4,715 個「Unguarded」樣本——函數定義與定理陳述已就位，但尚未驗證函數是否可解。

Stage 4（Guarded 單元斷言）：為每個樣本加上 #guard 內聯單元斷言——在 Lean 中可直接執行的具體輸入輸出測試。這確保函數定義至少對提供的範例是正確的，過濾掉根本不可解的規格。此階段產出 2,089 個「Guarded」樣本——已驗證函數可解、定理陳述與函數行為一致。

Stage 5（Plausible 屬性測試）：使用 Lean 的 Plausible 框架（類似 QuickCheck 的隨機測試）對定理進行屬性測試。Plausible 以隨機生成輸入執行定理，偵測反例。通過 Plausible 測試的定理具有高度可信度，雖非嚴格證明但大幅降低定理本身錯誤的機率。此階段產出 1,083 個「Guarded and Plausible」最高品質樣本。

3.2 品質分層

FVAPPS 的三層品質分級使研究者可以根據需求選擇難度與可信度：

層級 樣本數 保證
Unguarded 4,715 函數定義 + 定理陳述，未經驗證
Guarded 2,089 函數可解，定理與範例一致
Guarded + Plausible 1,083 定理經隨機測試無反例

3.3 任務格式

每個 FVAPPS 任務包含英文問題敘述與一個 Lean 4 檔案。典型結構如下：

  • 問題敘述（英文）
  • 函數簽名（def solve_xxx ... := sorry）
  • 一組形式規格定理（theorem xxx ... := sorry）

正確提交需同時移除函數定義與所有定理中的 sorry，使整個檔案在 Lean 核心中編譯通過。證明策略可使用 Lean 的任何合法語法：歸納、案例分析、重寫、自動化策略（omega、arith、simp）等。

4. 基準線評估

4.1 實驗設定

從 4,715 個 Unguarded 樣本中隨機抽樣 100 個問題（共 406 條定理），以兩種前沿 LLM 進行基準線測試：

  • Claude 3.5 Sonnet（2024-10 版本）
  • Gemini 1.5 Pro

實驗採用 agentic scaffold loop：模型生成程式碼與證明後，以 lake build 編譯 Lean 專案，將編譯器錯誤（stdout/stderr）回傳給模型進行修正，最多迭代 50 輪。

4.2 主要結果

指標 Claude 3.5 Sonnet Gemini 1.5 Pro
函數定義完成 93 / 100 71 / 100
至少一條證明通過 43 / 100 23 / 100
總定理證明率 30.0% (121/406) 18.5% (74/406)
0/1-shot 可解比例 ~20% ~20%

4.3 人類基準對比

一位形式驗證專家被分配 10 小時處理單一題目（sample 0023，Crooked Election——一個關於選舉結果計算的演算法問題）。結果：

  • 成功寫出函數定義（包含複雜終止證明，使用 termination_by 與 decreasing_by omega）
  • 未能證明任何定理——遞迴展開導致堆疊溢位

此人類基準揭示了形式驗證的內在難度：即使對專家而言，為演算法程式碼撰寫形式證明也是極其耗時且容易失敗的任務。10 小時僅完成函數定義（尚未觸及定理證明），對比 LLM 在少數迭代內可完成約 30% 的定理——形式上 LLM 在此任務上已超越單一專家的生產力。
