4. 透過解析器動態樹（Tree of Parsers）進行上下文相關解析

本文的上下文相關解析設計基於兩個洞見：

  • 要把上下文資訊注入一整套程式語言的完整 CFG 很困難；但如果只關心單一語言構件（例如一個型別標註），在局部建構一個用語意上下文（如附錄 B.2.6）充實過、只接受語義正確程式碼的另一個 CFG，是可行的。
  • 許多 CFG 規則天然對齊上下文邊界。例如，進入區塊時 scope 會改變，處理完變數宣告後上下文就會更新。

基於這兩個洞見，本文開發了一個建構「解析器動態樹（ToP）」的兩階段方案。樹中每個節點都關聯一個 CFG，以及為該 CFG 生成的互動式解析器（附錄 A.1）。

ToP 建構的價值不只限於受約束解碼：它能漸進式地驗證一個未完成程式的語義正確性，可作為強化學習微調 LM（使其更擅長生成語義正確程式碼）的獎勵模型。

第一階段：把完整 CFG 拆解為模組化 CFG 模板——首先把目標語言的完整 CFG 拆解成多個模組化 CFG 模板，這些模板留出「槽位（slot）」，在解析過程中由語意上下文填入。本文引入稱為 placeholder 的特殊終端符，標記一個遞迴點：若父解析器的合法終端符集合中含有對應的 placeholder，就需要在此處長出一個子解析器。附錄 B.2 詳細說明了 sLua 完整 CFG 的拆解方式。

範例 4.1：考慮 sLua 字串運算式的一個簡化模組化 CFG：

str_exp : str_sum
str_sum : str_atom (".." str_atom)*
str_atom : STRING | "(" str_exp ")" | "<STR_PREFIX_EXP>"

此文法匹配可用 .. 運算子串接的字串原子。字串原子可以是字面字串（終端符 STRING，其 regex 省略）、加括號的字串運算式，或字串型別的字首運算式（如字串變數、回傳字串的函式、或最終回傳字串的鏈式函式呼叫）。這裡用 placeholder <STR_PREFIX_EXP> 標示：一旦解析器期望這個終端符作為可能結果之一（除了字面字串與加括號的 str_exp 之外），就應該建立一個「字串字首運算式」型別的子解析器（附錄 B.2.7）。

第二階段：定義解析器樹節點——接著，為第一階段的每個模組化 CFG 模板定義一種樹節點型別。每個節點實例含有一個由對應 CFG 模板生成的解析器（附錄 A.1），其槽位在解析過程中由語意上下文填入。每個節點支援與第 3 節相同、但針對其模組化 CFG 特化的三個函式：has_finished、next_regex、feed_text。每個節點管理自己的解析狀態，整個上下文相關解析器就是這棵樹的根節點。

圖 1 說明了 ToP 在解析一個 sLua 局部變數宣告時的演變。解析流程包括：

  • 取得下一個 regex：形成 regex 前，節點先檢查其合法終端符集合中是否有 placeholder；若有，為每個 placeholder 建立一個子節點。若合法終端符集合中還有非 placeholder 的終端符，父節點會生出自己的一份副本作為子節點，處理接下來的延續。要生成下一段程式合法內容的 regex：若某節點沒有子節點，回傳其解析器所有合法終端符聯集所代表的 regex；否則回傳其所有子節點 next_regex 的聯集。這個聯集 regex 描述了當前程式所有合法的延續。
  • 推進解析器狀態：當一段新片段（如 LM 生成的 token 序列）餵給父節點時，父節點把這段文字轉發給所有子節點。若某子節點解析失敗（表示衝突），該子節點就從父節點中移除。若某子節點在餵入片段後 has_finished 回傳真，父節點的所有子節點都會被移除，並用該完成子節點對應的 placeholder 推進父解析器（若該子節點是父節點的自我副本，則直接用子節點的解析狀態取代父節點的解析狀態）。

附錄的演算法 2 提供了節點基底類別的虛擬碼。在任何時刻，從根節點到某葉節點的任何路徑，都代表一個至少存在一個合法完整程式能從這些解析狀態延續生成的巢狀解析器狀態堆疊。隨著程式碼不斷被消化，會導致衝突的樹分支被剪除，確保只留下合法路徑。

環境管理（Environment management）：如同靜態分析，本文假設有一個依已解析程式追蹤的靜態環境（其追蹤方式依語言而定，例如用堆疊追蹤各 scope 中的符號）。在建立一個帶槽位的 CFG 模板節點之前，先查詢當前環境並填入對應的槽位內容。環境會在某些解析器完成解析時（如定義一個局部變數）或消化某些終端符時（如遇到 do/then/end 進出 scope）更新。例如，在範例 4.1 中要生出字串字首運算式子解析器時，需要查詢環境找出所有最終能得出字串型別的符號。雖然 ToP 有多個分支處理未來的歧義，但因環境只依賴已解析的程式，所以整棵樹只需要一份環境。

控制 ToP 的大小：ToP 的解析時間複雜度與樹的大小成正比。一般而言樹可能會很大，但如果程式語言把能降低解析歧義的規格前置（例如在任何運算式之前先寫型別標註），樹的大小可以大幅縮小。本文刻畫了一種讓 ToP 保持「掃帚形（broom shape）」的情況，確保樹維持精簡。

假設（A2）（掃帚形 ToP）：當一個解析器節點 x 生出超過一個子節點時，x 的所有祖先節點都只能有一個子節點。

附錄的引理 B.1 證明本文的 sLua ToP 滿足此假設。

滿足不可延伸匹配性質：為確保 ToP 根節點的 regex 滿足 A1，本文建議一個 look-ahead 策略，要求模組化 CFG 滿足以下假設：

假設（A3）：模組化 CFG 中，任何 placeholder 終端符、或違反 A1 的終端符，其後必須接著一組滿足 A1 的非 placeholder 終端符。

多數流行程式語言天然滿足此假設，因為它們常包含大量分隔符，例如 C 風格語言中敘述後的 ;、Lua 中結束區塊的 end、或多種語言中函式呼叫後的 )。（本文禁止用 placeholder 接續 placeholder，以避免遞迴式的 look-ahead。）

延伸 regex 以滿足不可延伸性的 look-ahead 策略：當某個終端符或子節點回傳的 regex 違反 A1 時，本文往前查看「接受該終端符或 placeholder 之後」的下一組終端符集合，把匹配該集合的 regex 附加到現有 regex 上。為確保模組化 CFG 不會以違反 A1 的終端符結尾，本文在起始規則末端視需要加入一個「結束符號」槽位。實例化時，查詢父解析器「在接受該子節點 placeholder 之後」的終端符集合，把代表這些終端符聯集的 regex 填入結束符號槽位。套用此策略後為 sLua 得到的範例 regex，可見附錄 C.10。
