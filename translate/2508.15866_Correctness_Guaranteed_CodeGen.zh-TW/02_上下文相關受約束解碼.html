3. 上下文相關受約束解碼

演算法 1（Context-sensitive constrained decoding with token healing）：輸入為上下文相關解析器 P、語言模型 L、提示 prompt；輸出為生成的程式。演算法維護 prog（已確認的程式）與 prefix（部分匹配的 token 前綴），只要 P 尚未 has_finished()：先用 re.escape(prefix) + "(" + P.next_regex() + ")" + ".*" 建構修改後的正規表示式 r（支援 token healing，見圖 2），由 r 建出 DFA A；接著用自適應拒絕採樣（adaptive rejection sampling）——以 Gumbel-top-k 技巧對 LM 的 next-token logits 排序，依序檢查每個候選 token 是否被 A 接受，一旦接受即推進 DFA 狀態並加入輸出——直到 DFA 進入終態；然後將輸出 token 拼成字串，若「去掉最後一個 token」仍被 A 接受，代表最後一個 token 只是部分匹配，取出該 token 使其匹配的最長前綴 new_prefix，把新確認的片段 new_prog 餵給 P.feed_text() 推進解析器狀態；如此反覆，直到 P 判定已生成完整程式。

Overview（總覽）：演算法 1 接收一個上下文相關解析器 P 與語言模型 L，生成能被 P 解析的程式。P 需支援三個介面：has_finished()（是否已解析出完整程式）、next_regex()（回傳一個滿足 A1、匹配下一段的正規表示式）、feed_text(s)（餵入片段 s、推進解析器狀態）。每一步用 P 的 regex 引導生成下一段程式，再用 token healing（圖 2）處理 token 跨越前後兩個 regex 邊界的錯位問題。

Regex Requirement（正規表示式的要求）：用一連串 regex 引導受約束解碼時，主要挑戰是要讓 LM 有機會在 regex 已匹配時選擇停止生成，讓解析器狀態往前推進。一般 LM 會輸出特殊的停止 token 來結束生成，但這裡是要 LM 一次只生成程式的一個片段——由於 LM 通常是在完整程式上訓練的，它在程式中途取樣到停止 token 的機率接近零。

範例 3.1：假設解析器指出下一個程式片段應為整數，regex 為 /[0-9]+/。由於這個 regex 可以無限匹配數字，為了讓生成停下來，受約束解碼演算法必須自行決定何時停止。但如果把 regex 改成 /[0-9]+<END>/，其中 <END> 是一組依當前上下文而定、標誌「整數結束」的符號，那麼「何時停止」的責任就交還給身為程式碼生成者的 LM——例如若該整數是函式呼叫的最後一個引數，<END> 應包含 )；若該整數是算術運算式的一部分，<END> 應包含任何算術運算子，以及（若已有配對的 (）)。

為將範例 3.1 的直覺形式化，本文引入以下假設：

假設（A1）（不可延伸匹配，Non-extensible match）：在演算法 1 中，P.next_regex() 回傳的任何 regex 必須滿足——若字串 s 匹配該 regex，則 s 的任何延伸都不能再匹配該 regex。

換言之，在演算法 1 建構的 DFA 中，不能從一個終態再走到另一個終態。因此一旦 DFA 進入終態，就能放心停止生成、往下一步走。第 4 節說明如何用 look-ahead 策略讓解析器 P 滿足 A1。

用自適應拒絕採樣加速：用 regex 引導生成時，本文先建構一個接受字元的 DFA，再用自適應拒絕採樣（Gilks & Wild 1992）在每個解碼步驟採樣出合法的下一 token。採用自適應拒絕的觀察是：現代 LM 在不加約束時多數情況下也能生成正確程式碼——因此若第一個採樣到的 token 本就合法，自適應拒絕就退化為無約束採樣。另一種做法是把接受字元的 DFA 編譯成接受 token 的 DFA（Willard & Louf 2023；Koo et al. 2024），但由於 regex 持續在變，每個語意片段都要重新編譯一次，成本很高。表 1 的基準測試顯示，在演算法 1 中，自適應拒絕採樣比 Willard & Louf（2023）與 Koo et al.（2024）快 3 倍以上。

處理 Regex 邊界的 Token 錯位（Token Healing）：由於 LM 使用自訂的子詞分詞器，其 token 可能跨越上下文相關解析器輸出的兩個連續 regex 的邊界（圖 2 舉例：while ({ 是單一 token，卻跨越了「NewTalent(」與「{」兩個 regex 的邊界）。為解決此錯位問題，演算法 1 加入了圖 2 所示的 token healing 策略：用一個 prefix 變數記錄前一 regex 中部分匹配 token 的前綴，並把 regex 修改為「前綴的跳脫字串 + 原 regex + .*」，確保第一個生成的 token 必須以 prefix 開頭，同時允許最後一個 token 只部分匹配。得益於 A1，修改後的 regex 只要對應 DFA 進入終態，就能確知最後一個 token 是完全或部分匹配，可以安全停止該 regex 的生成。
