6. 分析（Analysis）

6.1 機制：結構化打破檢索-動作迴圈

SaP bundle 在一次回應交付兩個結構化信號（帶類型合約 + 內聯動作模板），而 GoS 強迫 agent 在長篇混合散文中定位兩者——"lost-in-the-middle" 退化（Liu et al. 2024a）實例。三觀察支持：

  • 檢索後動作正確率： SaP 檢索後下一環境動作成功 29.3% vs GoS 20.5%（pooled 3 seeds）；差距在 READ_SKILL 事件擴至 29.8% vs 19.0%（1.57x）——agent 明確查閱技能時 SaP bundle 顯著更可靠地發出正確即時動作。
  • 迴圈為失敗單元： 失敗遊戲發出 ~4x 更多 SkillRequests 及 "Nothing happens."；SaP 在失敗遊戲 SkillRequest/game 減少 ~30%。
  • Trace 對比： idx_36（put a hot mug in a cabinet）：GoS 22 步 4 次 SkillRequest 獲勝，三次 near-syntax errors；SaP 7 步一次 READ_SKILL 獲勝，直接發出 bundle 暴露的模板。第二 SaP-only zero-retrieval win（idx_122）在附錄 P、Q。

6.2 BE 與 RC 各自修復什麼

元件消融隔離兩失敗模式（詳 §5.4）：RC 修復 parent 殘留動詞衝突（Example block 發出引擎不接受的動詞）；BE 丟棄 30% 確定性調用點為偽陽性。兩者瞄準散文誘發迴圈的不同上游成因：未改寫內容中的陳舊語法（RC）與偽陽性群集成員（BE）。

7. 結論（Conclusion）

結果提出更廣泛問題：技能庫應否直接以偽代碼撰寫？Markdown 為人類作者最佳化，但 LLM agent 每次檢索支付散文→結構轉換成本。SaP 展示此成本可事後以確定性品質控制回收——在索引時而非每次讀取時支付。帶類型目錄（OpenAPI、MCP）發布者可於索引時預先代換；無法直接寫偽代碼的領域專家繼續寫散文，驗證器驅動管線為他們維護 agent 可讀偽代碼層。更廣泛地，SaP 的紀律——每個 LLM 提取是假設，由確定性規則檢查，非黑箱輸出——可移植至其他散文→結構任務（runbooks 的 schemas、法律文件的 terms、wikis 的 API specs）。四個檢查因域而異，規則通用：通過附見證，拒絕附命名原因。

局限（Limitations）

  1. 庫範圍： 僅在 skills_500 markdown 庫端到端運行。Typed-API 庫（Stripe OpenAPI 587 endpoints、GitHub OpenAPI 1153 endpoints）parser+candidate 階段完成，未在驗證重構管線下主實驗。
  2. Replacement 為靜態： 驗證器檢查 invoke(κ, ⃗a) 語法替換的可行性，未測試 agent 運行時是否正確落地調用。未實作運行時 invoke 展開機制（如 sap_invoke tool）。
  3. SkillsBench 取樣： 10/87 取樣（6 easy + 4 medium），報告為通用性檢查與案例研究，非錦標賽級比較。全 87 任務評估因經費推遲。

倫理聲明（Ethics Statement）

所有技能庫公開可用（GoS skills_500 於 HuggingFace；ALFWorld 開源；SkillsBench 開源於 GitHub）。無 PII、專有數據或人類受試者。LLM 開支 ~$30。Risk 驗證器有意保守——防止庫分解時無聲聚合不安全操作，但不聲稱為完整安全解決方案（不檢測 prompt injection、adversarial chains 或高層推理失敗）。管線以 CLI 腳本序列釋出，附帶重構後 skills_500 庫、全部 134-game 與 10-task 實驗輸出、校準策略文件。Temperature=0 運行名義確定性，實際受限於 OpenAI API 底層非確定性。
