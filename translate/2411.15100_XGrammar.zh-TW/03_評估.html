4. 評估

XGrammar 以 12,000 行核心 C++ 實作並提供 Python 綁定，便於與推理框架無縫整合。回答四問：mask 生成效率、端到端開銷、各優化效果、對下游任務影響。

4.1 mask 生成效率

以 JSON schema（可轉 regex）測試 regex-based 方法；再以超出 regex 能力的 CFG 測試：無約束 JSON（ECMA-404，因任意巢狀無法被 regex 處理）、XML（XML 1.0）、Python DSL（基本控制流與資料型別，忽略縮排）。基線：Outlines(v1.0)、llama.cpp 文法引擎（b3998）、lm-format-enforcer（v0.10.9，regex-based、不支援 CFG）。硬體 Llama-3.1-8B-Instruct＋Ryzen 9 7950X＋RTX 4090。結果（圖 9）：XGrammar 各任務延遲最低——JSON Schema 與 CFG(JSON) 每 token <40µs，XML 與 Python DSL <200µs；JSON Schema 最高 3×、CFG 最高 100× 加速（對各自最佳基線）。

4.2 端到端 LLM 引擎評估

以 §3.5 重疊技術與服務引擎協同，整合進 C++ 的 MLC-LLM 與 Python 的 SGLang。先比較支援結構化生成的引擎（vLLM v0.6.3＋Outlines、llama.cpp 內建文法引擎），指標為每輸出詞元時間（TPOT），Llama-3.1-8B-Instruct、JSON schema 與 CFG，AMD EPYC 7R13＋H100，固定 batch，平均輸入 139 / 輸出 53 token。結果（圖 10）：XGrammar 在 JSON Schema 與 CFG 皆取得最佳 TPOT；vLLM 在大 batch 時因文法處理壓在 CPU 而明顯變慢；整體最高 80× 輸出詞元率。

表 1（TPOT ms，JSON Schema，SGLang）：

模型 +Outlines +XGrammar
Llama-3.1 8B 44.2 6.8
DeepSeek-V2-Lite 16B MoE 15.8 4.8

表 2（MLC-LLM 上開/關 XGrammar，TPOT ms）：JSON Schema batch 1：6.2→6.3、batch 16：9.0→9.2；CFG(JSON) batch 1：6.3→6.3、batch 16：9.0→9.1——近零開銷且輸出品質更佳。

4.3 優化技術消融（表 3）

CFG（無約束 JSON）、Llama-3.1 8B、json-mode-eval，逐步疊加優化的每詞元延遲：

配置 每詞元延遲（ms）
PDA Baseline 65.776
+ Node merging 38.280（1.7×↓）

+ Context Expansion 0.018（1.9×↓）

adaptive token mask cache 貢獻最大，其餘技術亦有明顯改善。

4.4 對結構化生成任務的影響（表 4）

評估 function calling（JSON schema 導引）與 XML 生成的語法正確率，Llama-3.1 8B：function calling 62%→100%、XML 生成 80%→100%。沒有 XGrammar 時模型常在程式輸出外夾帶額外解釋、或生出非預期型別的 JSON，令輸出無法被下游直接使用；XGrammar 以強制文法約束避免此問題，達 100% 語法正確。

5. 相關工作

  • 演算法改進：Koo et al.(2024) 把字元級 PDA 轉 token 級 PDA；有工作以 prompting 指定輸出結構；也有以 finetune 提升結構化生成品質——XGrammar 與這些正交、可結合。
  • 受約束解碼：lm-format-enforcer 用 regex 表示語法但無法處理複雜 CFG；Synchromesh、llama.cpp 分別用 LR parser/PDA 處理 CFG 生 mask，但執行期須檢查整個詞彙表、開銷大；Outlines 以 lexer+parser＋快取加速，但只考慮最近一個 lexer token，當 LLM token 跨多個 lexer token 時可能誤判；SynCode 用跨多 lexer token 快取的 lexer+parser，但須全部離線處理、前置開銷大。XGrammar 以 PDA 支援 CFG，並以 adaptive token mask cache 在預處理與執行期自適應處理 token、結合系統優化，兩階段皆達最小開銷。
  • 宣告式框架：Guidance、LMQL、SGLang 提供靈活的結構宣告方式——XGrammar 與其互補，可作後端引擎加速。
  • 服務引擎：MLC-LLM、SGLang、vLLM 等用 continuous batching、PagedKVCache 等技術；AICI 提出 CPU-GPU 平行範式加速結構化生成——這些皆可用 XGrammar 做高效結構化生成。

6. 結論

XGrammar 把詞彙分成 context-independent 與 context-dependent 兩類，預先檢查前者存進 adaptive token mask cache，以持久化堆疊加速後者檢查，並與 LLM 推理協同設計讓文法執行與 GPU 計算重疊。系統大幅加速 token mask 生成，在端到端 LLM 推理達成零開銷結構化生成，期望能支援跨平台更廣泛的結構化生成。

附錄要點

  • 附錄 A：PDA 變體的形式定義（本文採用之等價定義）。
  • 附錄 B（與 jump-forward decoding 的協同）：jump-forward decoding 在「後續輸出可由文法確定推得」時繞過 LLM 解碼、直接 tokenize 並附加到上下文以加速；此技術與受約束解碼正交，XGrammar 進一步支援並與之結合。SGLang＋Llama-3.1-8B（RTX 4090、batch 1）上（圖 11），XGrammar 一貫優於 Outlines，且與 jump-forward 結合達最佳 TPOT。
  • 附錄 C（跨平台部署）：以 Emscripten 把 XGrammar 編成 WebAssembly、建 JavaScript 綁定，使其能在筆電/手機的瀏覽器端執行，並整合進瀏覽器內 LLM 框架 WebLLM。以 4-bit 量化 Llama-3.1-8B（MacBook Pro M3 Max＋Chrome）與 Qwen-2.5-0.5B（iPhone 14 Pro Max＋Safari）測 TTFT 與 TPOT（圖 12），XGrammar 在兩者皆帶來近零開銷，展現支援未來裝置端 agent 的潛力。
