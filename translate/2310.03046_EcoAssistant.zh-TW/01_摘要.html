摘要

今日使用者把大型語言模型（LLM）當助手回答需要外部知識的查詢：問某城市的天氣、問股價、甚至問住家附近特定地點在哪。這些查詢要求 LLM 產生程式碼、呼叫外部 API 才能回答，然而 LLM 很少一次就寫對程式碼，需依執行結果迭代精修（iterative code refinement）。此外，用 LLM 助手支撐高查詢量所費不貲。本文提出框架 EcoAssistant（開源於 github.com/JieyuZ2/EcoAssistant），讓 LLM 更便宜且更準確地回答程式碼驅動的查詢。它含三個組件：(1) 讓 LLM 助手與自動程式碼執行器（code executor）對話，依執行結果迭代改碼或給出答案；(2) 使用LLM 助手層級（hierarchy），先用較弱、較便宜的 LLM 嘗試，失敗才 back-off 到較強、較貴者；(3) 從過去成功查詢檢索成功解當作 in-context 示範協助後續查詢。實證上 EcoAssistant 在成本與準確率上皆有明顯優勢——以不到 GPT-4 一半的成本、把成功率超出 GPT-4 達 10 個百分點。

1. 引言

使用者近來把 ChatGPT 等對話式 LLM 用於各種查詢；報告指出 23% 的 ChatGPT 查詢屬知識抽取用途。許多此類查詢需要預訓練 LLM 內部所無的外部知識：問城市天氣「What is the current cloud coverage in Mumbai, India?」、問股價「Can you give me the opening price of Microsoft for January 2023?」、問地點「I'm looking for a 24-hour pharmacy in Montreal」。這些任務只能靠呼叫含所需資訊的外部 API 完成——作者稱為程式碼驅動問答（code-driven question answering），要求 LLM 產生程式碼經 API 取得資訊。

正如人類工程師鮮少一次寫對程式碼，LLM 亦如此，且當前 LLM 缺乏「執行自己產生的程式碼並迭代除錯」的能力。此外查詢量巨大（ChatGPT 2023 年 7 月約 80M 查詢，其中 23% ≈ 4M 是知識查詢），用付費線上 LLM 服務處理成本高昂。

為此本文提出 EcoAssistant，首個為「用對話式 LLM 更便宜且更準確地處理程式碼驅動問答」量身打造的系統。它不需任何離線準備或訓練，是純線上服務、隨使用而改進。三個核心組件：

  1. 為支援迭代改碼，讓對話式 LLM 當助手代理與自動程式碼執行器對話、反覆精修程式碼以正確呼叫 API；系統建於 AutoGen（多代理對話框架）之上。有別於「單次生成程式碼或答案」的既有做法，本設計善用對話式 LLM 迭代精修輸出的能力。
  2. 採用助手層級：對每個查詢從最具成本效益的 LLM 開始，只有當前助手失敗才逐步 back-off 到更貴者；因 LLM 定價異質，此簡單策略能藉減少貴模型使用量而降低整體成本。
  3. 提出成功解示範（solution demonstration）：查詢成功後，把 query-code 對存進資料庫；新查詢進來時檢索最相似的 query 與其程式碼，當作 prompt 中的 in-context 示範，使助手更可能少迭代就產生準確高效的回應。

雖然層級與成功解示範各自即有優勢，兩者的交互作用產生綜效、放大各自效益：因層級中的助手共享同一 query-code 庫，強而貴的 LLM 產出的解成為弱模型後續查詢的有用指引，使弱助手日後能解更多查詢，進一步降低系統對貴 LLM 的依賴。系統性實驗顯示：層級大幅降成本、成功解示範大幅提表現，兩者合一（EcoAssistant）在更低成本下達更優表現，較單獨 GPT-4 助手高 10% 成功率且花費不到一半。

2. 程式碼驅動問答任務

本文聚焦一個實用而具挑戰的任務：LLM 須回答知識查詢，並產生程式碼呼叫 API 取得必要資訊。例如查詢某地某日的即時天氣——此資訊不在模型內部知識中，須靠天氣 API 取得。LLM 不僅要正確理解查詢，還要寫出像樣的 Python 程式碼，因此同時考驗自然語言與程式語言的理解與生成。這使它有別於開放領域問答或瀏覽器輔助問答（不考驗改碼能力），也有別於一般程式生成任務（本任務要求依查詢運用特定領域 API）。

迭代改碼（Iterative coding）：程式碼驅動問答天然需要迭代改碼。把底層 LLM 與程式碼執行器相連——執行器執行產生的程式碼，把執行結果或失敗 trace 回傳給 LLM；此互動可多次發生，LLM 依上次 trace 精修生成。可視為 LLM 與執行器間的自動多輪對話，完全在背景進行、無需使用者介入。採用 GPT-3.5-turbo 等 chat LLM。

查詢串流而來（Queries come streaming）：考量真實場景中查詢隨時間依序到來，故每個查詢不是獨立任務，可借過去查詢為指引；本系統探討如何用過去成功查詢更好地服務未來查詢。

3. EcoAssistant：更便宜且更準確地使用 LLM 助手

程式碼驅動問答既具挑戰又昂貴。EcoAssistant 含三個組件（見圖 1）：其一，把 LLM 當助手代理與程式碼執行器對話，LLM 讀執行器輸出或失敗 trace 迭代除錯、最終依取得資訊給答案；其二，用 LLM 助手層級，先試便宜者、再訴諸更貴者；其三，追蹤成功查詢與其程式碼、當作後續查詢的 in-context 示範。系統無需離線準備、無需資料整理、無需訓練。

圖 1（文字說明）：系統含兩個代理——執行程式碼的 executor 代理，與由 LLM 支援、負責建議程式碼以取資訊並回應查詢的 assistant 代理。query-code 資料庫存放過去成功的 query-code 對；新查詢進來時檢索庫中最相似 query，把其關聯程式碼展示在初始 prompt。對話先叫最具成本效益的助手，只有失敗才在層級中試更貴者。

LLM 助手與程式碼執行器的自動化對話：LLM 當 assistant 代理置於與程式碼執行器的對話中。執行器抽取並執行產生的程式碼、把輸出回傳，再等下一輪——LLM 據此精修或依執行結果給最終答案。系統建於 AutoGen 之上，利用其內建 AssistantAgent（LLM 助手）與 UserProxyAgent（程式碼執行器）。前者被配以 AutoGen 的專用系統 prompt，指示 LLM：1) 必要時在 coding block 中建議程式碼；2) 依執行結果精修程式碼；3) 想結束對話時在回應末尾附上特殊碼 TERMINATE。後者作為使用者代理，自動抽取並在本地執行程式碼、回傳結果；偵測不到程式碼時回傳預設訊息。整個對話自動化，使用者只需輸入原始查詢即可觸發，無需手動複製貼上執行。

對話在以下任一情形終止：1) 超出 LLM 的 context window；2) 來回輪數超過設定閾值（本文設每段對話最多 5 輪）；3) LLM 在回應末尾附 TERMINATE。

助手層級（Assistant hierarchy）：對多個 LLM 各起一個 AssistantAgent，從最具成本效益者開始自動對話。若當前助手與執行器的對話結束仍未解出查詢，系統就用層級中下一個更貴的 LLM 重啟對話。考量 LLM 定價異質（GPT-3.5-turbo 比 GPT-4 便宜一個數量級），此策略能藉最小化貴 LLM 的使用而顯著降本，同時仍有效處理查詢。

成功解示範（Solution demonstration）：真實場景中查詢依序到來，系統以過去成功協助未來。具體而言，每當查詢經使用者回饋判定成功解決，就捕捉並儲存該 query 與最終程式碼片段，存入專用向量資料庫；新查詢出現時，EcoAssistant 檢索庫中最相似 query，把其關聯程式碼附進新查詢的初始 prompt 當示範。此舉以更少迭代改進查詢解決流程、提升系統表現。

助手層級與成功解示範作為獨立設計各有優勢（前者藉減少對貴 LLM 依賴降本，後者藉借過去成功提升 LLM 表現）；合用則放大各自效益——即便無專門設計，強 LLM 助手也透過共享 query-code 庫隱式指導弱助手。
