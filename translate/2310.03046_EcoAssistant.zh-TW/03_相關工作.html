5. 相關工作

LLM 多代理對話：LLM 代理備受關注；近來有多代理對話以釋放代理間協作潛力的努力（AutoGen），應用含多代理協同完成任務（CAMEL、MetaGPT、ChatDev）、多代理辯論以鼓勵發散思考或提升事實性與推理。本文聚焦以多代理對話處理程式碼驅動問答，強調成本效率與表現。

LLM 的成本效益部署：多數既有努力藉量化、prompt 摘要/壓縮、批次化等改進時間/計算效率。本文則求降低使用 LLM API 服務的美元成本：與 EcoOptiGen（降低 LLM 推論超參最佳化的美元成本）、FrugalGPT（探索多種技術降低單輪文字生成的美元成本）目標相近，但本文聚焦在多代理對話中以成本效益的方式把 LLM 當代理。

6. 結論

本文探索程式碼驅動問答的可負擔且精確的 LLM 應用，提出建於雙代理對話框架的 EcoAssistant——含一個 LLM 支援的 assistant 代理與一個 code executor 代理，靠兩者互動處理查詢。它含兩項簡單而有效的技術：助手層級（優先用具成本效益的 LLM）與成功解示範（借過去成功解服務新查詢）。實證顯示 EcoAssistant 能同時降本並提升表現。

附錄擇要

  • A 局限與未來：局限——(1) 靜態層級未必最優、缺自適應選擇；(2) query-code 庫在百萬級查詢時成瓶頸，需剪枝機制；(3) 對高度專精/冷門查詢較弱；(4) 多輪迭代帶來延遲；(5) 長對話 context 受 token 上限限制。未來——更豐富的使用者回饋、加入更多代理、更進階的檢索機制、擴展至語音/影像等多模態。
  • B 模型評估 vs 人工評估：以人工評估為真值檢驗 GPT-4 評審——recall 全為 100%（GPT-4 判失敗時確實失敗），precision 介於 66%–84%（仍有改進空間）；故自主系統若有更好的 GPT-4 evaluator 應更佳。
  • C 對話可視化：以圖示範一段由使用者查詢觸發、assistant 與 code executor 自動來回直到終止的對話。
  • D 實作細節：實驗機為 Intel Xeon E5-2678 v3 + 512G 記憶體 + 兩張 48G NVIDIA RTX A6000（GPU 僅用於部署 LLAMA-2-13B-chat）。prompt 含推薦 API、（用示範時的）query-code 模板與使用者查詢；CoT 則於末尾附「Let's think step by step.」；模型評審系統 prompt 令 GPT-4 產生單一 yes/no 判斷。code executor 偵測不到程式碼時回傳預設訊息「Reply TERMINATE if everything is done.」讓對話推進。
  • E 案例研究：以 GPT-3.5-turbo 對比有/無成功解示範的對話（各領域一例）——無示範時 GPT-3.5-turbo 常因參數錯誤、誤用他 API 的金鑰、或程式邏輯錯（如 stock 的 price_on_date 變數未正確使用）而失敗；有示範後能正確取得餐廳/天氣/股價資訊並答對查詢。
