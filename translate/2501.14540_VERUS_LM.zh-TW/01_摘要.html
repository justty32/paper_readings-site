摘要

近期一種神經符號推理途徑是顯式結合 LLM 與符號 solver 的優勢來解複雜推理。然而現有方法有顯著限制：任務專屬 prompt 導致泛化差、知識與查詢未分離造成低效、推理能力受限——這些缺陷妨礙其可擴展性與跨域適用性。本文提出 VERUS-LM：採通用 prompt 機制、清楚分離領域知識與查詢、支援廣泛的不同邏輯推理任務。此框架提升適應性、降低計算成本、並支援更豐富的推理形式（如最優化與約束滿足）。我們在一個新資料集上於多樣推理任務顯著勝過 LLM；在常見推理 benchmark 上與同類 SOTA 競爭力相當，並在困難的 AR-LSAT 上大幅超越。VERUS-LM 推進混合推理的邊界，是邁向更通用神經符號 AI 的重要一步。（程式與資料：gitlab.com/EAVISE/bca/verus-lm）

1. 引言

邏輯推理是解題、決策、批判思考的核心。GPT-4、Gemini 等 LLM 經 CoT 展現類推理能力的躍進，但無法保證忠實、透明的推理——本質上是黑箱機率模型，難確保準確連貫的推理步驟，故其是否「真推理」仍有爭議。符號推理引擎則能導出可證正確且通常可解釋的結論，但難解讀模糊的自然語言。這給 NeSy 結合兩者之長創造機會（鬆散對應 Kahneman 的 System 1 快思 / System 2 慢思）。

但現有 SOTA 有限制：重度依賴任務專屬 prompt（經 in-context learning 生符號表示）→ 較不通用、難適配新域；且通常把每個查詢化約為同一種（或極少數）推理任務→ 缺乏多功能性。本文提出 VERUS-LM：通用 prompt 管線、語意精煉步驟、宣告式知識與問題清楚分離、支援廣泛邏輯推理任務。

2. 相關工作

本文聚焦「LLM 耦合顯式符號推理引擎」這類 NeSy（不談 in-context/微調式改進）。現有系統大同小異：給推理問題（領域描述 + 待答查詢），先讓 LLM 生形式表示再交推理引擎解。

  • [LLM]+ASP / ASP 管線：LLM 三次（抽常數→生謂詞→生 ASP 規則），邏輯謎題上比 GPT-4 基線 +71%；或 LLM 抽原子事實 + 手工「知識模組」（領域 ASP 規則）餵 ASP solver。
  • LINC：LLM 生 FOL → FOL 推理器；生 K 個形式化 + K-way 多數投票緩解形式化錯誤；在 FOLIO 競爭力、ProofWriter 顯著提升。
  • Logic-LM：兩大特色——(1) 支援邏輯程式/FOL/CSP/SAT 多種語言；(2) 自我精煉（LLM 依 solver 回饋迭代修語法錯）。但在多樣的 AR-LSAT 上僅 43.04%。
  • SymbCoT：內部用 in-context 把問題轉 FOL，但不用獨立推理引擎——LLM 自己逐步推理（模仿 solver 的 prompt）→ 對語法錯更穩健；在 PrOntoQA/FOLIO/ProofWriter 一致勝 CoT 與 Logic-LM。

多數方法依賴資料集專屬範例做 in-context、僅支援少數推理任務 → 泛化受限，在多樣的 AR-LSAT（LSAT 法學院入學考題）上尤其明顯。

3. 系統設計

3.1 需求

現有方法多聚焦單一推理任務；但現實用例（如車險數位助理）使用者會問「我符合投保資格嗎?/為何（不）符合?/依車型保費多少?/改什麼能讓保費最低?」。故兩大需求：(1) 須支援多種推理模式（任務專屬 prompt 行不通，由 AR-LSAT 結果為證）;(2) 推理組件須能做不同推理——可用多引擎（如 Logic-LM）但須為每種推理重新形式化（增成本與錯誤），故偏好用單一支援多種推理的引擎。

VERUS-LM 設計需求：(1) 多功能（驗證/解釋/最優化…）;(2) 知識複用（區分「領域知識」與「待執行任務」，知識可被不同任務複用）;(3) 通用（含 prompt 法在內，皆獨立於推理任務類型或領域）。

3.2 推理引擎

選 IDP-Z3——FO(·) 的推理引擎（古典一階邏輯的豐富擴展：型別、聚合、（歸納）定義等）。它顯式支援知識庫範式（Knowledge Base Paradigm）：同一份領域知識可用於多種不同推理任務。

FO(·) 範例（車險）：詞彙 V 含型別（Customer、Car）、函數（risk_factor: Car→Real、age: Applicant→Int）、常數（car_value、premium…）、謂詞（applicant）；結構 S 給部分符號解釋（age:={Ann→16,Brit→32}）；理論 T 含句子（∀ applicant 須成年；premium=car_value/100×risk_factor(car_type)）。S⊨T 即 S 為 T 的模型。同一 KB，IDP-Z3 可：判斷誰符合投保並解釋為何、算保費、「最優化」保費（找風險係數最低車型）——無需改 KB，直接知識複用。FO(·) 表達力足以建模眾多領域，且 FOL 在 LLM 訓練語料中常見故 LLM 對此形式流暢。

3.3 VERUS-LM 架構

兩階段（圖 1）：階段一 知識庫建立——LLM 把領域知識翻成符號 FO(·) 規格，此階段不考慮具體問題，造可複用 KB;階段二 推理——才考慮問題，解讀後以適當的 IDP-Z3 推理任務呼叫作答。同域多問只需形式化一次，大幅省算力。

4. 知識庫建立（三步）

4.1 符號抽取

LLM 先辨識領域的型別、函數、謂詞。Prompt 不含特定資料集範例，只給通用指示 + 三個不出現在任何資料集的通用範例；並要求為每個符號標註非形式語言意義供後續使用。

  • OWA 變通：IDP-Z3 不支援開放世界（FOLIO/ProofWriter 需要），它總用封閉世界假設（CWA）、要求所有型別（除內建 R/Z）完全列舉。VERUS-LM 在每個型別加一個額外「unknown」元素模擬 OWA——理論上不正確但實務一貫產出正確結果。

4.2 公式抽取

LLM 生對應領域描述的 FO(·) theory。給簡短 FO(·) 文法概覽 + 清楚指示 + 兩個步進式範例（每句邏輯配其自然語言意義）；要求也考慮隱含與常識知識;prompt 末附前面生成的詞彙與待形式化的問題描述。

4.3 自我精煉

雖 LLM 常產出正確邏輯句，仍會錯。引入用推理引擎回饋修錯的自我精煉（受指令式程式設計與 Logic-LM 啟發）。但 Logic-LM 等只管語法正確，本文新增語意正確一步（用可滿足性檢查）。迭代直到無錯或達上限。

  • 語法精煉：solver 報語法錯時，以「LLM 前次錯誤輸出 + solver 錯誤訊息 + 常見語法錯與修法範例」要 LLM 修；詳細錯誤由 IDP-Z3 的程式分析工具 FOLINT 提供。
  • 語意精煉：KB 語法正確後用可滿足性檢查找語意錯。KB 此時應可滿足（只含領域知識的形式化、尚無具體目標）；若已不一致 → 視為 LLM 翻錯，用 IDP-Z3 生的**「最小不可滿足子集」**當解釋去要 LLM 修。
