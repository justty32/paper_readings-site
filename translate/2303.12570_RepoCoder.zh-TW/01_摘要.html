摘要

倉庫級程式碼補全的任務，是根據倉庫的更廣上下文續寫未完成的程式碼。對自動補全工具而言，要利用散落在不同檔案中的有用資訊並不容易。我們提出 RepoCoder——一個簡單、通用、有效的框架：它把相似度檢索器與預訓練程式碼語言模型組進一條迭代式檢索-生成（iterative retrieval-generation） 管線，能有效利用倉庫級資訊、並在不同粒度上生成程式碼。我們另提出新 benchmark RepoEval，取材自最新的高品質真實倉庫，涵蓋 line、API 呼叫、function body 三種補全情境。實驗顯示 RepoCoder 在所有設定下都把 In-File 補全基線提升超過 10%，並一致勝過原生的檢索增強補全法；我們也透過完整分析驗證其有效性，為後續研究提供洞見。原始碼與 benchmark 皆已開源。

1. 引言

真實軟體開發中，開發者寫程式時必須顧及倉庫內的其他檔案。倉庫內的程式碼檔案常有互相關聯的依賴（模組化帶來的共用工具、設定、跨 API 呼叫），且每個倉庫通常遵循自訂的命名慣例與程式風格。因此倉庫級補全要求工具利用倉庫的更廣上下文，而非只靠檔案內（in-file）資訊。然而打造有效的倉庫級補全工具仍是未解難題：靠靜態程式分析與啟發式規則的方法能可靠解析特定倉庫上下文，卻限制了「在檔案任意位置做任意長度補全」的能力；在標註資料上微調語言模型的方法在各自評測情境表現好，但難以在不重新訓練下泛化到未見過的倉庫。

本文提出用現成檢索器在倉庫中定位有價值資訊、增強語言模型的上下文。如圖 1，我們先以檢索增強生成（RAG）強化傳統的 In-File 補全——從倉庫搜相關片段來輔助生成；再進一步提出 RepoCoder，用一條迭代式管線，把「生成出來的補全」拿去強化檢索，藉此橋接「檢索上下文」與「意圖中的補全目標」之間的落差。

圖 2 的例子說明設計動機：只靠未完成程式碼不足以從倉庫檢索到有用資訊。例中模型在第一輪「即興」寫出一個呼叫 COLMAP API 的語句，預測的參數看似合理卻不正確——因為補全點之前的殘缺程式碼，並不是能對準補全目標的良好檢索查詢。然而，只要用模型生成的補全再對倉庫做一次檢索，就能成功取回目標 API 的簽章、正確地補完程式碼。

此外我們提出 RepoEval benchmark，取自 GitHub 最新高品質倉庫，補上倉庫級情境缺乏公認 benchmark 的空白。RepoEval 是首個涵蓋 line、API 呼叫、function body 三種補全粒度的 benchmark，並利用倉庫內既有的單元測試提升評估準確度、克服相似度指標的侷限。我們用不同大小的語言模型（含 GPT-3.5-Turbo 與 CodeGen）做大量實驗，證明 RepoCoder 在各設定下對 In-File 補全的增益超過 10%，且迭代框架一致優於單輪原生 RAG。

貢獻：(1) 提出 RepoCoder——用於倉庫級補全的新式迭代檢索-生成框架；(2) 提出 RepoEval——支援多粒度評估、並用單元測試提升準確度；(3) 嚴謹實驗證明其顯著優於 In-File 範式、並強化原生 RAG。

2. 方法

2.1 整體框架

用語言模型 M 做補全一般可寫成 Ŷ = M(X)，Ŷ 為預測 token、X 為檔案內未完成程式碼。引入檢索模型 R 後即成 RAG：先把倉庫檔案切成程式碼片段集合 C_repo = {c1, c2, …}；用 R 以未完成程式碼 X 為查詢取回最相關片段 C_ret = R(C_repo, X)；再 Ŷ = M(C_ret, X)，把倉庫級上下文帶進補全。

但只用 X 當查詢會在「檢索上下文」與「意圖中的補全目標」之間造成落差（如圖 2）。為此我們提出 RepoCoder 這條迭代式檢索-生成管線：第 i 輪（i>1）用上一輪的模型預測 Ŷ^(i-1) 構造新查詢，得到新的片段集合 C_ret^i = R(C_repo, X, Ŷ^(i-1))；再用 C_ret^i 構造新 prompt、生成新預測 Ŷ^i = M(C_ret^i, X)。新補全可作最終輸出、或供下一輪使用。重點：M 與 R 的參數全程不變，且不需靜態程式分析或啟發式規則來建檢索庫。

2.2 程式碼檢索

檢索器可為任何「給查詢就能找相關文件」的模型。建庫用滑動視窗：視窗掃過倉庫檔案、抽出符合視窗大小 Sw 的連續多行程式碼，每次移動固定行數（滑動步長 Ss）。

首輪還沒有模型預測時，查詢用未完成程式碼 X 的最後 Sw 行，得 C_ret^1 = R(C_repo, X)。但此時查詢（基於 X）與目標（續寫 X）之間存在落差。先前工作曾用「把片段整體下移幾行以納入後續程式碼」的做法，但不分內容一律位移未必恰當。

RepoCoder 改以「上一輪生成的程式碼 Ŷ^(i-1)」增強第 i 輪（i>1）的查詢：預訓練程式碼模型雖無新倉庫的自訂資訊，卻有很強的通用理解與生成力，生成的 Ŷ^(i-1) 即使不保證正確，仍能為檢索提供有價值的補充資訊。因此第 i 輪查詢由「X 的最後 (Sw − Ss) 行」串接「Ŷ^(i-1) 的前 Ss 行」構成，得到接地的檢索結果 C_ret^i = R(C_repo, X, Ŷ^(i-1))。

這正是本文的核心機制——迭代式檢索-生成：先用未完成程式碼檢索 repo 相關片段 → 生成一份補全草稿 → 用草稿再檢索（縮小檢索與生成之間的落差）→ 再生成，如此循環；每一輪都用上一輪的產物把查詢往「真正要補的目標」推近。

2.3 程式碼生成

生成器可為任何「給 prompt 就能續寫 token」的預訓練模型。補全時須同時納入倉庫上下文 C_repo 與目標檔案內上下文。RepoCoder 取回最相關片段 C_ret 並與未完成程式碼 X 串接；為求可讀，用一個 prompt 模板（圖 3）把 X 與 C_ret 整合：檢索片段依相似度分數升冪排列、各附其原始檔案路徑；片段最大數量 K 視 prompt 長度而定，盡量塞入相關資訊。

3. Benchmark 建構（RepoEval）

RepoEval 取自 GitHub 最新高品質倉庫，涵蓋 line、API 呼叫、function body 三種粒度；function body 用倉庫內單元測試評正確性（而非只靠相似度指標）。每題標註來源倉庫、檔案路徑、行號與 ground-truth 補全；為分析與跑測試，倉庫在 2023 年 1 月完整封存。

篩選條件：開源授權、2022 年後建立（GPT-3.5-Turbo 與 CodeGen 的訓練資料到 2021，用 2022 資料防洩漏）、非 fork 原創、>100 星、>80% 檔案為 Python、且有明確單元測試。隨機選倉庫、建三個資料集：

  • Line completion：選 8 個大小/領域各異的倉庫，每倉庫隨機抽 200 行（非重複、非註解、每行至少 5 token），共 1600 題。
  • API Invocation completion：測倉庫內定義的 API（比補全內建/第三方 API 更難，因缺乏自訂訓練資料）；用與 line 相同的 8 倉庫，解析出倉庫內 API 呼叫、每倉庫隨機抽 200 個非重複呼叫，共 1600 題。
  • Function Body completion：需跑單元測試，故另選較小、易部署的倉庫；定位被單元測試覆蓋的函式、選主體 3–30 行者，共 373 題。
