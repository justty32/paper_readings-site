4. 實驗設定

比較方法：

  • In-File：只用未完成程式碼填 prompt，直接用預訓練模型 zero-shot 補全（基線）。
  • Oracle：單次檢索的上界法——用 X 的最後 Sw − Ss 行 + ground-truth 程式碼 Y 的前 Ss 行做查詢取 C_ret^gt，再 Ŷ = M(C_ret^gt, X)；代表在給定 R、M 下 RepoCoder 的效能上界。

實作：主實驗檢索器用稀疏 bag-of-words + Jaccard 相似度；另用 UniXcoder 密集檢索器（附錄 B）驗證，效果相當。生成模型：GPT-3.5-Turbo，以及 CodeGen 的 6B/2B/350M 三版。超參數（模型對超參不敏感，依經驗設定）：輸入+輸出最大 token 數 GPT-3.5-Turbo 4096、CodeGen 2048；檢索片段長度設為 prompt 一半；line/API 的生成上限、Sw、Ss 分別為 100、20、10，function body 為 500、50、10；最大檢索片段數 K=10。單輪 RAG、迭代 RepoCoder、Oracle 用相同超參以求公平。

評估指標：line/API 用 Exact Match（EM） 與 Edit Similarity（ES，基於 Levenshtein 距離）；function body 用執行式評估——跑倉庫內單元測試，全過為 1、否則 0，報 Pass Rate（PR）。

5. 實驗結果

5.1 Line 與 API 補全（表 2）

RepoCoder 在兩個資料集、所有模型大小上都一致提升 In-File：EM 絕對提升超過 10%、ES 超過 8%，且逼近 Oracle。兩輪以上時一致勝過單輪原生 RAG。搭配 RepoCoder 的 CodeGen-350M 可與 In-File 的 GPT-3.5-Turbo 相當。以 GPT-3.5-Turbo 的 line 為例：In-File EM 40.56 → Iter-2 55.31 → Iter-3 56.81，Oracle 57.75。改用 UniXcoder 密集檢索器結果一致，顯示 RepoCoder 對檢索/生成模型的選擇具穩健性。

5.2 Function 補全（表 3）

因函式主體補全較難，用 GPT-3.5-Turbo。趨勢與 line/API 一致：多數倉庫上顯著優於 In-File、逼近 Oracle，且多輪迭代穩定勝過原生 RAG。整體 Pass Rate：In-File 23.32% → Iter-1 38.34% → Iter-2 42.63%（與 Oracle 42.63% 持平），Iter-3/4 為 41.82%/42.36%。

6. 分析

6.1 檢索片段的品質

檢索品質對補全效能影響顯著；最有用的片段通常含與目標補全相似的語句、或目標 API 的用法示例。設計 GT-Code 對照（用靜態分析定位含 ground-truth API 呼叫的片段、按與未完成程式碼相似度排序入 prompt）：GT-Code 普遍最佳；而 RepoCoder Iter-2 對 ground-truth API 的召回率高於單輪，這很可能是其補全更佳的原因；且模型越強，Iter-2 召回越高——證實模型預測確實幫到檢索。

6.2 檢索片段的位置

選「Oracle/RepoCoder 補對、但 In-File 補錯」的樣本，依 Shrivastava et al. (2022) 分五類來源：Imported、Current File、Current Directory、Similar Import、Similar Name。發現 Oracle 與 RepoCoder 分佈相近，且相當比例來自「Similar Import／Similar Name／Current Directory」，凸顯上下文資訊的重要。消融（只限這些位置檢索）會使效能下降，反顯 RepoCoder 檢索的有效與簡潔。

7. 相關工作

  • 補全中的倉庫上下文：傳統靠分析+重排（效率好但無法任意粒度生成）；另一線把補全當語言建模，用 n-gram/LSTM/Transformer 把倉庫上下文納入訓練（但蒐標註+微調成本高）。Shrivastava et al. (2022) 也探索倉庫級補全，但靠不靈活的啟發式與分類器訓練來構造 prompt。
  • 檢索與生成的聯合建模：LLM 離線訓練限制了取得自訂/最新資訊；近期在 QA、對話上探索檢索-生成聯合建模，並延伸到把檢索到的文件/程式碼範例納入生成；隨模型變強，趨勢是把 LLM 當固定黑箱做上下文內的聯合檢索-生成，並有研究用模型預測當補充上下文來輔助檢索。本文證明「迭代結合檢索與生成」是倉庫級補全的有效方法。

8. 結論與未來工作

RepoCoder 是簡單有效的倉庫級補全框架：用檢索器 + 語言模型有效利用倉庫級資訊，透過迭代式檢索-生成橋接檢索上下文與目標程式碼的落差，提升補全效能。RepoEval 上的大量實驗證明它一致且顯著地勝過 In-File、超越原生 RAG。憑其簡單、通用、有效，RepoCoder 有望成為真實開發中的重要工具。

局限

  • 低重複度倉庫收益有限：倉庫幾乎沒有重複程式碼時，相似度檢索找不到足夠相關資訊（附錄 C 進一步佐證重複度與增益的相關性）。
  • 最佳迭代輪數難定：兩輪優於原生 RAG，但更多輪可能不穩（附錄 D 顯示每輪都會修好前一輪的錯、也弄壞前一輪對的）；作者試過自動終止策略，但無損效能的最佳停止準則仍待研究。
  • 即時部署的時間效率：額外檢索-生成步驟帶來延遲，可用量化/蒸餾/硬體加速/快取常用片段/預處理倉庫、或依延遲目標動態調整輪數來緩解，但超出本文範圍。
  • 實驗範圍有限：未探索不同 prompt 模板；主要只用相似度檢索；未納入 GPT-4／StarCoder／WizardCoder 等更新模型；baseline 僅 In-File 與 Oracle（因倉庫級補全是較新任務、缺可重現基線，另在附錄 E 對比 Copilot／Tabnine／CodeWhisperer 三商業產品做定性展示，該例中僅 RepoCoder 補對）。
