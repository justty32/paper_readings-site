3. 實驗設定

3.1 資料集（表 1）

四個資料集橫跨語義剖析、table QA、數學推理、基礎 Python：

  • Spider：由 NL 問題生成 SQL 的語義剖析資料集，7k 平行訓練資料（含標準程式，目標語言 SQL，8 shots）。
  • WikiTableQuestions（WikiTQ）：table QA，透過對來源表格生成並執行 SQL 求解；採用 Shi et al.(2020) 預處理表格與其標註 SQL，為原本弱監督的資料集補上標準程式（約 80% 例子有 SQL 標註）。
  • GSM8k：小學程度數學應用題，依前人做法由 NL 問題生成 Python 程式、執行得答案；原資料集只有 NL 無程式解，故對語言到程式碼而言是弱監督。
  • MBPP：NL 描述的基礎 Python 程式，每例配 3 個測試案例；用第一個測試案例入提示以生成正確函式簽名，用三個一起評估正確性。

3.2 Code LLM

用三種 code LLM 評估 LEVER：Codex（用 code-davinci-002 API）、InCoder（InCoder-6B，左到右生成）、CodeGen（CodeGen-16B-multi；雖訓練語料未含 SQL 檔案，仍能不錯地生成 SQL，可能因 SQL 混雜於其他語言的原始檔中）。

3.3 基線與評估指標

基線：Greedy（每步選最可能 token）；Maximum Likelihood（ML）（從 k 個樣本選生成對數機率最高者，是否用長度正規化依開發集決定）；Error Pruning + ML（EP+ML）（先剪掉有執行錯誤的候選，再取最大概似）；EP + Voting（對無錯程式的執行結果做多數投票）。主要與 EP+ML 比較，因它是簡單、跨資料集與 LLM 都穩定有競爭力的執行式重排法。評估指標為執行準確率（execution accuracy）：產出標準執行結果或通過所有測試案例的比例。

3.4 實作細節

驗證器訓練：以表 1 的取樣預算在訓練集上取樣建立驗證訓練資料。因把同一例的程式樣本批在一起，有效批量會乘上樣本數；樣本量大（實驗中達 100）時可能塞不進 GPU 記憶體，故每次迭代對每例的程式做隨機下採樣（down-sample），且每個 epoch 開頭重採，使驗證器每 epoch 見到不同程式。

執行結果表徵：驗證器輸入＝任務輸入＋候選程式＋執行結果的串接。Spider/WikiTQ 用 SQL 執行後線性化的表格；GSM8k 用執行後名為「answer」的變數值；MBPP 用函式回傳的型別與值（轉字串）。所有執行錯誤表示為「ERROR:[原因]」（如「ERROR: Time out」）。

驗證器選型：用開發集挑最佳驗證器——Spider 用 T5-base、WikiTQ 與 MBPP 用 T5-large、GSM8k 用 RoBERTa-large。（曾試以 code LLM 本身做少樣本驗證，但表現不如 EP+ML。）T5 訓練成對正/負例輸出「yes/no」、取生成「yes」的機率為驗證機率；RoBERTa 則於 [CLS] 頭上加線性層做序列分類。

4. 主要結果

4.1 LEVER 的有效性

LEVER 在所有 code LLM、所有任務上一致提升：對 Codex-Davinci 較貪婪解碼提升 6.6%（Spider）～17.3%（WikiTQ）；對較弱的 InCoder/CodeGen，Spider 最高提升約 30.0%、GSM8k 約 15.0%。搭 Codex-Davinci 在四資料集全部刷新 SOTA，增幅 1.2%（WikiTQ）～2.0%（MBPP）。在具挑戰的 Spider 上，前 SOTA 是微調 T5-3B（配關係感知自注意力）達到的，而 LEVER 只用微調的 T5-base 驗證器就更好。各表關鍵數字（dev/test 執行準確率）：

資料集 Greedy EP+ML LEVER 前 SOTA
Spider（dev） 75.3 77.3 81.9 RASAT 80.5
WikiTQ（test） 53.0 54.9 65.8 Binder 64.6
GSM8k（test） 67.2 72.6 84.5 DiVeRSe 83.2
MBPP（test） 62.0 60.2 68.9 Reviewer 66.9

作者指出 LEVER 是簡單方法，可望與更進階的提示法或模型架構疊加（留作未來工作）。

4.2 消融（圖 2、表 6）

消融含一個「Oracle」上界（只要樣本集裡有正確程式就必選中）。

  • 執行結果的作用：從驗證器輸入拿掉執行結果後四基準皆明顯下降（WikiTQ −6.6%、MBPP −5.6% 最大；Spider −3.0%、GSM8k −1.2%）；WikiTQ/MBPP 的樣本含較多執行錯誤，故 LEVER 對它們更有效。對更弱的 InCoder/CodeGen，去掉執行資訊往往降更多。LEVER 普遍勝過 EP+ML，顯示驗證器能利用「簡單執行錯誤」以外的線索。
  • 執行結果聚合的作用：對 Python 輸出的資料集有效，對 SQL 僅微幅——推測因 SQL 這類領域專用語言結構較不彈性，錯誤程式較易執行到「0 或空表」等瑣碎但錯的結果，聚合後可能累積足夠機率壓過正確結果、反傷表現。
  • 弱監督設定：不給標準程式時 LEVER 表現大致維持（最多降 1.1%），說明它在弱監督下運作良好，且程式本身相對執行結果對驗證較不具資訊量。

5. 分析

5.1 訓練樣本量縮放（圖 3）

以 Spider 為例，即使只給 250 例，LEVER 仍一致優於基底 LLM（各資料集/LLM 增益 1.7%～10.0%），可用於低資源。趨勢隨資料集/LLM 而異：訓練例愈多，對更難的資料集與更弱的 LM 影響愈大。與「用相同例數直接微調 T5 做生成」相比：驗證只需數百例即可學好，而微調 T5 生成器在少例時表現驟降——500 例時，T5-base 驗證器（配 InCoder/CodeGen）勝過微調 T5-3B 生成器約 7%。

5.2 樣本量縮放（圖 4）

推論時把每例樣本數由 50 降到 10，LEVER 掉 1.8%（Spider）～5.2%（WikiTQ），對推論期樣本量敏感（因其也大幅影響 oracle 上界）。相對地，LEVER 對訓練期的樣本量高度不敏感（三資料集差距皆 <1%）。整體上，較高取樣預算在測試時幫助更大。

5.3 驗證器與生成器的校準（圖 5）

把樣本按模型機率排序、移動百分位閾值，量測頂端正確程式比例。驗證器整體比生成器更好校準，尤其在低分位（更易憑執行結果挑出明顯錯誤）；但在頂端程式之間，驗證器在四中三個資料集校準不佳（推測頂端程式形式與執行結果太相似，小模型難分辨），此時生成器校準較好。把兩者機率相乘（LEVER 所用）在四基準皆最佳；GSM8k 上兩者頂端校準都差，聯合機率卻意外地校準良好，顯示兩模型互補。

5.4 定量分析（圖 6）

當 LEVER 把正確程式重排到頂、取代生成機率更高者，多半是因執行結果提供了關鍵資訊（執行錯誤、變數型別與值域），呼應 §4.2；也有「無錯執行結果與貪婪程式同型別同值域」的「其他」類，此時程式本身成為驗證器主要特徵。LEVER 失敗時，最常見原因是樣本裡根本沒有正確程式（已達上界，弱 LM 尤甚）；次常見是「重排上來的錯誤程式其執行結果與正確程式同型別同值域」，此時執行結果對驗證器資訊不足。
