3. 方法

ReGAL 分兩相：訓練/歸納相學抽象（helper functions），測試/合成相用抽象為測試 query 生成程式。給定 （query q, 標準原語程式 p） 示範集，先前處理聚類（§3.1），訓練相分批重構原語程式建立抽象（§3.2），測試相生成「黏合」抽象與原語的程式（§3.3）。訓練用 GPT-3.5；測試用多種 LLM，側重可自由取得的開源模型。

3.1 前處理

  • 加註解（可選）：讓 GPT-3.5 根據 q 為 p 加註解以對齊查詢與程式，並驗證加註後程式執行結果不變。
  • 聚類：抽象必須跨例共享，重構 LLM 需要多例視野（multi-instance scope）——一次收到一批相關的 (q,p)。作法：用 OpenAI Ada embedding 嵌入 query，Ward 演算法階層聚類，拓撲排序後分成大小 k 的批。
  • 課程（curriculum）：直覺上短而易的程式含有可重用於更難、更組合性程式的抽象，故按 query 平均 token 長度將批排序（由短到長）。

3.2 訓練

訓練輸出：**Code Bank（C）**＝訓練中抽象出的 helper function 庫；**Demo Bank（D）**＝函數使用示範。迭代流程（演算法 1）：

  • Stage 1 重構（refactorBatch）：輸入一批例子、指令與現有 code bank，提示重構 LLM 產出一組新 helper functions H^new 及（適當時）使用這些 helper 的重構版程式。
  • Stage 2a 驗證（verify）：執行重構程式並與原程式比對結果，即判定 p̂() = p()。通過驗證的重構程式 (q, p̂) 存為示範供代理未來使用；只有通過驗證的 helper functions 才加入 C。同時記錄驗證失敗的程式——它們是 editCodeBank 與 pruneCodeBank 的關鍵依據。
  • Stage 2b 回饋重試（retry）：對未通過驗證者，後續提示中呈現失敗程式、其 helper functions 及執行的環境回饋（輸出或錯誤訊息；LOGO 除外，因輸出是影像），LLM 產出新版本，通過驗證則其 helpers 入 C。
  • Stage 3a 編輯 Code Bank（editCodeBank）：有些 helper 因含錯誤抽象而未全數通過單元測試——例如 draw_triangle() 把 small 尺寸寫死，medium 三角形就失敗。每隔 editEvery 批，為每個函數構造提示，展示其通過與失敗的單元測試，請 LLM 提出修改；改後通過更多單元測試才替換。
  • Stage 3b 修剪 Code Bank（pruneCodeBank）：修剪「多數單元測試失敗且無法再經編輯改善」的函數。每個函數依「使用它的程式的成功率」計分：s = |P| − Σ_{p∈F} 1/n_p（P/F 為通過/失敗程式集，n_p 為程式 p 用到的函數數）——即每個通過程式 +1，失敗的扣分與程式中函數數成反比（因為失敗天真上可歸咎於程式中任一函數）。函數被使用足夠次數且 s 低於閾值 θ（全部實驗設 0）即修剪。

訓練可跑多個 epoch。超參數以 dev 集選定（附錄 C），全部提示見附錄 D。

3.3 測試

部署一個程式合成（語意剖析）代理逐例預測。對每個測試例，代理以向量相似度從訓練語料檢索 ICL 範例構造提示。ReGAL 增強代理可存取訓練資料、code bank 與 demo bank：ICL 預算（所有實驗 10 例）在原語範例與重構範例間分配（保留部分原語程式當 ICL 是必要的，因為並非所有測試 query 都能只靠 helper 解決；比例為超參數）。另按「query 與函數名稱/描述的相似度」檢索至多 20 個相關 helper functions 串入提示。並採 ReAct 式提示：先讓模型思考哪些函數可能相關、再生成程式碼——沒有這些「thought」語句，增強代理幾乎不用任何 helper。

4. 實驗設定

4.1 資料集

五個資料集的共通點：問題異質、需要多個 helper functions（不像排序那種一個函數可解的任務）。

  • LOGO：Turtle 圖形 DSL（forward(dist)、left(theta) 等），基於 Ellis et al.（2021）資料、Wong et al.（2021）重新標註；作者以 AST 規則把 Lisp 式語法譯成 Python 並釋出。train/test 200/111，另取 100 dev。
  • Date：BigBench-Hard 日期理解字題。以 Lyu et al.（2023）的 GPT-3.5 預測程式為 silver programs，切 66/113/180，訓練切分按正確性過濾。
  • TextCraft：文字環境中合成 Minecraft 物品；每例含目標與 10 條合成指令（含干擾項配方）。不同於原作的互動設定（每步收環境回饋），本文要求代理一次生成完成整個任務的單一 Python 程式，更具挑戰。用 depth-2 測試切分，190/50/77。
  • MATH：檢驗 ReGAL 在無預定義域語言之域發現函數的能力。用 GPT-4 + Program-of-Thoughts 生成 silver 訓練程式；取難度 1-2 級、Algebra 子集，194/61/74。除 Python 內建外沒有任何原語。
  • TabMWP：表格數學字題，同樣用 silver programs，取 1-4 級，194/60/74。

4.2 基線

  • 前人工作基線：LOGO 用 Grand et al.（2023）LILO 的 offline synthesis 數字；Date 跑 Lyu et al.（2023）Faithful-CoT 於本文測試切分；TextCraft 重跑 Prasad et al.（2023）的 ReAct 基線。（方法學差異使本文代理先天佔優，這些數字主要用來顯示本文基線本身之強。）
  • 基線程式代理：與 ReGAL 存取完全相同的資料但不用抽象——從同一訓練集檢索原語程式當 ICL（同樣 10 例預算），直接檢驗抽象的貢獻。

5. 結果

  • 對外部基線：ReGAL 全勝（LOGO：LILO 41.1 → 基線 45.6 → ReGAL 57.1，CodeLlama-13B；Date：Faithful-CoT 83.3 → 基線 88.9 → ReGAL 90.2，GPT-3.5；TextCraft：ReAct 25.6 → ReGAL 30.8，CodeLlama-34B——ReAct 還多拿了環境回饋）。
  • 非數學域對自建基線（表 1，3 seeds）：各模型普遍大幅領先。CodeLlama-13B 受益最大：LOGO 45.6→57.1、Date 42.8→68.9、TextCraft 18.8→26.9。Lemur-70B 與 GPT-3.5 在 LOGO/TextCraft 也有大增益。最大的模型未必最好：LOGO 與 TextCraft 上 GPT-3.5 被開源模型（增強後）超越——CodeLlama-13B+ReGAL 在 LOGO 勝無抽象 GPT-3.5 達 19.2%（也勝有抽象的 GPT-3.5）。僅以約 200 例跑 ReGAL 訓練，就能把小得多的開源模型推到遠超（可能）大得多的系統。
  • 數學域：MATH/TabMWP 無明確域語言、該發現哪些 helper 較不明朗，但 ReGAL 仍普遍改善：GPT-3.5 在 MATH +12.2（43.2→55.4）、CodeLlama-7B 在 TabMWP +11（16.7→27.7，追平 13B 水準）。Lemur 在此二域大量輸出空白，計入標準誤後與基線相當。顯示 ReGAL 能泛化到無清晰域語言之域。
  • 消融（表 3，CodeLlama-13B，dev）：去掉任一組件都掉分；retry 與 curriculum 影響最大（去 retry：Date 77.0→51.9；換隨機順序：LOGO 55.0→36.3，掉 18.7%）。retry 既增加有用 helper 也擴充 Demo Bank。去 pruneCodeBank：TextCraft 34.1→25.3；去 editCodeBank：Date 77.0→69.6。
  • 重用性（圖 3）：CodeLlama-13B 測試程式中，top-5 常用 ReGAL 函數被大量重複呼叫，TextCraft 相對重用最多——證實抽象確實跨例共享。
