4. 成本模型與 Crossover 分析

4.1 記號與策略分類

|D| = 文件大小（token）、r = 壓縮比、N = 查詢數、Dq = 每查詢動態區塊、O = 輸出大小。

  • A — Vanilla：完整文件，無 cache、無壓縮。
  • B — Cache-only：完整文件標記 cache_control，無壓縮。
  • C — Query-aware compress：每查詢壓縮前綴，無 caching。
  • D — CAPC：Query-agnostic 壓縮至 |D|/r，以 cache_control 快取。

4.2 每策略成本表達式

cost_A = N (|D|+Dq) pin + O pout cost_B = N [(1−ρ_B)|D| cw + ρ_B|D| cr + Dq pin] + O pout cost_C = N (|D|/r+Dq) pin + O pout cost_D = N [(1−ρ_D)(|D|/r) cw + ρ_D(|D|/r) cr + Dq pin] + O pout

其中 ρ_B=ρ(N,|D|), ρ_D=ρ(N,|D|/r)。

4.3 Crossover 閾值（一般形式）

消去共同開銷、令 cache 與 compressed 成本相等，得到 provider-agnostic crossover ρ 閾值：

ρ_cross(r) = (cw − pin/r) / (cw − cr)

無因次形式：令 α=cw/pin（write 費率溢價）、β=cr/pin（read 費率折扣），則：

ρ_cross(r) = (α − 1/r) / (α − β)

任何 write/read 費率比接近 Anthropic（α≈1.25, β≈0.1）的 provider，其 crossover 閾值將接近下文數值。OpenAI 自動 caching 結構類似（α=1.0, β=0.5）。

Sonnet 4.6 實例（pin=3.00, cw=3.75, cr=0.30, α=1.25, β=0.10）：

r=2: ρ_cross=0.652 （B 勝 C 若 ρ>0.65） r=3: ρ_cross=0.797 （B 勝 C 若 ρ>0.80） r=4: ρ_cross=0.870 （B 勝 C 若 ρ>0.87） r=6: ρ_cross=0.942 （B 勝 C 僅若 ρ≥0.94） r=8: ρ_cross=0.978 （B 勝 C 僅若 ρ≥0.98） r=10: ρ_cross=1.000 （ρ>1 不可能→B 永遠不敵 C）

定價敏感度：固定 β=0.1，將 write 溢價從 α=1.25 減半至 α=1.1 會將「B 永遠不敵 C」的 regime 從 r≥10 下移至 r≥4。若 α=2.0（如 1 小時 TTL），則上移至 r≥16。定性發現——存在有限 crossover ratio 使 cache-only 敗給 compression——只要 β<1<α 就成立，這是所有現有 cache API 的標準定價結構。

4.4 從兩層 ρ 的實證 crossover N

將 crossover ρ 閾值轉換為 crossover N 值：在實證兩層模型下，r≥6 時 crossover 在實務上永遠不會發生（∞ in practice）。

4.5 對定價與基礎設施變化的穩健性

分析四種情境：(1) cache_read 更便宜——CAPC 優勢擴大；(2) write 溢價收窄——更多工作負載進入「B 不敵 C」regime；(3) 兩層架構消失——tier-preserving bound 失去閾值基礎，但 CAPC 的 token 減少優勢不受影響（即使 ρ=1.0，CAPC 仍勝基線 50–65%）；(4) 引入語義前綴匹配——query-aware compression 部分恢復 cache hit，縮小與 CAPC 差距。跨所有情境的三個不變量：(i) 壓縮至少匹配 CAPC（相等時為 ρ=1 且語義 caching 完美）；(ii) 成本模型保留其函數形式；(iii) RUN_NONCE 隔離的 ρ 特徵化方法直接轉移。

5. CAPC 演算法

5.1 核心 CAPC 程序

設 D 為靜態文件、Q1...QN 為查詢流、r 為壓縮比、Compress 為任意 query-agnostic 句子選擇壓縮器。

def CAPC(D, queries, r):
    D_prime = Compress(D, r)  # 一次，off the request path
    for q in queries:
        api.messages.create(content=[
            {"type": "text", "text": D_prime,
             "cache_control": {"type": "ephemeral"}},
            {"type": "text", "text": q},
        ])

關鍵設計選擇：(i) D′ 計算一次並在所有 N 查詢間重用；(ii) cache_control marker 放在壓縮文件區塊上，但不在查詢區塊上。

5.2 Tier-Preserving Ratio Bound

增加 r 減少 |D|/r 降低每查詢成本——直到 |D|/r 跌破 persistent-tier 閾值 T≈3500 token，此時 ρ 從 1 降至約 0.85，大量呼叫支付 write 費率 cw=12.5cr：

r_max^safe(|D|) = floor(|D| / T), T=3,500 token (Sonnet 4.6)

實證展示：12,191-token 文件在 r=3 時壓縮前綴 4,067 token（persistent）每查詢成本 $0.0057；r=4 時降至 3,119 token（hot），成本反彈至 $0.0101——單一 ratio 增量導致 77% 成本增加。

5.3 AdaptiveCacheBoundary：處理演變中的 Prompt

當文件跨呼叫演變時，CAPC 擴展 AdaptiveCacheBoundary 子程序，基於觀察到的 K 版本突變率將每個句子位置分類為 STATIC、QUASI 或 DYNAMIC。

對每個句子位置 p，計算指紋集合 {h(norm(D_p^(k))) : k=1...K}，其中 norm 是基於 regex 的正規化器（日期→[DATE]、大數→[NUM]、金額→[AMOUNT]）。突變率 μ_p = 1 − max_h count(h)/K。閾值 ε_static=0.05, ε_quasi=0.30 劃分位置為三類。cache 前綴是最大連續 STATIC-or-QUASI 前綴。

空白正規化：第 3 節的發現——Claude 的 tokenizer 正規化前導和尾隨空白——意味著僅有空白的段差從 cache 角度看不是真正的突變。演算法在指紋化前正規化空白。

5.4 AdaptiveCacheBoundary 實證驗證

在三個 LongBench-v2 文件（~6k, 12k, 24k token）上評估，合成但現實的版本漂移，K=25 版本，四種突變率 μ∈{0.05, 0.10, 0.20, 0.40}。12/12 配置全部實現正向節省（savings +73–86%）。

真實 Git 歷史追蹤驗證：在生產倉庫三個工程師驅動文件（main.py, orchestrator.py, analysis_module.py）上運行，每個文件 25+ commits。結果：adversarially 編輯的生產文件中 DYNAMIC 佔 44–80%，adaptive prefix 僅 12–749 token，但仍產生 −62.6% 至 −70.5% 的節省 vs naive cache-all——演算法正確拒絕 cache 動態多數。

5.5 實務指南

  1. 靜態單版本文件：使用核心 CAPC 程序，選擇 r_target 與 r_max^safe 中的較小值。
  2. 演變中文件：觀察 K≥3 版本，運行 AdaptiveCacheBoundary，使用 adaptive prefix 作為 cache block。
  3. 低於 persistent-tier 閾值的文件：CAPC 不是正確策略；改用 cache-only（策略 B）。
