摘要

以語言模型為基礎的程式碼生成與補全工具已廣泛採用，但它們有時會產生不符必要約束的程式碼，例如語法錯誤或呼叫不存在的 API。約束解碼（constrained decoding）技術被開發出來，藉由在生成過程每一步貪婪地剔除違反約束的選項，協助模型生成符合約束的程式碼。然而，約束解碼有一個嚴重限制：它會扭曲模型的輸出意圖，迫使模型產生「雖滿足約束、卻不符開發意圖因而錯誤」的程式碼。針對此挑戰，本文提出 AdapTrack。透過在生成過程中導入回溯（backtracking），AdapTrack 避免扭曲模型的輸出意圖，因而產生的結果不僅符合約束，也在語意上更貼近模型的輸出意圖。在自建的合成 API 補全資料集上，AdapTrack 較約束解碼最多提升 360.87%；在自行蒐集、同樣呈現此問題的真實世界 API 補全資料集上，AdapTrack 較約束解碼最多提升 38.93%；在通用程式碼生成基準上，AdapTrack 較約束解碼在 HumanEval 上最多提升 7.84%，在 MBPP 上最多提升 6.42%。這顯示僅憑更貼近模型輸出意圖，AdapTrack 就能帶來顯著改善。我們提供理論證明，AdapTrack 產生的分布在已知生成歷史的條件下與模型的分布一致，從而確保模型的輸出意圖不被扭曲。在領域特定語言（DSL）問題上的實驗顯示，相較既有方法，本方法產生的生成結果更貼近語言模型的分布。

1. 引言

以語言模型為基礎的程式碼生成與補全工具（如 GitHub Copilot）日益普及，能理解開發者意圖並生成貼合脈絡的程式碼。合法的程式碼須滿足各種約束，例如語法規則、被呼叫的 API 須存在，但語言模型本質上只被設計來預測下一個 token 的分布，並無內建機制保證輸出合乎這些約束——即使生成內容貼合開發者意圖，仍可能不合法。

約束解碼方法（Picard、Synchromesh、Monitor-guided decoding、Repilot 等）用約束器（constrainer）判定「已生成文字後接哪些 token 非法」，直接把非法 token 在模型輸出分布中的機率設為 0。此類約束器通常已現成可得，因為 IDE 常提供類似功能協助開發者。

但約束解碼存在嚴重限制：它會扭曲模型的輸出意圖，迫使模型生成不自然的程式碼——生成結果雖滿足約束，卻可能偏離模型原本預期的功能、無法對齊脈絡語意。論文以 Figure 1 具體示範：情境是想用 PyTorch 2.0 計算矩陣秩，可用 API 有 torch.matrix_rank（PyTorch 1.0–1.8）與 torch.linalg.matrix_rank（1.8 之後）。模型原本最想輸出的候選是 matrix_rank，次高候選是 linalg.matrix_rank；用約束器可知目前版本唯一合法的是 linalg.matrix_rank，理應讓約束解碼輸出這個次高候選。然而實際上，約束解碼下機率最高的輸出竟是 matrix_power（57.70%），而這個 API 在無約束情形下的生成機率僅 0.20%，代表模型認為它高度不適合此脈絡。

逐步拆解可發現原因：第一步合法選項包含 matrix、l 等，因為還有其他以 matrix 開頭的合法 API（如 matrix_power、matrix_exp），約束器不會剔除 matrix，模型以 60.46% 機率選了它。但生成 matrix_ 之後才發現，佔模型意圖 99.59% 的 rank token 被約束器禁止；此時模型已生成 matrix_，被迫在約束下繼續，選出與其原意完全不符的 power。即使模型清楚知道「除了 matrix_rank，最合適的輸出應是 linalg.matrix_rank」，約束解碼仍逼它以 57.70% 機率輸出模型自認高度錯誤的 matrix_power。

問題本質在於：約束器一次只能發現一步的錯誤，所以 matrix 這個選項在當下仍合法；但當我們發現模型的主要意圖被後續阻斷時，仍被迫基於先前已生成的 matrix_ 繼續。結果程式碼雖合約束，卻偏離模型的原始輸出意圖。若是人類寫程式碼，發現先前用的 API（matrix_rank）已不可用、但記得看過 linalg.matrix_rank，通常會刪掉已寫的 matrix_ 重新開始。受此啟發，作者提出 AdapTrack：在約束解碼過程中，依「目前下一步選項中非法選項所佔比例」動態回溯——比例大就代表模型不太可能想沿此分支繼續，應換分支；否則代表模型的意圖多半仍在此分支上，可繼續生成。

論文提供演算法的證明，顯示其產生的分布，在已知生成歷史條件下，與模型在約束下的分布完全一致，證實此法確實避免了約束解碼扭曲生成意圖的問題。為驗證 AdapTrack 確實解決 Figure 1 揭示的問題（正確使用模型不熟悉的 API），作者構建合成資料集 TFv1（基於 TensorFlow API 更新，刻意誘導模型使用 TensorFlow v1 專屬的 API），多個程式碼語言模型上 AdapTrack 較 naive constrained decoding 最多提升 360.87%。為確認結果不只在合成資料上成立，作者另基於 GitHub 真實用例構建 TFv1Real，AdapTrack 較約束解碼最多提升 38.93%。為驗證此問題與 AdapTrack 在通用程式碼生成中的普遍性，在 HumanEval、MBPP 上搭配型別約束器實驗，pass@1 分別最多提升 7.84%、6.42%。在 DSL 問題上採樣 2000 次比較分布，顯示 AdapTrack 產生的分布與正確分布的 KL 散度顯著更低。另有溫度與模型規模的穩健性分析，以及有限回溯距離下的效率與可擴展性實驗，顯示短程回溯即已足夠。

貢獻總結：(1) 提出 AdapTrack，一種能避免貪婪約束解碼扭曲模型輸出意圖的解碼方法；(2) 證明 AdapTrack 的分布在已知生成 token 條件下與模型分布一致，DSL 實驗證實其分布更貼近模型真實意圖；(3) 構建 TFv1、TFv1Real 資料集模擬模型不熟悉 API 的場景，顯示顯著改善 API 生成準確率（TFv1 最多 +360.87%、TFv1Real 最多 +38.93%），HumanEval/MBPP 實驗驗證通用程式碼生成上的可推廣性。

2. Motivating example（動機範例）

Figure 2 逐步展示如何把回溯直覺套進約束解碼流程。已生成 matrix_ 之後，下一步 token 候選中，rank 的生成機率高達 99.59% 但非法。若把「從第一個 token 到每個候選為止的整體序列機率」列出（如生成 matrix_rank 的整體機率約 60.21%），剔除非法選項後對合法選項重新正規化，可得到「matrix 的機率應從 60.46% 下修為 0.55%」——這才貼合直覺：得知首選 matrix_rank 不合法後，模型應優先考慮不以 matrix 開頭的次選項。

問題是：已經生成了機率 60.46% 的 matrix，如何把它調整成 0.55%？直接整條序列重新取樣太浪費運算資源。作者的直覺是：機率變動越大，越該離開此分支；否則多半該留在原分支。據此提出以拒絕取樣做自適應回溯：已生成 matrix（機率 60.46%），再做一次接受率約 0.91% 的第二次取樣；成功則保留 matrix，否則換成別的 token。兩次取樣合併後，matrix 被採用的機率恰為 0.55%。若這次重新取樣後首個 token 換成了 l，就會導向次選項 linalg.matrix_rank 的生成路徑。
