6. Evaluation（評估）

評估分四個研究問題：RQ1 AdapTrack 在正確且合法的 API 預測上表現如何？RQ2 在真實世界 API 補全上表現如何？RQ3 在通用程式碼生成上表現如何？RQ4 AdapTrack 與約束下 oracle 分布的對齊程度如何？

6.1 RQ1：TFv1 資料集上的 API 補全

資料集：模擬「函式庫版本演進、舊 API 轉為新 API」的場景——要求模型分別在 TensorFlow v1、v2 情境下輸出相同語意的 API，模型不知道當前的版本。從 TensorFlow 2.16 官方文件收集所有以 tf.compat.v1 開頭、在 v2 無對應項的 API，過濾後保留 419 個獨立 API，並用「wrapper 函式」的提示手法誘導模型直接轉發呼叫該 API（Figure 3 範例）。

指標：EM@k（k=1,3,5,10,20），k=1 用貪婪解碼，k>1 用 20 次隨機取樣估計。基線：無約束解碼、約束解碼。模型：Qwen2.5 Coder 7B、DeepSeek Coder Base 6.7B、StarCoder2 7B、CodeLlama Python 7B（皆為 base model，因補全任務更貼合其訓練目標）。實驗機器：64 核 Intel Xeon、8× NVIDIA RTX A6000。

結果：所有模型、兩種版本情境下，AdapTrack 皆顯著優於約束解碼，最多提升 360.87%。以 Qwen2.5 Coder 7B 為例，TFv1（v1）情境 EM@1 從無約束 61.58%、約束解碼 66.11%，AdapTrack 提升到 80.19%——顯示約 14% 的案例中，模型認為 oracle 是約束下的最佳候選卻因約束解碼無法修改已生成 token 而生成失敗。TFv2 情境更明顯：無約束僅 7.16%、約束解碼 18.38%、AdapTrack 達 54.89%（較約束解碼 +198.70%），甚至優於約束解碼的 EM@10。整體最大改善出現在 DeepSeek Coder Base 6.7B 的 TFv2 EM@1，從 10.98% 提升到 50.60%（+360.87%）。

6.2 RQ2：TFv1Real 上的真實世界 API 補全

資料集：從 GitHub 搜尋 tf.compat.v1.API( 用法蒐集 46,785 個 Python 檔案，去重、切分、過濾（移除前綴含 tf.compat.v1 或後綴非 API 呼叫的檔案）後得 14,237 個檔案；再依前綴 token 長度（以 CodeLlama 7B Python 分詞器估計，平均 1,624.78 token）篩去過長者，得 12,883 個檔案，隨機抽 1,000 個組成 TFv1Real。

結果：所有模型上 AdapTrack 皆顯著優於約束解碼，最多提升 38.93%。以 Qwen2.5 Coder 7B 為例，EM@1 從無約束 21.70%、約束解碼 35.60%，AdapTrack 提升到 49.30%（+38.48%）。最大改善出現在 StarCoder2 7B，EM@1 從約束解碼 29.80% 提升到 AdapTrack 41.40%（+38.93%）。改善幅度雖不如合成資料集 TFv1 顯著，但仍屬大幅提升。

6.3 RQ3：通用程式碼生成

資料集：HumanEval、MBPP，搭配 Mündler et al.（2025）的型別約束器確保生成型別正確；因該約束器僅支援 TypeScript，改用 MultiPL-E 資料集的 TypeScript 翻譯版本。指標：pass@k。取樣策略：因逐一檢查整個詞彙表過於耗時，改用類 top-p（nucleus）取樣的變體——按機率由高到低檢查 token，累計「已知合法 token 機率」佔「已知合法+未檢查 token 機率」之比超過 p 後，剩餘未檢查 token 一律視為非法（無約束情形下自然退化為標準 top-p 取樣）。實作：修正約束器套件的若干 bug 並加速，開源發布；若約束器對某 token 60 秒內無法判定合法性，重啟生成，貪婪取樣重啟 20 次仍失敗則視為空樣本。

結果：AdapTrack 幾乎全面優於約束解碼，pass@1 在 HumanEval 最多 +7.84%、MBPP 最多 +6.42%（僅 CodeLlama 7B 在 HumanEval 的 pass@20 是例外），顯示分布扭曲問題在通用程式碼生成中同樣普遍存在，可由 AdapTrack 修正改善。相較無約束解碼，AdapTrack 在 StarCoder2 7B、CodeLlama 7B 於 MBPP 的 pass@1 上表現較差——因 pass@1 取自貪婪樣本，若無約束的貪婪樣本本就能通過測試，理應也能通過約束器並被約束解碼貪婪選中，但實際上並未如此，顯示問題出在約束器本身的限制，而非 AdapTrack 演算法；即便如此，AdapTrack 仍能藉修正分布扭曲改善約束解碼的表現。

6.4 RQ4：AdapTrack 與 oracle 分布的對齊程度

作者延用 Park et al.（2024，即 Grammar-Aligned Decoding 論文）的實驗設定，在 4 個 DSL 資料集上比較與模型真實分布的貼近程度：SLIA（字串+線性整數算術，15 題）、INV-BV（位元向量迴圈不變量生成，15 題）、CP（成分句法剖析，6 題）、binary（要求生成 5 位元隨機序列，但約束只允許 00000 與任何以 1 開頭的 5 位元字串——正確分布下 00000 機率應約 1/17，但樸素約束解碼因首步只有 0/1 兩個選項會給出約 1/2）。

指標：以取樣所得分布與語言模型分布間的 KL 散度衡量（SLIA/INV-BV/CP 各採 2000 樣本，binary 採 100 樣本）；由於分母的正規化常數 Z 相同，KL 散度只在同一問題內比較才有意義。基線：約束解碼（CD）與 ASAp（Park et al. 2024）——ASAp 可視為 AdapTrack 不做回溯的變體：取樣完一條序列後，只用累積的 Q 資訊影響「同一問題後續的其他取樣」，但不回頭調整已生成序列本身。模型：沿用 Mistral-7B。

結果：四個資料集上 AdapTrack 皆優於 CD 與 ASAp（平均 KL：CD 11.46、ASAp 11.90、AdapTrack 9.97）。SLIA、CP 資料集上 CD 與 ASAp 表現相近，AdapTrack 領先明顯；INV-BV 三者相近（可能因該資料集各步非法 token 比例分布較均勻）；binary 資料集是唯一 ASAp 明顯優於 CD 的情形，AdapTrack 仍優於 ASAp。滑動視窗分析顯示，隨著 Q 中累積資訊增多，AdapTrack 的 KL 散度持續走低或維持低點，在 SLIA/CP/binary 上一開始就找到不錯的分布，INV-BV 上則持續學習改善。
