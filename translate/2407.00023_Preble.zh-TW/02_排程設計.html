3. Preble 設計

3.1 整體架構

Preble 支援 data parallel 與標準 model parallel。兩層 scheduler 分工如下：

  • Global scheduler：request-level placement，維護整個 cluster 的 load 與 prefix-cache view。
  • Local scheduler：每 model instance／GPU 一個，做 iteration-level batching、queue 與 eviction。

中心化 global view 讓 E2 能看見 prefix 在哪裡，也避免把 iteration 級細節搬到分散式 control plane。作者的 implementation 估計單 global scheduler 可支撐至少 70–391 GPUs；更大規模則以多個 Preble clusters 分區。

3.2 E2 global scheduler

Global scheduler 維護 radix trees。每個 node 記錄 token count、cache 該 node 的 GPU set，以及 history window H 中各 GPU 使用該 node 的 request count。沒有任何 GPU cache、且 H 內無 request 使用的 node 會移除。

新 request 先做 prefix match：

  • 若 matched tokens > unmatched tokens，節省的重算大於需要平衡的新工作，選 exploitation。Request 送到 cache 最長 matched prefix 的 GPU；多張卡都有時選 load 最輕者。
  • 若 matched prefix 較短，選 exploration，依 prompt-aware load cost 找 GPU。這讓 prefix 能在新卡落地，換取長期負載平衡。

Explore cost 將三項都換算為 GPU compute time：

  1. 最近 H 內的 prefill + decode load；預設 H=3 分鐘。
  2. 為容納新 request 而 eviction 的 KV，日後重新使用時造成的 miss／recomputation cost。
  3. 新 request 在該 GPU 的計算 cost，已 cache 的 tokens 計為零。

實作只在 global scheduler 保存 token counts，再用 regression 估 prefill time、用 token count 估 decode time，避免維護過細的 runtime profile。

Prefix placement 後仍可能因熱門度改變而失衡。當最重 GPU 超過最輕 GPU 的 configurable threshold，Preble 把原本會 exploit 熱卡的未來 request 轉送到輕卡；若 popular prefix 的平均 queue time 在 history window 中加倍，系統複製 prefix 並按 subtree load 拆分流量。

Prefill 比 decode 更 compute-intensive。完全 cache-hit 的 request 幾乎只剩 decode，可當 decode-phase unit；cache miss 的長 prompt 加短 output 則是 prefill-phase unit。Global scheduler 優先把 miss-heavy request 配給 decode-heavy GPU，以利用尚未占滿的 compute；local scheduler 另保留傳統 chunked prefill。

3.3 Local scheduler

每個 local scheduler 維護 waiting queue、local radix tree 與各 node 的 active-request count。每個 iteration 後重組 batch；長而不共享的 prompt 會 chunk。GPU memory 不足時，依 tree-node access time 做 LRU eviction，並非同步阻塞 global scheduler。

FCFS 公平但忽略 reuse；最高共享量優先會 starvation。Preble 建立 P 個 priority groups，依 request 的 cached-token percentage 分組。例如 63/100 tokens cache-hit、P=10 時進第 6 組。組 batch 時按 priority 配額比例取 requests，高組取得較多名額，低組仍有固定前進機會。
