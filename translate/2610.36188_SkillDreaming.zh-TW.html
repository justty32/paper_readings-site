論文／訪談原始來源

Skill Dreaming: Evolving Repository Skills through Pull Request Streams

摘要與第 1～2 節：問題

軟體庫的 API、結構與實作慣例會隨時間改變，從過往任務學到的技能可能過時。Pull request（PR）的程式差異、審查及驗證紀錄提供專案如何演進的線索。Skill Dreaming 從 PR 流整理可重用技能，用它們指引後續功能及維護工作，再依新紀錄修訂技能庫；底層語言模型權重保持固定。作者將此與只針對個別任務檢索既有紀錄的做法區分，也討論其他經驗蒸餾與技能管理方法。（§1～2）

第 3 節：問題形式化

第 t 輪有專案狀態 R_t、技能集 S_t、先前 PR 及新請求 τ_t。系統建構並驗證 PR 紀錄，更新技能，再由固定權重代理使用技能提出 P_t；若接受，專案才成為 R_t+P_t，其結果和回饋供後續技能更新。

作者將目標寫為跨輪次成功效用之和，扣除檢索、候選建構、驗證、技能維護及執行的資源成本，並設定任務完成、既有功能維持與預算約束。文中的機率門檻是期望的可靠性要求，現有測試不提供保證；分階段流程僅近似此目標，不保證全域最佳。

歷史評估與構想中的持續部署不同：每個請求使用其記錄的歷史 base commit，只有技能集跨請求演化，生成的專案改動不串接成下一題的專案狀態。（§3，式 1～6）

第 4 節：從 PR 到技能與實作

系統先定位請求涉及的功能與依賴，依功能相似度及程式重疊檢索先前 PR，也可把歷史 commit 切成連貫變更。它依相容性、API 變化及審查／CI 回饋，將紀錄分類為可用、可修復、過時、無關或不安全；透過重用、修復或合成產生候選，再以測試和專案要求驗證。成功紀錄及可辨識的失敗原因均可供技能學習。（§4.1）

固定權重的 LLM writer 依模板將紀錄蒸餾為技能，寫明適用時機、實作方式與驗證方法，並保留來源 PR 與版本。技能涵蓋 PR 偵測、PR 建構、功能實作、維護補全及技能演化；失敗與審查修正可提供負面限制及修復策略。（§4.2）

新舊技能依觸發條件、步驟、元件及版本相容性對齊，採新增、更新、特化、擴充、標記衝突、取代或保留七種操作。過時版本連同來源封存，只有現役技能可供檢索。代理根據任務相似度、版本及過往效果擷取有限數量的技能，實作程式並補測試、文件、設定與相容性；失敗可在預算內修復後再驗證，結果回饋技能庫。（§4.3～4.4，表 2）

第 5 節：評估與指標

作者使用 SWE-bench Pro 子集（Ansible、qutebrowser、Open Library）及涵蓋 12 個專案的 SWE-bench Verified 題目；各題使用歷史 base commit，並稱只使用此前可得的 PR 與技能以避免未來資訊洩漏。代理採 mini-swe-agent，模型使用 Claude Opus 5 與 Sonnet 4.6；比較含檢索及多種技能方法。（§5.1）

官方解決率為官方測試通過題數除以總題數。Safe Rate 要求有效且非空的測試執行及所列安全要求，但不保證功能完成。Maintenance Surface F1 以必要與實際修改類別的精確率、召回率計算每題 F1，再取平均；涵蓋程式、測試、文件、設定、範例與變更日誌，不能驗證每項修改是否正確。效率分別計 token 與牆鐘時間，排除的離線技能建構成本應另報。（§5.2，式 9～10）

第 6.1～6.2 節：主要結果與跨專案

作者自報官方解決率如下；差值為百分點：

基準／模型 無技能基礎代理 Skill Dreaming 差值
Pro／Opus 5 79% 88% +9
Verified／Opus 5 83% 92% +9
Verified／Sonnet 4.6 77% 79% +2

作者因 Sonnet 在 Pro 的基礎表現較弱而未報該組。Verified／Opus 比較中，作者自報 Skill Dreaming 的 Safe Rate 為 1.00、Surface F1 為 0.74；append-only 分別為 0.94、0.72。主結果表未列各評估集題數或不確定性，因此這些比例的精度及差異的不確定性無法由表中判定。（§6.1，表 3～4）

跨專案實驗在 Click、Black、Rich、HTTPX、Arrow、Agents 各自將歷史 PR 分成技能建構及評估集，再從空技能池建立該專案技能。作者自報六個專案的 Task Success 均較基礎代理高 0.07～0.20，Surface F1 也均提高；這是以各專案自己的歷史建立技能，並非直接證明技能可跨專案移植。（§6.2，表 5）

第 6.3～6.5 節：分析、消融及持續演化

作者自報在 1,000 個 SWE-bench Pro Ansible PR 的品質分類中，正文稱五類 F1 均高於 0.86；表 7 的 unsafe 類別則列 0.86。定位實驗的模組層表現高於檔案及函式層。PR 實作比較中，Skill Dreaming 與 Best-of-K 在共用候選輸出上均報 Task Success 1.00、Surface F1 0.87，單次抽樣為 0.94／0.80。（§6.3，表 6～8）

作者報告，在技能過濾與混合檢索兩種設定下，完整方法的 Task Success 分別為 0.93、0.94；移除過時／取代關係過濾後結果較低。另一技能更新比較中完整方法為 0.93、append-only 為 0.89。這些是指定消融設定的比較，不能單獨確定所有元件對其他專案都具有相同因果效果。（§6.4，表 10～11）

持續演化實驗以 500 個歷史 PR 初始化，之後每階段增加 50 個，直至 1,000 個；作者報告 Task Success、解決率與 Surface F1 整體上升但偶有波動。歷史回放並未串接生成的專案變更，因此不能直接視為長期真實部署的結果。（§6.5，圖 2、§3）

第 6.6～7 節：成本與結論

作者自報效率表中 Skill Dreaming／SkillLens 的每題 token 為 26,894／14,300，牆鐘時間為 36.00／32.90 秒；對應 Task Success 為 0.93／0.61，Surface F1 為 0.80／0.71。前者 token 約為後者 1.88 倍；表 12 未清楚列明離線技能建構成本是否包含在比較中，不能據此推定端到端總成本。（§6.6，表 12）

作者結論是，從 PR 紀錄建立、對齊及更新專案技能，可改善所測代理的任務結果與維護涵蓋度。這些結果取決於所選任務、歷史紀錄、模型與驗證程序；測試通過及修改類別涵蓋均非完整正確性證明。（§7、§5.2）
