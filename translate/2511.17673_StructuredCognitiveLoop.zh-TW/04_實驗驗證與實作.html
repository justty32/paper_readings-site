4. 實驗驗證與實作

4.1 實驗設計

兩種互補驗證：(1) 受控 SCL Core 實驗（完全開源、可重現、以 mock LLM 確保確定性）；(2) GPT-4o 驅動的即時示範（展示真實世界的適用性）。

評估指標：策略合規（違例數）、冗餘防範（冗餘調用數、記憶緩存命中率）、可追溯性（審計軌跡完整度、證據引用率）。基準比較對象：ReAct、Reflexion、AutoGPT、記憶增強系統文獻中記錄的行為。

4.2 實驗一：多步驟條件推理

任務：「當基礎溫度為 55°F 時，查詢舊金山、邁阿密、亞特蘭大的天氣，然後按以下條件規劃旅行：(1) 若三地皆高於參考溫度→去最涼爽的城市，繪製該地天氣圖像；(2) 若僅兩地高於→去其中較涼者，發送郵件至 test-scl@test.com；(3) 若僅一地高於→去該地；(4) 若三地皆低於→取消旅行，推薦便利商店零食。」

任務測試：證據收集（序列 API 查詢與狀態持久）、條件邏輯（含溫度比較的複雜分支）、約束執行（單一最終行動、證據引用要求）、記憶一致性（跨多迴圈無狀態漂移）。

SCL Core 透過 4 個 CCAM 迴圈執行：Loop 1 舊金山天氣→Loop 2 邁阿密天氣→Loop 3 亞特蘭大天氣→Loop 4 決策整合（三地皆高於 55°F，選最涼爽的舊金山 64°F，生成天氣圖像）。每迴圈記錄：[COGNITION]、[CONTROL] ✓ PASS、[ACTION]、[MEMORY]。

結果：策略合規 0/4 違例（100%）；冗餘調用 0（記憶緩存有效性 100%）；審計完整性 100%（13/13 追蹤記錄）；證據引用率 100%。關鍵觀察：與常因不確定性重新查詢 API 的 prompt 中心系統不同，SCL 的 Control 模組在授權任何行動前檢查 Memory 中是否已存在證據，從架構層消除此類錯誤。

4.3 實驗二：受約束任務分配

任務：四位員工——Alice（資料分析）、Bob（UX 設計）、Charlie（後端）、Dana（前端）——依技能分配五項任務（財務報告、儀表板、UI 模型、後端 API、前端整合），確保工作負載平衡（無人承擔超過 40%），並以郵件總結分配。

執行過程：迴圈 1–4 查詢每位員工資料並存於記憶；迴圈 5 初始分配方案 A 被拒絕——[CONTROL] 檢測到 Bob 過載（2 項主要任務 = 40% 負載），方案存於記憶備審計；迴圈 6 修正方案 B 通過——重新分配 UI 工作給具前端專業與容量的 Dana；迴圈 7 起草含分配表的郵件並發送。

關鍵發現：被拒絕的方案 A 保留在記憶中，實現事後審計與分析——這與 prompt 中心系統（失敗嘗試通常丟失）形成對比。軟符號控制展示：約束被架構式執行（Regulation 形塑的檢查點拒絕方案 A），但以自適應方式應用（系統透過提出方案 B 復原而非災難性失敗）。

分析：(1) Prompt 中心系統：推理、記憶、執行在單一生成迴圈中糾纏，完全依賴 LLM 「記住」約束——在複雜性下脆斷。(2) 記憶增強系統：外部化存儲大幅減少記憶漂移，但缺少治理層確保已存資訊被正確使用。(3) SCL：透過架構式執行達到所有指標零違例。

4.5 即時示範：GPT-4o 旅行規劃智能體

以 GPT-4o（temperature=0.7）作為 Cognition 引擎，使用 OpenWeatherMap API 與 SendGrid 郵件服務，PostgreSQL 持久存儲含完整審計日誌。部署於 Streamlit Cloud。介面展示透明條件檢查、基於證據的推理與明確決策理由。初步統計：150 次以上交互，平均 4.2 CCAM 迴圈/任務，0 策略違例，98.7% 完成率（2 次因 API 逾時失敗，非架構問題）。
