3. 基於檢索的推測解碼

3.1 背景：推測解碼

在標準自回歸解碼中，給定前文 s=(x_1,…,x_t)，下一 token 由 x_{t+1} ~ p(x | x_1,…,x_t; θ_large) 生成，每步都需一次 LLM 前向，受記憶體頻寬所限而非常耗時。推測解碼藉一個小得多的模型 θ_small 減少 θ_large 的執行次數，每步迭代如下：

  • 草稿構造（Draft construction）：小 LM θ_small 自回歸地生成接下來 m 個 token x̃_{t+1},…,x̃_{t+m}。仍是逐一生成，但用小模型故算力成本低。
  • 草稿驗證（Draft verification）：草稿連同上下文 s 一起餵入 LLM，θ_large 以單次前向平行算出各位置的條件機率 p(x|s;θ_large), p(x|s,x̃_{t+1};θ_large), …。
  • 草稿接受（Draft acceptance）：從草稿第一個 token 起，比較 θ_small 與 θ_large 的條件機率，用**修正拒絕採樣（modified rejection sampling）**匹配 LLM 分布：位置 t+i 先抽 r~U(0,1)，若 r < min(1, p_large/p_small) 則接受 x̃_{t+i} 並繼續驗下一個；否則停止、重採 x_{t+i}、拒絕其後全部草稿，並從 t+i+1 開始新一輪推測解碼。

3.2 我們的方法：REST

經典推測解碼用小 LM 當 draft 模型，但找高品質 draft 模型通常困難：(1) 效率上要夠輕、不引入太多開銷；(2) 品質上要能準確預測 LLM 輸出；(3) 系統整合上要與 LLM 同詞表、且架構易於以相近配置分散部署。這些要求往往迫使人為每個新 LLM 精選甚至訓練專屬 draft 模型。

本文換一種解法：發展一個免訓練的推測解碼方法，能輕易整合任何新模型來加速推論。不依賴參數化 draft 模型，REST 改用檢索來構造草稿。以下先說明建庫與其上的操作，再說明如何用於草稿構造與驗證。

  • 資料庫構造（Datastore construction）：REST 基於一個預建資料庫 D={(c_i, t_i)}，c_i 是一段上下文、t_i 是 c_i 的對應延續。給定文字／程式碼語料，就用每個位置的「前綴上下文 + 對應延續」建成 D。

  • 從資料庫檢索（Retrieving from the datastore）：推論時給定上下文 s，目標是構造「很可能是 s 之延續」的草稿 token。不同於用小 LM 生草稿，我們直接從庫 D 檢索。檢索回一組延續候選 S = { t_i | (c_i,t_i) ∈ Retrieve(D,s) }。雖可用 dense retriever 找與 s 相似的 c_i，但那會增加推論開銷；我們改用快速精確匹配（exact-match）。

    • 檢索演算法（Algorithm 1）：目標是找出庫中與 s 最長後綴匹配的上下文。採貪婪策略，從預設的匹配長度上限 n_max（實驗設 16，因超過 16 token 的最長匹配極少）起，對每個後綴長度 n 取 s 的 n-token 後綴 q，找出所有以 q 為後綴的 c_i；只要有至少一個匹配（S≠∅）就回傳對應的上下文-延續對，否則把 n 減一、試更短後綴。用 suffix array（Manber & Myers 1993）實現高效精確匹配。整個檢索開銷極小（實驗中 <6%）。

  • 由檢索結果構造草稿（Trie 選詞，Algorithm 2）：候選集 S 可能很大，無法全部餵入 LLM 驗證；隨機抽子集又因 S 大而有隨機性、次優。作法是用 Trie：每條 t_i 的前綴對應 Trie 中「某節點到根」的唯一路徑，每個節點賦一個權重＝該前綴在候選中出現的頻率。先用 S 全部序列建 Trie 並更新節點權重，再用最大堆（依權重）挑出權重最高的 top c 個節點——即選出 top c 個高頻前綴當草稿序列。

  • REST 的草稿驗證（tree attention）：從庫檢索出的多條草稿常共享前綴；若把它們當獨立序列各自送進 LLM，共享前綴會被 Transformer 層重複計算、浪費算力。為此，我們用廣度優先搜尋（BFS）把子樹壓成一條偽序列（pseudo sequence）——每條草稿都是它的子序列，任何共享前綴只出現一次。再在每個注意力層施加精心設計的注意力遮罩，確保每個 token 的計算精確反映其在原始草稿序列中的依賴關係。此策略即 tree attention（Cai 等，2023；Miao 等，2023；Spector & Re，2023）。

  • REST 的草稿接受（更簡單的策略）：把草稿餵入 LLM 得各位置由 θ_large 給出的條件分布並採樣新 token，再檢查各位置採到的新 token 是否與草稿一致；從頭起所有正確草稿 token 皆接受，第一個錯誤之後全拒絕。如此，REST 產生的序列與標準自回歸生成完全相同（無損）。

  • 與既有方法比較：現行推測解碼依賴高品質小模型生草稿，須在小體積與強預測力間權衡、還要匹配基礎模型詞表，並額外佔用 GPU 記憶體、增加推論複雜度；REST 直接從庫檢索草稿，可輕易整合任何大小、詞表、架構的語言模型。與需訓練專屬模組（Stern 等 2018、Cai 等 2023）者不同，REST 免任何額外訓練，是跨模型的即插即用高效解碼方案。REST 的效果受檢索結果品質影響，故可藉更好／更大的資料庫或更先進的檢索模型進一步增強；亦可與傳統推測解碼結合（用 REST 加速小 LM 本身的生成），留待未來工作。

4. 實驗

4.1 實驗設定

  • 採樣策略：實作 greedy 與 nucleus（top-p）兩種。無論哪種，只有當草稿 token 與「從 LLM 採到的 token」一致才接受，故 REST 輸出與標準自回歸生成相同。
  • 資料集與模型：HumanEval（164 題人寫 Python 程式題）與 MT-Bench（80 個多輪問題）。HumanEval 用 CodeLlama（greedy 做 1-shot、nucleus 做 10-shot），MT-Bench 用 Vicuna（皆 1-shot）；各測 7B 與 13B，最大生成長度分別 512、1024 token。單卡 NVIDIA A6000 + 96 CPU 核，結果取三次平均。
  • 超參數：精確匹配起始後綴長度 n_max=16，逐一遞減至找到匹配；每條檢索延續候選長度 m 截斷為 10；依 Medusa 經驗「64 個草稿 token 為最佳算力配置」，故 Trie 中選出的草稿 token 上限 c=64。
  • 度量：Mean Token Time（平均生成一個 token 的時間）；Mean Generated Length M = L/F（生成 token 長度 L 除以 LLM 前向步數 F）——M 是 REST 加速的上界（忽略檢索與構造草稿的開銷）。
  • 資料庫：CodeLlama 用 The Stack 的約 270 萬筆 Python 碼（27GB）；Vicuna 用 UltraChat 約 77.4 萬則 ChatGPT 對話（12GB）。
  • 基線：實作標準推測解碼作對照，小 draft LM 測 Llama 68M、Llama 160M（Miao 等）、TinyLlama 1.1B、TinyLlama-Chat 1.1B（Zhang 等），草稿 token 數從 1 到 15（>15 反而變差）。

4.2 主要結果（表 1）

REST 相較標準自回歸與推測解碼皆有顯著加速：HumanEval 上 CodeLlama 達 2.12×～2.36×（如 CodeLlama 7B greedy：自回歸 27.89 ms/token → REST 11.82 ms/token，2.36×；同設定推測解碼僅 1.75×）；MT-Bench 上 Vicuna 達 1.62×～1.77×。要點：

  • nucleus 加速不如 greedy：推測是 nucleus 引入的隨機性所致。作者不宣稱 REST 在所有情況都勝過推測解碼（若有更強、更貼合 LLM 的 draft 模型，推測解碼可能更好），但 REST 無疑是快速推論的有力而直接的方案。
  • 加速依領域而異：HumanEval（程式碼）加速明顯高於 MT-Bench（一般對話）——此現象在推測解碼與 Medusa 也曾觀察到。
  • 檢索開銷可忽略：含建 Trie 在內的平均每 token 檢索時間 <1 ms。
