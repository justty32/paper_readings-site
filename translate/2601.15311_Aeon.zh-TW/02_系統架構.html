3. 系統架構

Aeon 實作一個混合的認知核心架構，在高效能系統程式設計與高階 AI 推理之間架橋。

3.1 設計哲學：Core-Shell 模型

核心設計哲學是 Core-Shell 分離：

  • Core（Ring 0）：以 C++23 實作，負責所有高頻、低延遲操作——向量相似搜尋、樹遍歷、記憶管理、WAL flush、EBR。直接操作原始記憶體頁並利用硬體加速（ARM NEON SDOT／x86-64 SIMDe）。
  • Shell（Ring 3）：以 Python 實作，管理高階控制邏輯——LLM 互動、提示工程、圖拓撲管理。
  • 零拷貝約束：Core 與 Shell 間在正常操作期間永不序列化資料。Shell 透過 nanobind 操作共享記憶體頁的唯讀視圖。

3.2 The Atlas：空間記憶核心

Atlas 是 Aeon 長期記憶的基礎資料結構，作為語義向量的空間索引。記憶節點定義為 N = {id, v, C, meta, sq}，其中 id 為唯一識別碼，v 為嵌入向量（FP32 或 INT8），C 為子節點指標集，meta 為固定大小的元資料區塊，sq 為量化比例因子（僅在 v 為 INT8 時使用）。Atlas 位於持久儲存但透過 mmap 映對至處理程序虛擬位址空間，避免標準堆積配置以確保連續性。

3.2.1 INT8 對稱純量量化：Aeon 引入對稱 INT8 量化作為一級儲存格式。對向量 v ∈ R^D，比例因子 sq = max_i|v_i| / 127，量化值 q_i = clamp(round(v_i / sq), -127, 127)。若 max_i|v_i| = 0，比例預設為 1.0 且輸出全零。所有輸入嵌入必須為嚴格的 L2 歸一化（∥v∥_2 = 1），使內積等價於餘弦相似度。

磁碟節點步幅：FP32 每節點 3,392 B、100K 節點 440 MB；INT8 每節點 1,088 B、100K 節點 141 MB——3.1x 壓縮比。

3.2.2 Greedy SIMD Descent：檢索使用 greedy SIMD descent。FP32 儲存時直接計算餘弦相似度；INT8 儲存時先以 NEON SDOT 指令計算 raw_dot = Σ(q_i^(query) · q_i^(node))，再解量化得 sim = raw_dot × sq^(query) × sq^(node)。複雜度為 O(log_B M)，B 為有效分支因子，M 為總節點數。 3.2.3 動態維度：嵌入維度因模型而異（MiniLM 384、e5-large 768、OpenAI v3 1536）。Aeon 透過動態步幅計算解決——AtlasHeader 儲存 D、M、Q，核心載入時計算 node_byte_stride = align_up(64 + payload(D,Q) + M, 64)，使單一編譯二進位可服務任意嵌入模型與精度，防止模型鎖定。

3.3 Write-Ahead Log（WAL）

為確保崩潰可復原性而不犧牲插入吞吐量，Aeon 實作解耦的 WAL 搭配三步鎖定協定：(1) 序列化（無鎖）——節點編碼為位元組緩衝區，含 16 位元組 WalRecordHeader（記錄型態標籤、payload 大小、CRC32 校驗）；(2) WAL Flush（僅 wal_mutex_）——序列化記錄寫入 WAL 檔案並透過 fdatasync() 刷入磁碟，此時 delta_mutex_ 未被持有，delta buffer 的並行讀寫不阻塞；(3) 寫入 RAM（僅 delta_mutex_）——wal_mutex_ 釋放後，節點 memcpy 至 delta buffer。核心洞察：磁碟 I/O（步驟 2）與 RAM 變異（步驟 3）永不競爭同一 mutex，將磁碟 flush 延遲隱藏在插入操作之後。復原時依序重播 WAL、CRC32 驗證、丟棄 torn records。

3.4 Sidecar Blob Arena

情節 Trace 將事件儲存為固定 512 位元組的 TraceEvent 結構體（O(1) 隨機存取）。先前版本將文字直接嵌入 440 字元欄位，不足以儲存 LLM 筆錄。Aeon 以 BlobRef 間接取代：一個 64 位元組 text_preview（前 63 字元對齊單一快取線）+ blob_offset/blob_size 指向附加型 mmap 支援的 sidecar 檔案（trace_blobs_genN.bin）。Sidecar 檔案使用 2x 倍增增長策略（ftruncate → munmap → mmap），提供零拷貝讀取（mmap 區域上的 std::string_view）。世代垃圾回收期間建立新世代 blob 檔案，僅複製非墓碑事件參照的 blob，舊世代檔案在所有 EBR reader 推進後刪除。

3.5 Double-Buffered Shadow Compaction

為支援即時應用（如 60 FPS 遊戲引擎），Aeon 實作受 Redis BGSAVE 啟發的零卡頓垃圾回收機制：(1) 微秒級凍結——獲取鎖、交換 active delta_buffer 與 frozen_delta_buffer、快照當前狀態，<10 µs；(2) 背景複製——背景執行緒迭代 mmap 檔案與 frozen delta buffer 中的活節點，連續寫入新世代檔案（atlas_gen2.bin），主執行緒繼續服務讀取並接受寫入；(3) 熱交換——背景複製完成後短暫鎖定以交換 MemoryFile 控制代碼；(4) 清理——關閉並刪除舊世代檔案，截斷 WAL。主執行緒僅在步驟 1 與 3 被阻塞（總計 <10 µs）。

3.6 The Trace：情節脈絡圖

Trace 提供時間與因果脈絡，結構化為一個有向無環圖 G = (V, E)。頂點集合 V 包含異質 TraceEvent 節點（V_user、V_system、V_concept）。邊集合 E 定義時序邊（E_next）與參照邊（E_ref），將情節節點連接至 Atlas 中的語義基礎。此神經符號架構的精髓在於：神經嵌入使節點可被相似性搜尋（語義檢索），符號邊（因果鏈）使每條記憶的來源與影響可被追溯與審計。這正是 ai_core §3.6「神經符號記憶管理 = 固化引擎記憶」所刻畫的雙重表徵——固化引擎既需要語義相似性來召回相關經驗，也需要符號因果鏈來保證每條固化產出可被問責。

3.7 Trace Block Index（TBI）

樸素的 Trace 線性掃描為 O(|V|)，對 10⁵ 事件不可行。Aeon 實作 Trace Block Index：將事件分組為固定大小 B = 1024 的 TraceBlock，每區塊維護一個增量更新的質心（來自其組成事件嵌入）。檢索採兩階段 SIMD 掃描：(1) Phase 1（區塊掃描）——SIMD 搜尋區塊質心以識別前 K 個最相關的時間窗口，成本 O(|V| / B)；(2) Phase 2（事件掃描）——僅對前 K 個區塊內的事件進行深度掃描，成本 O(K·B)。總搜尋複雜度 T_search = O(|V|/1024 + K×1024)，K 典型值 3–5 時對大型 trace 仍 sub-50 ms。

3.8 零拷貝介面

Aeon 使用 nanobind 向 Python 暴露 C++ 記憶體結構。介面將原始 C++ 指標包裝進 Python Capsule，重新解譯為唯讀 NumPy 陣列緩衝區。Shell 端任何修改底層記憶體的嘗試皆引發執行期例外。

4. 語義旁視緩衝（SLB）

SLB 是利用對話局部性達成 sub-5µs 檢索延遲的高效能快取機制。

4.1 理論：語義局部性：傳統快取依賴位址透明性；在向量資料庫中精確相等罕見。引入「語義慣性（Semantic Inertia）」概念：連續對話中，第 i 輪的主題向量 t_i 與 t_{i+1} 高度相關——P(dist(q_{i+1}, q_i) < ε) ≈ 1。

4.2 架構：SLB 為固定大小 K = 64 的小型連續環形緩衝，調校至容納於 L1/L2 快取。每個條目 e_k ∈ B 儲存質心 c_node ∈ R^D 與指向 Atlas 中完整節點的直接記憶體指標。關鍵架構決策——FP32-Only Cache：SLB 一律儲存 FP32 向量，無論 Atlas 量化格式為何；若 Atlas 為 INT8 量化，向量在插入 SLB 時解量化為 FP32，以 3.56 µs 快取命中延遲避免每次掃描的解量化開銷。因 K 小（64），採用 AVX-512/NEON 指令的窮舉線性掃描，其牆鐘時間低於 O(log N) 樹遍歷的數步（完美硬體預取、零指標追逐）。

4.2.1 多租戶隔離：多代理人部署時 SLB 分片為 64 個獨立環形緩衝，各受其專屬 mutex 保護，路由為 shard_id = hash(session_id) mod 64。此 lock-striping 架構確保競爭與語義脈絡嚴格隔離，單節點支援 10 萬+ 併行 session。

4.3 推測提取演算法：查詢時對 B 中 K 個元素執行向量化 SIMD 內積迴圈，尋找相似度超過閾值 τ_hit 的最佳質心；命中則 LRU-Insert 更新快取並返回節點指標；未命中則退回至 Atlas 樹搜尋。
