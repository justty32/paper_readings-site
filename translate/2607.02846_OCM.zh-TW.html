論文／訪談原始來源

Object-Centric Environment Modeling for Agentic Tasks

摘要與第 1 節：動機

LLM agent 能從經驗改進，但自由文字記憶越長越難維護、驗證與重用。既有程式技能常只是局部程序；程式化世界模型則常假定較小、明確的狀態空間。OCM 提出中間層：將環境的持久實體與機制編成物件模型，並讓程序知識建立在這個共同基礎上。

作者評估 ScienceWorld、ALFWorld、PlanCraft，宣稱平均排名最好且減少無效動作。這是作者的實驗結論，並非完整語意正確性的證明。

第 2 節：相關工作

Reflexion、ExpeL 與 workflow memory 顯示經驗可重用，但自然語言記憶會過期、冗餘、矛盾且難稽核。Voyager 等儲存可執行技能，WorldCoder／PoE-World 則學程式世界模型。OCM 的差異是把程序與共享物件模型綁定，而不是只保存單一側。

第 3.1 節：表示與學習迴圈

環境以多個 episode 互動。K_o 是定義類別與 helper 的 Python module，涵蓋物件狀態、affordance、限制、關係及轉移機制；K_p 是程序檔集合，記錄「何時適用、為何成功／失敗」的聚焦模式。每份程序必須 import 並使用 K_o，不能當成孤立軌跡摘要。

一個 episode 結束後，系統先由軌跡、結果、物件 signature 與程序索引產出更新計畫，再寫候選程式碼並驗證；通過才提交。

第 3.2 節：物件中心 reflection

Reflection 不直接把整段軌跡寫入長期庫，而先判斷可重用的學習目標。物件更新應描述經常出現的機制，例如「封閉容器要先打開才能取內容」，而非記住某個櫃子曾關著。若要修訂既有 symbol 或程序，計畫會列出待讀的舊原碼，降低重複定義與不相容修改。

第 3.3 節：更新與驗證

新頂層物件定義加入 module；同名定義則替換。程序以獨立檔保存，每檔只描述一個模式，不得實作完整 action controller。候選更新的 gate 是：候選 K_o 下的每一個程序都必須成功執行。失敗時回傳錯誤重新生成，成功才提交。

此 gate 只維持「可執行相容」不變量，沒有聲稱模型完整或正確；這是採用時最容易被誤讀之處。

第 3.4 節：漸進式揭露

決策時先看 public 類別、方法、docstring 與程序索引，不把完整原碼全塞進 context。需要細節才發出內部 Inspect[...]，檢索相符定義或程序；若找不到或 inspection 預算耗盡，必須回到環境動作。作者把這視為可擴張性與可稽核性的配套。

第 4 節：實驗與第 5 節：結論

作者以三個互動 benchmark 比較方法，報告 OCM 的平均排名最佳並降低 invalid action，並以案例分析說明物件化知識如何改善可行性。這些數字受所選 backbone、提示與 benchmark 分布限制；原文的驗證也不能偵測錯誤但仍能 import 的規則。結論是：以物件知識約束程序知識，可形成較結構化、可檢查且可按需讀取的累積記憶。
