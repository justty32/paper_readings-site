3. Lookahead Decoding

Lookahead Decoding 沿用 Jacobi 的「單步多 token」能力，但解決其限制。關鍵設計是追蹤 Jacobi 解碼的軌跡並從中生成 n-gram：維護一個固定大小的 2D 視窗（兩維分別對應序列軸與時間軸），平行從 Jacobi 軌跡生成多個互不重疊的 n-gram，此過程稱 lookahead branch（前瞻分支）；並用 **n-gram pool（池）**快取沿軌跡生成的 n-gram；有潛力的 n-gram 由 **verification branch（驗證分支）**驗證以維持輸出分佈，通過者併入序列。

3.1 前瞻分支（Lookahead Branch）

原始 Jacobi 只用上一步的歷史 token（等同只生成 2-gram），而 Lookahead 用過去 N−1 步的歷史 token 平行生成多個 n-gram（n≥2），更充分利用軌跡資訊。2D 視窗由兩參數刻畫：W 定義向未來 token 位置前瞻的寬度（平行解碼的位置數）；N 定義向過去 Jacobi 軌跡回看的步數（用以取回 n-gram）。以 W=5、N=4 為例，回看 3 步、每步前瞻 5 個位置：對所有 5 個位置執行修改版 Jacobi 迭代生成新 token，再與前 3 步軌跡上的 token 組成 4-gram 收入池中。每步移除時間與序列兩維上最舊的 token、附加新生成的 token，以維持固定視窗大小。

3.2 驗證分支（Verification Branch）

驗證分支藉此維持輸出分佈。貪婪取樣下：先從 n-gram 池中查找「有潛力」的 n-gram——即其開頭 token 恰好等於當前序列最後一個 token 者；再用 LLM 平行驗證這些 n-gram（作法類似推測解碼，但一次驗證多個互不重疊的 n-gram 候選）。進階取樣支援：既有樹狀驗證（tree-based，Miao et al.）針對 token 樹，不適用於本文的互不重疊 n-gram；本文改為沿 n-gram 長度漸進驗證並剔除前綴不符者。又因推測解碼式取樣須保存「草稿 token 取樣時的機率分佈」以在拒絕時更新分佈，而池中 n-gram 眾多、逐一存整個詞彙表大小的分佈記憶體開銷過大；關鍵洞見是：驗證與草稿 token「如何被取樣」無關——不同取樣法只影響接受率、不改輸出分佈，故可在生成端（lookahead branch）強制貪婪取樣，使機率分佈退化為 one-hot，只需記錄選了哪個 token（正確性證明見附錄 B）。此外設一上限 G 限制每步平行驗證的候選數以控管成本；經驗上建議 G 正比於 W，實作中直接令 G=W。

3.3 在同一步驟內解碼、預測、驗證

執行時，lookahead 與 verification 兩分支可整合進單一解碼步驟以善用平行處理，這需要一個特製的注意力遮罩（依「每個 token 只對位置索引比自己大的 token 可見」原則導出）；lookahead 分支的 token 與 verification 分支的 token 互不可見。與 FlashAttention 整合：FlashAttention 強制因果（下三角）遮罩，不適用本文更精細的遮罩，故將 Lookahead 的注意力樣式（可調 W、N、G）硬編入 FlashAttention，實測較 PyTorch 原生實作帶來約 20% 的端到端加速。

3.4 Lookahead 平行化（Lookahead Parallelism, LP）

兩分支皆易於在多 GPU 上平行：lookahead 計算由數個互不相干的分支組成，可分置不同 GPU 而不需通訊；verification 各候選彼此獨立，可分派到不同裝置亦不需通訊。前向傳播結束後只需同步各裝置生成的 token。與切分模型參數／狀態的管線平行（PP）、張量平行（TP）不同，LP 為每顆 GPU 保留一份完整模型（因而更耗記憶體），改為把 token 分派到不同 GPU，每步引入近乎零通訊——因此在推論上更具優勢（既有模型平行法在每步關鍵路徑上有大量通訊開銷）。並可隨多 GPU 增加的 FLOPs 放大 W、N、G 以進一步降延遲。

4. Lookahead Decoding 的擴展律

4.1 推測解碼的加速估計：以 β 表每個 token 通過驗證的機率（接受率），E(β)=α。若每步猜 γ 個 token，接受 token 數期望為 E(#tokens) = (1−α^(γ+1))/(1−α)（式 4）。若改為每步猜 b 條序列（各 γ token），則 E(#tokens) = (γ+1) − Σᵢ₌₁^γ (1−αⁱ)ᵇ（式 5，b=1 時退回式 4）。

4.2 Lookahead Decoding 的加速估計：定義步驟壓縮比（step compression ratio）𝒮 = 自迴歸步數 ÷ Lookahead 步數（生成同長序列）。Lookahead 每步搜尋以當前輸入 token 起頭的 n-gram，至多 G 條長度 N−1 的推測；因 G=W，可對應式 5 令 G=W=b、N−1=γ。設平均每 f 步有一次好推測（接受 E(#tokens) 個 token），其餘 f−1 步退回自迴歸，則 𝒮 = (f−1+E(#tokens))/f（式 7）。結論：給定夠大的 γ（即 N），可依每步 log(b) 線性減少解碼步數；且與推測解碼不同，同時增大 γ 與 b 時 Lookahead 不會碰到式 4 那種上限。由於每步 FLOPs 大致正比於輸入 token 數 (W+G)·(N−1)，這揭示了「依每步 log(FLOPs) 線性減少解碼步數」的擴展律，也意味它能強擴展到多 GPU——用更多 FLOPs 換更低的每 token 延遲，對延遲敏感任務極有利。

5. 實驗結果

模型與平台：使用 LLaMA-2 與 CodeLlama 的 7B/13B/34B/70B。S1 為單顆 80GB A100（70B 用 2 顆 A100 管線平行），S2 為 8 顆 40GB A100 的 DGX（含 NVLink）。皆 FP16、batch=1。資料集：MT-Bench（多輪對話、獨特 token 多）、GSM8K（數學）、HumanEval（補全＋填空）、MBPP（指令式生成）、ClassEval（類別級補全）；另在 XSum、CNN/DailyMail 驗證取樣。基線為 HuggingFace 貪婪搜尋，並以 FlashAttention 為更強基線；分散式比較 LP vs TP（DeepSpeed）／PP（Accelerate）。

  • 5.1 端到端：在各資料集上加速 1.5x–2.3x；程式碼補全表現更佳（如 2.3x，因重複 token 多、較易預測）；小模型加速較大（大模型很快撞上 GPU 算力上限，壓縮步數的能力較弱）。
  • 5.2 LP 與 FlashAttention：FlashAttention 讓 PyTorch 實作再快 20%；7B 在 MT-Bench 對比「帶 FlashAttention 的自迴歸」得 1.8x（1.9x vs 1.07x）。TP、PP 的多 GPU 反而拖慢（0.75x–0.82x），但 LP 能用多 GPU 的 FLOPs 續降延遲（如 ClassEval 達 4x）。
  • 5.3 生成品質（表 2）：在 CNN/DailyMail、XSum 上，無論是否開取樣，Lookahead 的 Rouge-1/2/L 與自迴歸幾乎一致（保住輸出分佈），同時加速 1.46x–1.60x；開取樣加速較小（接受率較低，與既有研究一致）。
  • 5.4 消融（表 3）：以平衡的兩分支（如 N=5,W=15,G=15）最佳（1.78x，加 prompt 為參考達 1.88x）。只給極小 lookahead 分支（W=1）雖仍有不錯加速但不如平衡；只給極小 verification 分支（G=1）則因可接受推測潛力低而較差。用 prompt 建 n-gram 池可進一步提升，已整合進實作。
  • 5.5 討論與限制：主要限制是需額外算力——忽略注意力隨長度增加的成本，7B/13B/34B 每步分別約需 120x/80x/56x 的額外 FLOPs；但因解碼受記憶體頻寬而非算力限制，這些額外 FLOPs 只造成有限的每步牆鐘拖慢。故 Lookahead 需要大量剩餘 FLOPs 才能高加速；在算力受限環境（如大 batch 服務）可能反而變慢，弱 GPU（RTX 3090）加速也較低。依 §4，需指數增加每步 FLOPs 才能線性減少步數，故有邊際遞減；但在 FLOPs 不足時，仍可輕鬆取得溫和加速（3090 約 30%、A100 >50%）——這是無需額外模型、訓練、也不改輸出分佈的免費午餐。A100 上單 batch 服務的近最佳設定：7B→W=15/N=5、13B→W=10/N=5、34B→W=7/N=5。
