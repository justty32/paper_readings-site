5. 實驗

模型：code-davinci-002（Codex）、gpt-3.5-turbo、gpt-4、StarCoder（15.5B）。初始生成單程式用貪婪解碼（τ=0）、多樣本用 τ=0.7 加執行式選擇；Self-Debugging 的解釋/回饋/新程式一律貪婪解碼。最多 10 輪除錯，實際成功案例多在 3 輪內。基線兩類：任務特化訓練模型（T5-3B+N-best reranking、LEVER）與純提示重排序法（MBR-Exec、Coder-Reviewer）。

5.1 主要結果

對比先前重排序法（表 1）：Spider 開發集上 Codex Self-Debugging+Expl 達 84.1，勝過需訓練的 LEVER 81.9 與 T5-3B reranking 80.6、純提示的 MBR-Exec 75.2；MBPP 上 Codex（n=10）72.2 → UT+Expl 75.6，勝過 LEVER 的 68.9（n=100）。

Spider Codex 81.3 81.3 —（無測試） 84.1 —
TransCoder Codex 80.4 89.3 91.6 92.5 87.9
TransCoder GPT-4 77.3 80.9 88.8 90.4 89.5

Spider 上簡單回饋幾乎無效（無解釋時模型分不出對錯 SQL，也不會對初始預測做有意義的修改）；TransCoder/MBPP 上因至少有一個測試可用，簡單回饋也隱含利用執行結果判對錯，故仍有增益。整體而言回饋越豐富越好，尤其當執行資訊出現在回饋訊息中。跨模型觀察：GPT-4 在 Spider 上初始生成與除錯皆遠遜 Codex（可能因其為 zero-shot 調校、不擅跟隨 few-shot 範例；GPT-3.5/GPT-4 零樣本 SQL 比 few-shot 差 10% 以上）；GPT-4 在 MBPP 初始生成最強，而除錯增益與 Codex 相當（TransCoder +12% 以上、MBPP +8%）；StarCoder 基線雖弱，單元測試執行同樣帶來顯著增益（MBPP 用 Trace +6%）。

5.2 消融研究

5.2.1 樣本效率（圖 6a）：Spider 上，對貪婪解碼單一預測施以 Self-Debugging 即匹敵 16 樣本基線；從 8 樣本出發除錯勝過 32 樣本基線。通常一輪除錯即足，其後增益 <0.1%。TransCoder 上單輪完整回饋較貪婪解碼 +12%，貪婪+除錯勝 5 樣本基線、接近 10 樣本基線（附錄 C）。

5.2.2 程式碼執行的重要性（表 3）：拿掉單元測試執行（模型全靠自己推斷正確性）後：Codex 仍可 +5%（TransCoder 80.4→83.9），Trace 回饋相對 Simple 一致較優；GPT-4 在 MBPP 無執行仍 +3.6%（72.8→76.0/76.4），其他 benchmark 增益僅約 1%；GPT-3.5 幾乎不動（TransCoder 89.1→89.1）。與 Codex 不同，few-shot 提示對 GPT-3.5/GPT-4 的除錯幫助不大，兩者全靠內部知識；無執行結果時兩者傾向對自己的初始預測過度自信。結論：程式碼執行在 Self-Debugging 中扮演關鍵角色；不過有時 LLM 仍能純靠自生回饋改善，其中執行軌跡回饋提供一致增益。

5.2.3 修復的錯誤類型：Spider 上增益集中於難題——依 benchmark 標注的難度分級，extra hard 題 +9%（63.9→72.9）。初始 SQL 通常「不是全錯」，而是複雜查詢下的小錯（漏 WHERE 條件、漏 SELECT 欄位等）；帶解釋的除錯讓 LLM 發現「問題 vs 預測 SQL」的落差。修復類型分佈（表 4a）：錯誤 WHERE 條件 25.7%、漏 DISTINCT 17.1%、錯誤 JOIN 14.3%、SELECT 欄數錯 11.4%、INTERSECT/UNION 錯 8.6% 等。TransCoder/MBPP 上（表 4b）60–70% 成功案例修「輸出不符」（初始碼已接近正確）：輸出不符 61.9%/69.2%、執行期錯誤 38.1%/30.8%；TransCoder 逾 30% 的成功修復處理跨語言實作差異（執行讓問題顯形化），MBPP 逾 10% 靠調換參數順序、對齊參數型別即修好。

6. 相關工作

Language models for code：單一預訓練 LLM 已可跨多種程式任務 SOTA，但對程式執行的理解仍有限——即使題目給了單元測試，生成的程式仍可能違反。既有工作用執行來從多候選中挑選（訓練 reranker、或以執行輸出共識做選擇）；本文則是利用並解釋執行來除錯，樣本效率優於只把執行用在初始生成。

Prompting techniques：程式碼解釋在精神上近似 chain-of-thought（逐行自然語言解釋利於除錯分析）；Self-Debugging 亦把除錯過程分解為多階段、對解釋與回饋觸發不同提示（近 decomposed prompting）。

Code repair：先前神經修復模型需專門訓練，部分利用執行軌跡、編譯/執行錯誤等額外資訊；Self-Debugging 同樣用執行結果與自生解釋輔助修復，但用預訓練 LLM + few-shot 提示、不訓練獨立修復模型。

Training with feedback / Prompting with feedback：RLHF、Constitutional AI、訓練 refinement 模型等皆需訓練；提示式的 Reflexion、Self-Refine、RCI、DERA 已在自然語言/推理/電腦操作領域展示自我批評的潛力。本文專注程式碼生成，同時證明自生回饋與執行取得的單元測試回饋皆有效；特色是以 rubber duck 式程式碼解釋讓模型察覺錯誤，不要求回饋明說錯在哪、怎麼修。

7. 結論

Self-Debugging 讓 LLM 為自己生成的程式除錯，能執行 rubber duck debugging、無人類指示即找出並修正 bug；跨多個程式碼生成領域 SOTA 並顯著提升樣本效率（Spider 無測試：解釋帶來一致 +2–3%、最難題 +9%；TransCoder/MBPP 有測試：最多 +12%）。這顯示除了增強從零生成程式的能力，教 LLM 迭代除錯自己的預測是提升編碼能力、降低取樣成本的另一條有前景的路。未來方向：更好的程式碼解釋能力（假說：解釋力越好→除錯力越好）、在解釋中兼顧高階語義與實作細節、在回饋中加入潛在 bug 描述——初步結果顯示模型自生的「語義錯誤訊息」在逐行解釋之上沒有額外增益，如何預測更有資訊量的錯誤訊息留待未來。
