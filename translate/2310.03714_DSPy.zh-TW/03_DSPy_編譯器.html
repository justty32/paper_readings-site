4. DSPy 編譯器

DSPy 表達力的關鍵來源是它能編譯（自動優化）此程式設計模型中的任意程式。編譯靠 teleprompter——一個透過 prompting 或 finetuning（在 DSPy 中兩者統一）改善模組品質或成本的優化器。DSPy 不強制，但典型 teleprompter 走三階段：

  • 階段一：候選生成（Candidate Generation）。編譯器先（遞迴地）找出程式中所有唯一的 Predict 模組（predictors，含巢狀於其他模組者）。對每個 predictor，teleprompter 可為其參數生成候選值：指令、欄位描述、或最重要的——示範（範例 I/O 對）。本版 DSPy 聚焦示範，發現簡單的類「拒絕取樣」法就能 bootstrap 出高效多階段系統。最簡的非平凡 teleprompter BootstrapFewShot：以 teacher 程式（未設則用待編譯程式的零樣本版）在部分訓練輸入上模擬（可高溫多次）；compile 模式下透明且執行緒安全地追蹤多階段 trace；用程式指標過濾出能共同讓 pipeline 通過指標的多階段 trace，丟掉壞例、留好例當潛在示範。LM 雖不可靠，卻擅長為多階段設計搜尋解空間——良好分解的程式通常能找到幾個「LM 能通過簽章與指標約束」的訓練例，據此迭代 bootstrap。
  • 階段二：參數優化（Parameter Optimization）。此時每個參數都有一組離散候選（示範、指令等）。可套多種超參調校演算法（隨機搜尋、HyperOpt 的 Tree-structured Parzen Estimator、Optuna）來挑選——即 BootstrapFewShotWithRandomSearch、BootstrapFewShotWithOptuna。另一型優化是 BootstrapFinetune：用示範更新各 predictor 的 LM 權重（該模組的 LM 參數即更新為新權重），通常以指標搭配交叉驗證優化平均品質，即使各階段無標籤也適用（視指標性質）。
  • 階段三：高階程式優化（Higher-Order Program Optimization）。修改程式控制流。最簡形式是 ensemble：bootstrap 同一程式的多份副本，替換成一個並行跑它們、再用自訂函式（如多數投票）把預測歸約為一的新程式。未來此階段可容納更動態（測試期）的 bootstrap 與自動回溯式邏輯。

5. 評估目標

程式框架可從計算效率、開發者效率、程式與概念直觀度等多維度評估。本文聚焦當前 LM pipeline 最迫切的問題：手寫、任務專屬 prompt 對達成高效系統的角色。三個假設：

  • H1：用 DSPy，可用簡潔、定義良好的模組取代手寫 prompt 字串，而不降品質或表達力。
  • H2：把模組參數化、把 prompting 當優化問題，使 DSPy 更能適配不同 LM，並可能勝過專家手寫 prompt。
  • H3：由此得到的模組化，使人能更徹底地探索有用效能特性或契合細緻指標的複雜 pipeline。

作者希望這能把「不同 LM 在 GSM8K 上怎麼比」這種欠定問題，轉向「它們在程式 P、以策略 S 編譯下怎麼比」這種良定、可重現的執行——最終目標是降低精雕 prompt 的角色，改以開發新的模組化、可組合程式與優化器為主。

6. 案例研究：數學應用題（GSM8K）

在 GSM8K（小學數學題）上評估：從官方訓練集抽 200 題訓練、300 題開發，最終用 1.3k 官方測試集；依前人做法評估 LM 輸出中最後出現的數值準確率。

所考慮的程式：三個簡單 DSPy 程式——一步的 Predict（vanilla）、兩步的 ChainOfThought（CoT）、多階段的 ThoughtReflection（reflection）。reflection 內部用 ChainOfThought(..., n=5) 取樣五條推理鏈，再用內建 MultiChainComparison（推廣自 Yoran et al. 2023）並行比較五次嘗試、綜合出新答案。關鍵：所用模組皆為通用，無一針對數學或特定 LM。

編譯：評估零樣本（none，不編譯）與多種編譯策略——LabeledFewShot(k=8)（從訓練集隨機抽 8 個示範，只取問題與答案欄位、不含推理，報 3–5 次平均）；BootstrapFewShotWithRandomSearch（bootstrap 出示範鏈，並以隨機搜尋把「選哪些示範」當參數優化，得 bootstrap）；把 bootstrap 當 teacher 再 bootstrap 一次（bootstrap×2，對零樣本表現差的程式尤有用）；以及對前 7 個候選程式做多數投票的 ensemble。另有 +human CoT（把 GSM8K 自帶人工推理鏈併入訓練集）。編譯一般在數分鐘至數十分鐘量級（即使較貴設定也只需跑程式數千次，如 150–300 個驗證例上 10–20 trial，且可平行）。

結果（表 1）：vanilla 程式顯示 GPT-3.5 與 llama2-13b-chat 在不先寫推理鏈直接預測答案時很吃力，尤其缺好示範（none 零樣本與隨機 fewshot）時；但 vanilla 經 bootstrap 與 bootstrap×2 顯著改善（檢視被 bootstrap 出的 prompt 發現：prompt 讓 LM 先在 answer 欄位裡推理，而指標只取最後數值故被允許）。CoT 程式方面，人工推理鏈（+human CoT）在有時能大幅提升，但用 bootstrap 可匹敵或超越它，證實 DSPy 能省去手寫 prompt。reflection 雖只多幾行卻是明顯贏家，CoT 配 ensemble 也很有效。整體上 bootstrap 編譯對每個程式、兩個 LM 都帶來大幅增益——表中所有程式都只由 2–4 個 DSPy 模組與 teleprompter 組成，揭示在 DSPy 的新範式下：是「組對通用模組」而非「操弄字串 prompt」把不同 LM 從 4–20% 準確率提升到 49–88%。（另與外部文獻做非正式比較，因評估方法差異大不逐一對齊。）

7. 案例研究：複雜問答（HotPotQA）

在 HotPotQA（多跳問答）的開放域「fullwiki」設定上探索：檢索用官方 Wikipedia 2017 abstracts dump 的搜尋索引、以 ColBERTv2 檢索。測試集隱藏故改用官方驗證集抽 1000 例當測試；訓練集切 70/30 為 train/valid，只保留標為 hard 者，抽 200 訓練、300 開發。

所考慮的程式：baseline vanilla（沿用 §6，question -> answer 簽章夠通用）；baseline RAG（§3.2 那個帶 ChainOfThought 的 RAG，此任務表現不佳，故引出兩個多跳程式）；ReAct（Yao et al. 2022 的多步工具使用代理，DSPy 內建模組，如 dspy.ReAct("question -> answer", tools=[dspy.Retrieve(k=1)], max_iters=5)）；以及自訂的 BasicMultiHop（模擬 Baleen/IRRR 的資訊流、近似 IRCoT）——forward 中跑兩「跳」，每跳用 ChainOfThought("context, question -> search_query") 生成查詢、檢索、累加 context，最後用 ChainOfThought("context, question -> answer") 作答。

編譯：沿用 §6 的編譯器，另考慮兩種組合——ReAct 從其較早的 bootstrap 出發再用 BootstrapFewShotWithRandomSearch；multihop 從其較早 bootstrap 出發用 BootstrapFinetune finetune 到 T5-Large（target='t5-large'）。

結果（表 2，報 answer EM 與 pair-retrieval 準確率）：相比 vanilla few-shot，CoT RAG 能在 DSPy 中自我 bootstrap 大幅提升 answer EM，但它全靠 ColBERTv2 直接從原問題找段落、召回受限；react 與 multihop 則在多「跳」中為檢索器生成查詢解決此問題。整體 multihop 最佳，bootstrap 再次對兩個 LM 都很有效地相對其 fewshot 變體拉高品質；bootstrap（與/或 bootstrap×2）可勝過 fewshot（對 multihop）與專家人工推理（對 react）。最重要的是——只靠編譯程式就能讓 llama2-13b-chat 與 GPT-3.5 競爭。為評估 DSPy 的 finetune 能力，multihop_t5 產出的 T5-Large（770M 參數） 模型在開發集達 39.3% answer EM、46.0% passage 準確率，僅用 200 個標註輸入 + 800 個無標註問題（teacher 為兩個 llama2-13b-chat multihop 的 ensemble/聯集）；考量其極小體積與本地可用性，推論成本比 GPT-3.5 這類專有 LM 低數個量級。（結果亦與多篇近期 HotPotQA 評估非正式對照，惟評估方法與測試樣本差異大。）
