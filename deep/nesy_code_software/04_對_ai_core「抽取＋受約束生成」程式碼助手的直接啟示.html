4. 對 ai_core「抽取＋受約束生成」程式碼助手的直接啟示

ai_core §5 的程式碼助手分兩層：上層抽取（聰明模型一次性把意圖／既有碼結構化成資產）＋下層受約束生成（笨模型在窄洞填碼，行數助手精準標記）。本批論文對這兩層各有可直接搬的零件。

4.1 上層「抽取」可借什麼

啟示 來源 落點
schema 約束抽取，把幻覺轉成召回遺漏 NeuroLog 12 關係 schema 2606.00669 ATP「抽取資產」階段定固定關係 schema（Def/Use/Call/型別簽章…），LLM 不確定就省略；每個抽取結果掛推導樹當可審計憑證
文法約束解碼讓小模型達大模型水準 VERUS-LM GNBF 2501.14540 下層笨模型生成時用 grammar-constrained decoding 強制輸出符合目標型別／簽章——直接是「受約束生成」的具體實作手段
知識/查詢分離，抽取產物可複用 VERUS-LM KB 範式 2501.14540、Foresighter 離線 2604.13290 ATP asset 設計成「一次抽取、多次查詢」；昂貴的結構化（呼叫圖/型別環境）離線做好存成工件，每次填碼只載入
抽取→正規化→確定性處理的極端版 AXIOM 正規化器 2606.00671 對「能完全確定性處理」的子任務（如 import 補全、簽章對齊），把 LLM 降格為正規化器，推導交確定性程式；棄答為一等公民——不確定就標記留給人，而非硬填

4.2 下層「受約束生成」可借什麼

啟示 來源 落點
零相依驗證器當接地錨，先天免崩 NeuroLog ASan/Foresighter FTA/全批 ATP v0 的「ast.parse 過 + 簽名符合」就是這種錨；可再加「單元測試 / 型別檢查」當第二層，全部純標準庫、確定性
執行引導比純機率枚舉強 GridCoder LTS 自陳 2411.17708、TheoryCoder-2 2602.00929 笨模型「填洞填錯結構」是最怕的失敗；把中間執行狀態回饋進每步生成（而非只在最後驗），對症解
SAT 模型/診斷當可消費工件 NeuroLog 2606.00669、Policy Compliance unsat core 2603.20449 驗證失敗時回「Step/行 X 違反約束 c」這種結構化診斷餵回生成，而非只回「失敗」；ai_core 的行數助手天然適合產這種定位
步級局部修補，不重生整段 VeryTrace 2606.24124 填碼出錯時只補該洞，保留其餘——對應行數助手的「精準標記」

4.3 自修正迴圈與飛輪治理可借什麼

啟示 來源 落點
驗證器結構化回饋驅動自我修正才是效能主因 LLM+ASP 54.6%→78.0% 2604.27960 ai_core 的 retry/guard 必須吃結構化錯誤訊息（編譯器/型別/測試），而非自由文字反思；平均 2.18 次修正就夠
context rot：精簡參考勝過冗長文件 LLM+ASP 2604.27960 給笨模型的 in-context 規範要蒸餾到 1/8 長度；冗長文件反而害模型漏約束——直接影響 ATP 留白的 prompt 設計
語意修正＝反向翻譯比對（低成本對齊驗證） ChatLogic 2407.10162、VERUS-LM 可滿足性 2501.14540 生成碼後反向翻回意圖描述、與原意圖比對，是廉價的語意對齊閘（補在語法驗證之上）
分級/只在必要時升級 VerIbmc 2606.16886、NOVA 2606.27243 對應「貴/便宜智能分工」：先用確定性 matcher（零 LLM）托底，解不了才升級到笨模型，再不行才升級到聰明模型；NOVA 的「驗證即梯度去噪」＝把失敗存成禁區方向回饋搜尋
可重用庫累積：緊湊抽象庫 > 龐大低階庫 DreamProver 104→76→53 2604.26311、CoCoDA 2605.08399 ATP 資產庫要做語意分群+去重+LRU 遺忘維持小而精；CoCoDA 的 typed DAG 檢索（符號簽章剪枝→描述排序→規格過濾→範例消歧）是「對庫大小次線性檢索」的現成設計，直解 ai_core「資產庫一大就撐爆上下文」的隱憂
ILP 學可審計規則演化護欄 AutoSpec 2606.24245 ai_core 若要為程式碼助手加「安全/風格護欄」，ILP（只提名判別謂詞、CEGIS 迭代）給出符號、確定性、可審計的規則自我演化層

4.4 一句話收斂

ai_core 程式碼助手 = 把本批的「LLM 提案 + 零相依符號驗證器把關 + 結構化診斷驅動自修正 + 緊湊可重用資產庫」這套配方，落在「檔案/行填碼」這個任務上。 與 cross_fusion 檔的最小路線（ATP v0 → 受約束生成換血 → 證書語意化 → 飛輪半自動 → 第二條 ARC 裁判線）完全相容——本檔補的是「下層驗證器與抽取 schema 該怎麼設計」的具體零件。

5. 研究空白與方向

跨本批可見的、與 ai_core 相關的開放問題：

  1. 形式化／約束翻譯仍無法全自動。 Policy Compliance 2603.20449 坦承「政策編碼是 open problem」；Foresighter 2604.13290、VeryTrace 2606.24124 的抽象語意/schema 庫仍須人工設計。對 ai_core：抽取 schema 與受約束生成的文法，短期內仍是「人類播種、機制接管」的半自動路線（呼應 cross_fusion 提案 1）。

  2. 可機械驗證性是增益天花板，純語義任務無解。 VeryTrace 在 CLUTRR、Logitext 在 LegalBench 都因「可機械驗證機會少」而增益縮小甚至倒退。對 ai_core：程式碼任務天生比自然語言任務更可驗證（執行/型別/測試），這正是程式碼助手作為「第一目標」的結構性優勢——但「意圖是否符合需求」這層語義仍無確定性錨。

  3. 組合/結構泛化未解。 GridCoder 2411.17708 結構 OOD 崩、NLI 2604.18907 靠昂貴 test-time 梯度搜尋才補上。對 ai_core：笨模型「沒見過的程式結構」填不出，執行引導（LTS）是已知但未在本批工程系統落地的方向。

  4. 靜默召回遺漏無法偵測。 NeuroLog 2606.00669 自承 schema 把幻覺轉成省略後，「缺的語意事實偵測不到」。對 ai_core：抽取階段漏掉的結構，下游無從補救——需要覆蓋率自評機制。

  5. 可重用庫的領域特定性 + 跨域遷移。 DreamProver/TheoryCoder-2/CoCoDA 的庫都「本質領域特定」。對 ai_core 資產庫：跨專案/跨語言的抽象遷移仍是開放題；CoCoDA 的 typed DAG 與 DreamProver 的語意分群是目前最有希望的「可檢索、可遷移」結構。

  6. 本地化部署 vs 雲端 frontier 的性價比拐點。 VerIbmc 2606.16886 證明本地開源 7B–120B + 符號托底可逼近雲端 frontier。對 ai_core「貴/便宜智能分工」：符號層（Phase 1 零 LLM 托底）能讓「便宜本地模型」承擔更多——這是把昂貴 API 用量壓低的關鍵槓桿。

  7. LLM 親手造驗證器的奇點。 LLM2SMT 2603.06931 把 LLM 從「用符號工具」推到「造符號工具」。對 ai_core 遠期（§6 v0 ATP 之後）：助手能否合成出自己後續要用的確定性 matcher／驗證器，是「固化飛輪自動化」的終極形態。
