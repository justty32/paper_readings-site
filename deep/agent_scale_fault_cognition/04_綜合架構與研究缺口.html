這張圖把三個問題接起來。規模靠稀疏喚醒與分層推理；錯誤治理靠不可繞過的驗證器與事件紀錄；思想模型則被落成顯式狀態，而非只藏在 prompt 裡。

最值得做的四個研究缺口

千萬級不是 N，再多一個零

AgentScope 已證明百萬 actor 與百萬 LLM 任務可執行，但未回答長期持久狀態、持續到達事件、跨日 policy 更新與部分節點故障。2407.17789 千萬級的好 benchmark 應同時量測活躍率、訊息扇出、狀態大小、推理階層、成本與故障恢復，不能只量一次性 makespan。

從單點歸因走向分散式因果圖

Who & When 顯示單一責任 agent／步驟已很難找。2505.00212 REFLECT 又主要處理單一最早決定性錯誤。2606.09071 下一步應容許多個必要原因、共同充分原因、延遲污染與共享記憶造成的跨軌跡故障，並用干預而非敘事驗證。

不確定性必須成為控制訊號

目前 UQ 多停在分數或 benchmark。2602.05073 真正的系統要回答：什麼分數觸發追問、換工具、換模型、召集其他 agent、棄權或人工介入；觸發成本是否低於避免的損失；校準是否會隨 policy、工具與環境版本漂移。

心智狀態需要型別、版本與撤回

SToM 把他者意圖變成可更新分布，是比人格 prompt 更好的起點。2510.18476 但完整系統還需區分觀察、假說、信念、承諾與目標；每項要有來源、時間、信心、作用域與撤回規則。否則錯誤信念一旦寫入共享記憶，就會從認知問題變成基礎設施事故。

若要收斂成一個研究題，最有價值的版本是：為千萬個持久、稀疏活躍的 agent 建立可驗證心智狀態與因果故障治理層。它同時碰到 actor runtime、agent UQ、可重播系統、Theory of Mind 與神經符號治理，且目前沒有任何一篇論文把五者接完整。

十二篇補上的控制平面

新納入的系統工作可對應成一條完整、但尚未被任何單篇實作的 machine step：

WakeIntent / queued Round
  → HiveMind 式 endpoint admission                         [[2604.17111]]
  → InferCept / Preble 式 context residency scheduling     [[2402.01869]][[2407.00023]]
  → HORMA 式 source-linked context manifest                [[2606.11680]]
  → LLM proposal
  → SEAgent 式 argument-level capability / flow policy     [[2601.11893]]
  → PCAA 式 action certificate / approval semantics        [[2606.04104]]
  → intent journal
  → external effect
  → verify-before-retry / outcome unknown                  [[2608.02645]]
  → deterministic goal / safety verifier                   [[2607.01793]]
  → telemetry anomaly monitor + typed restart              [[2608.02464]]
  → provenance graph / dependency invalidation             [[2606.04990]][[2607.20827]]
  → structured-memory invariants                           [[2602.11243]]

這不是把十二套框架硬疊在一起，而是用它們分辨不同語意：排程器決定何時執行；capability 決定可否執行；certificate 保存誰授權；effect verifier 判斷實際發生什麼；goal verifier 判斷是否達成；provenance 說明結果依賴哪些資料。任何一層都不能由另一層的「成功」位元取代。

Invalidation Contracts 把圖中的 dependency invalidation 從需求標籤落成 version stamp、row-level diff、dependency vector 與 rule fingerprint，並把 artifact validity 與 planner compliance 分開計量。 2609.00243 這補上 provenance graph 知道「依賴誰」之後，如何在上游漂移時精準撤銷派生記憶的協議空白；也反駁「快取仍新就等於執行者會用」這種跨層成功位元。（本檔補註，非作者自陳）不過證據來自兩個合成 API domain，且假設 honest server，簽章與惡意版本跳號仍未納入。 2609.00243

對 FreePy 最可檢驗的五個假說

  1. Dormant scale：固定 K 個 active Step attempts，將 Bot records 從 10K 擴到 10M；量測喚醒延遲、metadata resident set、queue fairness 與 recovery time，而非宣稱 10M 模型同時推論。
  2. Effect safety：對每個 transition 注入 crash-before-dispatch、crash-after-dispatch、lost receipt、stale read 與 partial write；驗證 operation identity、unknown outcome、late-result fencing 與 ledger settlement 不重複。
  3. Evidence completion：讓模型提交 completion claim，分別以 mechanical、probabilistic、human-authoritative verifier 裁決；統計 false completion、defer 與人工成本。
  4. Provenance invalidation：替 context item 翻轉 source authority、刪除合法 evidence、更新上游 memory generation；確認未授權資料不能影響 sensitive argument，舊派生狀態會失效。
  5. Replay／fork distinction：同一 event journal 重建必須得到相同 projection；重新呼叫模型必須產生新 branch 與新 attempt identity，不能冒充 replay。

這五項合起來，才是「千萬 agent 怎麼管理」的可證偽版本。它不以人格數量取勝，而以多少持久狀態能被正確喚醒、限權、恢復、驗證與撤回來衡量。

從 LLM-centric OS 到可驗證 agent machine

「LLM＝CPU、context＝RAM、RAG＝disk、tool＝peripheral」適合描述資料流，卻漏掉 OS 最重要的隔離、生命週期、授權、交易與恢復。把新一批工作接上後，較完整的 step 應是：

durable identity / event journal
  → AIOS-style syscall + admission                         [[2403.16971]]
  → Continuum-style active-request / KV residency          [[2511.02230]]
  → private filesystem branch                              [[2602.08199]]
  → structured intention                                   [[2602.23193]]
  → task/action/source/scope policy                         [[2603.19469]]
  → fresh authority witness at commit                      [[2607.10487]]
  → Atomix-style effect settlement                         [[2602.14849]]
  → external postcondition + goal gate                     [[2606.11688]]
  → append committed event / rebuild projection

AutoGen 2308.08155 與 CrewAI 類框架主要處理上層工作流表達、角色、訊息與 tool 接線（CrewAI 官方架構入口）。AutoGen 的 Docker executor 能縮小生成程式碼的執行面，但框架本身不因此自動獲得 end-user data authorization、完整 provenance 或跨工具 transaction；官方也明說 AutoGen Studio 未實作完整 jailbreak 與 end-user data permission 安全（AutoGen Studio 官方說明）。這些必須由部署者與下層 control plane 補上。把「可編排很多 agent」稱為「OS 級權限隔離」會混淆 abstraction convenience 與 enforcement guarantee。

對 FreePy 最直接的設計判準因此不是是否長得像 OS，而是每一個 boundary 能否回答：誰擁有狀態、誰能讀寫、何時權限失效、效果是否已提交、失敗後能否重建、完成由誰驗證。只有這些答案被寫進 durable schema 與不可繞過的 transition，OS 隱喻才變成可測的系統。
