6.2 修正二：固化引擎的「何時」有答案了，但價值判準要換

初版說「零件已就緒，難的是時機」。主題 11 的五篇把時機問題拆成四個可操作的子問題：

子問題 文獻給的答案 對 ai_core 的動作
固化的價值怎麼衡量？ 2603.23244：人類解謎的耗時被「線上庫學習模型估計的搜尋空間大小」預測，而非程式長度 判準應是「省下多少搜尋」，不是「壓縮了多少字」——與 MDL 路線（2405.06906 用 Stitch 壓漢字、2211.16605 Stitch）是兩種不同的目標函數，別混用
固化的時機？ 2605.09985 前瞻式壓縮：決策應前瞻而非事後，純貪婪固化在課程上會崩潰；2603.23244 人類策略從「早期求完整」轉向「後期求復用與成本」 固化器需要對未來任務分佈的預期，不能只看歷史頻次
固化的准入？ 2606.13317 SkillCAT：合併前先用來源任務重播評分驗證候選修補，再編譯成可路由子技能拓撲、只載相關節點 這就是 §3.4 憑證准入搬到「入庫」這道關卡——ai_core 的治理原則可以原封不動複用
固化完能丟掉原案例嗎？ 2603.17198：部分成立——未見關係的泛化上，免存重播可持平甚至勝過存 100 筆；但已知事實的保留仍略遜重播緩衝，作者定調兩者互補 抽象不能完全取代案例庫，得保留一個小的原案例集

另外兩篇提供了警告與方向：

  • 警告：2604.17308 SkillFlow 的 166 任務評測顯示，技能自我演化不是普遍有效——最強模型 +8.43 分，但多數模型停滯或退步，失敗模式是技能膨脹、庫碎片化、錯誤技能被繼承。ai_core 的固化引擎必須先設計這三者的防線，否則「會固化」比「不固化」更糟。
  • 方向：2605.17734 HASP 把技能從自然語言 prompt 升級成可執行的 Program Functions（should_activate/intervene 一對，只在失敗傾向狀態觸發），同時當推論期 guardrail、訓練監督訊號與技能庫准入機制——這幾乎就是固化引擎的字面定義。但它的「failure-prone 才觸發」回答的是何時介入，不是何時該把某個 PF 退役或收回策略內，後者仍是事後觀察而非自動機制。

對照組值得記住：2303.11366 Reflexion 把經驗固化成易失的自然語言反思（滑動窗口、跨題不保留），2209.07753 Code as Policies 生成的函式只在同一 session 累積、無驗證、不持久化。從 Reflexion → Code as Policies → Voyager → HASP，是一條「經驗載體從自然語言走向可執行程式、從易失走向持久且有准入」的清楚演進線，ai_core 想要的是這條線的終點。
