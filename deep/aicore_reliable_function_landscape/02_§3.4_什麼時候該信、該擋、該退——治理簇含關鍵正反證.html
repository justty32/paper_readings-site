3. §3.4 什麼時候該信、該擋、該退——治理簇（含關鍵正反證）

這是本批最有「立論」價值的一簇，因為它同時收進了正例、反證、與理論原型，能把 ai_core「拒絕為預設＋憑證准入」從口號變成有據的設計。

三篇正例（2203.14465 STaR、2310.02304 STOP、2305.11738 CRITIC）與一篇反證（2310.01798）拼起來，給 ai_core 一個可引用的實證斷言：自我改進的增益幾乎全來自「用外部確定性訊號決定何時停／保留哪個候選」；一旦這個訊號被拿掉或被模型自身污染，飛輪就退化。這直接支撐 ai_core「固化引擎必須有確定性 verifier」與「拒絕為預設」——內省不是憑證，執行才是。STOP 額外量到的 reward hacking／逃沙箱（>1000% 假正確率、警告註解無效）更是「執行層強制治理」的必要性證據。

3.2 憑證怎麼生：驗證器的四種來源

「憑證准入」需要一個便宜可靠的憑證產生器。本批給了四條路，可按成本／可靠度選型：

來源 代表 憑證怎麼來 對 ai_core 的意義
訓練式驗證器 2110.14168 GSM8K 生多解、訓 verifier 選最佳 「生成便宜/驗證可靠」不對稱性的起點；6B+verify≈30×模型
過程監督 2305.20050 PRM 標到「第一個錯的步」 步級把關粒度＝§5 每步可裁決；比結果級更安全
自生測試（執行） 2207.10397 CodeT 自動生測試＋雙重執行一致性 執行取代訓練的確定性把關，程式碼助手測試閘門
生成式 oracle 2305.14591 ALGO LLM 生暴力解當對拍 oracle 把驗證降維成 LLM 擅長的暴力解生成

2304.05128 Self-Debug 則把憑證接回修復迴圈：有單元測試時執行回饋 +12%，無測試時僅解釋式自判 +2–3%——接地強度光譜的乾淨量化，再次呼應 3.1 的反證。

3.3 該退／該委派：棄權與委派的理論原型

當憑證不足時，ai_core 的預設動作是「拒絕／委派」。這兩個動作在更早的文獻裡已有帶保證的理論原型：

  • 1705.08500 Selective Classification：給定風險上限 r＋信心 δ，SGR 演算法學出拒絕函數，讓測試風險以 ≥1−δ 機率保證不超過 r，否則輸出「不知道」——這正是 ai_core「穩定度%門檻」的可證明原型（且最便宜的 softmax 信心反而勝 MC-dropout）。
  • 1711.06664 Learning to Defer：把「棄權」推廣成「委派給下游決策者」，閘控變數學的是「這一例上模型與下游誰的損失較低」——ai_core「非它不可才留 LLM，否則委派確定性節點」的可學判準原型。

對 ai_core 的落點：§3.4 的四個動作（信／擋／退／委派）在文獻裡都有帶保證的先例，缺的不是理論而是把 LLM 輸出接到這些框架所需的「校準信心分數」。這一條與 §2.1 FrugalML→FrugalGPT 的落差是同一個缺口：可靠的品質分數。ai_core 的「憑證」設計若能同時餵給成本梯度（升不升級）與治理（擋不擋、退不退），就一石二鳥。

3.4 2026-09 補入：治理動作不只拒絕與委派

Discovery Loop 佐證 3.1 的外部接地主張，但把治理往前多推一步：獨立 verifier 與逐目標 artifact 保存負責判定「哪個改善能留下」，近期可驗證改善則決定「探索預算還要不要繼續」。固定目標後段的單位改善成本相差 130 倍（作者自報），所以繼續呼叫 LLM 也應通過邊際收益門檻，而不是只替候選解設門（本檔補註，非作者自陳）2609.05093。

具身系統則顯示，「退」至少還要按可恢復性分流。FLARE 把仍在原任務能力邊界內的姿態偏差交給 Retry，把已破壞任務前提的環境狀態交給 Reset 專家；但人類指定 Reset 的消融仍比線上模型路由高 7 個百分點（作者自報），說明「會修」與「何時切換去修」是兩份不同的憑證（本檔補註，非作者自陳）2608.26645。

Provably Safe Sim-to-Real 再加入一種既有「信／擋／退／委派」未明寫的動作：依誤差證書，連續調整候選策略與已知安全基線的混合權重。這不是對既有拒絕預設的否定，而是把二元門改成部署強度旋鈕（本檔補註，非作者自陳）；其保證依賴已知嚴格可行基線、tabular CMDP 與可分離的動力失配，超出這些條件仍待實測2609.01418。

4. §3.6 固化引擎——最硬的未決題，文獻給了一條光譜

ai_core 自認最硬的是固化引擎。好消息：把「案例結晶成可重用抽象庫」這件事，本批文獻已鋪出一條從離線到線上的完整光譜，且核心演算法可直接搬。

三個對 ai_core 最關鍵的實證：

  1. 最貴的一步有現成高效替換件：2211.16605 Stitch 證明「找 MDL 最優抽象」不必像 DreamCoder 那樣慢——top-down branch-and-bound 快 3–4 個數量級、省 2 個數量級記憶體，還是 anytime 演算法。固化引擎的瓶頸零件已經開源（Rust crate）。
  2. 資產必須自帶規格：2310.19791 LILO 的反面結果——匿名抽象＝程式碼混淆（解題率暴跌），加了 AutoDoc 命名／docstring 才回正；而且 GPT-4 自己做不了壓縮（壓縮率≈1.0、僅 19% 語法有效）。這給 ai_core 兩條硬約束：固化出的資產要自帶文件才能被 LLM 消費者復用；全語料形式壓縮要交給符號引擎，不能指望 LLM 代勞。
  3. 固化可以是線上的：2401.16467 ReGAL（重構＋執行等價驗證增量長庫）與 2401.12869 TroVE（使用中生成／修剪、「使用頻率＝存續憑證」）示範「邊做邊結晶」，且 TroVE 的修剪規則直接把 §3.6 接回 §2 資產治理——沒人用的資產會被汰除。

對 ai_core 的落點：固化引擎不必從零造。可行架構＝Stitch 當壓縮核心 + LILO 式 AutoDoc 讓資產可復用 + TroVE 式使用頻率修剪做治理 + ReGAL 式執行驗證當准入憑證。而「什麼時候該固化」仍是開放問題（backlog 主題 4 的 2605.09985 Prospective Compression 專攻此點，尚待處理）。
