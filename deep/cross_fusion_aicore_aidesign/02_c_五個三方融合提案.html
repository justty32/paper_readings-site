(c) 五個三方融合提案

每個提案標明主觸及哪兩三方、可落地步驟、引用零件。

提案 1：把【核】未決的「固化引擎」做成【設】的經濟淘汰 ＋【論】的閉環去重

觸及：【核】§3.6（最硬未決問題）＋【設】bucket-brigade ＋【論】2507.14172 2501.17848

【核】roadmap §3.6 把「固化引擎手動 vs 自動」列為「這題優先」的未決問題；【設】的 bucket-brigade／破產淘汰／元件入庫正是一台現成的自動固化引擎；【論】提供讓它不空轉的兩個技巧。

  • 步驟 1：v0 先手動固化（【核】§6 路線），但把「固化決策」結構化成一張可被經濟機制接管的表：每個 LLM 留白記錄 (命中次數, 成功率, 平均成本)。
  • 步驟 2：把上表接成【設】的最小 bucket-brigade——留白＝節點、命中＝收入、固化成本＝支出，接不到單（長期低命中）的留白被標記「可撤照」，高頻穩定的留白被提名「可固化成 matcher」。
  • 步驟 3：用 2507.14172 SOAR 的「搜尋軌跡 hindsight relabel 回灌」思路，把笨模型填洞的成功軌跡存成 few-shot 資產（不丟）；用 2501.17848 eggp 的等式圖去重，避免資產庫塞進語意等價的重複 snippet。
  • 產物：把【核】「手動 vs 自動」的二選一，變成「手動播種 → 經濟自動接管」的連續譜，且 v1 不必重寫。

提案 2：統一「證書 ↔ 財富 ↔ 接地比例 αₜ」為單一可稽核量

觸及：【核】§3.4 nondeterministic 證書 ＋【設】Q-table/財富 ＋【論】2601.05280 αₜ、2509.21780 EIC

三方各自發明了同一個量的三種記法，融合後可互相校準：

三方 它的「可靠度量」 撤除機制
【核】 證書：(模型 Z, 測試組 B, 穩定度 X%) 撤照（有確定性解法就踢出）
【設】 節點財富 / Q-value 破產淘汰
【論】 接地比例 αₜ（2601.05280）；EIC 結構穩定度（2509.21780） αₜ→0 即崩；EIC 過濾數值病態
  • 步驟 1：把【核】ATP asset 的 certificate 欄位（§6 寄生第九軸）擴成 {model, test_set, stability, wealth, alpha_grounded}——一個欄位同時當證書、財富、接地度。
  • 步驟 2：用 2601.05280 的判據給「准入」一條理論底線：任一 LLM 留白若其接地訊號來自「靜態 benchmark proxy」而非「程式可執行 verifier」，標記 Goodhart 風險旗標（DGM 2505.22954 正落此風險帶）。這把【核】§3.4 的「夠穩才准入」從工程直覺升級成有定理背書的閘門。
  • 步驟 3：用 2509.21780 EIC 當「結構穩定度」的免 ground-truth 量測，補進證書——區分「看似穩定但數值病態」的假穩定。
  • 產物：一個可稽核、可撤照、有理論天花板的統一可靠度量，三方共用。

提案 3：程式碼助手下層＝「歸納合成 + 執行引導」的受約束生成

觸及：【核】§5 下層受約束生成 ＋【論】2411.02272 2411.07279 2411.17708（次要觸及【設】base 解題器）

【核】§5 下層要「把笨模型輸出收縮到窄面 + 行數助手精準標記」；【論】的 ARC 程式合成正好是「在窄約束下生可驗證程式」的成熟方法論，可直接搬。

  • 步驟 1：把【核】「行數助手 + 固定 snippet」升級為歸納⊕轉導集成（2411.02272）——笨模型先走歸納（生可執行片段，用單元測試/ast.parse 過濾），無解再走轉導兜底。這正對應 2411.02272 的「歸納為主可驗證、轉導兜底總有答案」。
  • 步驟 2：把【核】§6 ATP 的「插入後 ast.parse 過 + 簽名符合」當作 2601.05280 意義下的完美 verifier——這是 v0 驗收的接地錨，免崩。
  • 步驟 3：補上 2411.17708 GridCoder 自陳的 LTS 執行引導（中間執行狀態回饋進每步）——【論】已論證「搜尋只能補網格層 OOD，補不了程式結構 OOD，唯執行引導可」（proxy 10%→80%）。對「笨模型填洞填錯結構」這條【核】最怕的失敗，這是對症解。
  • 產物：【核】v0 的對照實驗（raw 笨模型 vs 鷹架）直接拿【論】的成熟組件當鷹架，少走彎路。

提案 4：資產 schema ＝ DreamCoder 元件庫的時間版（把【設】的詞彙表變成【核】的 ATP）

觸及：【核】§6 ATP asset ＋【設】#5 元件庫/詞彙表（次要觸及【論】2501.17848）

【核】roadmap §7/§8 把「生資產的 schema 長什麼樣」列為未決；【設】#5 的「元件庫 + 遷移介面＝詞彙表」正是這個 schema 的內容學定義；兩者拼起來缺口互補。

  • 步驟 1：把【核】ATP 的「資產」內容欄位，按【設】DreamCoder 兩半設計：components[]（可復用元件＝詞彙表）+ repair_heuristics[]（修復啟發法＝Q-table 的工程化）。
  • 步驟 2：對接時間維度——【設】的「貴搜尋發現元件」對應【核】「聰明模型一次性工廠」；【設】的「便宜復用」對應【核】「笨模型高頻消費」。【設】缺的工程外殼（CLI/register/沙箱）正是【核】的 ATP/SFC/subprocess 隔離。
  • 步驟 3：入庫時用 2501.17848 eggp 等式圖去重，避免元件庫塞語意等價重複（【設】#5 的「控粒度」問題的現成解）。
  • 產物：【核】拿到一份有內容學依據的 asset schema；【設】拿到一個能跑的元件庫宿主。

提案 5：開第二條驗證線——ARC 當【核】飛輪的共同裁判

觸及：【設】#8 ARC 裁判 ＋【核】§6 v0 鷹架 ＋【論】2411.02272 2508.14481 2509.21780

【核】v0 只有「程式碼編輯」一條線；【設】#8 已論證 ARC 是「最友善裁判」（少範例、結構 OOD、可執行驗證）。加一條 ARC 線，能在同一套鷹架上交叉驗證「飛輪是否真的在轉」，且裁判完全客觀。

  • 步驟 1：把【核】的「行數助手 + 受約束生成 + retry/guard」鷹架，套到 ARC 的歸納程式合成任務上（DSL 填洞而非檔案填洞）。
  • 步驟 2：用【論】成熟的回復率評測——2508.14481 FastSRB 的「可接受表達式清單（函數等價）+ early termination」當公平裁判，2509.21780 EIC 補結構穩定度。避免【核】自建評測的坑。
  • 步驟 3：用 2411.02272 的「歸納為主 + 轉導兜底」當對照組基線，量【核】鷹架相對的增益（呼應【核】§6「對照組失敗、實驗組成功」的驗收哲學）。
  • 產物：一條客觀、可被數據反駁的飛輪驗證線，且【設】的 ARC 押注與【核】的工程鷹架在此握手。

（備選提案 6）正交增強層搬進【核】的 Unix/八軸哲學

觸及：【核】SFC + 八軸 metadata ＋【論】SR_landscape §C（正交增強層）

【論】SR 領域近兩年最大轉向是「從比 solver 強，轉向可組合的正交增強層」——e-graph 去重 2511.05849、降維 2506.19537、物理先驗 2512.04204、EIC 評估 2509.21780 都不是獨立 solver，而是可掛到任一 solver 上的模組。這與【核】「只提供規範與標準實作、遵循 Unix 哲學、一堆小命令行函式 + 組合」是同構的設計哲學。把每個增強層做成一支帶八軸 metadata 的 CLI 函數，即可被 SFC 自由串接——【論】的可組合性直接落進【核】的 SFC。
