對讀者的價值

  • 對 ai_core §1「可優化計算圖」：EvoPrompt 把 prompt 明確當成計算圖節點上的可優化參數，但走的是與梯度法（ProTeGi 的文本梯度、TextGrad 的自然語言反傳）截然不同的路線——族群式、無梯度的黑箱搜尋。它不需要對單一節點做「哪裡錯了、怎麼改」的精細歸因，只需要一個可重複查詢的分數函數，這對「節點內部不透明、只能黑箱調用」的場景（閉源 API、無法回傳可解釋錯誤訊息）特別友善。
  • 對 ai_core §3.3「成本梯度」：本文附錄 C.3 明確給出成本公式——評估開銷＝ N（族群大小）× |D|（development set）× T（世代數），候選生成再加 N×T 次 LLM 呼叫。這意味著演化式 prompt 優化的離線煉製成本是族群大小與世代數的乘積，屬於一次性但不小的投資；與 ProTeGi／OPRO 等「每輪只需少量梯度式編輯」的方法相比，EvoPrompt 用更多平行探索換取跳出局部最優的能力，是 §3.3 決定「值不值得為這個節點做自動 prompt 優化」時的具體代價參照。
  • 對 ai_core §2「工廠/消費者」：EvoPrompt 是典型的離線資產工廠——用較貴的 LLM（GPT-3.5）跑演化過程，煉出一個固定 prompt 字串，之後部署時該 prompt 可反覆驅動更便宜的模型（Alpaca-7b），呼應「貴智能離線煉資產、便宜智能線上消費」的分工。
  • 對 ai_core §3.6「固化引擎」：演化終點交付的是一段人類可讀的自然語言 prompt（而非程式碼或結構化規則），比 Reflexion 那種「不跨任務保留的易失反思」更接近可固化的資產，但仍停在「prompt 字串」這個層級，沒有進一步結晶成確定性程式碼——固化的「深度」介於 Reflexion 的情節記憶與 DSPy/程式合成類把邏輯編譯成程式碼之間。
  • 與庫中已入庫方法對照（同屬主題 10：LLM-as-optimizer／自動 prompt 優化）：相對 OPRO（../summarize/2309.03409_OPRO.摘要.md，讓 LLM 讀「解＋分數」的完整優化軌跡、自行外推下一個解，無明確演化算子）、APE（../summarize/2211.01910_APE.摘要.md，「示範反推候選＋驗證集評分挑選」的一次性/迭代重採樣，無族群交配機制）、DSPy（../summarize/2310.03714_DSPy.摘要.md，以編譯/bootstrap 示範為主、非以 prompt 文字本身做演化）、MIPRO（../summarize/2406.11695_MIPRO.摘要.md，用貝氏代理模型做指令與示範的聯合優化）、TextGrad（../summarize/2406.07496_TextGrad.摘要.md，把自然語言批評當「文字梯度」逐節點反向傳播）——EvoPrompt 的差異化在於顯式借用 GA/DE 這兩套有理論保證探索-利用平衡的演化框架，並把交配/突變操作明確委派給 LLM 執行、同時維持族群（population）而非單一候選的迭代。另（此批次同時處理但尚未入庫）2305.03495 ProTeGi 走的是「錯誤案例→自然語言偽梯度→beam search」的路線，同屬扣掉梯度存取但強調利用（exploitation）而非族群式探索，可與 EvoPrompt 互補對照。
  • 與庫中 D 類演化計算/meta-evolution 論文的分野：本庫 D 類（如「不斷演化的強化學習演算法」「用大型語言模型演化發現強化學習演算法」等）多是傳統遺傳規劃（GP）——演化對象是程式碼/符號表達式，突變/交配是語法樹層級的機械操作，不要求輸出「連貫可讀」。EvoPrompt 的關鍵洞察恰恰相反：演化對象是自然語言，若沿用傳統 GP 對 token 獨立編輯的算子，會破壞語意連貫性；因此把演化算子的執行本身外包給 LLM（LLM 讀懂兩個父代 prompt 的意思、生成語意通順的子代），而非人工設計語法規則——這是「LLM 當演化算子」與「LLM 被演化」（D 類多數論文是後者，即演化出的是控制 LLM/RL 的程式或超參數）的本質區別。
