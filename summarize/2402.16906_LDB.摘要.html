作者：Li Zhong, Zilong Wang, Jingbo Shang（University of California, San Diego）

日期：2024-02

arXiv：2402.16906

論文／訪談原始來源

《LDB：透過逐步驗證執行期狀態的大型語言模型除錯器（LDB: A Large Language Model Debugger via Verifying Runtime Execution Step-by-step）》重點摘要

一句話概括

LDB（Large Language Model Debugger）：模仿人類設中斷點除錯的做法，把 LLM 生成的程式依控制流程圖切成 basic block（基本區塊），逐塊追蹤執行期中間變數值、讓 LLM 一塊一塊地把「實際執行狀態 vs 任務描述」比對出 True/False 判決並定位錯誤，再據此重生程式——用細粒度、以真實 runtime 資訊為錨的驗證取代「把程式當不可分割整體、只看最終 pass/fail」的既有除錯法。

解決什麼問題

既有 LLM 程式修復法（Self-Debug、Reflexion 等）把生成程式視為不可分割的整體，僅靠「執行後的輸出／錯誤訊息」或「讓 LLM 自己乾跑、逐行解釋」來反思。問題有二：(1) 面對複雜控制流與資料操作時，這種整體式 pass/fail 回饋無法精準定位 bug；(2) LLM 自我修正能力有限（Huang et al. 2023c），它無法準確心算變數值、也無法正確預測分支/迴圈的執行流，自我乾跑的回饋常常出錯、反而誤導修復。人類開發者其實會設中斷點、觀察執行軌跡與中間變數——這些 runtime 資訊在既有文獻中被嚴重低估。

核心方法（三步驟迭代迴圈）

  • Profiling（剖析，§2.2）：對失敗的可見測資執行 seed 程式，取得執行軌跡；依 CFG 把軌跡切成 basic block（單一入口單一出口的直線程式段），並在每個 block 結束處收集當下所有變數的實際 runtime 值（等同人類的中斷點）。中間狀態記為 (V_{i-1}, B_i, V_i)：進入狀態、當前區塊、執行後狀態。
  • Debugging（除錯，§2.3）：把逐塊的中間狀態灌進 prompt，讓 LLM 對每個 block 逐一判決 correct True/False 並給出解釋、定位出錯區塊。兩項工程設計：Selective Debugging（迴圈/遞迴軌跡過長時只抽樣 N_b 個 block，避免超出 token 上限，仿人類跳過冗長軌跡）與 Batch Debugging（把所有 block 狀態打包成一次查詢，token 複雜度由 O(B²·N) 降為 O(B·N)）。
  • Regeneration（重生，§2.4）：把判決 D 與解釋 E 連同任務描述回饋給 LLM 重寫程式；三步迭代直到通過所有可見測資或達到上限（最多 10 輪）。

結果（具體數字）

  • 主結果（表 1）：在 HumanEval / TransCoder / MBPP 三個基準、三種 backbone（GPT-3.5、CodeLlama-34B、StarCoder-15B）上一致優於 Self-Debug，最高增益 +9.8%（CodeLlama 在 TransCoder 69.8→79.6）。GPT-3.5 上 HumanEval 73.8→82.9（+9.1）、MBPP 67.6→76.0（+8.4）。StarCoder 上 Self-Debug 甚至退步（HumanEval −0.6），LDB 仍正向。
  • 對強生成器仍有效（表 2）：以較弱的 GPT-3.5 當除錯 backbone，去修 GPT-4 / Reflexion 生成的 seed，仍能糾出被忽略的細微 bug——把 Reflexion 的 91.5% 推到 95.1%（SOTA）；換 GPT-4o 當 backbone 更達 98.2%（附錄 A）。
  • 切塊粒度：block-level 在準確率與 token 成本上雙贏 line-level 與 function-level（line 語意不完整、function 太粗需 ~8.1 輪）。
  • 持續改善：LDB 隨迭代持續上升（20 輪達 84.1%），而 Self-Debug/Repeated Sampling 約 2~3 輪即停滯。
  • 除錯品質（附錄 H）：bug 定位準確率各資料集 >85%（MBPP 95.3%、HumanEval 93.7%、TransCoder 86.7%）；約 80% 修的是語意錯誤。剖析開銷僅 0.09 秒，可忽略。

局限

  • 強制需要正確測資：LDB 必須執行程式並把執行流與任務描述比對，因此可見測資是必要條件。「無測資除錯（test-case-free debugging）」——即 LLM 只看中間執行、卻不知結果對錯就能自我修正——仍是未解的開放問題。
  • 沿用人類除錯法的固有限制；實驗以 Python 為主（宣稱不依賴 Python 專屬特性、可換 executor/分析工具移植，但多語系實驗留待未來）。

對讀者的價值

  • 對 ai_core §3.4「細粒度驗證器」的直接範本：LDB 把「整體 pass/fail」拆成 block 級的逐點 True/False 判決＋定位，正對應 ai_core 主張的細粒度驗證勝過粗粒度整體驗證。更關鍵的是它把驗證錨定在確定性程式分析產出的真實 runtime 值（CFG 切塊、實際變數值由 interpreter 給出），LLM 只負責「比對語意」這個判斷步驟——這正是「多數確定性節點＋少數 LLM 節點」符號神經網路計算圖的縮影：程式分析是可靠函數、LLM 只在最需要語言理解處介入。
  • 對 §5「程式碼助手」修復迴圈的啟發：LDB 是一個現成的「上層抽取（把執行狀態結構化成 block 狀態）→ 下層受約束修碼」的迭代管線；其 Selective/Batch Debugging 是把驗證器做成可靠、token 高效函數的工程細節，值得直接借用。
  • 對照已入庫的 Self-Debug：兩者同屬修復迴圈，但 Self-Debug 靠 LLM 自我乾跑（LLM 心算執行流，易錯、2~3 輪即停滯），LDB 靠確定性執行取得的 ground-truth runtime 值（持續改善、定位更準）。這正印證 ai_core「逐步剃除對 LLM 依賴」的路線：把「算變數值/預測執行流」這種 LLM 不擅長的工作交還給確定性程式碼，LLM 只做它擅長的語意對齊判斷。歸 I 類。
