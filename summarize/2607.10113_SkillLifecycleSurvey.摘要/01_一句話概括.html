一句話概括

Yubo Li（CMU）的 TMLR 綜述：掃描 124 篇 2023–2026 論文後，把動態技能庫定義為 lifecycle-managed、verified、evolving artifact stores。核心貢獻是三件工具：(1) 六感分類學區分論文裡「skill」的六種結構性歧義（可執行程式碼／NL 啟發式／SKILL.md 套件／參數化 adapter／記憶軌跡／能力標籤）；(2) 八階段生命週期架構：證據取得→提案→驗證/准入→組織/儲存→檢索/組合→維護/修復→蒸餾/可移植性→治理/溯源，把 124 篇論文可比地放進同一個架構；(3) 十算子詞彙 {Add, Refine, Merge, Split, Prune, Distill, Abstract, Compose, Rewrite, Rerank} 作為跨系統比較的通用語言。最重要的實證結論（經消融或收斂性 benchmark 證據支撐）：准入閘門（admission gates）重複被證明重要、驗證器品質在 skill-aware RL 中往往是決定性的工程選擇、平面檢索在~百級技能庫規模會退化、中等以上庫規模時維護（Prune/Merge/Repair）變成剛需。對 ai_core 而言，這篇就是 §3.6 固化引擎目前最缺的那份"退役/收斂"機制的地圖——它把技能生命週期形式化為可編輯記錄 ⟨C, π, T, R, φ, ν, ≺⟩ 與庫級狀態轉移 Lt→Lt+1，直接給出標準算子語義與驗證架構選型。

解決什麼問題

LLM agent 的「可重用技能」已成為活躍研究方向（Voyager/LATM 的程式碼技能、OpenClaw/SkillClaw 的 SKILL.md、SkillFlow 的社群 registry），但領域內存在三個根本混亂：

  1. "skill"一詞過載：不同論文用 skill 指六種結構上完全不同的東西（程式碼 vs NL 教訓 vs SKILL.md 套件 vs LoRA adapter vs 記憶案例 vs 能力標籤），無法跨論文比較。
  2. 技能庫被當成靜態物件：多數系統把技能庫當作"授權一次、偶爾版更、與軌跡弱連結"的提示片段集合——但實際部署中，任務、工具、base model、安全約束都在漂移，靜態庫會過時。
  3. 缺乏共享詞彙與 benchmark 協定：更新操作命名不一致（同一件事在不同論文叫 refine/repair/merge/consolidate），benchmark 多只報終端效能、不報庫軌跡、不報使用率與效益的落差。

這份 survey 的貢獻不是另一套方法，而是給一個共同的語言與架構讓後續可比。

核心貢獻

1. 六感分類學（Six-Sense Taxonomy，Table 1）

依 artifact 是否 executable/edit/portable/inspectable/有 verification handle，把 skill 分成六類：

  • 可執行程式碼：Voyager, LATM, SAGE, ASI, SkillOps（有單元測試/合約驗證）
  • NL 啟發式：ERL, RetroAgent, EvolveR（只能間接驗證）
  • SKILL.md 套件：MetaClaw, Memento, Trace2Skill, AutoRefine, SkillGrad（L1 路由/L2 指令/L3 程式碼的漸進揭露）
  • 參數化 adapter：SkillsCrafter, SKILL0, SELAUR（權重差、僅行爲探針驗證）
  • 記憶/軌跡：SimpleMem, MUSE, CASCADE（邊界案例，介面不完整）
  • 能力標籤：Co-Evolving, GEA（無強健編輯體）

2. 可編輯技能記錄與庫級轉移（§3）

把 SoK-Skills 四元組 ⟨C, π, T, R⟩（適用/策略/終止/介面）擴充成七元組：

St = ⟨Ct, πt, Tt, Rt, φt, νt, ≺t⟩

新增 φ（編輯欄位——proposal kernel 產生候選版本）、ν（驗證欄位——admission predicate）、≺（譜系關係——版本取代鏈）。庫級轉移：

Lt+1 = T(Lt, τt, rt) = Apply(⃗ut(τt, rt), Lt)

其中 ⃗ut 取自十算子詞彙。靜態庫是 ⃗ut ≡ ∅ 的特例。

3. 八階段生命週期架構（§5）

階段 設計問題 代表算子 典型失敗
證據取得 什麼觀察能證成庫變更？ — 雜訊證據、非平穩效益
提案 證據如何轉為 artifact？ Add, Abstract 任務特化或過度泛化
驗證/准入 什麼閘門決定候選進庫？ Refine, Rewrite 看似合理但錯的技能、verifier hacking
組織/儲存 准入後 artifact 放在哪？ Split, Merge, Rerank 平面檢索崩潰、結構過時
檢索/組合 哪些技能影響下次行動？ Rerank, Compose 使用≠效益、distractor 負載
維護/修復 如何保持庫緊湊正確？ Prune, Merge, Refine, Rewrite 無界增長、負遷移
蒸餾/可移植 什麼在外在內之間移動？ Distill, Abstract 參數崩潰、相容性失效
治理/溯源 編輯可被審計/歸因/回滾？ Add–Prune 序列 技能注入、洩漏、歸因丟失

4. 七個實證模式（§9，經證據分級）

  1. 准入閘門重要（A/B 級）：curated skills 勝過 unverified self-generated skills，跨十餘方法收斂。
  2. 驗證器品質在 skill-aware RL 中決定性（B 級）：CoEvoSkills surrogate verifier 移除掉 30 分，CODE-SHARP 從 24.3%→41.0% 靠 learned gate。
  3. 平面檢索在~百級規模退化（B/C 級）：Single-Agent-Skills 的受控曲線：16→97%, 64→92%, 128→78%, 256→64%。
  4. 弱 backbone 相對增益大（C 級）：跨系統收斂但非受控效應量。
  5. 聚焦庫常勝全面庫（B/C 級）：distractor load 機制。
  6. 中等以上規模時維護變成剛需（B 級）：AutoRefine 關掉維護→35.6%→31.1%、4.5x 庫膨脹、利用率 0.71→0.08。
  7. 寫入時抽象通常強於讀取時抽象（B/C 級）：Trace2Skill/CASCADE/SimpleMem 的 write-time compression 一致勝 read-time summarizer。

5. 八個安全表面（§11）

技能注入（ClawSafety 平均 69.4% ASR）、供應鏈投毒（26.1% 技能含漏洞模式）、有害但有效的技能、憑證洩漏（76.3% 需 NL+code 聯合分析）、掃描器偽陽性與上下文敏感性、技能竊取、領域發布準備度、歸因與組合誤用。

《Dynamic Agent Skills：技能庫的生命週期綜述與分類學》重點摘要（續 局限與價值）

局限（論文 Limitations 章）

  • 語料凍結於 2026-05-31，後續作品可能改變個別模式證據。
  • 搜尋協定為迭代搜尋+滾雪球非 PRISMA 式，假陰性可能（尤其不使用"skill"一詞的工具/記憶/工作流論文）。
  • 證據異質：方法論文、benchmark、基礎設施、安全論文的證據效力不同，lifecycle framework 用來對齊證據角色而非排名。
  • 算子詞彙刻意粗糙，不定義封閉性/結合律或編輯組合律；不是 agent 開發環境的完整操作語意。
  • 多數結論是架構性而非因果性，不提供跨論文排行榜。

對讀者的價值

  • 本批 I 類"系統架構／智能體"的地圖級作品——不是發明新方法，而是給整個技能庫領域一個共同語言。對 ai_core 而言，這篇直接對應 §3.6 固化引擎最核心的缺口：技能庫的退役與收斂機制。論文的形式化工具（七元組記錄、十算子詞彙、八階段生命週期）可以直接作為設計"技能庫生命周期管理器"的規格書。
  • 最值得記的三個實證結論：(1) 准入閘門重要——curated > unverified self-generated；(2) 平面檢索在~百級規模退化——庫越大不等於越好；(3) 維護是剛需——只 Add 不 Prune/Merge 的庫會自我毀滅。這三個結論共同指向：ai_core 的固化引擎不能是純 append-only 的，必須有 retirement/convergence 機制。
  • 對正在設計 agent 技能系統的人，這篇的 Table 1（六種 skill 語義）、Table 2（生命週期設計問題）、Table 4（驗證架構）、Table 3（分類學家族）、Table 7（七個實證模式）和 Table 10（八個開放問題）可以直接當設計決策檢查表。
