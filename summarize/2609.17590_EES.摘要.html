論文／訪談原始來源

Evolutionary Ensemble Search: Council-Guided Program Evolution with Persistent Memory 重點摘要

一句話

Evolutionary Ensemble Search 讓分工明確的 council 提出搜尋方向，由 orchestrator 派發實驗，再以有實測紀錄的 parent 產生、執行並篩選 child program；operator credit、session memory 與跨任務持久記憶則把經驗帶到後續搜尋，但本文的 MLE-bench Lite 數字是可見評分下的開發紀錄，不是盲測 agent 成功率。

方法架構

  • 搜尋物件與測量契約：candidate 不只是模型超參數，而是一套涵蓋資料、特徵、模型結構、訓練、推論、後處理或 ensemble 的可執行程序。可修改規格與比較協定分開保存；不同程序只有在共用評估列、目標語意與 metric 計算時，分數才可比較。
  • Council 與 orchestrator：Discovery Driver、Methodology Advisor、Memory Keeper 持續在場，ML Strategist 與 Code Reviewer 輪替。它們輸出互補欄位而非投票決定答案；orchestrator 把建議轉成有預算界線的 profiling、研究、實作、訓練與綜合工作。
  • 有證據的演化：mutation 從已評估 parent 的 residual、泛化落差、fold 變異與預測相關性出發，修改設定、pipeline 或程式碼；crossover 與 fresh draft 另行記錄。child 不繼承 parent fitness，必須重新執行並留下 parentage、實際 diff、protocol、runtime、failure 與 artifact identity。
  • 選擇、archive 與記憶：有效 child 可因品質、多樣性或複雜度取捨進入 population 或 archive。parent-relative operator credit 改變後續 mutation 分布，session memory 保存本輪發現與失敗路線，problem-indexed library 則跨 run 檢索 lesson 與 warm start；取回的程序仍須在新任務重新測量。
  • 預測層重組：只有 row identity、target order、class semantics 與 validation provenance 相容的預測才能進 ensemble。ensemble 必須在共同 validation 基礎上明確勝過最佳單一程序，否則保留 incumbent；反覆選成員與權重仍可能過度適配內部 validation。

作者報告的結果

公開 MLE-bench Lite 開發 ledger 在 22 個任務中記錄到 19 個達 medal threshold 的 artifact，占 86.36%；最佳紀錄包含 11 gold、5 silver、3 bronze（作者自報）。三欄 confirmation 都在相同 19 個任務保有 medal，但等級會變；57 筆帶 medal 的 confirmation record 對應 46 個不同的 task 與 submission hash 配對，表示 confirmation 並非一致且互相獨立的完整重跑（作者自報）。

這些數字必須按作者設定的證據邊界解讀。任務 grade 在開發 iteration 之間可見，會影響後續工程；ledger 也沒有統一預算、所有失敗 candidate、完整計算成本或每個 artifact 啟用了哪些 council 與 memory 元件。因此 19/22 是達成過的開發成果（作者自報），不是 frozen agent 的 pass@1。此外有四條結果路線明確使用外部來源或歷史查找，未標旗號的其餘任務也不因此自動取得乾淨資料認證。

局限

作者自陳，現有案例沒有證明完整 council、nested evolution 與 memory stack 共同產生每個 artifact，也沒有估計各元件邊際貢獻、統一成本優勢或對未接觸任務的盲測泛化。有限 validation 上的反覆選擇可能利用雜訊，parent-relative reward 只是操作性的 credit，不是因果歸因；retrieved memory 也可能帶入任務特定 artifact 或來源權限錯誤。最後，公開 repo 提供 ledger、solution note、部分 artifact 與重現說明，但 EES engine 是專有軟體，不能完整重跑搜尋過程。

對 ai_core 的價值／接點

EES 對 ai_core 最有用的是把「提案、執行、比較、保存」拆成不同權限：LLM council 可以決定值得試什麼，卻不能直接替 child 宣告 fitness；每個後代都要在可比的 measurement contract 下產生自己的證據。這能避免把 inherited code、漂亮解釋或舊任務高分誤當成新環境的有效憑證。三種記憶尺度也值得借用，但每筆跨任務 lesson 應附 task fingerprint、資料來源、protocol 與適用範圍，檢索只能形成 prior，不能豁免重新驗證。本文對開發 ledger 的自我限縮尤其重要：達成過的最佳結果、可重現 artifact 與真正的盲測泛化，是三種不同強度的證據。
