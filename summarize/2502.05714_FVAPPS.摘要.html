作者：Quinn Dougherty、Ronak Mehta

日期：2025-02

arXiv：2502.05714

論文／訪談原始來源

《Proving the Coding Interview：一個形式驗證程式碼生成的基準》重點摘要

一句話概括

FVAPPS（Formally Verified Automated Programming Progress Standards）：將 APPS 競賽程式基準從 Python 單元測試升級為 Lean 4 形式規格與數學證明——模型不僅要實作函數，還須完成形式正確性定理證明（以 sorry 填補 Lean 證明空缺），是目前最大的形式驗證程式碼生成基準（4,715 題）。

解決什麼問題

傳統程式碼生成基準（HumanEval、MBPP、APPS）仰賴單元測試判斷正確性，但單元測試不完整、易產生誤報、無法保證邊界案例無誤。FVAPPS 將信任從「黑箱 LLM 輸出通過幾個測試案例」轉移到「確定性 Lean 4 核心型別檢查器」，要求模型生成的程式碼搭配機器可檢的形式證明，使正確性不再取決於測試案例的取樣代表性。

核心方法

  • 五階段管線（§3）：
    1. Stage 1：從 APPS Python 問題預處理與聚合
    2. Stage 2：以 Pytest/Hypothesis 生成屬性式測試
    3. Stage 3：翻譯為 Lean 4（函數定義 + 未證明的 sorry 定理），產出 4,715 個「Unguarded」樣本
    4. Stage 4：加上 #guard 內聯單元斷言，確保函數可解，產出 2,089 個「Guarded」樣本
    5. Stage 5：以 Lean 的 Plausible 框架進行屬性測試，產出 1,083 個「Guarded and Plausible」最高品質樣本
  • 任務格式：每個任務給出英文問題敘述 + Lean 4 檔案，包含函數簽名與形式規格定理（以 sorry 佔位）。正確提交需同時包含實作程式碼與證明策略，並在 Lean 核心中編譯通過、無 sorry。
  • 評測協定：以 lake build 編譯回饋進行最多 50 輪迭代的 agentic scaffold loop。

結果

  • 基準線實驗（100 題隨機抽樣，406 條定理）：
    • Claude 3.5 Sonnet：定義完成 93/100 題，43/100 題至少一條證明，總定理證明率 30.0%（121/406）
    • Gemini 1.5 Pro：定義完成 71/100 題，23/100 題至少一條證明，總定理證明率 18.5%（74/406）
    • 零樣本/單樣本可解的證明僅佔 ~20%，多數證明需要 agentic scaffold 迭代。
  • 人類基準對比：專家耗時 10 小時處理單一題目（sample 0023 Crooked Election），成功寫出函數定義（含複雜終止證明 termination_by/decreasing_by omega），但未能證明任何定理——因遞迴展開導致堆疊溢位。
  • 關鍵發現：
    1. 命令式 vs 歸納式證明瓶頸：LLM 頻繁使用 Id.run do 命令式區塊實作，編譯容易但形式推理極難，導致證明策略臃腫與分歧。未來模型需學習以函數式風格編碼以保留歸納證明的人體工學。
    2. 編譯器回饋不可或缺：無 agentic feedback loop 的開源模型無法完成單次證明。
    3. 形式驗證重新定義信任：信任從 LLM 執行移至確定性核心型別檢查器。

對讀者的價值

  • ai_core §3.4 憑證准入的最高形式：FVAPPS 展示了「程式碼正確性憑證」的終極實例——不是測試通過率、不是人類審查，而是Lean 4 核心型別檢查器的機械驗證。這直接對應 ai_core §3.4「憑證必須是可獨立驗證的」原則，Lean kernel 就是一個不可欺騙的驗證器。
  • ai_core §5 下層受約束填碼的直接實例：FVAPPS 的任務格式——給定型別簽名與形式規格，要求填入實作與證明——正是 §5「受約束生成」的落地：型別簽名與定理陳述構成可機械檢查的規格合約，LLM 在此合約邊界內生成程式碼，不合約者直接編譯失敗。
  • 命令式 vs 函數式瓶頸對應固化引擎設計：論文的關鍵發現（命令式程式碼雖編譯容易但無法形式推理）直接對應 ai_core §3.6 固化引擎的設計取捨——固化後的確定性程式碼必須是可推理的（可被靜態分析、可被形式驗證），否則固化只是把 LLM 的不確定性換成另一種不確定性。
  • 與 2604.16584 LeetProof（agentic Lean 驗證器聯合合成）並讀為「形式驗證程式碼生成」的互補路線（FVAPPS 提供基準、LeetProof 提供方法）；與 2605.10712 AutoSOUP（記憶體安全單元證明生成）對照（AutoSOUP 以 C/嵌入式為域、FVAPPS 以 Lean/函數式為域，兩者共築形式驗證生成的全景）。
