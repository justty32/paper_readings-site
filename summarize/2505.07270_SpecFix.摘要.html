論文／訪談原始來源

《SpecFix：為 LLM 程式碼生成的歧義問題描述進行自動修復》重點摘要

一句話概括

首個自動修復歧義 NL 問題描述的方法：SpecFix 把任務拆成兩步——先用傳統測試與程式修補修正 LLM 的程式分佈（降低語意熵＋提高 I/O 範例一致性），再用**對比規格推斷（contrastive specification inference）**將分佈變化映射回最小文本修補；全自動、零人類介入，四款 LLM × 三個基準上修改 43.58% 描述、修改集 Pass@1 +30.9%、全量絕對 +4.09%，且修補對其他模型也有效（+10.48%）。

解決什麼問題

  • NL 問題描述的細微歧義可導致 LLM 產生錯誤程式碼（即便附有釐清用的 I/O 範例），過往研究觀察到歧義使效能下降 20%。
  • 直接讓 LLM 修復歧義（Vanilla Repair / ClarifyGPT-auto）會產生無關或矛盾編輯——LLM 難以反思「文字變動如何影響自身將產出的程式」。
  • 既有推理增強方法（µFix）在歧義存在時也失誤：無法正確「逆向工程」範例以推斷被省略的參數語意。

核心方法

  • 程式分佈作為 LLM 詮釋的代理：取樣 N 個程式、依輸入輸出行為分群成語意簇（semantic clusters），以語意熵（SE）量化詮釋不確定性，以範例一致性（EC，程式通過嵌入 I/O 範例的比例）度量與意圖的對齊。
  • 兩種修補策略：
    1. 機率引導修補：若存在 EC=1 的簇，選機率最大者當 P_select，其餘為 P_reject，用對比推斷增強調優選詮釋的機率。
    2. 程式修補式修補：若無任何簇通過所有範例（EC 皆 <1），對最大簇的代表程式用 self-refine 以 I/O 範例修復，產生 P_select，原程式為 P_reject。
  • 對比規格推斷：將選定 vs 拒絕的程式行為同時餵給 LLM，要求診斷歧義來源並產生最小文字修訂，使只有預期行為可接受。
  • 自我迭代最多 K 輪，每輪取樣→分群→修補→推斷→評估（SE↓ 且 EC↑ 才接受）。

結果

  • HumanEval+ / MBPP+ / LiveCodeBench × DeepSeek / Qwen2.5 / GPT-4o / GPT-4o-mini：SpecFix 在所有 12 組模型×基準組合中 Pass@1 最高。
  • 平均 43.58% 描述被修改，修改集 Pass@1 +30.9%；全量 Pass@1 絕對提升 4.09%；語意熵顯著降低。
  • 跨模型泛化：對一個模型產生的修補使其他模型效能平均提升 10.48%。
  • 修補長度僅微幅增長（SpecFix 的 diff 最小），遠少於 ClarifyGPT-auto 的冗長附加。
  • SpecFix 是唯一在 Majority@20 上持續改善的方法（多數投票一致性提升）。

與 µFix 的對比

  • µFix 以推理鏈分析範例，但在歧義存在時會錯誤歸因誤差（如「高度」是垂直高還是斜高，µFix 推成「四捨五入誤差」），而 SpecFix 因先修補程式分佈再推斷規格，正確分辨出參數語意。

局限

  • 依賴非零溫度取樣的多樣性——若 LLM 在歧義處碰巧只產生單一（錯誤）詮釋，SpecFix 無法觸發修補。
  • 極端語意變異仍可能失敗；人類回饋保留為最後手段。
  • 僅處理功能性行為規格，未涵蓋非功能性需求（效能、風格）。

對 ai_core 的價值

  • §5 上層結構化抽取＋§3.4 constraint-spec alignment auto-completion：SpecFix 示範了「程式分佈→規格推斷→文本修補」的自動閉環——等於把意圖對齊量化成 SE/EC 可優化指標，對 §3.4 的「憑證准入」與 §5 的「從執行反推規格」提供了實作原型。
  • SpecFix 的對比推斷原理與 §3.4 的「好/壞案例對比形成閘門」同構：P_select 是「該放行的詮釋」、P_reject 是「該攔下的詮釋」，規格修補是把兩者的區別「寫回介面語言」。
  • 辨識到「讓 LLM 反思自身 NL 詮釋變化」的固有難度——這正是 ai_core §3.6「固化」的切入點：與其讓 LLM 在每次生成時重新解讀歧義，不如修補規格使其確定化。
