論文／訪談原始來源

《EcoAssistant：更便宜且更準確地使用 LLM 助手》重點摘要

一句話概括

EcoAssistant：為「程式碼驅動問答（code-driven question answering）」設計的純線上系統，把 LLM 助手與程式碼執行器（code executor）配成雙代理對話迭代改碼，再疊上兩招——assistant hierarchy（助手層級，便宜模型先試、失敗才 back-off 到貴模型） 降成本、solution demonstration（成功解示範，把過去成功的 query-code 對存進向量庫、新查詢時檢索最相似者當 in-context 示範） 提準確率；兩招共享同一 query-code 資料庫而產生綜效（貴模型 GPT-4 產出的解會回頭指導便宜的 GPT-3.5，使便宜模型解得更多、進一步降低對貴模型的依賴），最終以不到 GPT-4 一半的成本、把成功率超出 GPT-4 約 10 個百分點。

解決什麼問題

使用者常問需要外部知識的查詢（天氣、股價、地點），LLM 得產生程式碼呼叫外部 API 才能回答（作者稱之為 code-driven question answering）。兩大痛點：(1) LLM 很少一次寫對程式碼，需依執行結果迭代除錯；(2) 大量查詢用付費 LLM 服務非常昂貴（ChatGPT 2023 年 7 月約 80M 查詢，其中 23% ≈ 4M 為知識查詢）。既有做法多用單次生成、或只針對單輪文字生成降本（FrugalGPT），未針對「多代理對話 + 程式碼迭代」場景兼顧成本與表現。

核心方法（三組件，建於 AutoGen 之上，無需離線訓練/資料整理）

  • 自動化雙代理對話：LLM 當 AssistantAgent 提出程式碼，UserProxyAgent 當 code executor 自動抽取並執行、把輸出或失敗 trace 回傳給 LLM 迭代改碼；助手在回應末尾附 TERMINATE 或達上限（本文每段對話最多 5 輪、超出 context window）即結束，全程無需使用者手動複製貼上。
  • Assistant hierarchy（助手層級 / back-off）：對每個查詢先用最具成本效益的 LLM 開始對話，該助手失敗才重啟並改用下一個更貴的 LLM。因 LLM 定價異質（GPT-3.5-turbo 比 GPT-4 便宜一個數量級），可大幅減少貴模型使用量。實驗用 AssistantHier-G（GPT-3.5-turbo + GPT-4）與 AssistantHier-L（LLAMA-2-13B-chat + GPT-3.5-turbo + GPT-4）。
  • Solution demonstration（成功解示範 / 固化雛形）：查詢經回饋判定成功後，把 query 與最終程式碼存進向量庫（Chroma，multi-qa-mpnet 嵌入 + cosine 相似度）；新查詢進來時檢索最相似的 query-code 對，附進初始 prompt 當示範，讓助手更少迭代就寫出正確高效的程式碼。
  • 綜效關鍵：層級中的所有助手共用同一 query-code 庫，故強模型的解會成為弱模型後續查詢的隱式指導——不需額外設計。

結果（GPT-4 當評審 + 人工評估）

  • 個別資料集（Places/Weather/Stock，各 100 題，取自 ToolBench）：solution demonstration 幾乎讓 vanilla GPT-3.5-turbo 成功率翻倍（Stock 更 3 倍）；assistant hierarchy 相較 vanilla GPT-4 省成本約 10%–50%。
  • EcoAssistant（AssistantHier-G/L + SolDemo）在所有資料集達最高成功率，較最佳 GPT-4 變體高約 10 個百分點，且較單用層級再省約 30%–50% 成本。
  • 人工評估 Mixed-100：EcoAssistant 成功率 80% / 成本 5.90，vs GPT-4 59% / 13.77——成功率高 10+ 點、成本不到一半；且 GPT-4 的 avg model calls 從 2.51 降到 1.25（對貴模型依賴減半）。
  • 對混合資料集三種不同查詢順序穩健（大致 order-agnostic）；無人回饋的自主版（改用 GPT-4 evaluator）仍勝 GPT-4 10+ 點、省本 >50%，但成功率較有人回饋版低約 8 點，且執行時間大幅縮短。

局限

  • 依賴預先定義的靜態層級，未必對所有查詢最優，缺乏自適應選擇；query-code 庫在百萬級查詢時可能成瓶頸（需剪枝機制）。
  • 對高度專精/冷門查詢較弱；多輪迭代對話帶來延遲；長對話 context 受 token 上限限制。
  • 成功與否的判定倚賴使用者/GPT-4 回饋（自主版的 GPT-4 evaluator recall 100% 但 precision 僅 66%–84%，偶爾誤判而不升級到 GPT-4）。

對讀者的價值

  • 歸 I 類，短名 EcoAssistant。對 ai_core 有兩個直接接點：
    1. §3.3 成本梯度／級聯路由：assistant hierarchy 是「便宜高頻智能先試、失敗才升級到貴稀有智能」的乾淨實作——與 2305.05176 FrugalGPT 的 cascade 互補，差別在此處以多輪對話 + 程式碼執行的自動成敗訊號當 back-off 判據（成功/失敗由 code executor 與回饋界定），而非另訓一個評分函式；正對應「拒絕為預設、憑成敗准入」的成本梯度直覺。
    2. §3.6 固化引擎（雛形）：solution demonstration 把 LLM 反覆處理的案例沉澱成可複用的成功示範（query-code 對入庫、檢索複用），是「固化」最輕量的一步——尚未結晶成確定性程式碼/抽象庫，但已展示「成功解沉澱→降低未來 LLM 依賴」的雛形。最值得 ai_core 借鏡的是那個綜效：貴模型固化出的解讓便宜模型解得更多，等同讓「資產工廠」產出的資產（成功程式碼）被「資產消費者」複用，系統整體對貴智能的邊際依賴隨使用遞減——正是「逐步剃除對 LLM 依賴」的具體機制。
  • 定位：系統/實證論文（建於 AutoGen，開源 github.com/JieyuZ2/EcoAssistant），純線上、無需訓練，適合做成本感知代理、級聯/back-off 路由、檢索式成功解複用、程式碼助手的人。
