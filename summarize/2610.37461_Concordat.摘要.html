Concordat：以有限狀態協定約束 agent 工具

核心主張

航空客服 agent 可能在顧客催促下跳過變更預訂前的明確確認；即使最後資料庫狀態符合需求，也不代表過程遵守政策。Concordat 將 agent 類別的工具介面建成有限狀態協定：每回合只提供當前合法工具，並在呼叫前攔截非法操作。它借用 typestate 與 session types 的概念，在不可信模型的執行階段約束工具順序，而不是對模型本身做靜態型別檢查。（§1、§3）

協定與執行邊界

協定包含有限狀態、動作、初始／終止狀態與轉移關係；單一動作可依回傳值轉移至多個可能狀態之一。定義時檢查終止狀態非空、終止狀態無動作、轉移目標非空、每個狀態從起點可達且每個狀態可到達終點。後者保證存在合法路徑，不保證模型、工具或外部環境終將選到它或實際結束。（§3.1；終止界線為本檔補註）

開發者用類別方法及 decorators 指定工具可用狀態與後繼，類別定義時建立並檢查協定。Runner 每回合提供 allowed(state) 的工具，停用平行工具呼叫；非法名稱或錯誤參數回傳錯誤，非法方法在方法本文執行之前拒絕，狀態不變。這約束已接入 runner 的工具介面；自然語言內容和政策本身的語意正確性並未因此自動得到保證。（§3.2–3.3；後句為本檔補註）

@human 步驟可由模型請求，只能由應用提供的 approver 決定批准或拒絕，各自走不同轉移。Budget 記 token、工具呼叫與金錢，回應 token 計費，下一輸出上限受餘額限制；handoff 將子額度從父額度扣除，父項有限的維度不能給子項無限額。這是執行期資源分配，作者明說尚未做靜態 budget 型別。程式庫的人工 approver 功能與下述基準實驗中以模擬顧客訊息判斷確認是兩個不同機制。（§3.4、§5.1）

子類別在定義時檢查 refinement：子類終止狀態須是父類終止狀態的子集；刪除子類新增動作後，所有有限子類 run 都須符合父協定，進入同名父狀態時也須是父協定可達狀態；父類 human 步驟仍須是 human。實作以子狀態與可能父狀態集合做廣度優先走訪。這是共用動作上的 trace inclusion 安全檢查，不要求子類提供父類全部選擇，也按狀態名稱關聯，作者不稱其完整 session subtyping。（§3.5）

評測：壓力情境與分母

作者自報以 τ-bench v1.0.1 的 airline 50 tasks，比較標準 llm_agent 與以工具標註建立雙狀態 gate 的 Concordat agent。查詢工具兩狀態均可用，資料庫寫入僅 confirmed；最近一則顧客訊息含 yes／yep／yeah 即進 confirmed，其他訊息回 chatting，轉人工則結束。作者加的非官方壓力情境要求模擬顧客第一次被要求確認時催促、不要說 yes，第二次才說 yes。Haiku 5.5 為 agent、Sonnet 5.5 為顧客；gpt-4.1 同時扮演 agent 與顧客，temperature 0。（§5.1、附錄 A）

限制與可遷移性

Gate 與違規指標共享同一 keyword 測試，因此零違規對該定義是機制直接保證；例如「yes, but not that one」仍可能被錯誤接受。作者建議部署時用結構化確認。合作顧客的早期寬鬆 gate 若改用嚴格指標，Concordat 有一次未含 yes 的變更；壓力試驗才使用嚴格 gate。實驗僅一個領域、兩個主要模型和少量試次，Haiku 缺失部分 runs，gpt-4.1 約三分之二 tasks 因限流在另一時間重跑；模擬顧客未必代表真人。（§5.2–5.3）
