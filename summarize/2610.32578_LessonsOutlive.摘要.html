論文／訪談原始來源

Harness 教訓是否比促成它的失敗更長壽？

一句話概括

作者追蹤自己的單人文件庫及三種代理 runtime 六週，整理失敗紀錄、測試 LLM 文件稽核，再把五種舊失敗在有無修復的隔離版本中重播。少數重播中，一些行為未再出現，文件計數過時則仍會發生；樣本小、重播會受到時鐘與其他條件影響，不能由此判定一般規則已失效或可安全移除。（摘要、§7）

單人系統與失敗紀錄

研究對象是作者私人 Markdown／Python repository，供求職、語言學習與行政工作使用；兩個互動 runtime 和一個排程服務共享規則。Harness 由始終載入的 維護說明、按需技能、命令前 guard、編輯後提醒、提交前檢查與每月唯讀文件稽核構成。作者要求可重現失誤的修復留下紀錄，規則或檢查變更需其批准；沒有自動淘汰舊教訓的機制。（§3）

作者從 commit、變更紀錄、稽核報告和日記建立 118 筆失敗 ledger，兩次 LLM 編碼分歧由本人裁決。未有至少七天可觀察期或紀錄不足者標為未知。作者自報其中 39 筆同類失敗再發、8 筆至少七天內未再發、71 筆未知；不能將未知等同沒有再發。文件過時為 48 筆，但其中 35 筆集中在同一天兩次全面稽核的發現，計數受觀察強度影響。（§4.1、§5.1，表 1）

檢查也有副作用：作者記錄命令文字比對誤擋無害文字、背景 Git 同步與進行中 session 發生衝突，以及帶全域參數的命令繞過簡單 regex 等例子。因此「用程式檢查」仍須依實際涵蓋範圍及運行方式檢視。（§5.1）

文件稽核：召回與 precision 不同

作者對一個歷史快照準備 47 個已知真實過時陳述和 20 個植入錯誤；三種 Claude 模型各跑三次唯讀稽核，另以模型評分並由作者審查。47 項中 22 項先前已由 LLM 稽核發現，11 項屬邊界案例，因此這個答案集可能偏向可被稽核找到的過時陳述，且不完整。（§4.2）

作者自報，Sonnet 5.5 單次對 47 個真實項目的平均召回為 49.6%，三次聯集為 30/47（63.8%）；九次所有模型執行合併仍漏掉 12/47。各次 precision 為 0.93–1.00，九次另找到答案集外 9 個真正過時陳述。高 precision 表示報出項多數正確，不等於召回完整。作者觀察 Opus 將讀檔派給 Haiku 子代理，但未測試這是否造成其召回差異。（§5.2，圖 4）

五種失敗的反事實重播

作者選出五種有清楚觸發任務及獨立修復 commit 的舊失敗：技能數量過時、引用已推翻決策、信件破折號、危險 Git reset 及時間高估。條件 A 為修復前的 repository，條件 B 為同一狀態僅加入該修復；兩者使用相同中性 commit 訊息，無網路 remote。Sonnet 5.5 每條件各三次，並對破折號與時間估計情境加測較舊模型及另一 runtime。（§4.3）

作者自報 Sonnet 5.5 的技能數量過時在無檢查時 3/3 發生；有檢查且執行的 2/2 未留下過時數，第三次因 deadline focus 規則拒做，不能算成功檢查。作者對 3/3 與 0/2 報告單尾 Fisher 精確檢定 p=0.10，未達統計顯著。另三個完成的情境在有無修復下各 0/3 重現。時間估計情境的六次均因讀取真實主機時鐘而觸發 deadline focus、拒做，故沒有測得該規則效果。（§5.3，表 3）

沒有重現也不等於修復可刪：破折號情境的文字禁令在兩條件都存在，只測提交檢查；危險 reset 情境中沒有任何 run 走到危險命令，無法測 guard 是否仍必要。較舊 Sonnet 4.5 在時間估計有無文字規則時都 2/3 高估；另一次 Sonnet 5 草稿產生破折號、被啟用的 lint 擋下後修正。每格僅三次，屬探索結果。（§5.3，表 4）

研究界限

  • 只有一位作者的私人系統、六週觀察；作者設計記錄政策、挑重播情境並裁決編碼。聊天中修正但未記錄或提交的小錯不在 ledger；一次密集稽核也使過時文件計數集中。（§7）
  • 三次重播無法證明失敗已消失；重建提示也可能遺漏原始觸發因素。作者承認原事件所用模型／runtime 與主要重播不同，而主機真實日期讓舊快照中的 deadline 看似迫近。（§7）
  • 私人原 repository 與逐字紀錄不公開；匿名 ledger、稽核分數和腳本由作者依請求提供。本檔補註，非作者自陳：此研究支持定期檢查教訓是否仍有作用的問題意識，但移除規則仍須有針對觸發條件及副作用的額外證據。（§7–8）
