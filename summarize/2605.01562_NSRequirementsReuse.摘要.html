論文／訪談原始來源

《神經符號代理：無幻覺需求重用》重點摘要

一句話概括

Neuro-Symbolic Multi-Agent Requirements Reuse：以 LangGraph 打造四代理（Navigator / Interpreter / Validator / Scribe）神經符號多代理系統，將 LLM 定位為非確定性啟發式（透過自然語言專案願景遍歷 OOMRAM 需求晶格樹），同時以純確定性的符號驗證器（Python 函式，零 LLM 成分）在迴圈內強制執行所有布林約束——以「拒絕為預設、演算法把關」徹底消除幻覺需求組合，在兩組應用家族共 10 個專案願景的自主基準測試中達到 100% 完成率與僅 0.2% 約束違規（全部在校驗迴圈中被攔截修正），首次將 OOMRAM 形式化需求晶格從「精確 ID 查詢」解鎖為「自然語言驅動遍歷」，為安全關鍵需求工程提供可審計、絕對無幻覺的神經符號架構。

解決什麼問題

OOMRAM（Object-Oriented Method for Requirements Authoring and Management）是成熟的軟體產品線需求重用框架，以形式化晶格（lattice）建模需求物件的階層、判別式（discriminants）與變異性約束，但其原本的檢索機制要求使用者指定精確需求 ID——這道「精確匹配瓶頸」使分析師無法用自然語言專案描述自動生成規格。

LLM 雖能解讀自由文本並建議相關需求，卻易產生幻覺：憑空捏造不存在的 ID、忽略必要約束、組合互斥選項。既有 RE 工具的 LLM 整合缺乏形式化正確性保證，而檢索增強、迭代紮根等幻覺緩解法僅提供啟發式過濾而非確定性強制。

本工作的核心張力在於：如何在保有 LLM 語言彈性的同時，保證產出規格的結構正確性？

核心方法

神經符號架構（LangGraph 四代理）

  • 需求晶格 L = (V, E, T, Φ)：將應用家族表示為有向無環圖（DAG）。節點分四類——Core（必要）、SA/Single Adaptor（XOR，擇一）、MA/Multiple Adaptor（OR，至少一）、Op（可選）。約束 Φ 為布林可滿足性條件，定義整體一致性謂詞 Ψ(S)。
  • Navigator：基於規則，選取下一個待展開的判別式節點，模擬深度優先遍歷。
  • Interpreter（LLM，temperature=0）：將自然語言願景對映到當前節點的子需求 ID 集合，輸出結構化 JSON。是系統中「唯一含 LLM 的組件」。
  • Validator（純 Python，零 LLM）：對照晶格綱要執行 Ψ(S) 一致性檢查——(1) 所有可達核心節點皆已選取；(2) SA 節點恰選一個子節點；(3) MA 節點至少選一個子節點；(4) 所有被選節點之父節點也在選集中。違規時回傳拒收訊息給 Interpreter 重試，自身永不呼叫 LLM。
  • Scribe：將最終選集編譯為格式化規格文件。

狀態轉移形式化

Interpreter 實現映射 f: (V, σ) → P(C(v))，Validator 執行布林檢查 B(σ′)。若 B(σ′) = False，記錄違規於錯誤日誌 E，指示 Interpreter 以更嚴約束重試，直到所有約束滿足後 Navigator 才推進下一節點。最大遞迴步數 250、最多 100 次 LLM 呼叫。

子圖導航（線性可擴展）

Navigator 限制 Interpreter 僅關注當前節點的直接子節點，使輸入上下文大小保持 O(1)，總遍歷時間 O(|D|·K)（D 為判別式節點數，K 為平均分支因子），可線性擴展至工業級晶格（如 49 節點的電信模型）。

語意路由

以 sentence-transformer 嵌入將願景文字自動對應到最相近的晶格家族（eRecordKeeping、SmartHome 等），實現單一管線支援多領域。

結果

  • 10 個專案願景（eRecordKeeping ~60 節點，SmartHome ~20 節點），Ollama + llama3.1:8b-instruct-q4_0，Apple M1 Pro / 32 GB。
  • 100% 完成率：所有願景皆成功遍歷，無超時。
  • 0.2% 約束違規：全測試僅發生 1 次違規（er_small_biz），當場被 Validator 攔截修正，最終規格零違規。
  • F1 0.47–0.81（對照人工金標準）：中等分數反映合法可選/替代選項的多重性（非系統失效）——每一份輸出皆結構有效且滿足所有必要領域規則。
  • 平均牆鐘延遲 210 秒（eRecordKeeping 263 秒、SmartHome 160 秒）；平均每願景 78 次 LLM 呼叫。Validator 本身耗時可忽略（純 Python 檢查數百個選取）。
  • 意圖衝突現象：Interpreter 為滿足 stakeholder 偏好（如「廉價輕量」）試圖跳過必要安全需求，Validator 阻止非法省略——晶格作為符號護欄防止便利性覆蓋安全/法規需求。

對照：早期無 Validator 的設計中 LLM 頻繁產出多約束違規（錯誤基數、遺漏必要需求、孤立子節點），引入確定性 Validator 後此類錯誤從最終輸出中完全消失。

局限

  • 測試規模較小（兩個領域，10 個願景，單一 LLM），尚未在大型工業晶格或跨異質 LLM 上驗證。
  • 僅保證結構有效性（約束不違反），不保證需求內容的領域語意正確性——那是 LLM 解釋 stakeholder 意圖的職責。
  • 單一金標準 F1 無法捕捉多合法配置的現實，需要更細緻的「配置空間覆蓋率」評估指標。
  • 未進行消融研究（已規劃於全文版），未做人機互動使用者研究。

對讀者的價值

  • 對 ai_core §3.4「憑證准入」的原型示範：Validator 是純確定性硬閘——不經它通過的 LLM 產出根本無法進入最終規格。這正是 ai_core 治理模型「拒絕為預設＋憑證准入」在需求工程領域的具體實作：LLM 提案必須通過外部、獨立、不可繞過的結構驗證才能被採納，且驗證器本身永不引入 LLM 幻覺風險。系統中「Interpreter→Validator 反覆修正直到零違規」的迴圈，對應 ai_core「生成便宜/驗證可靠」的基礎成本不對稱原則。
  • 對 ai_core §5「確定性驗證」的直接示範：本工作的核心洞察——「把結構邏輯卸載給符號組件」——正是 §5「下層受約束填碼」與「固化引擎」思想的跨領域案例：LLM 負責理解模糊意圖並映射到領域模型（上層語意橋接），確定性演算法負責執行結構約束滿足（下層形式驗證）。兩者間的精確分工——神經＝啟發式探索、符號＝確定性把關——示範了 ai_core「系統像符號神經網路計算圖（多數確定性節點＋少數 LLM）」的理想架構形態。
  • 固化引擎的直接隱喻：OOMRAM 晶格本身就是「將領域知識固化為形式結構」的產物——把需求工程專家的領域知識結晶為 DAG 類型與布林約束，使 LLM 只能在已被專家審查過的合法空間內探索。Validator 則是該固化知識的執行器。這與 ai_core「把 LLM 反覆處理的案例結晶成確定性程式碼／抽象庫」同構：此處的抽象庫是形式化需求晶格，確定性程式碼是約束驗證器。
  • 子圖導航的規模啟示：O(1) 上下文的前沿策略解決了 RAG/長上下文中的「lost-in-the-middle」退化——這對 ai_core 的長鏈推理場景（大程式碼庫遍歷、多文件分析）提供了「逐步局部聚焦而非一次性全局傾倒」的導航模式。
