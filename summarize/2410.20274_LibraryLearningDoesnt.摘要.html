作者：Ian Berlot-Attwell, Frank Rudzicz, Xujie Si（University of Toronto / Dalhousie University, Vector Institute）

日期：2024-10

arXiv：2410.20274

論文／訪談原始來源

《庫學習沒有學到庫：一次性"庫"的奇特案例》重點摘要

一句話概括

兩個宣稱透過「庫學習（library learning）」提升數學推理準確率的 LLM 系統——LEGO-Prover 與 TroVE——經細粒度分析發現：函數/引理重用極罕見（各僅 1 次與 3 次），消融實驗顯示真正的效能增益來自自我修正（self-correction）與自我一致性（self-consistency／多數投票），而非庫學習宣稱的「可重用工具累積」。

解決什麼問題

近期 LLM 庫學習系統（LEGO-Prover 學習 Isabelle 引理、TroVE 學習 Python 函數）皆報導準確率提升，但都只用任務準確率當評估指標——準確率無法區分「靠庫的真重用」與「靠其他機制（如多取樣、自我修正、思維鏈）的假進步」。一個好的庫配上弱推理器會無用，一個強推理器配上無用庫也可以從第一原理推導——必須直接觀察系統是否真的在「重用」學到的工具。

核心方法（雙系統分析 + 消融實驗）

LEGO-Prover 分析（§3）

  • 公開日誌分析：直接統計 LEGO-Prover 發布的最終求解日誌中，引理是否被 PROVER 重用。
  • 系統學了 超過 20,000 條引理，但僅 **1,233 條（~6%）**出現在最終解的輸入 prompt 中。
  • 這 1,233 條中，只有 1 條引理被逐字重用（且只 1 次）；若放寬為「引理名稱出現」，也僅零星幾次，且沒有引理被重用超過 1 次。
  • 消融實驗：拆掉跨問題共享（每個定理獨立狀態、獨立資料庫），以 GPT-4o-mini 重跑驗證集的隨機 12 題子集（原著用已棄用版 GPT-3.5-Turbo），結果只比基線少解 1 題，僅解決的題目中來自共享庫的最簡單引理（如 a^2 >= 0）可能被用到——連「複製已驗證證明」這種基本重用 LLM 都做不好。

TroVE 分析（§4）

  • 重新實作並分析日誌：因 TroVE 未釋出日誌，作者重跑 MATH 資料集（準確率在±2% 內重現）。
  • 最終庫僅含 15 個學到的函數，且只出現在 7 個 MATH 子主題中的 3 個。
  • 這 15 個函數中，僅 2 個（is_perfect_square、is_prime）被正確解重用，總計 3 次成功重用——對 3,201 題測試集而言幾近於零。
  • 消融實驗：禁用 IMPORT 模式（庫永不出現在模型輸入），但維持 15 次取樣（8 次 SKIP+7 次 CREATE），使用 CodeLlama-7b。結果：消融版在多數子主題上勝過基線（count、number 達統計顯著），只有 geometry 子主題上略輸——但該子主題的庫僅含 import 語句。

結果（具體數字）

指標 LEGO-Prover TroVE
總學到工具數 >20,000 引理 15 函數
最終 prompt 中使用 1,233 (~6%) —
逐字重用次數 1 次（1 條引理） 2 函數、3 次成功重用
重用超過 1 次 0 0（is_prime 被重用 2 次仍未超過 1 次門檻）
消融後表現 只少解 1 題 多數子主題勝過基線

作者的核心論點

  1. 準確率作為庫學習的評估指標是誤導的：必須直接觀察重用行為，並設計最小改動的消融實驗。
  2. LEGO-Prover 的增益機制：不是庫重用，而是透過 request db 進行的自我修正（重試失敗引理）＋思維鏈（PROVER 提議有用子步驟給 EVOLVER 解）。
  3. TroVE 的增益機制：不是函數重用，而是集成（ensembling）與自我一致性（多數投票）——這與之前「增加取樣即提升效能」的文獻一致。
  4. 現有庫學習系統可能根本沒在做庫學習：要麼 LLM 太弱做不到，要麼資料集（如 MATH）本身就沒有足夠的跨題重用機會（問題太分散、共通組件已被標準庫涵蓋）。

對讀者的價值

  • 直接命中 ai_core §8.1 驗證假設「搜尋節省 vs 壓縮長度」作為固化價值指標。本文用實證展示：若庫學習的增益來自自我修正/多取樣而非真正重用，則以「壓縮長度」當價值度量會把假復用誤判為真固化——真正該量的應是「省了多少搜尋」（即庫中的工具是否真的被後續任務直接調用而不需重新生成）。這正是 deep/ §8.1 提出「三條品質分數路線同任務 PK」時的核心動機：需要一個能區分真/假復用的指標框架。
  • 對 §3.6 固化引擎的警示：DreamCoder/LILO/Stitch 等經典庫學習系統是以壓縮（MDL）為驅動——壓縮即發現結構。但本文證明，在 LLM 庫學習場景中，壓縮增益可能來自完全不相干的機制（自修正、多取樣）。若 ai_core 要從 LLM 反覆處理的案例中結晶出確定性程式碼，必須用「實際調用次數」而非「程式碼行數減少」來衡量固化價值——這是從函數式壓縮路線（Stitch）到 LLM 庫學習之間的方法論斷層。
  • 消融設計的方法論教訓：兩篇原始論文都選擇了「太激進的消融」（把整條管線砍掉），而本文展示「最小改動消融」（LEGO-Prover: 只切斷跨問題共享；TroVE: 只禁用 IMPORT 但維持取樣數）才能隔離出庫重用本身的貢獻。這對 ai_core 的實驗設計有直接參考價值：測試固化引擎時，若不控制取樣預算，就無法判斷增益是來自「庫更好了」還是「多試了幾次」。
  • 對照 §3.4 治理：庫若充斥從未被重用的函數（TroVE 庫 80% 未被任何正確解使用），則庫本身成了雜訊來源——這與「拒絕為預設＋憑證准入」同構：只創建而不驗證重用的庫，等價於一個沒有治理的開放 API。歸 G 類。
