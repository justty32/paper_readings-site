論文／訪談原始來源

《CodeRL：以預訓練模型與深度強化學習精通程式碼生成》重點摘要

一句話概括

CodeRL：把程式碼生成當 actor-critic 強化學習問題——訓練一個 critic 網路預測「單元測試會編譯錯/執行錯/測試失敗/全部通過」四類結果，用它產生的 token 級分數當**密集回饋（dense reward）**微調當 actor 的程式碼 LM；推論期再以 critical sampling 用同一 critic 導引，對通過樣本重生子序列（refine）、對失敗樣本挑最佳送修復模型（repair），在 APPS 與 MBPP 上以 770M 小模型刷新 SOTA、勝過大得多的模型。

解決什麼問題

既有程式碼生成 LM 只用「自然語言題目→標準答案程式」做監督式微調，有兩個缺陷：(1) 只靠 next-token prediction（NTP） 的 teacher-forcing 目標，測試時逐 token 自回歸會累積誤差，而 BLEU 等 token 相似度分數與功能正確性（functional correctness）相關性極低，無法衡量完整程式對錯；(2) 完全沒用到單元測試（unit test）這個直接決定成敗的訊號——無論訓練期的優化目標，或推論期（題目常自帶 example unit tests）都被忽略。既有 AlphaCode 雖用 example test 過濾排序輸出，卻不能據此改寫程式。

核心方法

  • RL 形式化：把 LM 參數視為隨機策略（policy），每個 token 是 action，整段程式跑完由編譯器（環境）依單元測試給 return。用 REINFORCE／policy gradient 優化期望 return。
  • 以單元測試定義 return（Eq.4-7）：編譯錯 −1.0、執行錯 −0.6、測試失敗 −0.3、全通過 +1.0。
  • 相對 return（baseline）：以 greedy decoding 當基線，樣本贏基線才給正 return，允許探索「不完美但比基線好」的程式，降低梯度變異。
  • Critic 當誤差預測器（§3.3.3，核心）：另訓一個較小的 Transformer critic，輸入題目＋取樣程式，預測四類測試結果之一；取其 token 級 hidden state 算出每個 token 對「達成真實測試結果」的價值 q̂，把終端 return 細化為 token 級中間 return（避免「多一個空格→整段被重罰」的粗糙訊號）。
  • Critical Sampling（CS）推論期雙策略（§3.3.4）：先生 N=200 支程式對 example test 篩成通過集 P／失敗集 F。Program refining：對 P 用 critic 找價值最高的分割點，取左半當 seed 讓 actor 重生後半。Program repairing：對 F 用 critic 挑 top-M，連同編譯器錯誤型別與訊息送進 seq2seq 修復模型，修好再走 refine。
  • 骨幹：擴充 CodeT5-large（770M）——加入 NTP 預訓練目標、擴 10 倍 Python 資料（GCPY 10.5B tokens）。訓練先用 L_ce 暖啟動、凍結 actor 訓 critic，再以 L_ce＋L_rl 等權微調。

結果

  • APPS（新 SOTA）：pass@1 2.69%、pass@5 6.81%、pass@1000 20.98%；n@k 為 1@k 8.48%、5@k 12.62%。k=1000 即匹敵 AlphaCode 用 k=50000 的成績。
  • MBPP 零樣本（APPS 訓練直接測 MBPP）：770M 拿 63.0% pass@80，勝過微調過的 GPT-137B 的 61.4%。
  • 消融：return 估計上「baseline＋trained critic」（Model D）最佳；CS 以 refine＋repair 且 M=1 最佳；NTP 預訓練目標把 pass@5 從 2.06 拉到 2.9；critic 用 GPT-2 small 即達 >75% 誤差預測準確率（成本相對骨幹極小）。

局限

  • 多訓一個 critic 與修復模型有額外算力成本（作者稱相對小）。
  • example unit tests 不如 hidden tests 全面，會有 false positive，限制 CS 效益；建議用測資變異增強。
  • 沿用大型 code LM 的通病：可能生出有偏見／不安全／有漏洞的程式，輸出仍需人工驗證；NTP 帶來的對齊失敗（輸出不符使用者意圖）依然存在。

對讀者的價值

  • 直接命中 ai_core §3.4「學習式驗證器當獎勵訊號」＋治理「憑證准入」：CodeRL 的 critic 就是一個學來的驗證器——不靠形式證明、而是用單元測試結果訓練出「這段碼會不會通過」的機率打分，既當訓練期密集 reward，又當推論期的准入／重生依據。這正是把「拒絕為預設＋憑證准入」量化的一種做法：唯有 critic／實測給出高通過機率的程式才被採信，其餘退回 refine/repair。
  • 對 §5「程式碼助手」的下層「受約束填碼」是可操作範式：CS 的 refine（保留正確前綴、只重生可疑後段）＋repair（帶編譯器錯誤訊息定向修復）示範了如何用確定性訊號（編譯器／測試）閉環約束 LLM 生成，把單次昂貴呼叫變成「生成→實測→定點重生」的可靠函數，貼合「逐步剃除對 LLM 不確定性依賴」的北極星。
  • 歸 I 類（學習式驗證器／執行回饋），與 2305.14263 LEVER（訓驗證器據執行結果重排）、2207.10397 CodeT（自生測試 + 雙重執行一致性）對照：三者都以「執行／測試訊號」取代 token 相似度當品質判準，但 CodeRL 更進一步把驗證器訊號灌回訓練梯度與推論期重生，而非僅事後過濾排序。對 ai_core 而言，這說明「驗證器」不只是准入閘門，也可反哺資產工廠的訓練迴圈。
