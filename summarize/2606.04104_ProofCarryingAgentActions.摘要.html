論文／訪談原始來源

《Proof-Carrying Agent Actions：異質 Agent 系統的模型無關 Runtime 治理》重點摘要

一句話概括

PCAA 把治理主體從某個 vendor 的 session log 改成可攜的 action certificate：一個高風險動作必須經過 admissibility、action open、assumption capture、approval、outcome closure 五個 checkpoint，並附上 runtime receipts、approval semantics、externality facts、replay bundle 與 integrity reference。它解決的是「異質 runtime 如何用同一治理語彙留證」，不是讓 LLM 為動作生成形式化數學證明。

核心信任物件

對 raw action a，certificate 包含：

  • E(a)：正規化 action envelope；
  • Q_r(a)：pre-input、pre-tool、post-tool、pre-output 等 runtime-stage receipts；
  • Q_h(a)：human approval、approver lineage 與 accountability facts；
  • P(a)：replay-ready proof state；
  • I(a)：commitment、attestation 或未來 verifier receipt。

Envelope 不只記動作名稱，還記 tenant/agent、runtime family、adapter mode、authorization、workflow、evaluation、accountability 與 externality context。Externality 進一步描述 destination visibility/ownership、tenant provenance、company/personal account、client provenance、是否外部寫入、敏感資料、可逆性與 approval enforceability。

五個 Checkpoint

  1. guard：在副作用前決定 allow、warn、block、simulate-first 或 require-approval。
  2. createAction：建立穩定 certificate identity。
  3. recordAssumption：保存當時相信、預期及依賴的條件。
  4. waitForApproval：政策需要時暫停或交由外部 runtime hold。
  5. updateOutcome：寫入結果、證據及 terminal closure。

作者稱它為 route-review-prove：先用穩定語彙路由，再選擇性人工審查，最後封裝可重播、可匯出的證據。

異質 Runtime 與誠實的控制深度

Runtime family 分 OpenAI-compatible gateway、managed platform、framework SDK、tool hook、observer/import-only。Adapter mode 分 inline SDK、lifecycle hook、session adapter、gateway、bridge、observer，並標示 strong／moderate／selective／weak interception。

這個區分很重要：只有 post-hoc receipt 的 observer 不能宣稱能在副作用前阻止動作。Approval 也不能只記 reviewed bit，而要分：

  • pre_execution_gate：PCAA/governor 真能在執行前暫停；
  • observe_only：執行後才匯入證據；
  • delegated_runtime_control：外部 governor 真正執行 gate，PCAA 保存 certificate；
  • runtime_controlled：runtime 已執行，沒有硬 gate。

Authority 也拆成 workspace、runtime、external governor。Runtime 負責實際執行與 native trace；外部 governor 可就近 enforcement；workspace-visible PCAA certificate 仍負責 tenant scope、approval、replay export 與 proof closure。

Proof、Replay 與 Integrity

Proof bundle 含 human-readable summary、evidence payload、verification projection 與由 canonical payload 算出的 manifest。Replay 會重新計算 envelope、risk result、policy snapshot 與 manifest，檢查 missing evidence、manifest mismatch、policy drift、risk drift。

即使動作被阻擋或等待 approval，也要產生 non_execution_proof 或 pending_execution_proof，不能因沒有副作用就消失。Receipt completeness 明確區分 complete、partial、missing。

Integrity 分三層：快速 commitment、可攜 attestation/credential、未來更強 verification。論文特別說 chain receipt 或 wallet attestation 不能取代 certificate closure。因此這裡的「proof」目前主要是結構化稽核證據、digest 與 replay check；zk proof／公開可驗證計算仍屬 future lane。

Public Validation 數據

  • Protected corpus 由 24 seed templates 跨四 runtime family replay 成 96 traces。
  • Decision buckets 為 allow 24、simulate-first 20、require-approval 28、block 24。
  • Static rules：exact accuracy 0.583、macro-F1 0.493、severe recall 1.0、block precision 0.400。
  • Scalar heuristic：0.375、0.296、0.778、0.182。
  • PCAA：四項皆 1.000。
  • PCAA review 29.2%、simulate-first 20.8%、block 25.0%；manifest stability 1.0、replay readiness 1.0、receipt completeness 0.516。
  • 延遲平均 0.35 ms、P95 0.54 ms、P99 0.72 ms。

Ablation：移除 externality，exact accuracy 1.0→0.875、review 0.292→0.167；移除 approval enforceability，accuracy 0.917、review 0.375；移除 integrity，routing 不變，但 manifest stability 1.0→0、proof closure 1.0→0.708。三者分別影響 route、review posture 與 proof，而非同一種效果。

對 Agent 錯誤與責任管理的價值

PCAA 把「誰授權、何時批准、runtime 能否真的阻止、依據哪些假設、最後發生什麼」變成一個 versioned object。這對跨 runtime 錯誤追查比拼接多套 dashboard log 更有用：每次 side effect 有同一 certificate ID，執行 receipt、人工決策、外部邊界與結果都能連回同一條 proof path。

它也提醒治理系統不要把 observer telemetry 冒充 enforcement。管理千萬 agent 時，certificate schema 可以統一，但並非每個動作都需要人工 review；路由器必須在 review budget 下選擇性升級，並讓低控制深度清楚暴露。

局限

  • 96 traces 來自 24 protected templates，raw scenarios、threshold、heuristic weights、connector rules 都未公開，外部無法重算 1.000 成績。
  • Benchmark 由同一實作與治理 taxonomy 建立，PCAA 完美對齊可能反映 benchmark construction；缺少獨立資料、第三方標註與 deployment outcomes。
  • Static rules 與 scalar heuristic 是弱基線，沒有和成熟 policy engine、OPA、工作流 approval 系統或現有 managed governance 做等條件比較。
  • 這不是 proof-carrying code 式 machine-checkable safety theorem。現有 proof 主要是 receipts、canonical manifest、replay/drift check；強密碼學 verifier 仍未完成。
  • Observer/import-only runtime 無法 preempt side effects；certificate 能誠實記錄控制不足，不能把 post-hoc visibility 變成安全保證。
  • 論文大量依賴作者公司的 OSuite reference implementation，程式與 protected corpus 可取得性、版本穩定性及利益衝突需要讀者自行評估。
