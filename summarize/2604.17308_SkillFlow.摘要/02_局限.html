局限

  • 論文未設獨立「Limitations」章節，以下為其自陳的評測範圍限制：技能補丁生成被刻意與執行 harness 解耦、限制為單輪、固定格式輸出，以維持跨 harness 的公平比較，但這也意味著沒有測「harness 原生技能撰寫流程」下的表現；同一家族內任務刻意不與其他家族交錯（family reset），因此本 benchmark 測的是單一工作流內的終身學習，而非異質工作流間的技能檢索與遷移；「歷史上下文 vs 技能庫」對照實驗只在 Claude Opus 4.6 一個模型上做，作者自陳「未隔離所有變因、範圍有限」；每家族僅 8–9 題，序列長度不足以檢驗更長期（數十至數百步）的庫演化動態；任務環境限定在可離線執行、無需外部網路服務的辦公室/資料處理類工作（試算表、OCR、文件、財務分析等），未涵蓋開放式或具身（embodied）場景。

對讀者的價值

  • 對 ai_core §3.6「固化引擎——庫爆炸怎麼避免、何時該固化」（backlog 主題 11）：這篇不是新方法，而是評測端的關鍵補件——固化引擎最硬的未決問題正是「怎麼知道庫變差了/該收斂了」，而 SkillFlow 首次把這件事拆成可量測的三組訊號：技能使用率 %use（是否真被讀取/呼叫，非只是存在）、最終技能數 #Skills（庫大小是否隨任務單調膨脹）、任務成功率的增量 Δ%comp.（外化是否真的換來能力提升）。三者交叉比對就能診斷出「碎片化技能庫」——Qwen-Coder-Next 是活教材：#Skills 累積到 5.45 個、%use 卻只有 12.05%，Δ 還倒退 0.60 點，等於庫在長、但沒人用、還拖累表現。
  • 對照已入庫同主題論文，SkillFlow 的定位更清楚：
    • 2605.09985 前瞻式壓縮：主張抽象該為「未來任務」而非「過去語料」服務；SkillFlow 的協定本身就是逐題向前演化（每題產生的補丁只服務下一題起的未來任務），等於用真實 agent 資料實證了「回溯式壓縮不足以解釋/最佳化技能演化」——這篇的 Finding 3（統一技能優於碎片化）可視為前瞻式壓縮假說在 agent 場景的間接印證。
    • 2410.15184 ActionPiece：用 BPE 式方法從高回報軌跡中自動抽取動作子序列成塊；SkillFlow 的技能補丁生成則完全交給 LLM 自身（Model_g），沒有 ActionPiece 那種可靠的統計壓縮保證——兩者對照凸顯「Increment（不斷加補丁）」與「Replace（統一重寫/合併）」的取捨：SkillFlow 的 Finding 4（技能膨脹）正是「只 Increment、不 Replace/consolidate」的具體代價實測。
    • 2305.16291 Voyager：技能庫雛形（把驗證通過的行為存成程式碼供檢索組合），但 Voyager 沒有量測「庫本身是否健康」；SkillFlow 可視為給 Voyager 這類系統補上的庫健康度評測層——用它的三組指標回測 Voyager 式技能庫，才能回答「Voyager 的技能庫會不會也碎片化」。
    • 2006.08381 DreamCoder／2211.16605 Stitch／2310.19791 LILO：這三篇是符號式、有壓縮最優性保證的固化管線（MDL 貪婪抽象、可證明最優的 λ 抽象、AutoDoc 文件化），本質上是「Replace/consolidate」的工程解法。SkillFlow 的 Finding 6（差距在修復、不在寫技能）恰好指出：當固化交給 LLM 自身（而非符號壓縮演算法）時，「寫」很容易但「修」很難——這正是 DreamCoder/Stitch/LILO 那條符號化路線想用演算法保證解決的問題，也提示 ai_core 的固化引擎若想避開 SkillFlow 揭露的失敗模式，不能只靠 LLM 自我摘要式的補丁，而需要類似 Stitch 的壓縮/去重步驟做把關。
    • 2401.16467 ReGAL：用「執行結果等價」驗證＋週期性編輯/修剪過度特化函數，屬於「邊做邊長、但有修剪機制」的路線；SkillFlow 顯示的失敗模式（技能膨脹、錯誤繼承）正是沒有 ReGAL 這種週期性修剪/驗證步驟時會發生的事——兩篇合看，等於一個提出修剪機制（ReGAL），一個給出「不修剪會怎樣」的量化證據（SkillFlow）。
  • 一句話結論：SkillFlow 沒有回答「該怎麼固化」，但它給出了判斷固化引擎是否健康所需的最小指標組合（使用率×庫大小×增量收益），並用 11 個真實模型的對照實驗證明「多數 LLM 自我固化都會走向碎片化或錯誤繼承」——這正是 ai_core §3.6 在設計固化引擎前必須先防的兩個具體陷阱。歸 I 類。
