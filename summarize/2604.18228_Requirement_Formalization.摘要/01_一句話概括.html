一句話概括

提出一條三階段代理式（agentic）LLM 管線——先把非結構化自然語言規格拆成結構化原子需求，再由 LLM 依目標形式模型的語意邊界分類哪些需求可形式驗證（過濾不可驗證者），最後把可驗證需求翻成目標形式語言（UPPAAL SMC 查詢）——並用「LLM 判官＋編譯器」三層方式評估，在三個機器人情境上取得抽取 81.8%、可驗證性分類 88.7%（recall 94.2%）、形式翻譯（含語意等價寬鬆計分）77.8% 的表現。

解決什麼問題

安全關鍵系統（如需與人近距離互動的服務機器人）早期規格通常只以自然語言撰寫，難以直接導出可供模型檢驗（model checking）的形式屬性。既有 LLM 生成形式產物的工作多半只顧語法正確（能否通過文法/編譯檢查），卻不保證生成屬性與原始非形式需求語意一致——即模型驗證的到底是不是使用者真正關心的那件事。本文要解決的正是這道「語意對齊」缺口：如何從自由文字中，自動萃取出「既語法合法、又語意忠實於原規格」的可驗證形式屬性。

核心方法

管線分三個各由單一 LLM 擔綱的階段（皆用 gemini-3.1-pro-preview，temperature=0.1，輸出強制 JSON schema）：

  • Stage 1：需求抽取（Requirements Extraction）——LLM 讀取非結構化規格，抽出一組原子（atomic）自然語言需求，每條配識別碼，統一用「The system must…」「The robot shall…」等標準需求句式，輸出成 JSON 結構化清單。採 2-shot 提示：對每個情境，用另外兩個情境人工撰寫的 ground truth 需求當範例。
  • Stage 2：可驗證性分類（Verifiability Classification，本文核心判準）——LLM 扮演「精通形式方法與統計模型檢驗（SMC）的系統工程師」，逐條判斷該需求是否落在目標形式模型的語意邊界內。系統提示明確列出模型假設（例如系統無記憶性 memoryless、不偵測物理損壞、靜態機台視為資源無限且零處理延遲），並要求依結構化規則過濾掉：指涉不可觀測變數、定性設計意圖、或模型外部現象的需求。輸出為每條需求「Yes/No」＋簡短理由的 JSON。之所以獨立成一階段而不與抽取合併，是要讓 Stage 1 的 LLM 能不受目標模型限制、盡量完整地列需求，避免因預先考慮形式模型侷限而漏抽。
  • Stage 3：形式翻譯（Formal Translation）——把 Stage 2 判定可驗證的需求，依系統提示中提供的緊湊 BNF 文法（UPPAAL SMC 查詢語言）與「LIrAs DSL 文法↔UPPAAL 模型」的明確映射規則，翻成可直接在生成的隨機混合自動機（Stochastic Hybrid Automaton, SHA）模型上做模型檢驗的查詢（形如 P[<=τ](<> ap)，對應 MITL 的 ◆≤τ 運算子）。

評估法（三段獨立評測、以 GT 為準，避免誤差跨階段串接）：

  • RQ1 用 LLM-as-judge 對生成需求與 GT 需求做多對多語意比對，分 Match／Partial／NoMatch 三類並給信心分數與理由；
  • RQ2 直接比對 LLM 的 Yes/No 標籤與人工 GT 可驗證性標籤（confusion matrix）；
  • RQ3 採三層驗證：先用 verifyta 編譯器做語法檢查，再做精確字串比對，最後對「編譯成功但字串不同」的查詢用 LLM 判官做語意等價評估（容許邏輯交換律、蘊涵改寫、空間對稱性、SMC 時間界的微小差異；但嚴禁把 reachability 與 safety invariant 混淆）。

結果

資料集：3 個機器人／機電系統情境（Coffee_Delivery、User_Guided_Transport、Factory_Pipeline），人工建構 GT 共 71 條需求，其中 52 條可驗證、對應 72 條 SMC 查詢。

  • RQ1 需求抽取：精確語意匹配 43.6%、部分匹配 38.2%、無匹配 18.2%（合計匹配+部分匹配 81.8%）；對 GT 的 recall 僅 60.6%（71 條中有 28 條未被任何生成需求覆蓋）。兩類常見失誤：⑴ 遺漏嚴格邏輯邊界與形式前提（防止無窮迴圈的條件、任務完成保證、失效偵測機制），SC2 尤其嚴重，漏掉電量、疲勞等狀態轉移與物理限制；⑵ 依常識幻覺出規格未寫的合理限制（如 SC1 中臆測「員工」角色、SC2 中臆測安全跟車距離），且抽象層級抓不穩（SC3 把高層搬運操作過度拆成細瑣操作步驟，拉高部分匹配比例）。
  • RQ2 可驗證性分類：整體準確率 88.7%（各情境 84.2%–92.3%），63/71 條分類正確；precision 90.7%、recall 94.2%（TP=49、FN=3、FP=5、TN=14）。高 recall 代表極少誤刪真正可驗證的需求；5 個 false positive（誤判為可驗證）被作者認為會在下游語法/語意檢查中被攔下。
  • RQ3 形式翻譯：72 條查詢中 69 條（95.8%）通過 UPPAAL 語法編譯；僅 25 條（34.7%）與 GT 逐字相符；LLM 判官另外認可 31 條為語意等價，寬鬆整體準確率升至 77.8%（SC1 73.3%、SC2 56.5%、SC3 94.1%，SC3 因大量「查詢編排器完成狀態」取代「直接查座標」等等價改寫，語意判定後準確率由 20.6% 大幅躍升）。

局限

  • 三階段各自獨立評測（以 GT 為各階段輸入），刻意避免誤差跨階段累積——因此論文未報告端到端整條管線串接執行的真實表現，實務上 Stage 1 的低 recall（60.6%）會直接限縮下游可用的需求集合。
  • 需求抽取階段仍有明顯幻覺（編入規格未寫的常識性限制）與抽象層級不穩的問題，尚未解決。
  • 管線內沒有跨階段的回饋/精修迴圈——每階段是一次性前向生成，論文在未來工作中明確列出「建立精修迴圈以降低誤差傳播」尚待完成（相較於已有工作示範迭代修復的價值，這是本文目前明顯缺的一塊）。
  • 僅用單一模型（gemini-3.1-pro-preview）、單次執行、3 個情境、單一領域（HRI／機電系統）與單一目標形式化框架（UPPAAL SMC via LIrAs DSL），樣本量小（71 條需求），尚未做跨模型/多次重複的穩健性驗證。
  • Stage 3 的語法保證來自「提示中給 BNF 文法＋事後編譯器把關」，而非生成時的硬約束，故仍有 4.2% 查詢編譯失敗。
  • 論文本身為 AIPV 2026 workshop 的非正式出版（non-archival）先導性工作。
