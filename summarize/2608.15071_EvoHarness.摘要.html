Evo-Harness: Context-to-Harness Skill Compilation for Self-Evolving Agents 重點摘要

一句話

Evo-Harness 提出「online harness learning」：凍結模型參數，只讓一份外部結構化 skill harness 隨任務序列持續更新；核心是 context-to-harness compilation——只對失敗/負回饋的執行做 reflection 產生候選記憶，再由 evolver 決定 Add/Merge/Revise/Skip，寫入分成「跨任務通用技能」與「局部任務型技能」兩層的 harness。

方法

單次任務執行後得到 context（輸入、軌跡、結果、回饋）；reflection 只在失敗或負回饋時觸發，輸出 (lesson, trigger, evidence, scope_hint) 候選記憶，刻意不處理成功案例以避免把任務特定細節寫死進去。一批任務跑完後，evolver 同時執行 CompileTaskType（保留局部任務型程序）與 CompileCrossTask（抽取跨任務共通結構），把候選記憶編譯進既有 harness 而非直接附加，solver 端保持凍結。

作者報告的實驗與資料限制

作者在 WebArena-Infinity、TerminalBench2、SWE-bench Lite、CL-Bench、τ-bench 五個 benchmark、以 Claude Opus 4.6 為預設 solver/evolver 下報告：Evo-Harness 在全部五個 benchmark 都勝過 No-Evolve 與 AWM／Dynamic Cheatsheet／Evo-Memory／ACE／XSkill 等既有方法（如 TerminalBench-2 從 62.92% 升到 73.03%）。跨五個 solver 模型測 CL-Bench，Opus 系列增益 +3.7~+4.5，Kimi-K2.5 與 GPT-OSS 只有 +1.1／+0.8，作者稱較強模型更能吃到 harness 增益。消融顯示 general-only 與 topic-only 哪個更有用取決於任務類型（CL-Bench 靠 topic skill、SWE-bench Lite 靠 general skill）。作者特別報告兩個負面/反直覺結果：其一，用未接地的 LLM 自我判斷（Self-Generated feedback）取代環境訊號會讓分數低於 No-Evolve（CL-Bench 29.54→27.96、SWE-bench Lite 63.67→61.67），顯示未接地反思會產生誤導性更新；其二，Sonnet 4.5 演化出的技能能提升 Opus 4.7 solver，卻讓 Sonnet 4.5 自己 solver 表現低於 No-Evolve（55.3/55.7 對 58.0），說明 harness 遷移效果同時取決於 solver 能否理解與套用該指引，不是單向「evolver 越強越好」。以上均為作者自報數字，僅涵蓋文字型單一 agent（不含具身或多 agent），harness 僅以自然語言指引形式呈現，未涵蓋可執行程式碼技能。

對 ai_core 專案的價值／接點

這篇對固化引擎的啟發最直接：它給出一個具體、可移植的「只反思失敗、按批次分層編譯、以 Add/Merge/Revise/Skip 當編輯算子」的固化流程，且明確拆成「跨任務通用」與「局部任務型」兩層儲存——這正是固化引擎在做技能沉澱時可以直接採用的分層設計，避免把單次任務雜訊寫死進通用知識庫。對驗證器設計的警示也很尖銳：Self-Generated feedback 傷害效能（甚至低於不進化的 baseline）證明反思迴圈若不接地於外部驗證訊號（測試、verifier、工具診斷），LLM 自評會產生誤導性更新，這對任何要做 self-critique 驅動固化的模組是硬性提醒。對自我改進迴圈的啟發：這裡的「frozen model + evolving external harness」是與 HELIX（見 2608.13951）的「model-harness co-evolution」互補的另一極端案例——完全不碰模型權重，只靠外部技能檔案演化就拿到穩定增益，可作為 ai_core 低成本自我改進路線（先做 harness/skill 層演化，模型更新留到後續）的參照範本；Sonnet 演化的技能能餵給 Opus 但不能餵給自己這個發現，也提示了「用便宜模型做蒸餾、貴模型做推論」的成本梯度組合可能存在其非對稱的能力門檻。
