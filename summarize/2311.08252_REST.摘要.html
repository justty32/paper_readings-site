論文／訪談原始來源

《REST：基於檢索的推測解碼（Retrieval-Based Speculative Decoding）》重點摘要

一句話概括

REST（Retrieval-Based Speculative Decoding）：把推測解碼（speculative decoding）裡負責生草稿的小型 draft 模型，整個換成一個非參數的檢索資料庫——用當前上下文的後綴去庫裡做精確匹配，撈出「常見延續」當草稿 token，交給大模型單次前向驗證；免訓練、即插即用、可掛任何 LLM，在 7B/13B 模型上對程式碼與文字生成取得 1.62×～2.36× 的加速，且輸出與標準自回歸解碼逐字相同（無損）。

解決什麼問題

  • 推測解碼靠一個「小而準」的 draft 模型先生草稿、大模型一次前向驗證多個 token 來省下反覆載入十億級參數的成本；但取得高品質 draft 模型本身很難：要同時兼顧夠小（低開銷）、夠準（貼近大模型輸出）、且詞表與架構要與大模型相容，往往得為每個新模型專門挑選甚至訓練 draft 模型。
  • REST 的核心觀察：文字生成常包含共通的片語與模式——這些「常見延續」既然反覆出現，不如直接從語料庫檢索復用，而不必用一個參數模型去記憶／預測它們。

核心方法

  • 資料庫（datastore）：D = {(c_i, t_i)}，c_i 為上下文、t_i 為其後續延續；由文字／程式碼語料在每個位置切出「前綴上下文 + 對應延續」建成。
  • 檢索（近零成本、免向量模型）：以當前上下文 s 的最長後綴做精確匹配（exact match）——從上限 n_max=16 開始貪婪遞減，找到就回傳匹配到的一批延續候選；用 suffix array（Manber & Myers 1993）實現高效精確匹配。刻意不用 dense retriever（會增推論開銷），檢索開銷 <6%，實測每 token <1ms，近乎可忽略。
  • 草稿構造（Trie 選詞）：檢索到的延續候選集 S 可能很大，無法全丟給 LLM。作法是把 S 全部插進 Trie，每個節點權重＝該前綴在候選中的出現頻率，選出權重最高的 top c=64 個高頻前綴當草稿 token（實驗證明比隨機抽樣更好）。
  • 驗證（tree attention）：多條草稿常共享前綴，若當獨立序列各算會重複計算；REST 用 BFS 把子樹壓成一條偽序列、配合精心設計的 tree attention mask，讓共享前綴只算一次。
  • 接受策略（比原版更簡單）：把草稿餵給 LLM，在每個位置從 LLM 分布採樣，從頭起凡與草稿一致者全接受，第一個不一致之後全拒絕——因此 REST 產生的序列與標準自回歸生成完全相同（無損）。

結果

  • 加速（表 1，單卡 A6000、batch=1）：程式碼域 HumanEval 上 CodeLlama 7B/13B 達 2.12×～2.36×；一般域 MT-Bench 上 Vicuna 7B/13B 達 1.62×～1.77×。多數情形勝過以小 LM 為 draft 的推測解碼基線。
  • 資料庫（datastore）：程式碼用 The Stack 的 270 萬筆 Python（27GB）；對話用 UltraChat 約 77.4 萬則（12GB）。
  • 越大越快（表 2）：資料庫由 0.9GB→27GB，Mean Generated Length（M=生成長度/前向步數，即加速上界）由 1.96→2.65，加速由 1.83×→2.36×——顯示放大庫仍有進一步加速潛力。
  • greedy 採樣加速優於 nucleus（隨機性拖累）；n_max 只要 ≥6 加速就穩定，不需精調。

局限

  • 效果直接受資料庫的準確度與完整度左右；作者建議「用 LLM 自己生成的內容建庫」以更貼合模型輸出。
  • 缺乏 in-context 能力：如程式碼裡個人化的變數名這種依賴當前上下文的內容，純檢索難以命中。

對讀者的價值

  • ai_core §3.3 接點（把便宜端推到極致的另一條路）：FrugalGPT／級聯是「便宜模型先做、驗證沒過才升級到貴模型」；REST 更激進——連 draft 都不用模型，直接從資料庫撈匹配延續，近零成本、免訓練，是「成本梯度」最便宜端的一種極限形態（用確定性的檢索取代一次參數化推論）。
  • 呼應「固化引擎」（§3.6）：REST 的精神就是「把反覆出現的常見延續存進庫、直接復用」——與 ai_core 想把「LLM 反覆處理的案例結晶成確定性資產」同構；差別在 REST 結晶的是 token 級延續、且用大模型逐位驗證保證無損，可視為固化 + 廉價猜測 + 便宜驗證在解碼層的一個乾淨範例。
  • 可直接借用的形狀：精確匹配（suffix array）+ 頻率加權（Trie）選候選 + 大模型單次驗證接受——把「檢索猜測」與「權威驗證」解耦，猜錯零成本、猜對大幅省算；對「先查快取／規則猜、猜不中才動用貴智能」的可靠函數設計是很好的縮影。
  • 庫內對照：可與 2305.05176 FrugalGPT 並讀——同屬 I 類成本控制，FrugalGPT 在「請求層」用 scorer+閾值級聯選模型，REST 在「token 層」用檢索取代 draft 模型；一個換模型、一個換 draft 來源。
