對讀者的價值

  • 主題 3（工具創建與工具使用 agent）的評測端：ai_core 主張把 LLM 呼叫包成可靠函數、逐步剃除 LLM 依賴（§2 工廠/消費者），要做到這件事就必須先能量測「什麼時候值得用 LLM、什麼時候該轉交確定性工具」這個判斷力——API-Bank 正是為此設計的評測基準：它把「會不會呼叫」「該不該檢索」「能不能規劃多步」拆成三個獨立可測的能力層級，直接對應 ai_core §3.4「治理＝拒絕為預設（該不該呼叫工具本身就是一種准入決策）」的量化需求。
  • 與已入庫論文的分工對照：本篇不提出新方法，而是提供度量尺。已入庫的 Toolformer（2302.04761，自監督學「何時呼叫」）、Gorilla（2305.15334，微調小模型精準產生 API 呼叫、以 AST 子樹匹配判幻覺）、ReAct（2210.03629，推理與行動交錯的執行迴圈）、ToolDoc（2308.00675，用工具文件取代示範）分別是「學習/設計何時呼叫、如何呼叫」的方法論文；API-Bank 則是可以拿來驗證這些方法是否真的學到「正確的准入判斷」的獨立基準。同批候選中的 ToolLLM（2307.16789）與 ToolAlpaca（2306.05301）走的是同一路線（大規模工具資料/語料蒸餾），但尚未入庫，故僅提路線不加連結。
  • 明確區分「准入判斷錯誤」與「參數格式錯誤」：API-Bank 的錯誤分類法本身就是這種區分的具體化——No API Call（該呼叫卻沒呼叫，Alpaca 頭號錯誤 36.77%）、API Hallucination（呼叫了不存在/不對的 API，等於誤判了「這個工具存在且該用」，Lynx 頭號錯誤 61.38%）、Failed API Retrieval（准入前置的檢索關卡本身失敗，GPT-4 頭號錯誤 67.86%）三者，都屬於「該不該呼叫、呼叫誰」層級的准入判斷錯誤；而 Invalid/Missing Input Parameters、False API Call Format、Has Exception 則是呼叫決定正確之後的參數/格式層錯誤，性質完全不同。三個代表性模型（Alpaca/Lynx/GPT-4）的頭號錯誤全部落在准入判斷這一層而非格式層，直接支持 ai_core「治理閘門比執行細節更關鍵、更難做對」的判斷，也給出了具體可拿來對照評測「必要性閘」設計優劣的量化基準。
