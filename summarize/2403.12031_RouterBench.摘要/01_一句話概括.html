一句話概括

RouterBench：針對「LLM 路由器（router）」提出第一個標準化評測框架——用 11 個模型 × 8 個資料集（含 RAG）共 405,467 筆已產生的推論結果做成離線資料集（免重複呼叫 API 即可測任何路由策略），並用一套「非遞減凸包（non-decreasing convex hull, NDCH）＋單一標量指標 AIQ（Average Improvement in Quality）」的數學框架，把任何路由系統在美元成本 × 品質平面上的非參數化散點壓縮成可跨系統比較的一個數字，藉此揭露：多數既有路由器離「理論最佳（Oracle）」還有相當大的差距。

解決什麼問題

LLM 路由（依 query 動態選派最合適的模型）近年已有 FrugalGPT、Tryage、meta-model 等多種方案，各自宣稱能省成本、提性能，但沒有共通的評測協定——不同論文用不同資料集、不同基線、不同「省了多少/掉了多少」的算法，彼此無法比較，也難以判斷一個路由器到底做得「好不好」（相對於什麼上界？）。RouterBench 要解決的正是這個「路由器評測標準缺失」的問題：既提供可重複使用的離線資料，也提供一套能把任意路由系統（無論是否為機率性、無論參數化與否）化約成單一數字的數學工具。

核心方法

  • 資料集規模：405,467 筆樣本，涵蓋 11 個模型（開源：Llama-70B-chat、Mixtral-8x7B-chat、Yi-34B-chat、Code Llama-34B、Mistral-7B-chat、WizardLM-13B；閉源：GPT-4、GPT-3.5-turbo、Claude-instant-v1、Claude-v1、Claude-v2）× 8 個資料集（MMLU、HellaSwag、GSM8K、ARC-Challenge、Winogrande、MBPP、MT-Bench，另加一組 800 題、含真值答案的 RAG 資料集，額外用 You.com API、sonar-small/medium-online 3 個具檢索能力模型測試），共 64 個子任務。每筆樣本記錄 prompt、模型回覆、正確性/品質分數、以及以真實 API 定價（開源模型以 Together AI 計價）算出的美元成本。
  • 數學框架：把每個 （router, 參數 θ） 對應到 cost-quality (c, q) 平面上一點；用「線性內插（混合兩個路由器＝以機率 t 擲骰選其一）」與「外插（用重複生成等零收益手段把成本墊高、或內插到零成本零品質的 null router）」，讓任意一組路由系統的散點凝聚成非遞減凸包（NDCH）——即在成本域 [c_min, c_max] 上「同成本下最佳可達品質」的一條分段線性曲線。
  • AIQ 指標：AIQ(R) = 1/(c_max − c_min) · ∫ R_dc(c) dc（NDCH 曲線在共同成本區間上的歸一化曲線下面積），把「一個路由系統整體有多划算」壓成單一標量，可跨路由器、跨資料集比較。
  • 兩個基準路由器：Zero router（純靠靜態 LLM 集合的凸包做機率混合，不看 query 內容，是「顯著性」下限——路由器只有優於它才算有意義）；Oracle（每題永遠選「答對且最便宜」的模型，是理論上界）。
  • 評測的路由器類型：(1) 預測式路由器（Predictive）——KNN、MLP，用嵌入預測各模型的 performance_score = α·P − cost（α 即「願付價格 willingness-to-pay, WTP」，決定成本-品質取捨的旋鈕），70/30 切分訓練測試；(2) 非預測式路由器（Non-predictive）——級聯（cascading）路由器，依便宜到貴的模型序列逐一嘗試，用一個含誤差率參數的評分函式（judge）判斷是否達標即回傳、否則升級到下一個模型，並設有總成本上限 T；另有 overgenerate-and-rerank（生成全部候選再選最優，成本過高僅作示範）。

結果

  • Oracle：以低成本逼近近乎完美的準確率；意外的是 GPT-4 極少被 Oracle 選中——多數題目只要用 WizardLM-13B、Mistral-7B 等便宜模型就能答對，凸顯「便宜模型答對時何必用貴模型」的路由潛力；同等表現的模型服務，美元成本可相差 2–5 倍。
  • 預測式路由器（KNN/MLP）：能達到「最佳單一 LLM 的水準、且成本相同或更低」，但多數任務下沒有顯著超越 Zero router 基線——僅 MMLU、Winogrande 上 AIQ 較高，HellaSwag、GSM8K 打平，ARC-Challenge、MBPP 反而較差。Oracle 則穩定大幅超越所有路由器與單一模型，顯示路由演算法仍有很大進步空間。
  • 級聯路由器：judge 誤差率愈低，總成本預算愈高時表現愈接近 Oracle；誤差率 ≤0.1 時明顯優於 Zero router，但誤差率超過 0.2 後性能迅速崩壞——揭示級聯路由的可用性高度依賴「評分函式/judge 的準確度」，而非只靠加大成本上限。
  • RAG 資料集：所有測試路由器都顯著優於 Zero router；分析顯示路由器能抓住查詢中的時效性線索（如「2024」）並路由到具連網檢索能力的模型（sonar-online 系列），時效不敏感問題則路由到 GPT-4/GPT-3.5，呼應「複合式 AI 系統（Compound AI Systems）」場景中路由的實用性。

局限

  • 目前只涵蓋「效能 × 美元成本」兩維，未納入延遲、吞吐量等生產環境常見指標。
  • 只評測了預測式（KNN/MLP）與級聯兩類路由器，其他更進階的路由設計（如強化學習式、meta-model）未涵蓋；RAG 情境僅測「自帶檢索能力的模型」，未涉及「檢索器＋LLM」兩階段路由。
  • 現有 7 個核心資料集（不含 RAG）覆蓋常見任務，但缺少長尾／領域特定任務（如低資源語言翻譯）；模型與任務清單會隨時間過時，需持續擴充。

對讀者的價值

  • 本篇是主題 2（LLM 成本優化／路由）的評測與量尺端，而非新路由方法。庫中已有 2406.18665 RouteLLM、2404.14618 HybridLLM、2407.10834 MetaLLM（三者皆屬「進門即分流」的路由式）、2305.05176 FrugalGPT、2307.02764 Cascade Deferral（貝氏最優延後規則）、2310.12963 AutoMix（POMDP 路由＋自我驗證）、2006.07512 FrugalML（MLaaS 加值服務路由）——這些論文各自用不同資料集、不同基線、不同「省了多少/掉了多少」的算法宣稱效果，彼此難以直接比較。RouterBench 的 NDCH + AIQ + WTP-α 框架，正是 ai_core §3.3 成本梯度若要落地成「可公平比較的量尺」所需要的協定：任何路由/級聯設計（不論 ai_core 最終挑哪一種）都能先轉成 (cost, quality) 散點、取 NDCH、算 AIQ，再跟 Zero router（靜態混合基線）與 Oracle（理論上界）對照，才知道「這個路由器到底值不值得上」。
  • 對 ai_core 期望管理最關鍵的發現：Oracle 揭示的理論上界極高（多數任務便宜模型就能答對，GPT-4 罕被選中），但實際可訓練出來的預測式路由器（KNN/MLP）在多數任務上並未顯著超越最簡單的「靜態成本-品質混合」基線 Zero router，只有級聯路由在 judge 誤差率夠低（≤0.1）時才明顯逼近 Oracle。這意味著 ai_core 規劃 §3.3 成本梯度／§2 工廠-消費者的降級策略時，不該預設「訓練一個路由器就能拿到 Oracle 級的省錢效果」；真正的收益上限取決於能否做出低誤差的升級判準（judge/scorer）——這正呼應 Cascade Deferral 的「貝氏最優延後規則」與 §3.4 憑證准入（用可靠的確定性/校準訊號決定要不要升級，而非只看單一模型信心）的必要性。若判準做不好，路由器很可能只是比「不分流、固定用一顆便宜模型混一顆貴模型」聰明一點點，而非接近理論上限。
