論文／訪談原始來源

《Don't Ask the LLM to Track Freshness：記憶衝突解決的確定性配方》重點摘要

一句話概括

不要叫 LLM 追蹤新鮮度：在 MemoryAgentBench (MAB) FactConsolidation 任務上，把 LLM 自由文本判斷（decode-and-answer）換成「結構化候選提取 + Python max(serial)」的確定性管線，gpt-4o-mini 單跳 +10.8pp（67.2→78.0）、多跳 30.2%（vs 已發表最佳 7%）、gpt-4o 單跳 94.8%。差距隨上下文長度擴大（6K +8pp → 262K +21pp）。瓶頸在組裝（post-retrieval aggregation），不在儲存架構（graph/hippocampal/agentic）。

解決什麼問題

LLM 記憶系統在衝突解決（同一事實多個矛盾值選哪個）上系統性失敗。MAB FactConsolidation 任務把事實編號、反事實版本有更大序號、並明確告訴 agent「較新事實序號較大」，但已發表的 22 個系統全數表現不佳：HippoRAG-v2 54%、BM25 48%、Mem0/Contriever 18%、Zep/Graphiti（專為時間性記憶設計的時間知識圖譜）僅 7%，多跳變體全數 ≤7%。問題不在儲存——在於這些系統把衝突解決交給 LLM 判斷（檢索/更新/答案生成），而非顯式的版本感知聚合。

核心方法

SH-conflict 管線（單跳，~50 行 Python）

  1. 檢索：BM25 TOP_K=10，事實級切片（每條事實獨立索引，保留序號為索引鍵）
  2. 候選提取：LLM 用結構化 prompt 提取語意匹配的候選（僅提取，不比較序號、不選最佳），輸出 JSON [{serial, text, entity}]
  3. 新鮮度揀選：max(candidates, key=lambda c: c.serial).entity（確定性 Python，精確、免費、可審計）
  4. 若無候選→返回 "no answer"（校準棄權，非幻覺）

CAR 管線（Chain-Aware Resolution，多跳）

  1. 分解：LLM 將多跳問題分解為原子 hop 鏈（HARD_CONSTRAINT：每 hop 不超過一個關係詞）
  2. 逐跳執行：每 hop 代入前跳答案後執行 SH-conflict
  3. 最終答案：最後一跳的答案；任一跳無答案則中斷返回 "no answer"

關鍵設計決策

  • 事實級切片（vs 既有的 chunk-512/4096）：每條事實獨立索引，序號保留為索引鍵，避免多序號擠在同一 chunk 迫使 LLM 做 chunk 內新鮮度推理
  • LLM 角色窄化：只做語意候選提取（擅長），不做新鮮度比較（不擅長）
  • 確定性聚合：Python max() 消除兩個 LLM 失敗模式——(1) prior-override（訓練先驗蓋過上下文規則）、(2) serial-comparison drift（候選池變大時追丟最大序號）

結果

LLM-judgment baseline gpt-4o-mini 67.2 —
HippoRAG-v2（最佳已發表） gpt-4o-mini 54.0 5.0
Zep/Graphiti（時間 KG） gpt-4o-mini 7.0 3.0
  • 差距隨上下文擴大：LLM-judgment baseline 在 64K→262K 暴跌 14pp（75→61），確定性管線不降（82@262K）
  • gpt-4o + CAR 多跳 51.5%：vs 已發表最佳 7%，+44.5pp
  • o4-mini 單跳 96.5%：單跳衝突解決實質上已被推理骨幹解決
  • 方法互補性：88.5% 題目至少一管線可解（軟天花板）；21.3% Python-only、10.5% LLM-only（嚴格提取過度拒絕的 case）
  • 跨基準泛化（LongMemEval）：max(serial)→max(timestamp) 移植成功，但整體僅平手（57.8 vs 64.4, n=45）；失敗全在非新鮮度題型（Yes/No/歷史/聚合），max() 是正確算子但需組合題型感知處理
  • 成本：gpt-4o-mini ~$0.0001/查詢，gpt-4o ~$0.005/查詢（50× 成本換 17pp）

局限

  • 主要評測僅 MAB FactConsolidation 一個基準（MQUAKE 衍生反事實，未必反映真實衝突模式）
  • 跨基準檢查 n=45、CIs 寬、單一題型
  • 需顯式版本標記（序號/時間戳）；無法處理偏序或因果依賴更新
  • 匹配比較變動超過 resolver 本身（prompt 格式、輸出格式、溫度均不同）——+10.8pp 是管線級效果，非嚴格隔離的 resolver 貢獻
  • 嚴格提取有召回代價：~10% 題目被過度拒絕，LLM-judgment baseline 反而答對
  • 多跳 30.2% 遠未解決（多數失敗在 hop-1 候選提取錯誤→級聯失敗）

對讀者的價值

  • §2 工廠/消費者的直接實例：LLM 是「工廠」（產候選），確定性程式是「消費者」（揀最新）——這是 ai_core 架構的核心分工模式。本論文以實證量化了這個分工的收益（+10.8pp 平均、+21pp 長上下文），提供了「把 LLM 判斷換成確定性程式」的乾淨基準證據
  • §3.6 LLM→確定性程式退化的具體路徑：當版本標記存在時，新鮮度比較可從 LLM prompt 中完全移除、退化為 max(serial) 一行程式碼。本論文給出了退化條件（顯式全序標記）、退化收益量化（+10.8～+21pp）、以及退化邊界（非當前值查詢需組合題型感知處理）
  • 對任何用 LLM 做「選最新/選最大/選最優」的管線都是必讀：本論文證明即使 prompt 明確寫了規則，LLM 仍會被訓練先驗覆蓋（prior-override）且隨候選池增大而漂移（serial-comparison drift），這兩個失敗模式是系統性的、不是 prompt engineering 能解決的
  • 與 2604.05150 Compiled AI（LLM workflow→確定性 Python）對讀：Compiled AI 是「覆蓋後整段換成程式碼」，本論文是「只換掉 LLM 不擅長的新鮮度比較子步驟」——兩者是同一退化光譜上的不同粒度
  • 與 2511.15715 Graph-Memoized Reasoning（子圖 memoization）並讀：本論文的確定性 max() 是最簡單的 memoization 形式（「最新=正確」規則被固化為程式碼），Graph-Memoized 是更一般的形式化框架
