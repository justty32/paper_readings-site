論文／訪談原始來源

《CodeSpear：語法約束解碼如何越獄 LLM 使其生成惡意程式碼》重點摘要

一句話概括

Grammar-Constrained Decoding（GCD）本為提升程式碼生成可靠性而設計——約束 LLM 只產出語法合法的程式碼——但這個中性的可靠性機制本身即為攻擊面：當 LLM 收到惡意請求時，套用標準 code grammar 會壓制自然語言拒絕回應（因自然語言不在合法輸出空間內），迫使模型在從未受過安全對齊訓練的 code modality 中繼續生成，導致其產出惡意程式碼（CodeSpear 攻擊）。為此提出 CodeShield：在 code modality 中訓練模型生成蜜罐程式碼——語意無害且結構多樣的程式碼——使安全行為不被固定語法模式綁定，難以透過收緊 grammar 移除。

解決什麼問題

現有 LLM 安全對齊幾乎完全立足於自然語言模態：教模型「I cannot assist with that」之類的拒絕語句，隱含假設推論時自然語言永遠可用。但 GCD 破壞此假設——一旦 code grammar 生效，R_refuse ∩ L(G) 即為空集合，模型學到的拒絕行為完全無從表達。這個漏洞嚴重且實務上廣泛：GCD 已被 vLLM、SGLang 等主流框架內建支援，OpenAI 與 Fireworks AI 等商業 API 也暴露 GCD 介面。更關鍵的是，CodeSpear 不需對抗性 grammar（普通 Python/C++/Java 語法即可）、不需梯度優化或 prompt 工程、攻擊成本近乎零（僅呼叫現有 GCD 介面）。

核心方法

CodeSpear（攻擊）

原則極簡：給定惡意 prompt p 與普通 code grammar G，以標準 GCD 介面取樣。GCD 將合法輸出空間從 V* 限制為 L(G)，自然語言拒絕因無效而被排除，模型被迫在 code modality 中繼續生成，產出可能實現惡意請求的語法合法程式碼。算法僅六行：初始化前綴 → 每步計算合法 token 集合 → 取樣 → 附加 → 遇 EOS 停止。無需對抗性 grammar、梯度優化、或 prompt 工程。

CodeShield（防禦）

核心洞察：在 code modality 中的安全行為需滿足兩條件：語意無害（不實現惡意請求）且結構多樣（不固定於單一語法模式，使攻擊者無法透過收緊 grammar 移除）。解法是訓練模型產生蜜罐程式碼——從通用語料庫 OpenCodeInstruct 隨機取樣的無害程式碼片段，語意與惡意請求無關且結構多樣。

具體以 DPO 實作，建構三層偏好階層：

  1. y_refuse ≻ y_honeypot（自然語言可用時，拒絕仍最優先）
  2. y_honeypot ≻ y_harmful（GCD 生效時，寧產蜜罐程式碼也不產惡意碼）

偏好資料建構：

  • y_refuse：取自既有安全對齊資料
  • y_harmful：以 GCD 查詢目標模型收集
  • y_honeypot：從 OpenCodeInstruct 抽取 K 個無關片段

以 2,000 筆惡意 prompt 訓練（744 筆種子經 DeepSeek-V4-Pro 擴增）。

結果

RQ1 本地部署 LLM（5 模型 × 2 benchmark）：CodeSpear 平均 ASR 從 54.92%→81.82%（+26.90pp）、MR 從 36.61%→54.58%（+17.98pp），顯著超越所有基線（含 PAIR、CodeJailbreaker、APT）。通用越獄攻擊對惡意程式碼生成效果不佳——僅 CodeSpear 與專為程式碼設計的 CodeJailbreaker 在 ASR/MR 皆正向增益。

RQ2 API 商業模型（5 模型含 GPT-5/MiniMax-M2.7）：CodeSpear 仍有效，平均 ASR 從 22.00%→67.39%（+45.39pp）、MR 從 11.04%→36.62%（+25.59pp）。GPT-5 與 GPT-5-mini 傾向在 GCD 下生成 pass 作為拒絕，但收緊 grammar 禁止 pass 後 ASR 進一步升高（55.49%→70.30%），證明固定語法模式的安全行為本質脆弱。

RQ3 CodeShield 防禦（3 模型）：在 GCD 下，CodeShield 將平均 ASR 從 83.11%→5.57%、MR 從 54.12%→2.78%（Qwen2.5-Coder-7B）。無 GCD 時亦進一步強化安全。Safe-DPO（僅對齊自然語言拒絕、無蜜罐碼）在無 GCD 時接近 CodeShield，但 GCD 生效後幾無作用（ASR 77.39% vs CodeShield 5.57%），證實 code-modality 對齊的必要性。

RQ4 良效保留：CodeShield 對 HumanEval/MBPP pass@k 影響輕微（Qwen2.5-Coder-7B MBPP pass@3：78.00%→77.00%），部分模型甚至上升（因安全訓練中混入通用程式碼任務）。

RQ5 敏感度分析：CodeSpear 在 Python/C++/Java 三種 grammar 皆有效；CodeShield 隨蜜罐碼數量 K 增加安全提升而良效持平。

自適應攻擊：攻擊者知曉蜜罐機制並以 LLM 代理迭代收緊 grammar（最多 10 輪），CodeShield 仍穩健——ASR/MR 上升極微，歸因於蜜罐碼結構多樣性使攻擊者無法在不排除惡意碼所需結構的前提下壓制安全行為。

局限

  • GCD 實作細節（不同推理引擎/API）可能影響絕對攻擊成功率。
  • 評測涵蓋 RMCBench（10 類惡意場景）+ MalwareBench（6 類），但無法窮盡所有惡意碼生成場景。
  • 僅以 DPO 驗證 code-modality 對齊，未探索其他對齊演算法（RLHF 等）的可能性。
  • 蜜罐碼來源（OpenCodeInstruct）的品質與覆蓋率影響對齊效果。

對讀者的價值

  • 直接命中 ai_core §3.4 治理憑證的核心兩難：CodeSpear 展示了當輸出空間被外部約束（grammar）重塑後，原本的「安全憑證」（自然語言拒絕）瞬間失效——這正是 §3.4 討論的「憑證只在特定輸出空間有效」的具體攻擊案例。CodeShield 的回應方式是在 code modality 中重新建立安全偏好階層（y_honeypot ≻ y_harmful），這對應於 §3.4 的「憑證必須依輸出空間條件化」原則。
  • §5「約束對齊的安全維度」的直接實證：此工作證明約束器（grammar）不僅影響功能正確性（2606.21619 的 97% 倒退），更創造全新的安全攻擊面。CodeShield 的「蜜罐碼 ≡ 結構多樣的無害輸出」思路，實質上是在約束空間內重新定義"安全輸出"的邊界——不是消極拒絕，而是積極產出無害替代品，這與 §5 討論的「約束器與安全對齊的交互作用」直接對接。
  • §3.4 的 modality 隔離風險：安全對齊局限於 NL modality 而 GCD 切換至 code modality，本質上是治理憑證的模態轉移失效。這與 ai_core 討論的「工具呼叫從文字規劃轉至 API 呼叫時的憑證斷裂」同構：模態邊界就是憑證失效邊界。CodeShield 的解法（在目標模態中直接對齊）是通用原則：每個模態獨立需要安全憑證。
  • 蜜罐碼概念的治理隱喻：蜜罐碼「語意無害＋結構多樣」的雙條件，對應於 ai_core 治理架構中「安全輸出」的形式化定義：不僅要否定惡意意圖（無害），還需確保無法被低成本繞過（多樣）。這為 §3.4 的「可繞過性評估」提供了具體的度量思路。
