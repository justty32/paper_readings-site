論文／訪談原始來源

Skill Dreaming: Evolving Repository Skills through Pull Request Streams 重點摘要

一句話概括

Skill Dreaming 從歷史 PR、程式差異、review 與驗證結果提煉 repo 專用 skills，再依版本、依賴與取代關係持續更新，讓固定權重 coding agent 重用有效慣例、避免舊技能無限制堆積；改善伴隨更多 token 與稍長執行時間。

解決什麼問題

Repo 的 API、檔案結構與維護要求持續改變。只檢索過去 PR，或把每次成功經驗永久附加成 skill，可能重用過期實作、忽略相關測試與文件。本文把 PR 記錄建構、技能萃取、關係管理與後續實作連成循環，目標是保存工程知識而不是更新 LLM 權重。（§1、§3～4）

核心方法

  • 先建可驗證 PR records：依功能與程式重疊檢索既有 PR，也可把歷史 commits 切成相關變更；分類為 usable、repairable、outdated、irrelevant、unsafe。對可修復內容做修補，或合成替代實作及測試，再以執行、測試、review／CI 等資訊驗證。成功記錄提供可重用做法，失敗記錄提供負面限制與修復策略。（§4.1）
  • 萃取有來源與版本的技能：固定權重 writer 將記錄寫成何時適用、如何實作、如何驗證的 skill，保留支持 PR 與 repo 版本。技能涵蓋 PR detection／construction、feature implementation、maintenance completion 與 skill evolution；內容不只核心程式，也包括測試、文件、設定、相容性等義務。（§4.2）
  • 明確處理關係與淘汰：新資訊與既有技能依觸發條件、程序、元件與版本相容性對齊，採 Add、Update、Specialize、Extend、Conflict、Supersede、Keep。取代舊程序時保留歷史與來源，只有 active skills 可被檢索；不是一律重寫或一律追加。（§4.3～4.4、表 2）
  • 用技能引導實作與回饋：actor 檢索適用 skills，以指令方式注入，再產生功能、跨檔案變更與維護內容；失敗可在預算內修復及重驗，結果寫回技能演化記錄。論文以成功機率減成本的序列目標描述此流程，但明說是分階段近似，不保證全域最優或式中期望可靠性。（§3、式 3～6、§4.4、算法 1）

重要評估邊界：方法的理想循環可把接受的 PR 合入下一個 repo；歷史評估卻是每題回到該題記錄的 base commit，只有技能庫跨題演化，不把 agent 生成的 repo 變更串成下一題的程式庫。所以此實驗與真實長期運作、自己改過的 repo 再影響後續任務，並非同一件事。（§3、式 2 後說明）

結果

依表列比例計算，前兩項增加九個百分點，Sonnet 增加兩個百分點，不能解讀成相對增加 9% 或 2%。作者未報 Sonnet 的 Pro 結果，理由是該模型基線表現較弱。（作者自報，§6.1、表 3）

在 Verified 的 Opus 比較，full method 的 Maintenance Surface F1 為 0.74，Base 為 0.62，append-only 為 0.72；full method 的 Safe Rate 與 Existing historical-test pass rate 均為 1.00。（作者自報，表 4）

指標不是可互換的「正確性」

作者分開定義 official resolved rate、各自實驗設定下的 Task Success（TS）、Safe Rate 與 Maintenance Surface F1。Safe Rate 要求符合式 6 的檢查及有效、非空的測試執行，但不保證功能完成。Surface F1 比較「要求修改」與「實際修改」的類別集合，涵蓋 code、tests、docs、config、examples、changelog；它測類別覆蓋及精確度，不驗證每個修改本身是否正確，logging 與 compatibility 也未分開評估。因此 Safe Rate 1.00 或較高 Surface F1 都不是形式安全證明。（§5.2、式 9）

跨 repo 與演化：仍使用各 repo 的歷史

作者在 Click、Black、Rich、HTTPX、Arrow、Agents 六個 repositories，先把各自歷史 PR 分成 skill-construction 與 evaluation sets，再由空技能池建立該 repo 的技能。六者 TS 均高於 Base，增幅介於 0.07～0.20，Surface F1 也改善。這展示在不同 repo 上適配的方法，不是把某一 repo 的技能零樣本直接移植到未知 repo。（作者自報，§6.2、表 5）

連續技能演化實驗在 Pro headline setting，以 500 個歷史 PR 初始化，每階段再加 50 個，直到 1000 個。作者報告 TS、resolved rate、Surface F1 整體上升但有波動，沒有聲稱每一步都單調改進。（作者自報，§6.5、圖 2）

關係管理與成本

在 Skill Filtering 設定，full method 的 TS 為 0.93，append-only 為 0.89；在 Hybrid Retrieval 設定，full 為 0.94，append-only 為 0.89。作者據此支持版本有效性、過期與 supersession 管理的作用。這些是各消融設定下的 TS，不應替代官方 resolved rate。（作者自報，§6.4、表 10）

局限

作者明載的界線：LLM 權重固定，演化的是技能內容與其關係。式中的安全及成功機率是期望可靠性要求，不是由現有測試推出的保證；分階段流程也不保證全域最優。歷史評估不串接生成的 repo 變更；Safe Rate 不保證新功能完成，Surface F1 不保證單項修改正確。（§3、§5.2）

本檔補註，非作者自陳：主文沒有清楚列出 headline 評估子集的總題數、重複種子、信賴區間及配對顯著性分析，因此不宜把表中差值當作已隔離混雜因素的長期因果效果。表 7 的 1000 個 Ansible PR 是 PR 品質分類資料，不是 headline resolved rate 的分母；圖 2 的歷史 PR 累積量也不是解題樣本數。不同表的 TS、候選選擇與資料來源設定不能直接串成同一條成功率曲線。更長期的技能污染、錯誤累積與真實 repo 連續演變，仍需另行驗證。

對讀者的價值・接點

本檔補註，非作者自陳：對 repo agent 的記憶與治理，最有用的是把技能視為有來源、適用版本、依賴與 supersession 的工程資產。應同時驗收功能完成、舊測試、維護類別與成本，並用固定歷史 base 的回放和真正串接變更的長期測試，分別回答技能重用與系統自我演化的效果。
