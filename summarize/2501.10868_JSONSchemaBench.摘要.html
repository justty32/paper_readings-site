論文／訪談原始來源

《從語言模型生成結構化輸出：基準與研究（JSONSchemaBench）》重點摘要

一句話概括

JSONSchemaBench：用 10K 條真實世界 JSON Schema（分 10 個難度／領域各異的子集）作為基準，對 Guidance、Outlines、XGrammar、llama.cpp、OpenAI、Gemini 六個「受約束解碼（constrained decoding）」框架，沿效率（efficiency）、覆蓋率（coverage）、品質（quality） 三軸做系統化評測——填補了「受約束解碼被廣泛採用卻沒有橫向比較」的空白；核心結論是受約束解碼不但不拖慢反而能加速生成、還能提升下游任務準確率，且六個引擎在真實 schema 上的可靠度差距巨大（最好的引擎支援的 schema 數是最差的兩倍）。

解決什麼問題

LLM 越來越多被用在輸出「給機器讀」的場景（工具呼叫、資料抽取、web 導航），輸出必須嚴格符合預定格式。受約束解碼（在每步 decode 時把不合語法的 token 遮罩掉）已成主流技術，並以 JSON Schema 為事實標準規格語言。但實務上有三個一直沒被系統回答的問題：Q1 效率——約束會拖慢還是加速生成？誰最快？Q2 覆蓋率——JSON Schema 特性龐雜且持續演進，各框架到底支援多少？Q3 品質——約束保證了結構，會不會反而傷害輸出的語意品質？既有評測要嘛只針對單一任務、要嘛用「人造形式文法」設定，與真實用例關聯不明。

核心方法

  • 基準（§3）：以 Baazizi 等人從 GitHub 收集的 6K schema 為底，再納入 JSON Schema Store、GlaiveAI 函數呼叫資料集、Kubernetes 設定、Snowplow、Washington Post 等來源，過濾非法 schema 並依 $schema 標準化版本，最終 9558 條，分 10 個子集（GlaiveAI 函數簽名、Kubernetes API、Github 依欄位數分 Trivial/Easy/Medium/Hard/Ultra 等）。
  • 效率（§4）：拆成三指標——GCT（文法編譯時間）、TTFT（首 token 時間）、TPOT（每 token 時間）。關鍵在消除覆蓋率偏差：只在「所有引擎都能處理的交集實例」上算指標，避免低覆蓋率引擎因只吃簡單 schema 而被高估。
  • 覆蓋率（§5）：定義三層——Declared（宣稱：不報錯即算）、Empirical（實測：實際生成出的輸出通過 schema 驗證）、True（真值：約束與 schema 語義完全等價，實務不可測）；並導出 Compliance Rate = Empirical / Declared（框架接受 schema 後真能保證合規的可靠度）。另以官方 JSON Schema Test Suite（45 類特性、正例須生成／反例須阻擋）做互補評測，區分 over-constrained（過嚴，擋掉合法輸出） 與 under-constrained（過鬆，放行非法輸出） 兩種失敗。
  • 品質（§6）：沿用並擴充 Tam 等人與 Will Kurt 的三個推理任務（Last Letter、Shuffle Objects、GSM8K），輸出統一為 {"reasoning":…, "answer":…} 的 JSON，比較受約束 vs 無約束的任務準確率。

結果

  • 效率：受約束解碼相對無約束最多可加速 50%。Guidance 的 TPOT 最佳（靠 guidance acceleration 跳過某些生成步），GCT 幾近 0；Outlines 因把 schema 轉成正則，編譯時間顯著偏高（Table 2 中 GCT 達 3–8 秒）。
  • 覆蓋率：Guidance 在 8 個資料集中的 6 個實測覆蓋率最高，且在所有資料集中 Compliance Rate 最高（最可靠）；閉源引擎（OpenAI/Gemini）覆蓋率最低但合規率近 1.0（採保守策略，只實作能穩定支援的子集）。最好的框架支援的 schema 數約為最差的兩倍。 Test Suite 上 Guidance 在 13 類達 100% 覆蓋、19 類單獨最佳；XGrammar 編譯錯誤最少但 under-constrained 失敗最多（偏寬鬆的取捨）。
  • 品質：所有框架、所有任務都優於無約束；Guidance 全面最佳，每個任務約比 LM-only 高 3%（GSM8K 80.1%→83.8%，Last Letters 50.7%→54.0%），可能得益於其 token-healing。下游任務最多提升 4%，即便像 GSM8k 這種結構極簡的任務也受益。

局限

  • 開源引擎（跑 Llama-3.2-1B）與閉源 OpenAI/Gemini（專有模型）的實測覆蓋率不可直接比較，因底層模型不同。
  • Empirical Coverage 受所用 LM 與取樣方法影響，非框架能力的純淨度量；True Coverage 因 JSON 實例無限多而無法實測。
  • Test Suite 表現與真實 schema 覆蓋率無直接對應——特性在真實 schema 中出現頻率不均，且 under-constrain 等於把責任丟回給 LM（LM 可能碰巧生出合法輸出）。

對讀者的價值

  • 直接對應 ai_core §5「受約束填碼」的選型基準：ai_core 把程式碼助手拆成「上層結構化抽取生資產／下層受約束填碼」，而本篇正是「下層填碼要用哪個引擎才可靠」的實證答案。結論很明確：在真實 schema 上 Guidance 於效率、覆蓋率、品質三軸皆領先且最可靠，XGrammar 偏寬鬆（under-constrained）、Outlines 編譯慢且硬 schema 覆蓋率低、閉源 API 保守但支援面窄——這是把「LLM 呼叫包成可靠函數」時挑選約束引擎的一手依據。
  • 強化 ai_core 的核心信念：本篇證明受約束解碼不是效能稅而是淨收益（既加速又提準確率），這替「把 LLM 輸出約束成確定性可解析的資產」提供了經驗背書——與「貴稀有智能生資產、便宜高頻智能消費資產」的分工相容：用小模型（Llama-1B）＋強約束就能在函數簽名這類 schema 上達到高合規率。
  • 對接 §3.4 治理（拒絕為預設）與 §3.6 固化引擎：三層覆蓋率／Compliance Rate 的框架，本質上是一套「憑證准入」的量化語言——一個 schema 能否被引擎可靠保證，就是要不要放行 LLM 輸出的憑證。而 over/under-constrained 的區分，提醒「固化」時必須驗證約束與規格語義等價，否則過鬆的約束會把不可靠性偷渡進確定性節點。
  • 定位：基準 + 實證研究論文（歸 I 類），開源於 github.com/guidance-ai/jsonschemabench。適合做結構化生成、工具呼叫、受約束解碼引擎選型的人直接參考。
