論文／訪談原始來源

《LILO：透過壓縮與文件化程式碼學習可解讀的函式庫》重點摘要

一句話概括

LILO（Library Induction from Language Observations）：一個「搜尋→壓縮→文件化」三模組的神經符號迴圈——LLM 引導合成（快系統）＋枚舉搜尋（慢系統）解任務、Stitch 符號壓縮從解集中抽出最優 λ 抽象、AutoDoc 用指令微調 LLM 為匿名抽象補上名稱與 docstring——把「解過的案例」迭代結晶成有文件、可重用、對人與 LLM 都可讀的抽象函式庫；在 REGEX/CLEVR/LOGO 三領域全面勝過 DreamCoder 與 LLM-only 基線。

解決什麼問題

  • LLM 會寫碼但不會「經營代碼庫」：軟體開發的核心是重構——把程式碼整併成簡潔、可重用、可讀的函式庫，這是多目標最佳化。
  • DreamCoder 等經典函式庫學習法搜尋極貴（一個領域 >2 CPU-月），大量時間耗在重新發現人類已知的基本抽象；學到的庫是匿名 λ 演算、難以解讀。
  • 直接把符號壓縮出的匿名抽象（fn_42）餵給 LLM 反而降低解題率（REGEX −30.6）——等同程式碼混淆；抽象要能被 LLM 復用，必須自帶語義（名稱/docstring）。

核心方法

  • 雙系統搜尋：LLM（Codex）依「函式庫描述＋已解任務的描述–解配對＋目標描述」few-shot 生成候選程式（解析/類型/執行三重驗證）；再以辨識網路引導的枚舉搜尋補足語言推不出的領域結構。
  • Stitch 壓縮：把重構表述為語料壓縮（式 4），branch-and-bound 找最小描述長度抽象；比 DreamCoder 壓縮快 1000–10000 倍、單 CPU 數秒跑完 → 支撐每輪從 L0 深度重構整個函式庫、淘汰早期次優抽象。
  • AutoDoc：循序提示 gpt-3.5-turbo 依使用範例為每個抽象命名＋寫 docstring（JSON schema、零樣本）；命名循序級聯（vowel_regex → consonant → 子音替換），領域通用、極易移植。

結果

  • 線上合成測試平均解題率：REGEX 77.07（DreamCoder 43.93）、CLEVR 96.76（94.50）、LOGO 48.95（28.53）；對 LLM Solver 基線 +0.94/+8.09/+16.82。
  • AutoDoc 是解鎖鍵：無它時加壓縮反而 −30.6（REGEX）；加上後 +9.73 回正。
  • 離線合成（無語言、純枚舉）：LILO 的最終函式庫相對基礎 DSL 提升 +42.27/+63.43/+43.24，勝過 DreamCoder 庫與事後壓縮庫——庫本身即資產，不依賴 LLM 也能用。
  • 成本：一輪 LLM 合成 ≈ 48 CPU-小時枚舉搜尋，美元成本同數量級（每輪 $1.6–2.2）。
  • C.2 關鍵反面結果：GPT-4 做不了壓縮——壓縮率 ~1.0（Stitch 1.5–3.5x）、抽象僅 19% 語法有效。

局限

  • AutoDoc 會產生含糊/錯誤文件（LOGO 命名偏實作、循序「加倍下注」錯誤語義），既傷可解讀性也傷下游合成（LOGO 上 AutoDoc 增益 +0.00）；待引入自我一致性/驗證。
  • 實驗限於 λ 演算 DSL 的三個玩具級領域、合成語言描述為主；人類語言下效能有折損（但 LILO 最穩健）。
  • 延伸到 Python 等命令式語言仍是待解 PL 研究問題。

對讀者的價值

  • ai_core §3.6 固化引擎的完整範式參考：LILO 就是一部可運轉的固化引擎——「案例（已解任務）→ 符號壓縮抽出共享結構 → 文件化入庫 → 下輪消費」的閉環，且每輪深度重構、允許淘汰次優抽象；「離線合成」實驗更直接證明固化出的庫可脫離 LLM 獨立發揮（枚舉搜尋解題率大增），正是「逐步剃除 LLM 依賴」的實證。
  • §2 資產文件化治理的硬證據：匿名抽象＝混淆，REGEX −30.6 → AutoDoc 回正——資產必須自帶規格（命名/docstring），否則便宜消費者（LLM）用不動；且文件品質直接影響下游復用率（LOGO 語義錯誤 → 增益歸零）。入庫審查應把「文件正確性」當准入條件（呼應 §3.4 拒絕為預設）。
  • 分工啟示（§1 符號神經計算圖）：C.2 顯示 LLM 能合成、能文件化，但不能壓縮——找抽象這種需全語料形式推理的活要交給符號引擎。三部曲脈絡：DreamCoder 2006.08381 立 Wake-Sleep 框架、Stitch 2211.16605 解壓縮效率、LILO 補上 LLM 合成與 AutoDoc；C.1 的 LLM-vs-CPU 成本換算也呼應 §3.3 成本梯度。
