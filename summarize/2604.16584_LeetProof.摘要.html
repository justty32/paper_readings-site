論文／訪談原始來源

《LeetProof：以多模態驗證器實現認證程式合成》重點摘要

一句話概括

LeetProof：第一個建立在基礎性多模態驗證器（Velvet／Lean）上的 agentic 認證程式合成管線，把 vericoding 拆為規格生成→程式／不變量推斷→最後一哩證明三階段，每階段配上最有效的推理模式（隨機化屬性測試 PBT、SMT 自動化、互動式證明腳本），並以隨機化規格測試揭露既有 benchmark 中約 10% 的缺陷；在 50 題 LeetCode 命令式問題上，多模態管線比單模式 Lean baseline 多產出 65% 的完全認證解（28 vs 17），所有部分驗證程式經 Aristotle 證明全數正確。

解決什麼問題

  • vericoding 兩難：(a) 非正式意圖翻成精確形式規格極難，且規格可能太弱（允許錯誤實作）或太強（排除所有正確實作）;(b) 證明實作滿足規格也很難——兩個難題互相回饋，壞規格連累正確程式、弱證明策略讓好規格也無從驗證。
  • 驗證器碎片化：auto-active（Dafny、Verus：SMT 自動但表達力受限）與 interactive（Lean、Rocq：表達力強但手動成本高）各有各的工具鏈與 prompt 策略，難以提煉可跨驗證器重用的原則。
  • 既有 benchmark 規格有缺陷：作者發現 VERINA 與 CLEVER 各有約 8.5% 與 11.2% 的規格存在欠約束或錯誤（underspecified／incorrect postcondition），需要自動化規格品質檢查。

核心方法

LeetProof 建立在 Velvet（嵌入 Lean 的 Hoare 式命令式程式驗證器，基於 Loom 多模態框架）之上，管線分三階段：

3.1 規格合成（Specification Synthesis）

  • LLM 從自然語言生成 Lean 規格（前置條件 + 後置條件）＋約 10 個具體測試案例
  • 三道 PBT 檢查（每組測試案例）：(a) 輸入滿足前置條件；(b) 預期輸出滿足後置條件——抓規格太強；(c) 所有其他輸出不滿足後置條件——抓規格太弱（欠約束）
  • 唯一性檢查使用型別導向突變（Boolean 翻轉、數值擾動、集合增刪改）搜尋虛假滿足的輸出
  • 隨機化屬性測試遠比符號規格測試（Lahiri 的 SMT 式檢查）更適合 Lean——PBT 快、不需證明工程

3.2 程式與不變量合成（Program & Invariant Synthesis）

  • LLM 生成候選 Velvet 程式（命令式）、LLM 再推斷迴圈不變量
  • 程式與測試案例立即執行（#guard），PBT 隨機生成滿足前置條件的輸入並核驗後置條件
  • 不變量透過 VC 生成 + SMT 自動化 + PBT 反例搜尋 + LLM 評估迭代精煉
  • 關鍵分工：PBT 能駁回不正確的不變量，但不能證明夠強——那是下一階段的工作

3.3 證明合成與殘餘義務（Proof Synthesis & Residual Obligations）

  • prove_correct 命令觸發 Loom 生成 VC（驗證條件），每個 VC 是普通 Lean 定理
  • 先用 SMT（lean-auto/cvc5）+ 內建 tactic（grind、aesop）自動關閉
  • 殘餘 VC 交給 LLM-based prover agent（仿 Hilbert 分解技術，有 Mathlib 搜尋、可註冊輔助引理、遞迴分解子目標）
  • 極難者委託給 Aristotle（IMO 金級 AI prover）

測試基礎設施（Sec. 4）

  • 型別類 Mutatable：為每種基礎型別實作突變操作，支援 corpus-guided fuzzing
  • 存在量詞處理：利用 VC 中出現的不等式約束推導有限範圍，把存在量化轉為有界枚舉
  • Lean 元程式：透過 monad transformer（ExceptT + StateT）生成 Velvet 方法的測試 harness，在迴圈入口與每次迭代後插入不變量檢查

結果

規格評估（VERINA 188 題）

類別 數量 說明
等價 150 生成規格與參考規格邏輯等價
參考問題 16 benchmark 自身規格不一致（8.5%）
前置條件變體 14 有效語義擴展
模稜兩可 3 語意模糊導致多種合理詮釋
過度約束 2 為保證確定性而加入未聲明約束
錯誤 3 真正偏離問題語意（1.6%）
  • 語義正確率 97.4%（扣除 benchmark 自身缺陷後）
  • PBT 在 LLM judge 通過後再攔截 2 個錯誤規格

合成評估（50 題 LeetCode 命令式 benchmark，GPT-5.2，每題 $5）

結果 Velvet（多模態） Lean（單模式）
完全證明 28 17
部分證明 + Aristotle 可關閉 18 23
部分證明 + Aristotle 失敗 0 7
合成失敗 4 3
  • Velvet 比單模式 Lean 多 65% 完全認證解（28 vs 17）
  • 所有 18 個 Velvet 部分證明經 Aristotle 全數關閉——即管線合成的程式與不變量全部正確
  • 跨 LLM 後端（GPT-5.2 與 Claude Opus 4.6）結論一致

局限

  • benchmark 僅 50 題演算法型 LeetCode，不覆蓋並行或 I/O 密集型系統
  • 固定 $5 預算——預算提高可能縮小差距，但多模態的成本分層（便宜 PBT/SMT 過濾→昂貴互動證明只用在最後一哩）無論模型多強都成立
  • 依賴 Aristotle 的能力證明殘餘義務可關閉（RQ3）

對讀者的價值

  • 「形式驗證把關」的典範級實作：把 PBT 當成線上品質過濾器而非事後評估，以「PBT→SMT→互動證明」成本遞增的三層過濾把 vericoding 成本壓到可負擔
  • 對照 ai_core §3.4（形式驗證准入）、§3.6（可驗證資產沉澱）、§5（受約束填碼）：LeetProof 三者皆具——PBT 是便宜的形式驗證把關、殘餘 VC 是可獨立驗證的證明資產、規格本身是約束的來源
  • 揭露 VERINA/CLEVER 的規格缺陷 → 任何以這些 benchmark 為基礎的評估都需注意基準線的雜訊
