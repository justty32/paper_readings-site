論文／訪談原始來源

《ClawTrace：成本感知的 LLM Agent 技能蒸餾追蹤》重點摘要

一句話概括

ClawTrace + CostCraft：以逐步成本歸因追蹤 agent 多步推論軌跡，將成功/失敗的二元切分替換為 preserve/prune/repair 三路技能修補，揭露聚合指標隱藏的規則型別轉移不對稱性——prune 修補（刪除昂貴但無影響的步驟）跨任務當品質護欄、preserve 修補（保留成功行為）跨任務導致品質衰退，證明 agent 技能應以規則型別粒度而非整體套件進行評估。

解決什麼問題

既有技能蒸餾管線（如 Trace2Skill）將軌跡二分為成功/失敗，從成功軌跡抽規則保留、從失敗軌跡抽規則修補——但沒有區分「修補遺漏步驟」和「刪除昂貴但無影響的已成功步驟」。第二種操作需要逐步成本訊號：管線必須知道哪些步驟昂貴，才能主張刪除它們是安全的。既有 observability 工具（LangSmith/Langfuse/Phoenix）記錄 per-span token 與成本，但呈現為人類儀表板而非蒸餾管線可攝取的緊湊摘要。

核心方法

  • ClawTrace 追蹤平台：註冊八個事件 hook（LLM 呼叫/工具使用/sub-agent 生成），將子 session 鏈回父 span、以四種費率（input/output/cacheRead/cacheWrite）計價 cache 命中（cache 讀取約為全新輸入的 1/10，忽略此差異會高估成本 1.6–2.0×）。
  • TraceCard 編譯：確定性編譯器將每個 session 的 span tree 壓成約 1.2–1.8 kB 的 YAML 摘要，含 per-step USD 成本、分型 token 計數、冗餘工具呼叫集群、失敗/修補步驟。足夠小讓數十個 TraceCard 裝進分析 agent 的 context window。
  • CostCraft 三動作蒸餾：
    1. preserve（保留成功行為→來自成功軌跡）
    2. prune（刪除昂貴但無影響的步驟→來自成功軌跡，須指名高成本步驟並附反事實論證）
    3. repair（修補特定失敗→來自失敗軌跡，附 oracle 證據）
  • 衝突感知合併：repair（有因果診斷）> prune（有名稱＋反事實）> preserve（兩軌跡以上才保留，單次出現者丟棄）
  • 訓練規模：50 軌跡 → 10 演進集（4 成功/4 部分成功/2 失敗）→ 產一個 SKILL.md（Trigger/Workflow/Stop rules/Artifact checklist/Cost control 五節，上限 1200 token）

結果

條件 品質保留率 衰退數（雙種子 pooled） 中位成本變化
Full CostCraft 83.3% 5 +22%
No-prune（去掉 prune 修補） 53.3% 14（2.8×） +15%
No-cost-attribution（去掉逐步成本） 70.0% 6 +49%
No-CF（去掉反事實閘門） N/A +2（15 任務子集） —
  • prune 修補是品質護欄而非成本壓縮器：在 30 題 held-out 集上，去掉 prune 修補使衰退數三倍、中位成本未降；八個 No-prune 衰退直接產出 Q=0（無輸出）。
  • 跨 benchmark 轉移（SkillsBench 84 題）：CostCraft 未節省聚合成本。但五個品質變化事件完全依規則型別分流——三衰退皆來自 preserve 規則（套用了 SpreadsheetBench 特有格式慣例）、兩改善皆來自 prune 規則（成本控制規則釋出 session headroom 讓 agent 抵達最終輸出步驟）。
  • prune 覆蓋率：10 軌跡訓練出 2 條 prune 規則（跳過工作記憶檔、每檔只讀一次並快取），匹配 17 個成功 held-out 任務中的 2 個（11.8%）；更大訓練集才能擴充 prune 庫。

失敗分類學（16 個非完美基線的七類操作失靈）

T1 無可交付物、T2 錯誤內容型別、T3 公式未求值、T4 佔位符不匹配、T5 大小寫/空白、T6 邏輯錯誤、T7 精度捨入。六類對應 repair、一類對應 preserve、零類對應 prune（失敗無法靠刪除不存在行為修補——prune 只能來自成功但浪費的軌跡）。

局限

  • 僅驗證 OpenClaw + gpt-5.4 組合，未測試其他 agent runtime（Claude Code/AutoGen）或 backbone
  • 10 軌跡訓練規模僅產出 2 條 prune 規則；SkillsBench 上未重複完整消融矩陣
  • 兩種 heuristic TraceCard 欄位（sub_agents.output_used_in_final、failed_or_repaired）未在此 backbone 上觸發
  • 成本變異係數約 43%，成本百分比為近似值
  • 失敗分類由單一標註者編碼

對讀者的價值

  • §3.3 成本梯度 + §3.6 固化引擎：ClawTrace 的 per-step cost attribution 正是 ai_core 缺少的「每步成本訊號」——沒有它，固化引擎無法區分「該保留的昂貴步驟」與「該刪除的無用步驟」。TraceCard（~1.5 kB YAML）的緊湊性直接示範了「把 observability 資料壓成蒸餾管線可消費的中間表示」的工程模式。
  • 規則型別轉移不對稱性是關鍵發現：prune 規則是跨任務品質護欄（不省錢但防衰退）、preserve 規則過擬合（跨任務反而造成衰退）。這為 §3.6 固化引擎的技能入庫審查提供了一個可操作的判準：技能入庫時應按規則型別分開評估轉移行為，而非把整套 SKILL.md 當一個黑箱評分。
  • 三路修補（preserve/prune/repair）的衝突感知合併優先序（repair > prune > preserve）是 §3.4 憑證准入在技能合併場景的直接實例。
