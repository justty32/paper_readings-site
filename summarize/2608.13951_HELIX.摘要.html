HELIX: Model–Harness Co-evolution for Recursive Self-Improvement 重點摘要

一句話

HELIX 主張 RSI 該遞迴改進的單位是「模型＋harness」這一對狀態，不是模型單獨；harness 既是決定當下執行力的行為運算子，也是為下一輪模型更新生產帶標籤 sibling 資料的資料運算子，兩者靠 build–update–rebuild 三段循環串起。

方法：把 harness 變成可宣告、可稽核的介入變數

harness 被拆成 shell、session/hooks、config、prompt、tools、turn loop、acceptance、policy 八個維度，用 port（穩定能力槽）、atom（來自 OpenCode／Pi Mono／Nanobot／Hermes Agent 四套開源 harness 的行為實作）、recipe（宣告式組合）三層表示。每個完整 product contract 暴露 96 個 port，五個獨立來源選擇給出 4⁵=1,024 種 recipe（acceptance 獨立選則 4⁶=4,096）。編譯器＋lockfile 在執行前做 conformance／boundary／source-purity 檢查，evidence plane 把 recipe 身分、trace、workspace diff、verifier 結果全程綁定，讓每次比較都可回溯到具體介入。

作者報告的實驗與資料限制

作者在 100 題 LiveCodeBench 衍生修 bug 任務上跑 65 個以 Pi 為中心的候選（Pi＋64 個 source-pure recipe），單次嘗試下最佳固定 harness 52/100 勝過 Pi 的 50/100（+4.0%），完整 portfolio 的 post-hoc oracle union 達 79/100（比 Pi 多 58.0% 相對覆蓋，但作者明確標註這是可能的資料上限，不是可部署的分數）。選定成員在 SWE-bench Verified 55 例的官方評測下，最佳固定成員 46/55 勝過 Pi 的 44/55，oracle union 49/55；LCB 矩陣裡表現最好的兩個候選換到 SWE-bench 後跟 Pi打平，說明沒有單一跨環境贏家。作者從 200 條精篩 sibling slot 產出 438 筆訓練紀錄（clean SFT、需清理 SFT、critic negative、filter sample、preference pair 五類）。以上全是作者自報數字，且矩陣中 65 個候選僅有 2 個勝過 Pi、23 個掛零，任務集是前 100 題而非隨機抽樣，各驗證階段的嘗試預算不同（1／10／2 次）故排名不可直接比較；論文只做到「materialize 訓練資料」，並未真的拿這批資料去更新模型驗證迴圈閉合。

對 ai_core 專案的價值／接點

這篇對「自我改進迴圈」的核心啟發是：把 harness（而非只有 policy/model）當作遞迴改進的一等公民，且明確區分「哪個固定 harness 現在最好用」與「整個候選族群能挖出多少 sibling 資料」兩個不同目標函數（式 5 的 α／β／γ 三項），對應到 ai_core 若要做成本梯度分析，可以借用它「fixed-harness performance vs. portfolio yield」的框架，把探索成本（Cbuild）與資料價值（Qdata）分開記帳，而不是混在單一分數裡。對固化引擎的啟發更直接：它把同一批 rollout 依 verifier 標籤（resolved／regression／target-miss／no-action／noisy）拆成 SFT／critic／filter／preference 四種輸出（Table 1／3），這正是「sibling contrast 驅動蒸餾」的具體範例，可作為固化引擎輸出格式設計的參考範本。對驗證器設計的提醒：論文強調「target test 通過」不等於「乾淨解」（pytest 案例：通過 F2P 但破壞 P2P 仍判負），驗證器需要多路標籤而非二元 pass/fail，且需檢查 patch hygiene（是否只動 production code、是否有 symlink/path noise）——這對 ai_core 驗證器若只看單一終端測試結果會漏掉退化案例，是可直接借鏡的教訓。
