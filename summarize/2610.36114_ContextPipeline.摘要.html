論文／訪談原始來源

Context Is a Pipeline, Not a Window: Information Attrition in LLM Agent Harnesses 重點摘要

一句話概括

Agent 的工具結果可能在進入模型上下文之前，就被 harness 截斷並失去重要欄位。作者在 Linux 核心追蹤診斷 agent 測得此現象；控制實驗顯示，在存在替代線索的測試中，截斷主要增加工作量，並未證實準確率下降。

五個邊界與現場觀察

作者把上下文視為從工具產生、交付、行動、保留、交接到跨執行保存的管線。工具輸出截斷和未交接的發現可能直接消失；worker 步數上限阻止後續工作；較長歷史保留則可能重送更多內容。跨執行持久化在此實驗中刻意關閉，以保持執行彼此獨立，不是觀測到的故障。作者提出逐邊界計數，並用「記錄的發現數／執行的計算數」作 yield；這只是工作交接的窄代理指標，不衡量發現是否相關。（§II）

在 720 次注入故障診斷中，11,189 個工具結果有 3,827 個遭截斷，這些截斷結果的 JSON 全部損壞；最大單次 prompt 僅用 400k token 視窗的 5.75%。固定長度取 JSON 文字前綴造成欄位位置偏差：同一類結果的兩個清單，在 742 次遭截斷的清單呼叫中分別僅 4.7% 和 99.3% 届達。故障類型對應到哪個清單與診斷分數有相關，但現場資料不足以證明截斷造成分數落差。（§I、§III-A）

另外一個 554 worker 的紀錄中，51% 恰好停在步數上限，98 個沒有交接任何發現；一個前後比較顯示保留上限由 80k 增至 150k 字元時，使用 token 由 303k 增至 545k。這些是特定設定的描述，不能單靠數量判定對最終正確性的影響。（§II、表 I）

重播與控制實驗

作者將 31 次執行中的 864 個已記錄結果重播：超過預算的結果經原前綴切法皆損壞，採按記錄列截斷的修補方式則沒有損壞。一個真實 21 容器部署的輸出長 33,370 字元，超過原 6,000 字元上限；原切法保留早期清單的 30/118 筆，後期清單 0/128 筆，故該案例整類線索在交付前消失。重播不涉及模型，證明的是這些輸入上的資料破壞機制。（§III-B）

控制實驗固定診斷 agent、模型、工具和任務，逐一重新加入缺陷，並以每類 5 個錄製追蹤、各重複 3 次跨設定配對；全部 145 次執行包含健康負控制，重複並非新的獨立故障實例。評分要求答案欄明確指出正確容器。作者發現舊評分器把提及當正解，在第 46 次執行審核後更正；其一設定分數因此由 14/15 修正為 2/15。（§IV、§VI）

對 spawned 類故障，修補版、前綴截斷版及反轉欄位順序後截斷版正確數分別 14/15、15/15、15/15。三者工具呼叫中位數為 53 → 68 → 76，計算 18 → 32 → 36，yield 0.61 → 0.34 → 0.31；反轉且截斷相對修補版是工具呼叫多約 43%、計算約兩倍。單純反轉順序而不截斷的控制組 yield 為 0.61。此處犯錯率未增加：即使截斷刪掉清單中的 culprit，模型仍可從另一個按事件量排序的表找到它，作者原先預測的準確率下降未成立。（§IV、表 II）

對另一個真實部署追蹤的重複測試，修補版 3/6 正確、無損壞 payload；截斷版 0/5 正確且每次均有損壞 payload。樣本少，修補版本身仍有一半失敗；作者明確不把它當成截斷獨自造成全體現場準確率落差的證明。此前建立基準時亦提高 worker 步數預算並加入請求分頁機制，本次分頁未觸發；兩臂使用相同追蹤與提示，缺陷臂重新加入截斷。（§IV）

適用範圍

作者檢視七個指定版本框架的工具輸出處理程式，找到兩個不依資料結構做位置截斷的通用裁切器；其餘包含不裁切、只裁 tracing 資料或按 shell 輸出行裁切的配置。這是程式碼調查，並未對其他框架做端到端實驗，也不代表所有工具或版本行為一致。（§III-C）

主要控制實驗只有一個 harness、一個模型與 Linux 核心追蹤診斷領域；其故障由作者自行注入，小型追蹤的截斷預算也按實驗規模調整。證據支持檢查輸出交付與成本，但現場準確率落差的因果貢獻，以及一般 coding agent 或其他任務上的效果仍待驗證。（§VI）
