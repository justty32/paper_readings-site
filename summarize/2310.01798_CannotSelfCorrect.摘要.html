作者：Jie Huang, Xinyun Chen, Swaroop Mishra, Huaixiu Steven Zheng, Adams Wei Yu, Xinying Song, Denny Zhou（Google DeepMind / UIUC）

日期：2023-10

arXiv：2310.01798

論文／訪談原始來源

《大型語言模型尚無法自我修正推理（Large Language Models Cannot Self-Correct Reasoning Yet）》重點摘要

一句話概括

反證論文（ICLR 2024）：定義內在自我修正（intrinsic self-correction）——LLM 只憑自身能力、無任何外部回饋地修改初答——並以嚴格重跑實驗證明：在推理任務上此設定不僅無效、多數情況反而使表現退化；先前文獻報告的增益其實來自用正確標籤（oracle）決定何時停止修正，拿掉 oracle 增益即消失。若 LLM 真能自我修正，為何不第一次就答對？

解決什麼問題

Self-Refine、Reflexion 等工作讓社群樂觀相信「LLM 能靠自我批評迭代改進推理」。但文獻對「自我修正」定義混亂——許多方法暗中使用 ground-truth 標籤或外部工具，卻以「self-」冠名，連領域專家都分不清何時有效。本文釐清：回饋來源（純內部 vs 外部）是關鍵分野，並專攻「無外部回饋時 LLM 能否修正自身推理」這一根本問題。

核心方法

  • 重跑 oracle 設定（§3.1）：照 Kim et al. / Reflexion 原設定（用正確標籤決定何時停止），在 GSM8K / CommonSenseQA / HotpotQA 上測 GPT-3.5 與 GPT-4，三步 prompt：初答→自我審查產回饋→依回饋重答。
  • 拆穿 oracle（§3.1.3）：設計「隨機亂猜＋oracle 停止」基線——CommonSenseQA 五選一，猜錯就換一個選項再猜，2 輪即追平自我修正、4 輪必達 100%——證明增益來自 oracle 而非修正能力。「若已知答案，何必再解題？」
  • 內在設定（§3.2）：拿掉標籤、跑兩輪自我修正，並分析答案變化四象限（不變／對改錯／錯改對／錯改錯）。
  • 多代理辯論對照（§3.3）：復現 Du et al. 的 multi-agent debate，與相同回應數的 self-consistency 公平比較。
  • 後設概念（§4）：把自我修正重新框定為 post-hoc prompting——只有當回饋能提供 pre-hoc（初始）prompt 給不了的資訊時才有價值；許多「修正增益」實為初始 prompt 寫爛、回饋 prompt 寫好的假象。

結果

  • 內在自我修正全面退化（表 3）：GPT-3.5 GSM8K 75.9→74.7、CommonSenseQA 75.8→38.1（回饋 prompt 誘導改選近似選項）、HotpotQA 26.0→25.0；GPT-4 GSM8K 95.5→89.0、HotpotQA 49.0→43.0。換不同回饋 prompt（附錄 B）結果一致。
  • 答案變化分析（圖 1）：GSM8K 上 74.7% 不改答案；會改的之中「對改錯」多於「錯改對」。
  • oracle 假象（表 1 vs 表 2）：oracle 下 GPT-3.5 CommonSenseQA 75.8→89.7 看似大增，但隨機亂猜基線 2 輪即 87.9、4 輪 100%。
  • 多代理辯論 ≈ 自我一致性（表 4）：GSM8K 上辯論 9 回應 83.0 vs self-consistency 9 回應 88.2——辯論本質是投票共識（self-consistency），非修正。
  • pre-hoc 打爆 post-hoc（表 5）：CommonGen-Hard 上作者「隨手寫」的初始 prompt 達 81.8，勝過 Self-Refine 修正 7 次呼叫後的 67.0；對好初答再套其修正 prompt 反降至 75.1。

局限

  • 只測 GPT-3.5/GPT-4 與三個推理 benchmark；「Yet」留有餘地——未排除未來模型或特定 prompt 在特定 benchmark 上有效（但搜 prompt 本身就是引入人類/訓練集回饋，已違反內在設定）。
  • 明確不否定自我修正的全部：改風格、提升安全性等「模型能判斷達標與否」的任務仍有效；外部回饋（工具、執行器、單元測試、訓練過的 verifier）下修正確實可行。
  • 多代理辯論僅在 GSM8K 上與 self-consistency 對比。

對讀者的價值

  • 本批的反證組：與同批 STaR（2203.14465）、STOP（2310.02304）、CRITIC（2305.11738）成正反對照——STaR 的自我提升靠答案正確性過濾（外部訊號），CRITIC 直接證明「靠工具批評才有效、純內省是弱基線」（本文 §3.2.2 引用之），STOP 的 improver 靠 utility 函數評分。四篇合讀畫出清晰邊界：自我改進迴路必須有接地的驗證訊號，否則崩壞。
  • 直接論證 ai_core 的立場：無接地訊號則自我改進崩壞。對 §3.6 固化引擎的啟示——把 LLM 產出結晶成確定性程式碼的過程，絕不能讓 LLM 自我審查通過，必須以執行器、單元測試、型別檢查等確定性節點當 verifier（本文明言 code generation 因有 executor+tests 而是 oracle 合法存在的場域）；這正好落在 ai_core 第一目標「程式碼助手」（§5）的甜蜜點：下層受約束填碼天然自帶可執行驗證。
  • 對 §3.4 治理的印證：「拒絕為預設」優於「先生成再自我修正」——本文表 5 證明把約束**前置寫進初始指令（pre-hoc）**比事後回饋修正更準更省 token；別付 5 倍呼叫成本買一個更差的答案。
  • 最值得記：oracle 停止條件是文獻增益的真正來源、隨機亂猜基線的拆穿手法、「內在修正＝額外 prompt 把模型拉離最優初答」的直覺解釋、以及作者的比較準則（報告呼叫成本、以同呼叫數的 self-consistency 為基線、pre-hoc/post-hoc 投入同等心力）。
