作者：Cheng-Yu Hsieh, Si-An Chen, Chun-Liang Li, Yasuhisa Fujii, Alexander Ratner, Chen-Yu Lee, Ranjay Krishna, Tomas Pfister（University of Washington / National Taiwan University / Google Cloud AI Research / Google Research）

論文／訪談原始來源

《工具文件使大型語言模型能零樣本使用工具（Tool Documentation Enables Zero-Shot Tool-Usage with Large Language Models）》重點摘要

一句話概括

Tool Documentation（工具文件）取代示範（demonstrations）：與其給 LLM 幾個「輸入→工具使用計畫」的少樣本示範來教它用新工具，不如直接把**每個工具各自的文件（doc，描述功能與呼叫方式）**放進提示；作者在 6 個橫跨視覺與語言的任務上證明，只給工具文件的零樣本（zero-shot）表現可與少樣本（few-shot）持平甚至更好，且在工具數量規模化時遠勝示範——文件通常隨工具「有機地」存在、中性、免人工挑選，因此是更可擴展、更穩健的教工具方式。

解決什麼問題

目前教 LLM 用工具的主流做法是提供少樣本示範（demos，即 <輸入， 輸出> 的工具使用計畫範例），但示範有三大痛點：(1) 難以取得、需為每個新任務人工精心策劃；(2) LLM 對示範選擇敏感，選錯會引入偏誤或過擬合到特定用法；(3) 缺乏原則性的挑選協定——該給幾個、給哪些沒有定論，且當工具數量規模化時，示範的選擇組合會爆炸性成長而變得不可行，且有限示範無法覆蓋大量工具的用法。作者的比喻：熟練工匠不需別人示範新工具，只要讀使用手冊（manual）就能掌握其能力。

核心方法

  • 核心主張：用 tool documentation（工具文件） 取代 demonstrations。doc＝針對「單一工具」的功能描述與呼叫方式說明（如 README / 函式簽章 / API 手冊），與具體任務無綁定、相對中性、通常隨工具建立而自然存在。
  • 通用工作流程（沿用「Tool learning with foundation models」框架）：給定自然語言指令，LLM planner 生成一段可依序執行的程式，每步可呼叫工具集裡的工具，最後由環境執行並回傳結果。工具集可為程式庫、訓練好的模型、API 呼叫等。
  • 實驗設計：系統性地在提示中「加/不加 doc」× 「示範數從少樣本降到零樣本」做組合比較。planner 預設為 ChatGPT（gpt-3.5-turbo）。
  • 6 個評估任務：ScienceQA（多模態科學問答，7 工具）、TabMWP（表格數學推理，9 工具）、NLVRv2（雙圖真偽判斷，沿用 VisProg 的 20 個視覺模組，作者自行為模組撰寫 doc）、新收集的 LLM Cloud CLI（把 GCP 命令列 200 條命令改名成 LLM 未見過的工具、含 50 題）、以及影像編輯與影片追蹤（質性評估，插入 SAM / GroundingDINO / XMem 等剛發布的新視覺模型當工具）。
  • 規模化處理：200 工具的文件塞不進單一提示，故用簡單的 TF-IDF 檢索以問題為查詢取最相關的 doc、截斷至符合長度。

結果（具體數字）

  • 文件讓零樣本追平少樣本（§4.1）：加 doc 後，把示範數從多降到 0 表現仍穩定——0-shot+doc 在 TabMWP 追平 16-shot、在 NLVRv2 追平 12-shot、在 ScienceQA 甚至勝過額外用 10-shot。不加 doc 則對示範數極敏感、減少示範表現大跌。
  • 對比基線（表 1）：0-shot+doc 在 ScienceQA 達 79.91（勝 CoT 78.54 與 0-shot 無 doc 78.25）、TabMWP 達 92.69（勝 PoT 89.28）；NLVRv2 上 0-shot 無 doc 為 0.00、加 doc 躍升至 63.40（ViLT 為微調後 76.30，而 LLM 為零樣本）。
  • 規模化更顯文件價值（§4.2，LLM Cloud CLI）：對未見的 200 工具，零樣本 F1 極低（text-davinci-002 為 0.02、gpt-3.5-turbo 為 0.13）；少樣本改善有限（最佳僅 0.05 / 0.19，因示範覆蓋不了大量工具的命令與旗標）；只讀文件則大幅躍升至 0.37 / 0.45。且「doc+示範」（0.35 / 0.42–0.44）反而不如「只 doc」（0.37 / 0.45）。
  • 即插即用重新發明新工具（§4.3）：僅憑 GroundingDINO、SAM、XMem、Stable Diffusion 的文件，LLM 就自動組出等同於當時剛發布的 Grounded-SAM（影像編輯）與 Track Anything（影片追蹤）的流程，事前並不知道這些衍生專案——指向「零樣本用工具→自動知識發現」的潛力。
  • 文件品質/長度消融（§4.4）：不做任何內容策劃，僅以截斷保留前 n 字為代理；表現隨文件加長而提升，直到約 600 字達峰，之後因長文理解困難而略降。

局限

  • 文件過長（>600 字）時表現下滑，受限於 LLM 對長文的理解能力（作者預期長上下文技術會逐步緩解）。
  • 200 工具無法全塞進提示，需靠 TF-IDF 檢索＋截斷，引入檢索環節。
  • 影像編輯與影片追蹤屬質性評估、非量化基準。
  • 更廣影響上：須審慎考量該把哪些工具開放給 LLM、以及如何解讀模型輸出；作者把文件視為引導 LLM「更安全、符合工具原始設計意圖」地使用工具的管道。

對讀者的價值

  • 對 ai_core 的接點：本篇是「工具資產必須自帶規格（文件）供便宜端復用」原則的工具版證據。ai_core 把 LLM 呼叫包成可靠函數、貴稀有智能當資產工廠、便宜高頻智能當資產消費者；本文正說明——只要工具自帶一份中性的文件（規格），便宜端（此處是 gpt-3.5-turbo 甚至更弱的 text-davinci-002）就能零樣本地正確調用它，無需昂貴的人工示範策劃。這與已入庫 LILO 的 AutoDoc（抽象自帶文件才可被復用）是同一原則的不同層次：LILO 談「LLM 合成的抽象/函式庫要自帶文件」，本篇談「外部工具/API 要自帶文件」，兩者都指向 ai_core 的資產必須攜帶可被便宜端讀懂的規格。歸 I 類。
  • 對 ai_core「符號神經網路計算圖（多數確定性節點＋少數 LLM）」的啟發：文件是把工具節點的介面契約寫死、讓 LLM planner 節點只負責組裝的關鍵——文件愈完整（到 600 字上限），planner 愈能正確編排確定性工具，減少對示範這種昂貴人工資產的依賴。
  • 對「固化引擎」的啟發：本文的「LLM 僅憑積木文件重新發明 Grounded-SAM / Track Anything」示範了「零樣本組裝→自動知識發現」，可視為把工具用法結晶成可復用流程的雛形——若把這些被 LLM 反覆組出的流程固化成確定性程式，即是 ai_core 想要的資產晶化。
  • 最值得記：「文件 > 示範」的反直覺結論、文件在工具規模化時的可擴展性優勢、doc+demo 反不如純 doc、以及600 字文件長度的甜蜜點。適合做工具/API 調用、agent 工具集設計、RAG 式工具檢索、降低對人工示範依賴的人。
