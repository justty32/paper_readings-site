論文／訪談原始來源

《Compiled AI：LLM 工作流自動化的確定性程式碼生成》重點摘要

一句話概括

Compiled AI：把 LLM 當編譯器而非直譯器——LLM 只在一次性編譯階段被呼叫，在經過模板約束生成窄域業務邏輯函式後，通過四階段驗證管線（安全→語法→執行→準確度）部署為確定性靜態程式碼，執行時零 token、零 LLM 呼叫、零隨機性。在 BFCL 函式呼叫上達 96% 任務完成率、僅 17 筆交易就攤平編譯成本、1,000 筆時節省 57× token（vs Direct LLM）和 84×（vs AutoGen）;DocILE 文件智慧的 Code Factory 變體在 KILE 欄位抽取上匹配 Direct LLM（80.0%）、LIR 行項辨識最高（80.4%）。安全評估：135 測試案例 96.7% 準確率偵測 prompt injection、87.5% 靜態程式碼安全分析、零誤報。

解決什麼問題

LLM agent 架構（AutoGen、LangChain）每筆交易都呼叫 LLM → 高 token 消耗、可變延遲、非確定性行為（即使 temperature=0 仍有 18–75% 輸出變異）、攻擊面大（每筆交易都暴露 prompt）、難以審計。醫療等合規場景（CMS 決策時限、HIPAA、FDA 審計）不能接受這種不確定性。79% 的多代理失敗源於規範與協調問題（非基礎設施），agent 成功率從單輪 58% 降到多輪 35%。

核心方法

  • 編譯式 AI 三要素：① LLM 僅在生成時呼叫一次（非交易時）、② 部署後零 token 確定性執行（生成碼是靜態的）、③ 必須通過多階段驗證（安全/語法/執行/準確度）。
  • Code Foundry 架構：YAML 工作流規範→Orchestrator 選模板/模組/合規約束→LLM 一次性生成業務邏輯（20–50 行）→四階段驗證管線→部署為 Temporal activity（失敗時帶錯誤上下文重新生成）。
  • 四階段驗證：Security（Bandit+Semgrep+自訂規則檢查 SQL injection/command injection/path traversal/secrets）→Syntax（AST 解析+mypy 型別檢查+ruff lint）→Execution（沙箱執行對測試 fixtures）→Accuracy（對 golden dataset 按任務特定閾值比對輸出）。
  • Bounded Agentic Invocation：當純確定性方法因語意複雜度失敗時，生成碼可以封裝聚焦的 LLM 呼叫（如從模糊臨床筆記中抽取結構化欄位），但整體流仍是確定性的——搭配 schema 定義、fallback 邏輯、漂移監控、人類升級閾值。
  • 安全架構（三閘門）：Input Gate（DeBERTa-v3 prompt injection 偵測+Presidio PII 掃描）→Code Gate（CWE-94/89/502/78/328 靜態分析）→Output Gate（密碼學 canary token 注入偵測 prompt 洩漏）+ Dual LLM 分離特權與隔離模型實例。

結果

  • BFCL（n=400）：Compiled AI 達 96% 任務完成率、100% 執行可靠性（16 個失敗全發生在編譯階段、部署前可偵測）、4.5ms P50 延遲（vs 2,004ms Direct LLM，450× 改善）、100% 再現性（vs runtime inference 95%）、1M 筆/月 TCO $555（vs $22,000 Direct LLM，40×）。
  • DocILE（5,680 張發票）：Code Factory 在 KILE 欄位抽取匹配 Direct LLM（80.0%）、LIR 行項辨識最高（80.4%）、延遲 2.3× 低於 Direct LLM（2,695ms vs 6,339ms）。純 regex 僅 20.3% KILE（差 80pp 來自語意欄位：客戶名 10.1%、幣值 9.2%）。
  • 安全：prompt injection 偵測召回 95.8% / 精確 100%（30 對抗輸入，零誤報）；程式碼安全閘召回 75% / 精確 100%（20 漏洞+20 良性，零誤報）。跨 135 案例整體精確 96.1%。
  • 驗證管線：語法/執行階段首過率 100%；準確度閘首過率 96%（16 失敗＝編譯時可偵測的語意錯誤，部署前攔下，轉為 100% 部署可靠性）。

局限

  • 規範品質依賴：假設使用者能準確指定 YAML 工作流；規範本身需要迭代細化。
  • 有限適用性：非所有工作流可簡化為確定性程式碼；需要真正創造力或適應新情境的任務仍需 runtime inference。僅評估兩種任務類型。
  • 生成失敗率：4% 編譯失敗（BFCL 16/400），雖全部語法有效且可於部署前偵測。
  • 模型依賴：生成碼品質取決於底層 LLM；模型更新可能需要重新驗證。
  • 基準覆蓋：評估框架尚未被其他系統採用，跨系統可比性有限。

對讀者的價值

  • 「LLM 節點→確定性程式退化」方向二的生產級實作：把 DSPy/LLM+P 的編譯理念推到企業合規場景（醫療），給出一套可操作的四階段驗證藍圖＋經濟學帳本（攤平點 n*≈17、57–84× 節省）。
  • 與 2310.03714 DSPy（宣告式→優化 pipeline）、2304.11477 LLM+P（NL→PDDL→經典規劃器）、2605.22148 Ratchet（失敗就退役）、2601.16286 SemanticALLI（意圖簽名快取取代 LLM 節點）並讀：編譯 vs 快取 vs 退役——三種讓 LLM 退出執行迴圈的策略。
  • 安全架構可直接對照 ai_core §3.2（前濾網）與 §3.4（接地把關）：Input Gate＝前濾網、安全/語法/執行/準確度四階段＝多層把關、Bounded Agentic Invocation＝「非它不可才留 LLM」的工程實例化。
  • 定位：系統架構論文＋雙任務實證＋開源基準套件（540 YAML 規範＋金輸出＋七類指標度量腳本），適合做 LLM 工作流自動化、企業 AI 部署、醫療 AI 合規、安全 AI 系統 的人。
