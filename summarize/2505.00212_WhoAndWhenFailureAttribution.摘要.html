論文／訪談原始來源

《哪個 Agent 在何時造成任務失敗？LLM 多 Agent 系統的自動錯誤歸因》重點摘要

一句話概括

Who&When 把多 agent 除錯正式化為 (agent, step) 歸因：若修正某一步並讓後續軌跡相應調整後，整體由失敗變成功，該步就是 decisive error；資料集收錄 127 種 agent 系統、184 個帶人工解釋的失敗歸因任務。現有 LLM 最好只能認出 53.5% 的責任 agent、精確定位 14.2% 的錯誤步，顯示「知道最後錯了」與「知道哪裡導致錯」是兩個難度差很多的問題。

問題定義

  • 系統採輪流行動協定，每個時間點只有一個 agent 採取動作。
  • 一條失敗軌跡可能有多個錯誤，但錯誤不一定是失敗原因。
  • 若把 agent i 在時間 t 的錯誤動作換成正確動作，保留此前前綴並相應調整之後的行為，結果由失敗轉成功，(i,t) 才是 decisive error。
  • 若有多個 decisive errors，資料集選時間最早者作主要失敗原因。

這個定義帶有反事實因果意味，但資料標註實際上依賴專家閱讀與共識，沒有真的為每個候選步驟執行可控重播。因此 benchmark 的標籤是專家對反事實的判斷，不是實驗驗證的因果效果。

Who&When 資料集

  • 共 127 種 LLM 多 agent 系統、184 個失敗標註任務，來源為 GAIA 與 AssistantBench。
  • 其中一類由 CaptainAgent／GPT-4o 自動為每個 query 建立團隊、角色、prompt 與工具，保留最佳配置仍失敗的執行紀錄；另一類是成熟的五 agent 系統 Magnetic-One。
  • 每筆資料包含 query、完整失敗 log、系統資訊、責任 agent、決定性錯誤步與自然語言原因。
  • 三名 AI agent 專家分三輪標註：獨立標註並標示不確定、針對不確定案例討論至全員共識、交叉檢查彼此標註並再協商。
  • 三人分別花 30.9、30.2、23.2 小時；初輪自報不確定比例約 15%–30%，說明人類也很難歸因。

三種自動歸因法

  • All-at-once：一次提供完整 query 與 log，直接預測 agent 和 step。全域資訊最完整，較會找對 agent，但難在長脈絡中精確找一步。
  • Step-by-step：逐步加入 log，每步問是否已出錯，首次判錯即停止。局部定位較準，但可能因太早決定而錯過後續證據。
  • Binary search：每次判斷錯誤在 log 前半或後半，反覆縮小到一步。效能與成本通常介於前兩者。

主要結果

  • 摘要報告的總體最佳值為 agent-level 53.5%、step-level 14.2%，尚無實用性。
  • GPT-4o 的細分結果顯示，all-at-once 在 agent-level 最好：依系統類型與是否有答案標籤，約 51.12%–55.17%。
  • step-by-step 在精確 step 定位通常最好，但幅度仍低：演算法生成系統、有正確答案時為 25.51%；手工系統、無正確答案時只有 8.77%。
  • all-at-once 的 step-level 平均甚至可能低於隨機，呈現長脈絡中的「needle in the space」問題。
  • Magnetic-One log 由 5–17 steps 增到 93–130 steps 時，三種方法皆退化；最長區間的 step-level 幾乎降到 0%。
  • 容許 ±5 steps 後，手工系統上 all-at-once 可到 43.10%，但這只表示大概區域，不是找到決定性動作。
  • 先用 all-at-once 找 agent，再只對該 agent 的動作做 step-by-step，手工系統上 agent-level 57.02%、step-level 12.28%；代價為 149,177 tokens，高於任一單法。
  • OpenAI o1 與 DeepSeek R1 沒有一致勝過 GPT-4o。DeepSeek R1 在四個比較中三個較差；換強模型不等於會做因果歸因。
  • 單筆結果雖差，聚合統計仍能找出最常造成 decisive error 的 agent，適合先作系統熱點排序。

對 Agent 錯誤管理的啟發

錯誤管理不能只放一個 LLM auditor 看完整 log。找「誰」需要跨 agent 的全域脈絡；找「何時」需要局部、高解析度檢查；兩者應分階段處理。實務上可先以全域方法縮小責任 agent／子圖，再對候選動作做局部審核，最後以重播或測試驗證，而不是直接相信 auditor 的文字理由。

這篇還揭示 observability 的最低要求：每步必須保留 active agent、輸入狀態、動作、工具結果、後續狀態與終局評分，否則連 Who/When 任務都無從定義。對千萬級 agent，應先做聚合熱點與故障域統計，再把昂貴的精確歸因限制在少數候選軌跡。

局限

  • 只處理輪流行動、單一 agent 每步的系統，不涵蓋真正並行、共享狀態競爭或多 agent 聯合錯誤。
  • 每條軌跡只選最早 decisive error，會壓平多因一果、共同責任與後續放大錯誤。
  • 標註沒有逐候選反事實重播；「修正後會成功」主要靠專家判斷，可能受主觀因果故事影響。
  • 184 個任務仍小，且集中在 GAIA、AssistantBench 與兩種系統建構方式；對程式開發、長期自治與不可逆工具操作的泛化未知。
  • step 編號不是時間或語意距離。容許 ±5 在短 log 中佔很大比例，不能直接解讀成可操作的精準除錯。
  • 有 ground truth 的開發情境較容易；線上真實故障往往沒有正確答案，效能會更差。
