《Autogrammar》重點摘要

一句話概括

Autogrammar 把「讓 LLM 學會替低資源 DSL 產 CFG」寫成一個 Kripke structure：LLM 決定非確定分支，LTL 約束規定 agent 允許採取的學習程序。只改 declarative temporal constraints，便能在作者實驗中以 3.8 倍較快時間取得未見資料近乎不降的 precision。

為何需要它

grammar-constrained decoding 能阻止 LLM 輸出不合語法的 DSL，但第三方 DSL 常沒有 CFG。作者指出 AWS 416 個 API service 中有 23% 暴露需符合 DSL 的字串參數，至少 59 種 DSL；這類語言的訓練資料遠少於 Python。問題不是「LLM 能不能寫 grammar」，而是如何取得一個會接受正確程式、又不放進錯誤字串的可用 artifact。

方法與保證

Autogrammar 從文件與成功 execution data 提取例子，呼叫 LLM 提案 Lark CFG，反覆用 validation／修訂。系統狀態、初始狀態、轉移、標記與原子命題構成 Kripke structure；LTL 限制哪些步驟可發生及先後關係。因限制約束的是 agent controller 而非生成結果的正確性，形式保證是「行為符合宣告的 temporal policy」，不是「學得的 CFG 必然正確」。

實驗

三個 DSL：CloudWatch Logs Insights、Dynatrace Query Language、Datadog Search Syntax。五折未見資料上，Autogrammar 的 precision 平均 91–100%。將性能型 LTL 約束加入後，時間快 3.8×，precision 沒有統計顯著下降。移除 documentation 通常不傷結果（DQL 有小但顯著下降），移除 execution data 則明顯變差，故應把真實執行軌跡視為關鍵資料源。

比較中，Arvada 在 CWIL 需平均 63k oracle calls、14.6 小時，未見 precision 0.025；LLM baselines 在兩個 DSL 也低一個數量級。把所生 CFG 放入 decoding pipeline 後，十項真實 CloudWatch 任務有八項端到端 LM 表現提升，並可匹配或勝過專業維護 grammar。

邊界

precision 高不表示 recall 一定高，也不等於語義正確；測試資料、execution log 與十個 end-to-end tasks 都可能有選樣偏差。作者也只實作約 2,300 行的 Python prototype，且測試三個查詢 DSL，尚不足以證明能泛化至所有 API 語言。對工程而言，最有價值的是把 DSL grammar、執行證據、LTL runtime policy 都作為可檢驗交付物。
