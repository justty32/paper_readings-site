論文／訪談原始來源

A Unified Definition of Hallucination, Or: It’s the World Model, Stupid 重點摘要

一句話

論文把 hallucination 統一定義成「模型輸出中可被使用者觀察的 atomic claim，與一個明示的 reference world model 衝突」，並要求評估同時說清楚世界真相、模型看得到什麼，以及多個資訊來源衝突時誰優先。

問題：同一個詞其實用了不同真相

Hallucination 從機器翻譯裡與來源無關的輸出，逐步擴張到摘要不忠實、開放域問答的事實錯誤、RAG 中忽略檢索內容、VLM 的圖文衝突，以及 agent 點擊不存在按鈕等行為。這些定義表面不同，核心卻都是模型輸出暗示的世界，與評估者採用的真相不一致。真正麻煩的是「真相」經常沒有寫出來：摘要可能以輸入文件為準，開放域問答以外部世界為準，RAG 還得先決定檢索內容和參數記憶何者優先。

作者回顧的 HALoGEN 橫跨 9 個知識領域，並把 hallucination 分成 3 類，正好顯示既有 benchmark 雖更細緻，仍把正誤綁在各自選定的外部來源與 verifier 上。這兩個數量是文獻整理，不是本文的新實驗結果。

統一定義

Reference world model 寫成 W=(S, H, R)。S 是可能的世界狀態，H 是可能的互動歷史，R 是限制哪些狀態與歷史可接受的規則。對一個輸入 x，view function V 只取出與任務相關、且允許模型看到的那部分世界；conflict policy P 規定文件、知識庫、模型參數記憶、環境觀察與指令互相衝突時如何裁決；truth function 再把每個 atomic claim 判為 true、false 或 unknown。

輸出 y 只有在至少一個可被使用者觀察的 atomic claim 被 truth function 判成 false 時，才算相對於 (W, P) 發生 hallucination。Unknown 不自動等於 false，因此沒有證據支持的敘述是否算 hallucination，取決於 benchmark 是否能建立反證，而不是由「無法驗證」四字直接決定。這也迫使每個評估回答三件事：真實世界是哪一個、模型看得到哪部分、資訊衝突如何解。

論文用 4 個代表案例展示同一模板如何涵蓋文件摘要、開放域問答、RAG 與 agentic web navigation。摘要可把來源文件設成 W，因而外部世界正確但文件未記載的內容可能只是 unknown；開放域問答則可把可驗證世界知識設成 W；RAG 必須顯式寫出檢索文件與參數知識的優先政策；瀏覽器 agent 的 W 可以是 DOM、頁面狀態與執行歷史，宣稱已點到不存在的按鈕就是 world-model mismatch。這個數量描述作者的說明架構，不是效能數字。

Benchmark 配方與論文結論

作者提出可擴充的環境式 benchmark 配方。先由已知 state 與 history 的 environment backend 產生文件、log 或頁面，再由 query generator 生成問題，最後改變 view function 控制可觀察性與 retrieval quality。對選擇題可直接比答案；對自由生成則抽出 atomic claims，交給能讀取明確世界狀態的 truth function 判斷。棋類只是示範：棋盤、走子歷史與規則提供可計算的 reference world，同一狀態能產生合法走法、位置追蹤、反事實與自由解說等查詢，而不必逐題人工標註。

這篇沒有訓練新模型，也沒有執行新的模型效能實驗，因此沒有可報告的作者自報實驗數字。主要產出是定義、歷史統整與 benchmark 設計主張。結論是 hallucination 應保留給 world-modeling error；如果模型理解世界卻選了差的計畫，那是 planning error；如果模型知道自己不確定卻因獎勵或提示而裝得肯定，那是 incentive error。三者可能同時出現，但不能因最後答案錯了就全部叫 hallucination。

局限與後續問題

形式化把爭議顯性化，卻沒有自動解決真相來源本身的爭議。真實應用中的 W 往往不完整、持續變動，P 也可能需要從使用者互動中推斷；claim extraction 與 truth function 仍可能出錯，unknown 的處理更會直接改變評估結果。論文提出的棋類 benchmark 仍是構想，不是已實作並驗證過的資料集；框架是否能讓不同研究團隊產生一致標註，也尚無 empirical evidence。

作者把後續工作放在四條線：系統性測試 conflict policy、處理非平穩的 reference world、把環境擴到更長歷史與部分可觀察的世界（作者明列 Web/DOM、Codebase/Repos、Databases/logs、Multimodal simulators 四類），以及在互動迴圈中分開 belief error 與 control error。真正困難之處會是維持 W、V、P 與 verifier 的版本一致，而不是再發明一個錯誤類別名稱。

對讀者的價值／ai_core 接點

這篇替 ai_core 提供一個很實用的錯誤帳本。每次判定「模型幻覺」時，都應一併保存 reference world 的版本、當時交給模型的 view、衝突政策，以及被判 false 的最小 claim。少了其中任何一項，錯誤名稱都不足以支持重現或治理。這與 ai_core 的憑證准入相容：憑證不是抽象的「可信」，而是相對特定世界、可見資訊與裁決規則的證明。

另一個接點是把 agent 的 belief 與 control 分開驗。工具呼叫失敗後仍宣稱成功，屬於對 execution history 的 world-modeling error；知道失敗卻選擇錯誤補救，才是 planning error。ai_core 若在 trace 中分別記錄觀察、內部狀態宣稱、決策與結果，就能把 remediation 對準真正壞掉的層，而不是所有失敗都回頭改 prompt 或知識庫。
