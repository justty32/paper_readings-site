對讀者的價值

  • 對應 ai_core §3.6「固化引擎」最硬未決題之一（何時該固化、留什麼丟什麼），本文站在主題 11 的記憶效率端給出一個乾淨但侷限的答案：「當抽象能廉價、確定性地從實例導出時，把抽象當成一次性 loss 項用掉、完全不存實例，也能比什麼都不做更穩定，甚至在泛化面優於存 100 筆的 reservoir buffer」。這對映到 ai_core「把案例結晶成抽象後就能丟掉原案例」的直覺——證據顯示這個直覺部分成立、但有明確代價：AAT 在「未知/需抽象推導的關係與敘事泛化」上確實優於或持平於 ER buffer 且完全免存儲；但在「已知/情節性事實保留」上，RCB 與 NAB 的 Acc_cumul^known 均顯示 ER buffer 仍略勝 AAT——單純的結構抽象 loss 不能完全替代「存實例」在情節記憶保真度上的作用，論文 §5.4 自己也定調兩者是「complementary mechanisms」而非替代關係。所以「結晶後即可丟棄原案例」這句話對結構性/可泛化知識站得住，對情節性/精確事實則站不住：只做結構抽象、不留任何案例痕跡的固化引擎，會系統性犧牲精確事實回憶。
  • 更根本的落差：與 **DreamCoder（2006.08381）／Stitch（2211.16605）／LILO（2310.19791）**這類「從解過的案例語料中歸納出可重用符號抽象、逐輪成長函式庫」的固化引擎路線相比，AAT 完全不處理「該抽象出什麼」與「庫如何成長不爆炸」——它假設抽象生成函式（實體遮蔽規則、諺語-敘事配對）已由外部管線給定，且用完即丟（不留存抽象本身，不構成任何持久資產）。換言之 AAT 跳過了 library induction 這一步，只回答「給定抽象後，該怎麼用它取代存儲」。理論上兩者可疊加：先用 DreamCoder/Stitch/LILO 式 library learning 從重複案例歸納出結構模板，再用 AAT 式的 loss 機制把該模板當免存儲的穩定化訓練訊號注入。
  • 與 ActionPiece（2410.15184）對照更細：ActionPiece 也是把重複子序列結晶成新 token，但那是持久化、增量成長的庫（chunk 加進動作空間、跨 episode 保留，Increment 版本刻意一次只加一個以避免庫爆炸）；AAT 的「抽象」卻是瞬時、每實例現算現丟，不構成任何庫。這凸顯 AAT 並非「庫」意義下的固化，更接近訓練期的結構先驗正則化/資料增強技巧，而非可被其他消費者讀取複用的資產。
  • 與 **前瞻式壓縮（2605.09985）**對照：該文問的是固化的「時序」該面向過去（回溯壓縮已見語料）還是未來（前瞻預測會被複用的結構）；AAT 完全不涉及這個時序決策——它的抽象在每個實例首次出現時就被動生成、即時用掉，不存在「要不要固化、固化這個還是那個」的選擇問題，因為它根本不建庫。可以說 AAT 站在 ai_core 固化引擎決策光譜的一個極端（完全不固化、只用結構先驗做訓練期正則化），是「真正建庫」這條光譜（ProspectiveCompression/DreamCoder/Stitch/LILO/ActionPiece）的補集/下界參照，兩者回答的是正交的問題。
  • 歸 I 類（認知科學驅動的連續學習訓練訊號設計，非程式合成/library learning 工程）。適合思考「固化引擎能否完全不留案例痕跡」「結構先驗 vs 存儲式記憶的取捨邊界在哪」的讀者；不宜誤讀為 library learning 方法本身。
