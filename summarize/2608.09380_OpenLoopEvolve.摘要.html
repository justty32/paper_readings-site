論文／訪談原始來源

《OpenLoopEvolve》重點摘要

一句話概括

OLE 把 agent 的整個執行迴圈變成可版本化資產：候選 policy 必須與 Champion 在相同條件下成對比較，通過效益、證據、風險、成本 gate 後才可在下一個任務邊界啟用，退化便回滾 parent。

物件邊界

Loop Policy 有八個可改元件：觀察、規劃、記憶、行動、驗證、復原、停止、預算控制。每個 Bundle 包含 policy、適用條件與 lineage；trace 記錄使用的 Bundle 版本、完整互動史與可驗證結果。從 trace 抽出的 evidence 必須指出改動方向、量化差異、目標元件和支持它的 trace 索引，避免把「某次成功」變成無法追溯的 prompt 直覺。

演化與發布

線上模式依近期可歸因 feedback 產一個 Challenger；線下模式從 archived traces 產多候選，跨代保留 nondominated 方向並變異／重組。兩者都用 shared applicability conditions 下的 Champion–Challenger paired evaluation。release gate 同時檢查效益、證據品質、tail risk、資源成本；註冊版本不等於發布，也不等於啟用。

線上成功候選只能在下一個 task boundary 生效，讓同一任務從頭到尾使用同一 Champion。CanaryMonitor 以後續可歸因 feedback 監看退化，觸發時退回 parent 並隔離造成回滾的 trace。這是本文最值得保留的部署語義：search、release 與 execution path 分開。

原文實驗結果

作者在 YC-Bench 模擬整年商業經營，以 DeepSeek-V4-Flash、官方 medium 設定、三個 seed 比較原生 agent、固定初始 policy、OLE-online、事前演化後固定的 OLE-offline。相對固定初始 policy，online／offline 的平均 final funds 分別增加 140.07%／166.31%，success rate 增加 13.98／17.92 個百分點，annual survival 從 1/3 變 2/3／3/3。

代價也明列：三 seed 的可觀測總 token 為 64.52M（online）與 59.63M（offline），含 29.82M／24.02M evolution-validation token；候選生成呼叫的 usage 未保存，因此不在總數內。結果是作者在單一模擬 benchmark 的主張，不是跨 host 或真實營運已證實的效果。

局限與接點

論文尚未驗證跨情境 transfer、長期穩定性與大規模成本控制，online/offline 由應用選擇而非自動切換。實作上應把 lineage、適用範圍、固定比較條件、回滾原因與 gate 證據做成不可省略欄位；否則只是「存了較好的 prompt」，不構成可治理的 policy release。完整原文逐節精要見下檔。
