作者：Cheng Qian, Chi Han, Yi R. Fung, Yujia Qin, Zhiyuan Liu, Heng Ji（Tsinghua, UIUC；EMNLP 2023 Findings）

日期：2023-05

arXiv：2305.14318

論文／訪談原始來源

《CREATOR：以工具創造解耦大型語言模型的抽象與具體推理》重點摘要

一句話概括

CREATOR：不把 LLM 當工具使用者而是工具創造者，以四階段管線——Creation（抽象推理：針對「問題類型」創造含文件的可復用工具）→ Decision（具體推理：決定如何呼叫工具、印出答案）→ Execution（純直譯器執行，無 LLM）→ Rectification（依錯誤回溯自我矯正）——把「造工具的抽象推理」與「用工具的具體推理」解耦，使 ChatGPT 在 MATH/TabMWP 達 59.7%/94.7%，大幅超越 CoT、PoT 與 WolframAlpha tool-use 基線。

解決什麼問題

工具增強 LLM 的三大痛點：(1) 範圍受限——依賴少量給定 API，新問題型態找不到合適現成工具；(2) 推理脆弱——逐例臨場推理易受隨機錯誤影響，缺乏人類「從相似問題萃取穩健共通性」的能力；(3) 錯誤處理不足——現有工具管線缺乏自動、針對性的錯誤修復。深層原因：規劃與執行糾纏在同一次隱式推理裡，認知負擔過重。

核心方法

  • 創造階段＝抽象推理：LLM 忽略數值細節、辨識問題內在特徵，為「問題類型」寫出封裝成函數的工具＋程式碼註解文件（如「解三元方程組」工具）。
  • 決策階段＝具體推理：LLM 讀工具文件，針對特定查詢寫出呼叫程式碼並以 print() 輸出答案——理解工具輸出與查詢的連結（如解還要加總）。
  • 執行階段：工具＋決策串接成一個程式碼區塊，交直譯器跑；截獲輸出或錯誤回溯。LLM 不參與。
  • 矯正階段：有錯誤→餵回原碼＋traceback，LLM 以自然語言分析＋改碼重試；成功→抽答案比對。推理因此非線性。
  • 程式碼作為工具創造的媒介（非外部工具）：對錯誤敏感→可自動矯正；可封裝→可復用。
  • 另建 Creation Challenge（2K 題，現成工具/套件解不了）評估工具創造能力本身。

結果

  • MATH 59.7%／TabMWP 94.7%／Creation Challenge 75.5%，全面勝過 Vanilla CoT（37.9/75.2）、PoT+矯正（53.9/87.3）、WolframAlpha Tool Use（43.0/79.6）。
  • 解耦本身就有增益：合併創造與決策的消融版（CREATOR-Entangled）在 MATH 57.2 vs 解耦 59.7；且愈難的題優勢愈大。
  • 矯正階段帶來約原值 10% 的準確率提升；工具創造**提示（hint）**最多再提升 18.7%。
  • 工具遷移實驗：100 組「同核心概念、異情境」三題組，遷移已建工具使準確率 63.0%→78.3%（+15.3%），39 組受益、僅 2 組變差——工具＝知識概念的抽象，可跨情境復用。
  • 有趣發現：MATH 上加 CoT 反而變差（自然語言思路干擾程式思維）；LLM 無引導即展現三級創造力——封裝改造既有 API、串接多 API 成管線、層級化工具（caller-callee，最常見）。

局限

  • 僅測 MATH/TabMWP/自建 Creation Challenge，基座只有 ChatGPT；泛化性待驗證。
  • 只評數值答案題（約 80%），複雜格式匹配未解。
  • 工具皆為單次會話內即席創造，論文未建持久工具庫（遷移實驗是人工安排的）；LLM 建完整專案管線級工具的正確性仍缺評估。

對讀者的價值

  • 對 ai_core 的核心啟發是 §2「資產工廠 vs 資產消費者」的另一個正交切軸：與 LATM（2305.17126）用「貴模型造工具、便宜模型用工具」按模型成本分工不同，CREATOR 按推理性質分工——抽象推理（造工具）與具體推理（用工具）即使在同一個模型內解耦也有增益（Entangled 消融證明）。兩者可疊加：ai_core 的資產工廠應同時做到「貴模型 + 抽象階段」。
  • 工具遷移實驗（+15.3%）是 §3.6 固化引擎的直接證據：工具＝「知識概念的抽象」，一次創造可覆蓋整簇同核心概念的查詢——這正是「把 LLM 反覆處理的案例結晶成確定性程式碼」的最小可行版本。CREATOR 的缺口（工具用完即棄、無持久庫）恰好就是固化引擎要補的東西：加上儲存、檢索與准入即成資產庫。
  • 執行階段完全不用 LLM＝ §1 符號神經網路計算圖的節點分型範本：LLM 只出現在創造/決策/矯正三個節點，執行是純確定性節點；矯正階段「traceback 餵回→改碼重試」則是把 LLM 呼叫包成可靠函數的錯誤處理迴路（對照 CRITIC 2305.11738 的工具驗證）。
  • 「hint 提升最多 18.7%」對 §5 程式碼助手有操作意義：上層結構化抽取若能先產出工具的 utility/輸入/輸出規格再讓下層填碼，品質顯著高於自由發揮——即受約束填碼優於無約束生成的又一實證。
