論文／訪談原始來源

《技能漂移即合約違反：LLM Agent 技能庫的主動式維護》重點摘要

一句話概括

把 LLM agent 技能庫的「技能漂移（skill drift）」重新定義為環境合約違反：只監控技能文件裡「角色承載（role-bearing）」的作業假設（如固定依賴、API 端點、schema），忽略附帶提及（如註解、徽章），從而將合約無監控（CI probe）的 40% 誤報率壓到零誤報——在 599 個無漂移與 false-alarm 負例上零誤報（Wilson 95% CI [0%, 0.6%]），同時在已知漂移驗證達 100% 精確率與 76% 召回率，且違反的合約可作為局部修復訊號，將單輪修復成功率從 10% 拉至 78%。

核心貢獻

  1. 合約違反框架：技能漂移不是「環境值變了」，而是「該技能作業上依賴的假設不再成立」。將監控單元從裸值（raw value）改為角色承載義務（operational obligation），徹底改變誤報特徵。
  2. SKILLGUARD 系統：(a) 提取——15 類正則家族先抓候選環境提及，再透過 LLM 語義判定其為 OPERATIONAL 或 INCIDENTAL；(b) 驗證——只在角色過濾後才匹配已知漂移或即時條件（套件註冊表、URL 回應）；(c) 修復——違反的合約記錄定位失效假設，作為局部編輯規格。
  3. DRIFTBENCH 基準：880 對資料集——174 對受控漂移（8 類，跨家族驗證 + 仲裁 99.6% 有效性）、107 對 LLM-free 真實世界漂移（PyPI/npm/GitHub Actions/Docker Hub），以及 599 組負控制（49 identity + 300 formatting hard negatives + 250 semantic hard negatives）；外加 20% 分層隨機人類審計。
  4. 實證三問：(Q1) 合約壓制誤報且不犧牲召回；(Q2) 在無已知漂移規格的即時發現中保守精確率 86%、召回 55%，2 例 FP 事後裁定為真正漂移；(Q3) 失敗合約使修復可操作——從純「技能過時」提示的 10% 升至 78%，使用更少 token（~10K vs ~18K Self-refine 三輪）。

對讀者的價值（與 ai_core 的接點）

  • ai_core §3.4 憑證（合約違反檢測）：SKILLGUARD 的 OPERATIONAL/INCIDENTAL 區分就是一種「合約憑證准入」——ai_core 的憑證機制不應只檢查輸出結果，也應檢查 agent 使用的技能文件中的環境合約是否仍然有效；本文提供了完整的角色判定→驗證→違反定位管線，可直接嵌入 §3.4 的憑證驗證層，作為技能載入前的合規檢查。
  • ai_core §3.6 固化引擎（技能庫維護）：技能從「曾經可用」到「已固化為可信模組」的中間環節，就是持續監控其環境合約是否仍成立。本文的合約驗證可作為固化引擎的「健康檢查」子系統——當技能綁定的 API 端點、依賴版本、schema 發生漂移時，自動標記該技能為「需重新固化」，觸發修復或人工審查，避免靜默失效累積。
  • risk-coverage 權衡的延伸：與 selective classification 的文獻呼應——不是追求召回 100%，而是保證「我報告的漂移一定是真的」（precision-first），將維護訊號的信任成本降到最低，這與 §3.3 成本梯度／級聯路由「便宜節點先答，不確定才升級」的哲學一致。
  • DRIFTBENCH 可直接用於 ai_core 技能庫評估：其 semantic hard negatives（改值但不違反合約）正好測試 ai_core 固化後的技能在文檔表面變化時是否被誤判為失效——對 §3.6「哪些案例已穩定到可結晶」的判斷極有參考價值。
