論文／訪談原始來源

AI4AI-Bench: Benchmarking LLM Agents in Algorithmic Design for Recursive Self-Improvement 重點摘要

一句話

AI4AI-Bench 用 10 個凍結的真實研究 repo，把「agent 改了訓練演算法本身」與「agent 只是改了這次 run 怎麼跑」拆成可分類的兩件事，發現多數提交只做到後者，且只有做到前者的提交才真的把分數拉高。

方法：4 小時改、12 小時重跑、evaluator 全程看不到 agent

每個任務是五元組 (C, a₀, q, m, d)：凍結的 repo 原始碼 C、起始模型 a₀、agent 可自由查詢的便宜 proxy metric q、最終指標 m 與方向 d。Agent 在一張 B300 上有 4 小時讀 repo、改訓練程式碼、用 proxy 測試想法，交出的只有原始碼 patch，不含任何自己訓練出的權重或快取狀態。4 小時一到，patch 被放進乾淨容器從頭訓練，最多跑 12 小時（不訓練的兩個任務 12 小時只是驗證階段的上限），取最近三個 checkpoint 中最好的一個，由評測前就固定、對 agent workspace 沒有存取權的 evaluator 打分。對照組是 repo 原本的演算法碼在完全相同流程（同硬體、同預算、同 evaluator、同資產）下的分數，這樣勝負只能歸因於 agent 改的程式碼本身。

10 個任務對應 10 個彼此不可比的訓練演算法家族：OpenR1（監督微調）、RAGEN（多輪 agentic RL）、OPD（on-policy distillation）、BTRM（Bradley–Terry reward modeling）、DPO（偏好最佳化）、DDPO（diffusion RL）、NPO（機器遺忘）、DiGress（離散圖擴散）、Model Soup（權重平均）、OWL（one-shot pruning）；後兩者不訓練，只執行一次。因為 10 個指標單位互不相同（勝率、AIME 分數、perplexity、美學分數……），論文把每個任務的指標映到同一個座標 σ(x)：0 分是不帶任何任務資訊的模型，0.1 分正好是 repo 自帶的演算法，1.0 分是任務理論最優；0.1 以下量的是離 repo baseline 還差多遠，0.1 以上量的是離最優還剩多少距離被補上。所有跨任務的平均都是 σ 的平均。

論文再用另一個語言模型讀每份提交的 diff，把改動歸到「run 側」（訓練多久／多常存檔、超參數、留哪個 checkpoint、可訓練容量與位置）或「learning 側」（loss、監督訊號、update rule 本身、訓練資料）八個家族之一，用以區分「改執行方式」與「改學習方式」。

作者報告的實驗與資料限制

以下數字均為作者自報。受測 6 個系統共 29 種 (model, harness, effort) 組合 × 10 任務 = 290 格：三個 GPT-5.6 變體（Sol、Terra、Luna）在 Codex 下跑全部六個 effort 等級，Opus 5、Sonnet 5 在 Claude Code 下跑五個等級，Kimi K3 在 Claude Code 下只跑最高等級。整體平均分 0.166，最強系統 Claude Opus 5 平均 0.250，單一最佳組合（Opus 5、medium effort）0.288；290 格中有 124 格（逾五分之二）低於 0.1，即比 repo 原演算法還差。系統排序：Opus 5 0.250、GPT-5.6 Sol 0.191、Kimi K3 0.174、Sonnet 5 0.145、GPT-5.6 Terra 0.135、GPT-5.6 Luna 0.117；花費與名次無關，Sol 每次探索中位數 $434、Luna 僅 $48，但 Opus 5 中位數只花 $181 就是全場第一。

280 份提交中 17 份無法歸類，餘 263 份：141 份只碰 run 側，122 份碰到 learning 側；碰到 learning 側的平均分 0.226，只碰 run 側的平均分 0.126，差距 0.100（標準誤 0.022），排除 agentic RL 任務後仍有 0.182 對 0.128 的差距。Reasoning effort 從最低拉到最高，碰到 learning 側的提交比例從 8.0% 升到 64.0%，平均分從 0.094 升到 0.196（差距 0.102，標準誤 0.027，在只換 effort 不換 harness 的 Codex 子集中是 0.094→0.204）；同時中位數評測次數從 4 次升到 16 次、改動行數從 18 行升到 246 行、輸出 token 從 1.1 萬升到 10.9 萬、每任務探索成本從 $1.69 升到 $34.60，全場探索階段共花 $5,334（不含 12 小時訓練與 evaluator 算力）。19 格拿零分：8 格根本沒交出可用 patch（其中 4 格是 agent 提早退出留下空 workspace），11 格交了完整 patch 且開始跑 12 小時但沒產出符合要求的模型；19 格中 12 格集中在最低兩個 effort 等級。

局限：本文沒有獨立的 Limitations 節，以下是作者散在正文的保留與本檔閱讀時的補註。作者自己標註的有三點：effort 的機制是「讓 agent 更敢碰 learning 層」而非「碰了之後改得更好」；碰 learning 側更多的系統本來就是較強的系統，這是相關而非可隨機化的因果證據；proxy 與最終 evaluator 的隔離是「存取與時序」的隔離而非樣本互斥，有些任務的便宜 proxy 就抽自最終評測用的語料，論文只保證 agent 無法用決定分數的那個指標打分候選。另可注意：提交分類語料是 280 份（不含 Kimi K3），歸類由另一個語言模型讀 diff 完成、家族不互斥（平均命中 3.13 個）；10 個任務的指標、baseline、proxy 均由作者自行凍結與設計，尚無第三方復現。

對 ai_core 專案的價值／接點

這篇最直接可借的是「執行層改動」與「學習層改動」的分類法（run 側 4 類 vs. learning 側 4 類，§4.1 Table 4），可以直接套進 ai_core 的固化引擎輸出稽核：一次自我改進提交如果只碰了 batch size、checkpoint 選擇、adapter rank，即使分數變好也不算「學到新演算法」，該用同一套分類原則區分「這次 run 調參調贏了」與「這次真的換了學習規則」，避免把執行層微調誤記為方法論進步。對驗證器與可比較評測底座的啟發更直接：它的 （proxy, 隱藏 evaluator, 同協定 baseline） 三件套——探索期可以無限次查 proxy，但決定分數的 evaluator 在提交後才跑、且對 agent workspace 零存取——正是防止「evaluator 洩漏進開發迴圈」的具體做法，可作為 ai_core 驗證器設計「探索可見／評分不可見」邊界的參考範本。§4.3 三個案例（OWL 案例先建 diagnosis 找出 layer 0/31 的 activation 覆寫 bug 才動手；Model Soup 案例先把評測 rig 從 190 秒壓到 0.38 秒才能大規模比較候選方法）也印證：能真正碰到演算法層的提交，共同點是「先造一個可測量的工具或診斷，再動手」，這對 ai_core 的成本梯度分析（區分探索成本與資料/改動價值）是可直接複用的觀察。
