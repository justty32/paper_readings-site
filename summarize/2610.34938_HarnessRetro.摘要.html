論文／訪談原始來源

Coding-agent harness 的回顧式調整是否在後續任務有效？

一句話概括

本研究讓 coding agent 在完成任務後執行 /retro，提出對 harness 的持久修改，再把個別修改轉移到同一 repository 的後續問題。作者觀察到：提出並載入修改不保證改變後續行為；在七個資訊充分的轉移事件中，兩項消除目標動作、一項降低、四項未降低。這是有限且針對特定環境問題選題的案例觀察。（摘要、§IV）

研究設計：從提案到後續任務

作者在 SWE-bench Verified 的 30 個 issue 上，以 Claude Code 2.1.295 與 Opus 5.5 執行編碼任務，完成後在同一 session 執行固定版本 /retro，保留 125 項編號提案。前 10 題是五個 repository 各隨機抽兩題；後 20 題則刻意挑先前出現環境問題，且能找到同 repo 較後 issue 的 repository，因此不代表任意 coding 任務。（§III）

兩條 LLM 編碼線以同一 codebook 分別判定提案的觸發來源與修改機制：一條讀完整軌跡，另一條讀摘錄；作者再處理分歧。兩線對 125 項提案的觸發與機制各有 109 項一致，Cohen κ 分別為 0.67／0.84。這是兩個 LLM 編碼程序和不同輸入的一致性，不是人類編碼者之間的信度。（§III）

作者挑選符合條件的 24 個提案，在原 session 和容器中由 Claude Code 實作；其中 11 項形成可在其他 issue 上評估的調整。另有一項與 session 事件無關的 pre-commit 提案，因權限系統阻止代理實作而由作者編寫，合計評估 12 項調整。研究者負責選擇要實作的提案、後續任務及結果標記，因此這是有人選擇與評估的自我演化研究，而非完全自主循環。（§I、III）

12 項調整對應 13 個轉移事件：其中一項在兩個後續 issue 測試。每事件分別在原 harness 與加入該項調整的 harness 下各跑五個新 session；三項調整另在無關控制題測試是否增加工作。研究者選擇已在新容器中確認可能重現目標問題的 issue，因此此設計檢查「問題可出現時行為是否改變」，不估計任意後續 issue 的受益機率。（§III）

提案：大多來自經驗，部分反映既有偏好

作者自報，125 項提案中 101 項根據 session 事件、19 項基於既有偏好、5 項與事件關聯較弱。最多的機制是可執行檢查，共 38 項；但只有其中 9 項可在當次任務環境按原樣回報失敗，其他多因缺工具或 session 沒有 commit 而不會觸發。30 個 session 中 29 個出現 lint 相關提案，共 43 項；其中 18 項屬既有偏好，沒有以本次事件為依據。（§IV，表 I）

這不代表依事件提出的建議必然正確。作者指出，調整可能只反映單次問題、以後沒進 context，或雖被讀取卻沒有改變行動；提案、實作、載入與效果是不同階段。（§I）

轉移結果：先看是否遇到、是否覆蓋

研究把「重複工作」操作化為後續 session 再執行調整意圖避免的特定動作，而不是直接判定該動作不必要或避免它一定提高任務成功率。作者把至少三個原 harness session 真正遇到目標問題的事件定為資訊充分；13 個事件中有 7 個符合。所有改過 harness 的 session 都載入轉移的 context-file 指示，但載入或查閱不等於採納其內容。（§III–IV）

調整與後續情境 原 harness 重複目標動作 調整後 作者觀察
SymPy：指出 bin/test，避免先試未安裝的 pytest 5/5 0/5 所遇問題被指示覆蓋
Astropy：列出三個已知失敗測試 3/5 0/5 所遇失敗被清單覆蓋
Astropy：快取修復與比對腳本 5/5 2/5 仍遇到清單未涵蓋的 NumPy 失敗
另外四個資訊充分事件 見原表 未降低 後續遇到清單未涵蓋的失敗

以上為作者自報的 session 次數；其中一個未降低事件有一個調整後 session 因認證錯誤排除，故有效分母是 4。七個事件中兩項完全消除、一項降低、四項未降低；依事後分組，兩項覆蓋實際遇到的案例，另外五項未完全覆蓋。作者明示調整之間不只覆蓋範圍不同，樣本不足以證明覆蓋程度是唯一因果原因。（§IV，表 II、§V）

控制題也可能出現反效果：一個 Sphinx 已知失敗清單要求把未列出的失敗視為新問題，在無關 issue 上，調整後 4/5 個 session 執行原本欲避免的基線比對，原 harness 為 0/5。SymPy 的測試命令指示消除了失敗的 pytest 嘗試，但同時要求執行 CI lint，五個調整後 session 均執行；中位耗時由 88 秒增至 156 秒。（§IV，表 II）

研究邊界

  • 每事件每種 harness 只有五個 session，資訊充分事件僅七個；各事件中任務成功數在兩種 harness 間最多相差一個 session，沒有一致證據顯示任務成功率改善。重複動作減少也沒有穩定對應較短耗時。（§IV–V）
  • 後續任務經挑選可重現目標問題，可能高估一般後續任務遇到可受益情境的頻率；實作沿用原 session／容器，變更可能帶入提案文字之外的資訊。標記者可從軌跡察覺是否讀到轉移檔，並非完全盲測。（§V）
  • 本檔補註，非作者自陳：測試 runner 等持久指示與針對特定環境的失敗清單具有不同的變動速度；要判斷某項更新是否值得保留，應在具體後續任務記錄問題是否遇到、更新是否被查閱、行動與整體結果是否改變，而不能只看產出數量。
