所以它一直在發生相當大的演變。剛開始時，非常符合它的名字，PROS 代表「依範例的程式合成」（Program Synthesis by Examples）。在剛開始時，我們研究的所有程式合成都是使用者透過範例給出意圖。因此，使用者不需要描述他們正在做什麼。他們只是在做他們的任務。合成器會捕捉使用者所做事情的範例作為某種意圖，然後預測一個公式或程式來自動化該意圖。最著名的例子當然是 Excel 中的 FlashFill。如果你要建立一個新欄位，並且手動填寫欄位中的一些值，它會自動學習一個程式來幫你填寫欄位的其餘部分。想像一下，比如取得名欄和姓欄，用點號將它們連接起來，並加上一個 @company.com。嗯，同樣的技術對於程式碼中的重複性編輯也發揮得非常好。想像一下你有一個在某處定義的函數，而你正在為它添加一個新引數。如果模型看到你進行了兩次這種修改，即你採取的步驟序列（也就是轉換前後變化的步驟），也可以轉化為輸入輸出範例。而這些輸入輸出範例接著可以用來學習對你的程式碼進行轉換，從而在你的整個程式碼庫中實際執行這種修改。

嗯，當然，這件事現在大部分已被 LLM 接管了，但特別對於 FlashFill 的情況，我認為保有符號方法仍然極具價值。嗯，此外這個框架也非常靈活。預測性程式合成還有一些應用，在這些應用中，你不用範例，只要你有非常好的啟發式規則（heuristics）來約束你想要的東西。例如對於表格，你知道一個欄位很可能具有一致的資料類型，比如在一個欄位中很可能全是數字、字串或日期，而不是混合在一起。因此，如果你給它一個網頁之類的東西，它也可以學習一個微型程式來從這些網頁中擷取表格。所以所有這些都是核心的符號方法，其中的意圖是透過範例或某些啟發式規則或範例外觀的屬性來給出的。

後來 LLM 出現了，情況就改變了，因為隨著 LLM 的降臨，以及語言面向在大型神經網路模型中變得越來越重要，指定那種意圖的方式也改變了。如今，大多數人——也許不是大多數，但很多人——不再手寫程式碼了，他們使用這些程式碼助手來幫他們進行程式設計，對吧？因為它讓你能夠非常輕鬆地用自然語言表達你想做的事情，然後直接生成一堆執行你任務的程式碼。所以這是 PROS 團隊中許多人現在正在研究的內容，特別是像 Excel Agent 這樣的項目，其目標是學習一小段程式碼來轉換試算表以執行非常複雜的任務，比如創建一個完整的財務模型之類的東西。然後它會繼續前進，它不僅僅是修改試算表，它實際上會寫出一段程式碼來為你修改試算表。

是的，是我的導師 Luc De Raedt，他有一個關於自動化資料科學的 ERC（歐洲研究委員會）專案。我的意思是，當時還不是自動化資料清理，他在自動化資料科學方面有一個 ERC 專案，而自動化資料科學的支柱之一當然就是自動化資料清理/爭議處置（data wrangling）。所以，我被分配到了那個支柱，也就是資料清理支柱，該任務的規範是：給定任何類型的輸入表格，想像有人打開了一個隨機的試算表，裡面有一個表格，他們想開始對它應用機器學習演算法，對吧？那能自動運作嗎？大概不行，對吧？表格可能沒有正確的形狀，比如你可能需要進行摺疊或展開（轉置/樞紐 Pivot 或取消樞紐 Unpivot），也許有一些缺失值，因為你需要進行前向填補（forward fill），畢竟看著重複的值不太舒服，對吧？或者任何情況都可能發生，對吧？表格極不可能是一個完美的關聯式表格（relational table）。因此，前提是我們能否將其轉化為關聯式形狀。

所以，與其直接——資料科學家會怎麼做這些類型的轉換呢？就是精確地編寫一段程式碼，對吧？資料科學家會使用 pandas 或他們想使用的任何程式庫或 R 語言，寫一小段程式碼來進行這類轉換。因此，嘗試學習這類程式，然後將表格轉換為適合資料科學的形式，似乎是非常顯而易見的方向。在知道了這一點之後，下一個問題就浮現了，那就是通常在程式合成中，你有某種意圖，在許多合成中（比如許多符號合成），意圖是一個範例或形式規範（formal specification）之類的東西，有某種東西說明了我們希望這個程式的輸出長什麼樣子。而對於資料清理來說，剛開始這一點並不十分清晰，對吧？我們只知道它必須滿足某些屬性。

但事實證明，如果你非常仔細地指定這些屬性，並對可能的程式進行某種聰明的啟發式搜尋，如果你找到一個合理簡單的短程式，能將你的表格轉換為能給出不錯的啟發式分數的東西，那麼它極有可能是正確的。對吧？人們在這些資料表格中產生的錯誤或缺陷並不是完全隨機的，對吧？它們會是非常具有結構性的。它會是像你需要做前向填補、樞紐轉換、取消樞紐轉換或移除空行之類的操作。這是一些非常有結構的操作。它通常不會是那種一次性的隨機事物，比如「好吧，我必須修改某處的一個小數值」，對吧？正因為是這些常見的轉換以及錯誤中常見的模式，預測性程式合成方法實際上運作得相當好。

一旦我們能夠轉換表格的形狀（即非常結構化的轉換），下一個部分就是特徵清理（feature wrangling）。同樣地，你有一個字串，例如你有來自房屋描述或某種位置資訊的一段文字，現在你想應用某種機器學習器或分群（clustering），文字字串將不會非常有用。同樣地，你的資料科學家會怎麼做？他們會寫一段 Python 程式碼或其他程式碼，將一欄轉換為可用的特徵。所以我們可以重複相同的想法，對吧？現在假設我們有一欄字串，那絕對不是一個好特徵。我們能把它變成一個好特徵嗎？所以再次定義一些以有意義的方式轉換字串的函數，比如分割字串、匹配某種正規表示式模式並擷取數字以及所有這類東西。嗯，然後如果你採取一個代理啟發式指標（proxy heuristic）——要麼你知道你想預測哪一欄（這是非常合理的假設），你基本上可以清理一堆特徵，就像你生成成千上萬個不同的特徵，然後使用某種特徵選擇方法來看看清理後的轉換中哪些是好的，然後你可以預先剪枝（pre-prune）其他所有東西，並且可以重複幾步。如果你的特徵選擇器引導得好，它實際上運作得相當好。對吧？這又是預測性合成，因為意圖就像（你知道的）你假設意圖是進行分類之類的事情，但這給了你一個非常好的啟發式指標，對吧？你使用使用該特徵的預測能力作為啟發式指標，看看我正在編寫的程式是否擷取了好的特徵。而這些就是我開始時所做的一些有趣的事情。
