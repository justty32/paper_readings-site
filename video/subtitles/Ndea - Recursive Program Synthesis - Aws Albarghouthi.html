好的，《遞迴程式合成》（Recursive Program Synthesis），這篇令人讚嘆的論文！第一，每個人都應該去讀讀看，我覺得它超級酷。你在其他方面發表的論文也都非常棒。我發誓我很少在 Google Scholar 上看到有人列出這麼多程式合成相關的論文，你真的絕對是這個領域的超級巨星。不過關於這篇論文，你剛剛給了我們一些背景介紹，但你和你的合作者當初是怎麼產生那個原始想法，並促使你聯繫 Sumit 的呢？

好的，就像我剛才提到的，我當時在讀博士，研究的是程式驗證（program verification），也就是自動化程式驗證：如何自動建構證明？具體來說，我博士早期的項目之一是關於證明帶有程序（procedures）以及遞迴（recursion）的程式的正確性。

當你在證明一個遞迴程式時，這是一種非常有意思的證明技術。舉例來說，假設你想證明這段程式碼能夠正確地反轉一個鏈結串列（linked list）。這種證明依賴於數學歸納法（induction），這是一種標準的數學證明技術；但即使它是標準技術，當你真正進行這種證明時，依然會覺得非常深刻且震撼——因為你在證明這個函式的某個性質，但當你碰到程序呼叫（procedure call）時，你必須先「假設」你試圖證明的性質確實成立，然後繼續往下推導。

所以這裡存在著這樣一個假設。我在那個領域做了一些工作，自動建構這些證明非常有意思。後來當我們開始關注程式合成時，我們成立了一個讀書會（reading group），去探索當時發表的一些論文。我們發現當時大多數論文生成的都是直線型程式碼（straight-line code）。

想像一下像位元微調（bit-twiddle）程式，也就是一連串低階組譯語言風格的指令。當時有一個來自 Armando Solar-Lezama 的項目叫 Sketch（當時他在柏克萊，後來去了 MIT），它主要也是在做無迴圈程式（loop-free programs）；或者即使有迴圈，也只會執行有限次數，實質上依然是無迴圈程式。

所以我們就想：好的，我們能否將這些想法擴展到遞迴？這純粹是一種美學上的追求，而不是說我們想生成某個極其龐大的東西，或是合成出某個非常實用的程式。當時更多的是出於好奇：這究竟有沒有可能做到？

於是我們開始思考這件事。我們試圖使用類似證明的想法：在證明中，你拿你要證明的性質，並在程序呼叫時假設它成立；而在程式合成中，你有一個規格（specification）或目標（例如：我想合成一個鏈結串列操作），當你建構程式時，如果你想呼叫這個函式本身，但你手頭上還沒有它（因為你正在寫它），那你就先假設它的行為符合你的預期，假設它會如預期般運作，然後繼續寫下去。這樣就有了遞迴，最終你就得出了那個程式。我們當時把這整套想法整理了出來。這是與 Zachary Kincaid 一起完成的，他現在是普林斯頓大學（Princeton University）的教授，當時他也是我的研究生同學，同樣在做靜態分析（static analysis）與驗證（verification）方面的研究。

如果我沒記錯的話，就在那個時間點，我們聯繫了 Sumit，跟他說：「這是我們正在做的事情，你覺得怎麼樣？」他回答說：「太棒了！我也一直在思考類似的東西。」我想我們當時試圖完全透過 SAT 和 SMT 求解器以符號化（symbolically）的方式來完成所有事情。

了解。那麼回到這個遞迴概念的大方向：就我所知，早期（特別是 2000 年代早期）的程式合成其實並不太處理遞迴。從最經典的角度來看，為什麼遞迴程式這麼難處理？

其實也不能說早期程式合成完全不處理遞迴，應該說是 2000 年代我們所基於的那些工作沒有處理遞迴。但是在我們的兄弟社群——也就是邏輯程式設計（logic programming）與傳統 AI 社群，也就是歸納邏輯程式設計（Inductive Logic Programming, ILP）社群——他們本質上就是在建構邏輯程式，而邏輯程式依定義就是建立在遞迴關係上的，例如「某人的祖父母就是其父母的父母」等等。

所以他們當時確實在做類似的事並生成遞迴程式。而我們當時寫論文時，完全不知道那整條研究脈絡！這很有意思，我還記得其中一份論文審稿意見，雖然給了正面的評價，但寫了一句讓我至今印象深刻的話：「這篇論文犯下的罪過在於，它完全忽視並無視了歐洲學者的研究成果。」

是的，有時大家甚至是在互不知情的情況下各自探索。好了，那麼這篇論文最核心的亮點、或者說名稱很酷的主角，就是這個名為 Escher 的演算法，對吧？

是的，它是一個歸納合成（inductive synthesis）演算法，用於學習這種遞迴程序。非常酷，它給定輸入-輸出範例（input-output examples）——這些範例可以來自使用者，甚至是非技術背景的使用者，這有點像是「依範例程式設計」（programming by example）的願景。

這是當初原始的願景嗎？另外為什麼取名為 Escher（艾雪）呢？我很好奇。

如果你看過艾雪（M. C. Escher）那些著名的畫作，它們都是遞迴性質的，比如「畫畫的手」繪製自身等等。這就是我們的靈感來源。

原來如此。傳統上對於程式合成，使用者有不同的方式來表達意圖（也就是你想要建構什麼）。如今當然可以使用自然語言，但在當時，自然語言實際上還不是一個可行的選項。

所以你當時要麼寫出一個完整的邏輯規格（logical specification）來描述你想做的事——不過這通常不是個好主意，因為在我看來，邏輯規格寫出來往往長得跟你最後要寫的程式碼差不多；你頂多能寫一些高階屬性（high-level properties）來規範限制，但寫不出具體的程式碼。另一種選擇就是「輸入-輸出範例」。

所以我們選擇了範例這條路。你剛剛問到了合成遞迴程式的挑戰所在，我覺得挑戰有兩方面：第一，你必須確保程式會終止（terminate）。你總是面臨生成一個會無限遞迴下去的程式的風險。

因此你必須確保你的搜尋過程所產生的東西，在某種「遞減」（decreasing）的定義下是持續減少的。

在那篇論文中，我們簡單地使用了一組固定的測度（measures）來定義遞減。例如如果你在操作一個串列（list），每次你進行遞迴呼叫時，串列的長度都必須縮小。

這是一點。當然你可以做更複雜的事，例如單純「生成終止性證明」（proof of termination）本身就是一個程式合成問題，因為你必須生成一個述詞（predicate）來證明某個量確實在遞減，而這個量在不同程式之間可能差異巨大。但大多數情況下，常見程式模式都非常有規律（stylized）：如果你在對一個串列進行遞迴，你幾乎總是對更小的切片（chunk）進行遞迴，對吧？除非你在做某些極其狂野的事情，讓串列非單調地一會變大、一會變小。

但幾乎所有時候它都在縮小。所以只要固定這個約束條件，就能走得非常遠，合成出非常多的程式。

第二個挑戰在於：正如我之前說的，當你進行遞迴呼叫時，你假設它的行為與你正在生成的函式相同；但在這裡，行為是用「範例」來定義的。當你發起遞迴呼叫時，你傳入的輸入可能根本不在你初始給定的範例集中。

那這時你要做什麼假設？我們不知道。所以我們提出的解決方案之一就是「飽和」（saturation）概念：你可以主動向使用者詢問更多資訊（範例），以便讓遞迴呼叫能夠順利運作。所以這是一個互動式的過程。

如果你只是想盲目地進行搜尋，你完全可以不假思索地直接列舉所有程式，一旦找到一個符合範例的，就可以大功告成。但在我們生成程式的過程中，我們意識到完整程式中的許多碎片（pieces），我們在搜尋途中其實已經碰到了。那為什麼不把這些碎片保留下來，等把所有碎片都找到之後，再把它們拼接在一起，而不是非要一上來就撞大運撞出整個完整的程式？

舉例來說，如果你要合成一個帶有兩個分支的 if 條件敘述，你可能會發現其中一個分支解決了一部分範例，而另一個分支解決了另一部分範例。你可以把這兩個分支保留下來，然後研究如何正確地把它們結合起來。於是你的問題就變成了：如何合成出一個條件判斷式（conditional），把這兩段程式碼拼接在一起。

這就是我們提出「目標圖」（goal graph）這個想法的由來。它本質上追蹤了「哪些子目標（或哪些範例）可以被哪組程式解決」，以及「如何將它們拼接在一起」。

另一個非常吸引我的點是「搜尋引導」（search guidance）——這也是我們在 India 非常關心的議題。在程式合成中，經典難題就是搜尋：即便你能定義出正確的程式，你要怎麼把那個該死的程式找出來？這涉及到可能性爆炸的組合爆炸（combinatorial explosion）。所以搜尋引導是 Escher 非常核心的一環，你能為大家詳細解釋一下你們具體提出了什麼嗎？

一點也沒錯。當你在生成程式時，你在生成指令序列，你發現：「噢，這個序列可以解決這些範例，那個序列可以解決那些範例。如果我把這兩個序列合在一起，就能解決所有範例了！」但此時問題倒轉過來了：我該如何合成出一個條件敘述，把程式拆分成兩部分，一部分解決這組範例，另一部分解決另一組？是否存在這樣一個條件敘述？這就是為什麼我們稱之為「反向搜尋」（backward search）——你是在回溯性地組合你的工作。正向搜尋生成程式碼片段，而反向搜尋則將它們拼接在一起。

所以我當時產生的想法是：我們能否為這類電腦自動生成編譯器（compilers）？因為歸根結底，即便這些電腦目前還沒做出什麼實用的事情，擁有一個編譯器能讓你回答諸如「對於這個應用，我需要多少資源？需要多少量子位元（qubits）？這項計算需要耗費多久時間？」等問題。如果沒有編譯器，你甚至無法回答這些問題，更不用說在電腦上執行程式了。

因此，我們開始研究為量子電腦「合成編譯器」這個課題，在這個領域深入探索了很長一段時間，如今取得了一些非常有趣的成果。

順便說一下，成果具體如何？

如果你思考量子電腦的編譯器，它看起來非常像傳統編譯器。不過它大多更偏向低階，因為我們目前所寫的計算依然是很低階的，就像 1970 年代的編譯器無法與今天的編譯器相比一樣。

我們主要是在處理組譯語言層級（assembly level）的指令，並將它們映射到具體裝置上。這就是我們所說的量子編譯器的概念。我們研究出了如何合成優化器（optimizers）。

優化器的作用與傳統編譯器一樣：接收一段程式並儘可能地精簡它，使其執行得更有效率。當你面對造價高達數百萬甚至數千萬美元的機器時，你在呼叫它們之前必須非常謹慎，所以你的計算最好儘可能精簡。而且目前的量子機器噪聲非常大、極易出錯；如果你的計算過程太長，最後輸出的就完全是一堆垃圾。所以你必須儘可能壓縮它。正如我提到的，指令集變更得非常迅速，所以我們說：「給我一個指令集，我就能還你一個針對該指令集的優化器。」

這就是我們在優化器方面的工作。我們成功推進了這一步，自動生成的優化器效能甚至超過了專家長期手工打造的優化器。這非常有意思。

多酷的發現啊！

是的，這很有趣。接著，量子編譯器開始與傳統編譯器產生分歧：傳統編譯器在轉換程式碼時必須保持嚴格的正確性（語意必須完全相同）；但在量子計算中，因為所有數值最終都是實數或複數，你永遠無法做到絕對精準。

因此作為優化器，你有更大的空間去進行近似（approximate），這其實蠻棒的。我可以取出一小段程式，替換成一段稍微不同但小得多的程式碼。所以這裡的程式合成問題變成了「近似程式合成」（approximate program synthesis）。

這非常有趣。如果再深入到更底層的具體裝置約束，不同裝置之間存在巨大的差異。例如像中性原子裝置（neutral atom devices），你真的可以在空間中移動原子（位元）！他們使用雷射把原子拉近，讓它們產生量子糾纏（entanglement），然後再放回空間中。這樣這兩個位元就完成了糾纏。

這太離奇了！那麼這類電腦到底有什麼功能和應用場景？我是說，我知道我們甚至還不知道未來的潛力，但就你剛才描述的，你們是在計算什麼？產出什麼？這是用來幹嘛的？

這是量子計算領域的一個大問題。歷史上，量子計算領域的第一次熱潮發生在 90 年代中期。從資訊科學的角度來看，最具代表性的是 Shor 演算法，它能夠透過高效分解大整數來破解公鑰加密（public key cryptography）。在傳統電腦上我們認為這是無法高效完成的問題。因此假設你擁有一台量子電腦，你就能獲得指數級的加速（exponential speedup）。當時大家意識到「這裡面確實有東西！」，於是人們開始密切關注。

從科學的角度來看，另一個應用是模擬分子動力學（molecular dynamics）與化學。這是另一個已知能夠獲得指數級加速的領域。

這就是大家最感興趣的兩大類應用。此外，人們對線性代數與機器學習中的應用也很有興趣，在某些演算法類別中我們也知道如何獲得指數加速；但那裡的狀況比較複雜（murky），因為對輸入資料有較多約束假設（例如矩陣必須是稀疏矩陣等），這些約束是否符合現實依然是一個開放性問題。

所以這些是主要的重大應用。大家的共識是，如果你能高效地模擬化學反應，就能推動新藥開發與新材料發現等等。這些就是量子電腦的應用前景，其中大部分都是面向未來的技術。

那是關於編譯器的論文。那究竟是什麼意思？我對它的含意非常好奇。

概念上，你在紙上或 IDE 裡撰寫的程式變數就是「邏輯變數」（logical variables），而存在於具體硬體裝置上的則是「物理變數」（physical variables）。就像在傳統編譯器中，你有程式裡的變數，同時也有暫存器（registers）和記憶體位址，那些是程式執行時真正駐留的物理位置。

這裡也是相同的問題：你在電路或程式中擁有邏輯位元，而實體裝置上則擁有物理位元（量子位元），你必須將前者映射（map）到後者。

另外還有額外一層複雜性：量子電腦極易受到噪聲干擾。雖然你我的筆記型電腦也會受到噪聲影響，但機率極低，低到我們根本不會去考慮。在網路傳輸中我們確實會考慮封包遺失（packet loss）；但在筆電上執行程式出錯時，你不會覺得「啊，大概是某個位元翻轉（bit flip）了」，你只會覺得程式有 Bug。但目前的量子電腦，錯誤率大約是千分之一（也就是每執行一千條指令就會有一條失敗）。

因此你嘗試做的幾乎所有計算都伴隨著巨大的噪聲。為了減輕噪聲，你必須進行糾錯（error correction）。量子電腦上的糾錯原理與傳統電腦類似，基本上就是透過冗餘複製位元：與其把你的名字寫一次，不如寫十次，即使其中一個損壞了，你比對之後依然能確認內容。

量子糾錯也是類似的道理（雖然複雜得多）。你將一大堆物理量子位元打包在一起，稱之為一個「邏輯量子位元」。在這裡，「邏輯」一詞的含意有所改變：它更偏向物件導向面向程式設計師的視角——從程式員的角度來看這是一個位元，但底層其實是由許多物理位元假裝成那一個位元。

透過提前規劃動作，這意味著如果它在執行過程中看到了奇怪的東西，它不會中途回溯並開始刪除你的檔案，因為它的動作已經預先規劃好了。這很棒，效果也非常好，能夠以可證明的保證（provable guarantees）防禦多種形式的提示詞注入；但與此同時，你的 Agent 就變得相當靜態，無法對環境做出動態反應。例如如果你讓它打開一個檔案，但檔案路徑錯了，它就會卡住，無法回溯並自動去其他地方尋找。

這就是我看到的挑戰。此外還有許多資訊流（information flow）層面的挑戰：例如如果它讀取了一封郵件，它能否將內容傳送給其他人？權限該如何控管？問題在於，一旦資訊進入了 LLM，產出的內容就變成了黑盒，你無法保證產出的資訊與輸入的是同一個東西，因為 LLM 可能用不同的方式重新包裝或描述該資訊。所以一旦資訊進入 LLM，它本質上就變成了一個黑洞，除非語法完全相同，否則你根本無法追蹤資訊的流向。對這些問題進行推理（reasoning）非常迷人。我不敢確定標準答案是什麼，但這非常值得探索。不過這又是一個快速演進的領域，9 個月後我們構建 Agent 的方式可能就會與今天天差地別。
