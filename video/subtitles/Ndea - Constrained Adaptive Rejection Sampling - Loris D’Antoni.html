Constrained Adaptive Rejection Sampling - Loris D’Antoni

歡迎來到《Abstract Synthesis》，在這裡我們會分享程式合成與神經符號 AI 領域中各種有趣學術論文背後的故事。本 Podcast 由 AGI Research Lab 與 DIA 共同製作，我是主持人 Brian Landers。今天的來賓是 UCSD（加州大學聖地牙哥分校，也是我居住的地方）的 Jacobs 學者兼計算機科學與工程系教授。因此，今天能 Saturn 和他聊天我感到非常興奮。他領導 UCSD 程式系統研究分組，並在我們最喜愛的主題——程式合成上發表了大量論文。他的研究團隊的使命是讓人們更容易建構出值得信賴的軟體，隨著如今越來越多程式碼由 LLM 生成，這一點變得越來越重要。所以，能更深入認識他，我無比興奮。歡迎來到我們的節目！可以請你自我介紹一下嗎？

好的，大家好，感謝邀請我來到這個 Podcast。我的名字是 Loris D’Antoni。正如 Brian 所說，我是 UCSD 的教職員。我在程式合成領域已經工作了許多，大概有 12、13 年了。在加入加州大學聖地牙哥分校之前，我曾在威斯康辛大學麥迪遜分校任教 9 年。除了我的教職工作外，我還在一家名為 Code Metal 的公司工作。不過我今天跟大家分享的內容，主要都會是我作為教職員的日常研究工作。

太棒了，我想這正是大家最想聽到的。我們今天要討論一篇非常棒的論文——《約束適應性拒絕採樣》（Constrained Adaptive Rejection Sampling，簡稱 CARS），我們稍後會深入探討。不過在深入之前，想再了解一點你的背景。我知道你剛才提到了一些細節，但在我們開始之前，能否跟我們聊聊你是如何一路成為教授的？你是在哪裡長大的？以及你探索並進入程式合成這個領域的歷程？

好的，我的歷程可以說相當不尋常。我在義大利長大，在都靈大學（University of Torino）完成了大學與碩士學位。在那裡，我研究的是完全不同的東西。其實一開始，我甚至不知道自己這輩子會去做學術研究。我只是遇見了一位名叫 Mariangiola Dezani 的教授，她教我編譯器課程。在課堂上她對我說：「噢，你看起來很聰明，想和我一起做研究嗎？」我說：「當然好啊，這門課我很喜歡，聽起來是個好計畫。」於是我就開始研究這個叫「型別理論」的東西，具體來說，你會發現我的第一篇論文是關於「會話型別 (Session Types)」的。現在人們依然在對它進行大量研究，我也因為那篇論文獲得不少引用。雖然我後來沒有繼續追蹤那個領域，但我聽到很多人對此感到興奮。之後，透過我的指導教授介紹，我開始與賓州大學的一些研究人員合作，她把我介紹給了 Benjamin Pierce 和 Nate Foster，他們後來都成了我的朋友和同事。我和他們一起做了一些相關研究，我想正是這些經歷讓我被賓州大學錄取為博士生。在那裡，我和 Rajiv Alur 一起工作了五年。這裡有個有趣的故事：那時 Rajiv 剛拿到一個關於程式合成的贊助計畫，叫做 ExCAPE 計畫（Expedition in Computer-Aided Programming），其目標就是實現程式合成。但當時的我卻想著：「我才不想做程式合成呢！」於是我花了五年時間研究自動機理論。然後，一旦我成為教授，我就想：「好，我再也不想做自動機理論了，現在我要去做程式合成！」所以我當時有點叛逆，但最終我還是找到了走向合成的路。

事實上，我寫的第一篇關於合成的論文是和 Rajiv 合作的，內容是關於利用合成技術為學習計算機科學概念的學生生成反饋。這個想法是，我們合成出可操作的方法，為那些試圖學習自動機理論的學生提供實用的反饋。後來這些想法被應用到教人們程式設計等事情上，比如如果我能合成出修正你程式碼的方法，我就可以告訴你你的程式碼哪裡出錯，並教學生一些有趣的東西。但自從我成為教授以來，我主要致力於生成能實現我們預期功能的程式碼，以及如何正確且大規模地做到這一點。我將程式合成應用到了許多領域，其中相當成功的一個是合成網路組態，這樣你的資料中心就不會因為一些意料之外的事情而宕機。我們還做了一些關於對可解釋機器學習模型合成微小修改的工作，以便幫助人們更好地設計它們。我們也合成過解碼器和編碼器（decoders and encoders），因為那是最初人們常常搞錯的東西。我自己就經常收到這種電子郵件：「親愛的 Loris，我的名字在 D 後面有一個單引號」，但信裡總是顯示著未被正常 UTF 編碼的單引號亂碼，這讓我感到非常挫折，所以我決定去解決這個問題。自那以後我做了很多事情，而最近，我必須擁抱 AI 時代，並摸索如何透過 LLM 正確進行合成，這就是我如何走到今天的原因。

多麼棒的故事啊！你簡直就是程式合成領域的超級巨星，你和你 UCSD 的同事們都是如此。所以我覺得你在這集 Podcast 之後還不能卸下重任，我們以後得做更多內容來介紹你更多的論文。也許我們可以做一集直播節目，採訪你的學生以及 UCSD 的其他教授等等，大家可以期待相關計畫。這真的很特別。對了，我想你和我們上一集的 Podcast 來賓 Aus Albarghouthi 也有淵源，對吧？

是的！我和 Az 實際上是在我讀博士的第 8 週時，在一個叫 Marktoberdorf 的形式化方法暑期學校認識的。那是德國的一個小村莊，我們在那裡相遇，兩年後我們一起在微軟研究院（Microsoft Research）實習，然後三年後我們在威斯康辛大學麥迪遜分校成為同事，共事了 9 年。這就是我經常給年輕學生的建議：無論你在會議還是其他地方，一定要多和人交流，因為不管怎樣，他們總會以某種方式重新回到你的列表中，你永遠無法預料。是的，我和 Az 合作了很久，特別是在 LLM 出現之前的早期工作中，我們將形式化方法與機器學習相結合。我們推動了許多關於神經網路驗證、機器學習賦能系統驗證的工作。我們長期合作，共同申請過許多研究資助。我想去年我們剛畢業了我們共同指導的最後一位學生 Ameer，她現在是卡爾頓學院（Carleton College）的教授。所以，當你第一次遇見一個人時，真的很難預測未來你們會如何一起工作這麼多年。

是的，完全正確。在符號領域或形式化方法與程式合成領域裡，這真是一個小世界。我覺得自己開始有點掌握那裡的名人與陣容了。不過還是有很多人我需要邀請到 Podcast 上，這並不意味著我們沒有更多可以探索的東西。這超級酷。你剛才提到了在 Code Metal 的學者角色，也就是參與了一點產業工作。正如你所暗示的，我相信就像任何營利公司一樣，那裡也有許多機密項目，但總體而言，是什麼吸引了你？為什麼你覺得你的研究、技能與關注點非常適合這家特定的公司？

是的，其實在 Code Metal 之前，我也在 Amazon 當了四年的學者，和那裡優秀的人們一起做很多有趣的工作，把形式化方法應用到他們關心的各種領域。然後大約在幾個月前，有一些對「LLM 加上驗證」感興趣的公司開始和我聯繫。我和其中幾家聊了聊，他們都在做非常有趣的工作。而 Code Metal 最吸引我的地方是——首先，我和他們合作過，或者說不算正式合作，但我們有過很多交流，他們對我的研究非常感興趣，特別是我們今天要講的約束解碼（constrained decoding）。讓我簡單講講他們在做什麼，然後我可以聊聊為什麼我的背景與他們相關。我不知道在細節上能公開講多少，但本質上 Code Metal 將自己定位於「如何使用 LLM 來編寫能實現我們預期功能的程式碼」這個領域。

而且他們並沒有試圖去解決其他一些公司正在嘗試解決的艱難問題，即：現在人們只想直接購買程式碼並用自然語言編寫程式碼，我們如何讓他們以某種方式寫出想要的程式碼？這樣做的挑戰在於，即使你用英文寫下你想要的東西，在傳統的合成或驗證中，我們通常會以某種方式編寫程式碼，再以另一種方式編寫規格（specification），如果兩者一致，那就太棒了。這意味著我們把同一件事寫了兩次而且能互相吻合，所以我們大概率是正確的。但現在的問題是，如果由 LLM 來編寫程式碼和規格，它可能會為了討好我們而說謊。所以本質上，即使我們提問了，並得到了一個聽起來合理的答案、一個寫著「是的，這就是你要的東西」的規格，但它並沒有告訴我們那些我們「沒有問」的問題。本質上就像是：你有沒有想過你的程式碼是否應該具備這個性質或那個性質？無論如何它們都應該運行嗎？就像資料中心的例子一樣，假設我要求 LLM 給我一個組態，將流量從 A 發送到 B，從 B 發送到 C 等等。是的，這可以運作，很完美，但通常當你手動設計時，你還會考慮到「噢，我還希望它具有容錯性，我還希望有其他性質」，那些你當時可能沒有明確指出但你可能希望具備的性質。因此，我們失去了過去人們將同一件事做兩次然後互相檢查時所擁有的那種程度的監督（oversight）。

對我來說有趣的是，Code Metal 沒有這個問題。他們做的是「經驗證的程式碼轉換」（verified code translation）。他們正在開發的產品是：你有一段用你不喜歡的語言寫的程式碼，你想把它轉移到你喜歡的新語言中，或者優化成你喜歡的語言，而你希望用 LLM 自動完成這件事。這裡有趣的是，規格非常清晰：輸出程式碼應該做輸入程式碼所做的事。當然這裡有一些注意事項，人們必須小心，因為當處於不同語言中時，「等價」意味著什麼？你是只關心輸入和輸出，還是中間的所有行為都必須等價？或者它是否應該跑得和以前一樣快？你可能關心某些性質，但在高層面上，形式化方法與形式化驗證如何提供幫助是非常清晰的——我們只是想提高輸出確實與輸入等價的保證。這對我來說非常新鮮。雖然我過去做過一點點相關工作，但這非常引人入勝且有趣，而且我非常喜歡這個團隊。正如我所說，他們在一年前聯繫了我，我們在研究層面上進行了某種合作，我在那裡做了一場演講。我真的很喜歡那些人，我想在 Amazon 待了四年之後，是時候嘗試一些新東西了。現在我才剛去了那裡一個月，但我非常享受，我也真的很喜歡和我一起工作的人們。

這太酷了！我覺得你所談論的大部分內容，正反映了我們在（正如你所說的）AI 時代，或者說 LLM 時代所處的位置——因為在 LLM 出現之前就已經有大量的 AI 了，對吧？但就程式碼生成而言，形式化方法和程式語言如何應用於此，這可以說是當下的核心問題。因此我真的認為你要分享的內容超級相關。正如你所言，今天的論文是一個非常棒的切入點，所以讓我們深入探討吧。我剛才提到了論文的名字是《約束適應性拒絕採樣》（Constrained Adaptive Rejection Sampling），每個人都得取個超棒的首字母縮寫，所以你們有了 CARS，我接下來可能就會這樣簡稱它。我太喜歡這個名字了，非常好記。有人在 YouTube 的留言裡說，希望能讓來賓直接在最高層面上解釋這篇論文在講什麼。那我們就這麼做吧！請用你自己的話給我們一個概括，這篇論文到底在講什麼？

好的。這篇論文的誕生，實際上要聊到我在這個領域寫的第一篇論文，以及人們在這個領域一直在做的事情，那就是：你如何讓 LLM 生成滿足你所喜歡的某個性質或約束的輸出序列（例如字串）？觀眾中的許多人可能對「約束解碼（constrained decoding）」或「結構化解碼（structured decoding）」這個概念非常熟悉。自從人們開始建構 Agent 以來，這項技術就變得非常突出，因為他們需要讓 LLM 的某些輸出符合某種 JSON 格式，以便發送到 MCP，基本上就是遵循某種 MCP 協議並調用某些工具。LLM 變得越來越好，但有些 LLM，比如你可能想使用有時會出錯的更便宜的 LLM，或者一般來說，一旦約束變得足夠複雜，LLM 總會犯一些錯誤。因此，約束解碼或結構化解碼所做的，就是在 LLM 生成輸出的同時，基本上為你試圖強制執行的約束類型運行一個語法剖析器（parser），並表示：「噢，只保留那些潛在會導向滿足約束序列的 Token。」所以，丟棄所有肯定會違反約束的 Token。這很好，也能運作，人們很容易就能建立這種演算法。要讓它們變得非常快很難，但人們也已經摸索出做法了。問題在於，我在這裡舉的例子是：現在發生的情況是，你事先不知道你試圖滿足什麼約束。我給的類比是：假設你要求 GPS 帶你去某個目的地，它開始導航，開到一半時，它發現道路封閉了，而你事先並不知道這件事。這就是約束解碼在做的事。現在它幫你把路封掉了，因為那條路會違反你之前不知道的約束。所以現在你必須繞路。因此你不再擁有通往目的地的最佳路線。你突然間必須沿途修正一些你在剛開始就應該知道的糟糕選擇。這實際上就是你在 LLM 上使用約束解碼時發生的事。兩年前我們在 NeurIPS 發表了一篇名為《Grammar-Aligned Decoding》的論文，我們在文中形式化地描述了這個問題。本質上的問題是，如果你貪婪地（greedily）遵循約束，你就無法再與 LLM 所學到的優異分布保持一致。LLM 非常擅長根據你的要求生成可能性高的序列，但現在因為你極度貪婪地遵循這些約束，你獲得的不再一定是可能性最高的序列。你得到的是這種奇怪的貪婪路徑，只是不斷嘗試一次又一次地滿足序列。這實際上會導致輸出品質的惡化。你有時會得到一些奇怪的程式，它們開了一堆括號試圖符合約束，或者它們開始產生非常不自然的輸出——你會得到數百萬個空格，因為 LLM 在某個時刻基本上不知道該怎麼辦了。這是一個問題，本質上在於你無法事先知道這是否會發生，因為這取決於你作為輸入提供的文法、約束、JSON Schema 等等。

然後我們開始了尋求解決這個問題的旅程：我們如何讓 LLM 既能滿足約束，又能生成優質的序列？目前我們知道如何生成滿足約束的序列，但有時它們不夠好，因為我們遵循的是這種貪婪演算法。

回到 GPS 的類比，你可以做幾件事：如果你發現路障，你可以決定隨便選另一條路繼續隨機開，希望最終繞路足夠多次後能到達目的地；或者你還可以做幾件事：也許你可以往回開一點點，把「現在你知道那裡有路障」的資訊加入進去，然後嘗試從前幾個街區重新選擇下一條最佳路線。另一件你可以做的事是：也許你開得不夠遠，或者你非常在乎一定要得到最佳路線，也許你就直接開回家，把那裡有路障的資訊記下來，然後重新開始。如果你重複這樣做足夠多次，也許你就能找到最佳路線。

而《約束適應性拒絕採樣》這篇論文基本上就是這個想法：如果我真的想找到好路線，而不僅僅是「還算好」的路線，你能做的最好的事情就是，基本上每當你在某處卡住——因為約束而做了糟糕的選擇導致遇到路障時——你所做的事就是直接從頭開始。現在你知道那裡有路障了，據此更新你的知識庫，再次開車；如果又遇到另一個路障，就再次重新開始。這聽起來非常低效，但事實證明，如果你真的在乎找到這些極高品質的路線，這是唯一的辦法。本質上，你真的需要每次都重新開始並抱持希望，最終一旦你積累了足夠的知識，你就會避開所有的路障並到達目的地。

現在暫時脫離這個類比。我們試圖解決的形式化問題是什麼？從機率的角度來看，LLM 是一個從某個分布中進行採樣的採樣器（sampler）。它根據某個分布生成內容，而我有一個約束會扔掉其中的一些內容，這就創建了所謂的「條件分布」（conditional distribution）。現在，我們要從 LLM 中根據該分布進行序列採樣，但條件是必須滿足約束。而 CARS 所做的，就是執行這種不斷發現路障並重新開始的演算法，我們保證的是我們確實是從這個正確的分布中採樣。因此，這個約束分布（這個條件分布）實際上就是我們採樣所依據的分布。在這篇論文之前，做到這一點最好的方法就是沿途記住這些路障，並在未來的嘗試中避開它們。而 CARS 所做的，基本上是汲取了這一切並改善了這個想法。這個想法是：一旦你找到了足夠多的路障並避開它們，最終你就能獲得優秀的採樣。但是你需要花多長時間才能做到這一點呢？如果你運氣不好，處於一個可能撞上大量路障的環境中，你可能需要很長時間才能發現足夠多的路障，從而開始足夠頻繁地生成採樣，而不是一次又一次地卡住。

CARS 所做的就是：我們知道沿途我們會撞上哪些路障，因為 GPS 告訴你那裡轉彎，但你無法轉彎。但在開車的同時，我們也會看到其他路障——我們不會開過去，因為我們可能不想開過去，但我們看到了那裡有我們之前不知道的其他路障。因此，我們在每一步都在學習地圖的額外狀態，以提高我們學習所有路障的速度，並在未來的採樣中避開它們。

撇開類比不談，我們非常關心的一件事是：我們正在使用這些演算法為編譯器生成測試案例（test cases）。這與此有什麼關係呢？我們現在正在使用 LLM 來測試那些在網路上不太常見的語言的編譯器。我不會深入太多細節，否則又是另一個大偏題。但是這些語言對 LLM 來說很難生成，所以我們提供這些約束、這些文法，以確保我們能獲得這些語言的一些採樣，否則我們永遠無法為我們的編譯器生成測試輸入。我們觀察到的情況是，LLM 基本上一千個採樣裡只有一個是真正符合該語言的，這很糟。你不能為了生成一個有效採樣並進行測試而生成一千個採樣，否則你永遠無法測試你的編譯器。因此，即使是只記住一個路障的演算法，也只能達到一千個裡面有兩個有效採樣，錯誤實在太多了，導致你根本無法取得任何進展。

而我們的新演算法能夠從所有這些可觀察到的錯誤、所有這些可觀察到的路障中學習，在經歷了一到三個糟糕的採樣之後，現在它突然能達到在一千個採樣中生成 350 個有效採樣！所以突然間我們在實用性上獲得了 300 倍的提升——這意味著過去調用一千次只能生成一到兩個有效採樣，現在我們能生成 300 個。這對我們來說是一個巨大的變化，事實上它讓我們發現了編譯器中的一堆 Bug，因為我們擁有了能極快生成大量測試案例的演算法。

好的，你剛才提到了你過去的經歷，而且論文中也確實談到了這一點。事實上，我要說這篇論文對我來說有點嚇人，因為它在第二頁就出現了自動機理論的符號，開始變得很技術性。不過沒關係，對於那些很久沒上過理論課（或者像我一樣從未上過）的人來說，你能簡單解釋一下什麼是「自動機 (automata)」嗎？

自動機能用於許多事情，但在計算機科學課程中，你通常學到它的方式是：它是最簡單的計算模型。想像一下，如果你只有有限數量的記憶體，你能造出什麼樣的電腦？假設你的記憶體裡只有 100 個儲存單元，每個單元只包含一個位元（bit）。基本上，自動機試圖捕捉這種「你只有有限個狀態可以進行操作」的想法。那麼你能用它做什麼呢？你常聽到的典型例子是：也許你可以計算一個字串的長度是偶數還是奇數，因為我可以只使用一個位元，每當我讀取一個新字元時就改變那個位元，所以這只需要常數量的計算，只需要一個位元。這就是人們所說的「有限狀態自動機」（finite state automata）。在這種情況下，兩個狀態就是位元開啟（on）或位元關閉（off）。現在從技術層面來說，這個計算模型被描述為：你擁有狀態（states）和轉移（transitions），你有一個進入的初始狀態，然後你一次讀取字串中的一個字元。當你讀取完字串時，你已經遍歷了這些狀態和轉移，直到到達最終狀態。如果那個狀態是一個好狀態，你就說「我喜歡這個字串」，否則你就說「我不喜歡它」。

那麼為什麼這與這項具體工作相關呢？自動機可以用來描述你喜歡和不喜歡的字串。在這種情況下，它們可以用來區分滿足約束的字串與不滿足約束的字串。所以在剛才的例子中，你可以想像你決定：如果字串末尾的位元是 0，你就喜歡這個字串，因為這意味著它的長度是偶數（或取決於你如何建構，是奇數）。很多人喜歡自動機的原因之一是，除了它是一個非常簡單易研的模型外，它還具有許多我們在建構特定類型演算法時喜歡利用的優良性質。

聯繫到大家更熟悉的東西：許多人在 grep 或他們的程式語言中使用正則表達式（regular expressions），而正則表達式的高效實現通常是透過將這些表達式編譯成自動機，然後在你的輸入上運行這些自動機來建構的。與這篇論文的另一個聯繫是：某些更高級的自動機被用來建構語法剖析器（parser），基本上是用來檢查你的程式是否符合文法所寫的某種語法規律。因此，它們出現在計算機科學的很多地方，它們就像是你所能擁有的最簡單模型，並且具有非常好的性質。

非常酷，謝謝你的解釋。我還有一個問題：對這篇論文的一種解讀或總結可以是「帶有記憶的拒絕採樣」（rejection sampling with memory），對吧？這可以說是關鍵解鎖。對於那些不知道的人來說，什麼是拒絕採樣？

是的。我想在剛才用地圖例子偏題之前，假設你想使用 LLM 來產生這些 MCP 調用。最簡單的方法（也是很多人所做的）就是不斷生成輸出，直到你獲得一個符合你心目中 Schema 的輸出為止。在此之前，只要沒拿到你喜歡的那個，你就扔掉所有的採樣（我這裡用「採樣 sample」表示一次 LLM 的輸出）。所以這被稱為「拒絕採樣 (rejection sampling)」，因為你採樣、採樣、採樣，用 LLM 生成這些潛在的 JSON 輸出，直到獲得一個滿足 Schema 的輸出。這就是為什麼它叫拒絕採樣——你不斷拒絕，直到拿到你喜歡的那一個。如果你想獲得不止一個，你就一直拒絕，直到拿到足夠多你喜歡的採樣。

拒絕採樣的問題在於，你無法事先知道需要花多長時間才能獲得一個有效的採樣。可能需要 1 個採樣、10 個採樣，甚至你可能永遠拿不到，因為滿足該性質的可能性太低了。而我們的工具所做的，只是隨著時間推移降低你拿到錯誤採樣的機率。我們學習得越多，沿途獲得有效採樣的可能性就越高。從數學的角度來看，假設你有 10% 的機率撞中有效約束，這意味著你有 90% 的失敗機率。而 CARS 所做的是，每當我發現一個違反約束的情況，且該違規具有一定的機率時，我們實際上是從那 90% 中減去該機率。假設我們發現這個空間中有 10% 的部分是無效的，並且它的機率是 10%（即 0.1）。現在那個 0.1 被移除了，所以突然間你的失敗率從 0.9 降到 0.8，你的接受機率就上升到了 12% 左右。僅僅透過扔掉那一部分，你就扔掉了失敗的大半部分。你說得非常對，這本質上就是「拒絕採樣加上對過去所犯錯誤的記憶」。

這太酷了！我的意思是，這顯然要高效得多。好的，這裡有一個問題：人們看到這個可能會想，如果我能生成有效的輸出，為什麼我還要在乎分布是否完全精確？那麼，為什麼你認為保持模型的原始分布（這可以說是 CARS 的核心要點）如此重要？特別是在你論文中提到的應用裡，比如模糊測試（fuzzing）、程式碼生成，以及像分子生成（molecular generation）這樣超酷的科學應用中，為什麼對這些應用而言保持模型的原始分布會如此重要？

是的，答案有兩個方面。第一個是，人們經常會說：「但歸根結底，你關心的不就是拿到一個能用的採樣嗎？」但通常人們用來約束 LLM 的條件並不是完整的答案。比如「序列具有有效的語法」，假設它在某個文法中是有效的，但這並不意味著它是正確的程式、是你想要的那個程式。所以你仍然希望獲得滿足語法的「最佳程式」，希望能從中拿到正確的那一個。這是第一部分的答案。

但你說得非常對，在論文中我們主要關注的是你想生成不只一個採樣，而是許多採樣的情況，而且理想情況下它們分佈得很好。在模糊測試（fuzzing）的情況下，這是一個非常好的場景。什麼是模糊測試？模糊測試是一種程式測試技術，你希望生成大量隨機輸入，並希望這些輸入能覆蓋你正在測試的系統的不同部分。如果你拿到的輸入只測試了 10,000 行程式碼中的 10 行，而且你拿到了 50 個這樣的測試，那沒有什麼用。你理想中想要的是接收到的輸入既有趣又多元。

我們在之前的論文中有證據表明，LLM 事實上非常擅長生成多元的輸入。但一旦你加上這些約束並扭曲了分布，突然間你就損害了它生成多元輸入的能力，因為它卡在了遵循約束並為你生成不自然輸入的死胡同裡。因此在這種情況下，多樣性（diversity）非常重要。在 CARS 的論文中，你會看到一張關於模糊測試評估的表格，它切實表明你越接近真實分布，你在測試系統中獲得的涵蓋率（coverage）就越高。從其他論文中我們也有證據表明，當你以這種方式進行時，實際上會發現更多 Bug。因此，你的輸入越分散（而 LLM 擅長這一點），你就越能發現有趣的新行為。

另一個你提到的應用是：我想這適用於任何你想進行某種「知識發現」（knowledge discovery）的領域。就像你不在乎從 LLM 拿到某個特定輸出，而是想獲得大量可能性來進行探索，進而看看它們是否對任何事情有用。所以生成分子就是另一個例子，人們正嘗試用它進行藥物研發。在其他情況下，例如現在人們正嘗試生成有趣的數學猜想（mathematical conjectures）。所以你可以想像，也許你將輸出約束為定理證明器（如 Lean）中的有效語法，但如果你一遍又一遍拿到相同的猜想，那就沒意思了。所以你仍然希望擁有某種多樣性。

我的意思是，有一點是：你可能並不總是關心是否擁有完美的分布，因為你可能不願意在拿到一個好採樣之前浪費無窮無盡的採樣。因此我們有其他更偏向混合（hybrid）類型的演算法，有點像是「盡力而為」（best effort）。它們在過程中嘗試學習這個分布，但可能最初它們產生的某些採樣分布得不是很好，但它仍會繼續給你採樣。那些本質上就是我之前提到的變體：遇到路障時，也許你不需要一路開回家，只要倒車兩個街區然後再試一次。所以有一些變體採用了這些其他方法，它們有權衡取捨（trade-offs）——比如你會獲得更高的採樣效率（採樣效率意味著你浪費更少的採樣、不拒絕採樣），但也許你的分布可能會有點古怪，需要很長時間才能達到正確的分布；但在某些應用中這是可以接受的。

第三件我想提的事是：並非所有約束都是簡單的「有效/無效」。有時候約束更像是「相比於這個，我更喜歡那個」。你想表達類似這樣的意思：「噢，你看，我有另一個模型，那個模型非常擅長預測蛋白質是否會折疊、或者這個特定分子是否可合成、或者這個程式是否會在過程中引發某些麻煩。」現在，如果你仍然想根據這些「定量約束」（quantitative constraints）從 LLM 中採樣，該怎麼做？所以現在我想將它們結合起來——本質上有一個應用是你有兩個 LLM，一個非常擅長 A 事，另一個非常擅長 B 事，我想獲得它們的乘積（product）。但也許有時我不要乘積，也許有時我要多數決（majority vote），或者有時我要 A 減 B，或者我要最大的分歧。所以現在我們試圖將這些想法擴展到這個設定中，你可以使用多個模型來「程式設計」，並表達：「給我這個專家同意、那個專家不同意、且另外兩個專家共同得出結論的輸出。」我們該如何為此建立採樣器？這也非常令人興奮。
