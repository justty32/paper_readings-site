基本上，我關注歸納邏輯程式設計（ILP）已經很長時間了，大概有八年了。我最開始是在讀博士期間與 Muggleton 合作，研究一種不同形式的 ILP，稱為元解釋學習（meta-interpretive learning）。其基本思想是搜尋範例的證明，並從證明中提取程式。然而，這種歸納邏輯程式設計的方法相當繁瑣，因為它需要建立證明，所以效率不是很高。因此在那之後，我開始尋找機能讓 ILP 問題更高效的方法。因此我加入了 Andrew Cropper 的研究團隊，我們著手將 ILP 問題重新表述為約束程式設計（constraint programming）問題。這帶來了許多新想法，極大地提升了可擴展性（scalability）與搜尋效率（search efficiency），這真的很棒。但單靠這一點還不足以解決大型複雜問題。因此接下來，我研究了問題分解（problem decomposition）的方法——即如何分解一個問題以提高學習效能。我們不再嘗試一次性直接解決所有問題（這在大多數情況下是難以處理的），而是嘗試學習一些只泛化部分範例的小型規則，然後嘗試將它們組合起來，這使得整體問題變得更容易解決。

是的，我認為這很重要，這樣大家就能在同一個頻道上，我們也可以為新手 clarify 概念。簡單來說，程式合成（program synthesis）就是從規格說明（specification）自動生成電腦程式的任務。用戶或使用者給出的規格說明，定義了我們試圖學習的程式應該具備什麼功能。因此，基本概念就是：使用者不需要直接親自撰寫程式，而是提供一種意圖（intent）——程式應該做什麼、應該具備什麼性質等等——然後程式合成系統就會在程式空間中搜尋滿足該規格說明的程式。

是的，所以主要核心思想就是：我們不是直接寫程式，而是在一定的程式空間中搜尋滿足規格說明的程式。

說得好，非常精煉！那麼，與我們今天要討論的論文相關的一點是「演繹式程式合成」（deductive program synthesis）與「歸納式程式合成」（inductive program synthesis）的概念。你能為我們拆解這兩者的區別嗎？

好的。基本上在程式合成中，我們可以提供不同類型的規格說明。我們不妨先從演繹式程式合成（deductive program synthesis）說起。演繹式程式合成接受完整的規格說明（full specification）作為輸入。也就是說，我們非常精確地描述了我們想要學習的程式的正確行為。舉個例子，如果我們想要學習一個返回兩個數字中較大值的函數，我們可以聲明：結果必須大於或等於兩個輸入值，並且必須等於其中之一。這就是一個完整刻畫了目標程式行為的規格說明。系統的目標就是推導出一個相對於該規格說明在邏輯上保證正確的程式。因此，在演繹式合成中，我們獲得的程式必須是正確的，但代價是我們必須具備完整且形式化的規格說明。

相比之下，在歸納式程式合成（inductive program synthesis）中——這也是我目前研究的方向以及我們今天討論的論文主題——規格說明是由輸入-輸出範例（input-output examples）組成的。系統獲得的是一組有限的範例，我們的目標是推斷出一個能夠泛化這些範例的程式。因此最大的區別在於：規格說明是不完整的（incomplete）。如果我們只有一組範例，可能會有許多不同的程式同時滿足這些範例。例如，我們可以給出範例對：1 變成 2，2 變成 4。對此我們可以推斷出很多程式：比如程式可以是「輸入的兩倍」，或者是「輸入加上 2」（在某些特定範例下）。因此可能有多個程式同時符合並泛化了這些範例。這就是這種規格說明所帶來的額外複雜性。

精彩！這完全講得通。還有另一個關於這些程式本質的關鍵構件，那就是「函數式程式」（functional programs）與「邏輯程式」（logic programs）的對比。你能給我們舉個例子嗎？而且我在包括你的論文在內的許多論文中讀到，邏輯程式如何神奇地縮減了約束空間。我很想具體聽聽它是如何運作的。

這歸結為我們想要學習的程式的表示語言（representation language）。在函數式程式設計（functional programming）中，我們希望描述「如何從輸入計算出輸出」（how to compute）。因此，我們通常編寫的程式是多個函數的複合（composition），這些函數對整個輸入進行轉換以產生輸出。我們可能需要編寫一長串這種函數的長複合鏈。這可能會成為一個問題，因為在程式合成中，搜尋空間（search space）會隨著我們搜尋的程式深度呈指數級增長。如果我們搜尋的是長函數鏈，我們就會擁有一個龐大的搜尋空間，從而使整個問題變得更加困難。

或許舉個例子會更清楚：在論文中，我們以「在列表中位置 3 插入字母 A」為例。如果我們要用函數式程式來實現這一點，我們必須顯式地使用 head 和 tail 或類似的函數來解構（deconstruct）列表，然後插入字母，再重新構建（reconstruct）剩餘部分。而這每一個解構步驟都需要在我們的函數式程式的長複合鏈中增加額外的複合元素。如果我們想在位置 5 或位置 7 插入字母，我們就需要在此長複合鏈中加入更多額外的元素，這會使整個程式變得更加難以學習。

相比之下，在邏輯程式設計（logic programming）中，這是一種宣告式範式（declarative paradigm）。我們描述的是「應該滿足什麼關係」（what should hold），而不是「如何計算它」（how to compute）。具體來說，我們描述的是輸入元素與輸出元素之間應該滿足什麼樣的關聯/關係（relationship）。再以在列表中某個位置插入元素的例子來說：在邏輯程式設計中，我們可以聲明「輸出中的前幾個元素等於輸入中相同位置對應的元素」；我們可以聲明「第三個元素是一個常數，即字母 A」；然後我們可以聲明「剩餘的輸出元素等於偏移了一個位置（i - 1）的輸入元素」。

因此，我們可以學習三條不同的規則來分別表達這些情況，而且不論插入位置為何，每一條規則都具有常數大小（constant size）。也就是說，無論我們想在位置 3、位置 5 還是位置 7 插入新字母，這些規則都是簡短的。正因為它們更短，在這個特定案例中，它們比函數式程式設計容易學習得多。

好的，當然。這是論文中一個非常重要的主題。基本上，它是將一個問題劃分為若干個子問題（sub-problems）的想法，每一個子問題都更容易解決，然後我們可以將每個子問題的解答結合起來，以獲得整體問題的解決方案。這就是分解問題的主要思想，其目標是讓初始問題變得更容易解決。

好的，沒問題。我絕對鼓勵大家去聽聽 Andrew 那集播客。但作為複習，歸納邏輯程式設計（ILP）是機器學習的一種形式，其目標是从數據中學習程式。但與其他形式的機器學習相比，ILP 的特殊之處在於我們使用的表示法——我們學習的是邏輯程式（logic programs），而不是統計模型或其他東西。所以是的，這就是核心思想：我們從數據中學習邏輯規則，也就是由邏輯規則集合構成的邏輯程式。因此我們可以說它是歸納式程式合成的一種形式，因為我們以範例集合做為輸入，並從這些範例中學習出一個邏輯程式。

好的，沒問題，這是一個極佳的理論結果。簡單來說，基本思想是：當你搜尋一個符合少量範例的程式時，你可能會發生過擬合（overfit）——也就是說，你可能會找到一個完美匹配你現有訓練範例的程式，但它無法泛化到未見過的測試範例上。你所搜尋的潛在程式空間越大，就越容易碰巧找到這樣一個完美契合訓練範例的程式。但這可能只是偶然發生的，並非是一個真正能泛化到未見數據的程式。

因此，該結果表明：給定兩個搜尋空間，假設兩者中都存在一個正確的假設（hypothesis），在較小的空間中搜尋將導致更少的泛化誤差（generalization error），從而實現比在較大空間中搜尋更好的泛化。這是因為在較小的空間中，能夠偶然、意外契合範例的假設數量更少。如果一個來自較小空間的假設契合了範例，我們就有更強的證據表明該假設抓住了真正底層的概念，並且能更好地泛化到未見過的測試範例上。
